## 一、历史 30 秒解析超时：根因定案（不是"候选解释"了）

R4 夜批 3/24 停批（rc5）的根因：**辅助解析经 `go tool` 包装且每样本独立 GOCACHE，每次解析都现场冷构建 pprof（约 23–28.5s），撞 30s 墙钟**；解析本身从未失败——被杀样本的 stdout 与 2026-10-31 冻结工具直调输出 **SHA 逐字节相同**（`f4ab2e6b…`，864B 完整报告）。

五条证据线：①被杀样本输出完整且与今日输出逐字节等价；②R3/R4 源码同构（`go tool` + 30s + 每样本独立 cache，R3 上限 30s 已在源码补实）；③离线实验 E1 冷调 28.515s/首字节 25.297s/子进程含 compile·asm·link，暖调 2.125s，符号化选项无关；④`go tool -n` 冷 cache 亦 23.291s；⑤u01 冷构建压线通过、u02 越线（刀锋抖动）。详见 `night-batch-2026-10-30/zcode/r52-next-analysis-r1/`（验证器 26/26）。

**边界**：旧批次 valid 台账与 rc5 停批事实不变（本记录只修正"为什么失败"的归因）；历史根因如需"复现级"闭环可另行授权一次受控重放，非必需。

## 二、启动采样窗 CPU 双样本归因（protobuf 只读解码，不经 pprof）

协调者收口校准：该profile窗口早于NewLazyApp启动、晚于生产M1结束，不能称为“M1段”。M1墙钟长度约占两窗24.6%/40.3%，这些长度比不表示CPU工作占比。以下全部百分比均为全采样窗统计，详见[口径校准](2026-10-31-M1采样窗口径校准.md)。

对两张真实窗口 CPU profile 的**输入文件**直接解码（叶子 = runtime 栈序 `location_id[0]`），并与 pprof -top / 旧解析输出逐 tick 交叉校验：

| 项 | u02（A-gomaxprocs2 × selected0-lazy） | u01（B-runtime-default × default-lazy） |
|---|---|---|
| 总采样 | 54 ticks/540ms（Duration 389.94ms，138%） | 46 ticks/460ms（Duration 265.61ms，173%） |
| Win32 系统调用路径（叶子 `runtime.cgocall`） | 32 = 59.3% | 21 = 45.7% |
| 字体 glyph 解析（go-text） | 8 = 14.8% | 14 = 30.4% |
| runtime 内部其他 | 11 = 20.4% | 11 = 23.9% |
| profile 自身开销 | 2 = 3.7% | 0 |

cgocall 的 Gio 层来源（runtime 自记栈）：d3d11.CreateDevice（11/7 ticks）、DefWindowProc 消息泵（10/4）、SwapChain.Present（2/3）、text.newShaperImpl（2/3）、SetWindowPos/CreateWindowEx/SetWindowLong/CreateBuffer 各 1、**text.ResolveFace 两样本各 1**（字体面解析走 syscall 路径，与 face-selection 工作直接相关）。

**结论**：两个启动采样窗都观察到Win32调用路径和字体解析工作。占比随case/stratum变化，现有样本不能推出M1区间内各项成本、策略优劣或“唯一优化项”；D3D11创建与字体解析可作为后续调查线索，尚无新的优化候选或性能验收。

## 三、cgo"异常"的消解（踩坑-021 详述）

`CGO_ENABLED=0` 构建下大量 `runtime.cgocall` **不是矛盾**：Windows 上 `syscall.SyscallN` 本就经 runtime 的 cgocall 机制发起 stdcall。既非符号化伪影（pprof 与 runtime 自记逐 tick 一致），亦非用户 cgo（buildinfo 实证 + 依赖清单无 cgo 用户）。此前"伪影 vs 真实 cgo"的二选一是错误的问题设定。
