# A5 验收报告：嵌套缓存行为与收益

- 日期：2026-10-19
- 任务：`TASK-CODEGEN-STATIC-CACHE-001` A5
- 环境：Windows amd64 / Go 1.26.1 / Gio v0.10.3 / `CGO_ENABLED=0` / 20 逻辑核
- 原则：**只测量不改实现**。是否调整缓存粒度由证据决定，不由预设决定

---

## 一、A5.1 录制行为矩阵

用三个**互相不可替代**的指标：

| 指标 | 含义 |
|---|---|
| 录制分支进入次数 | 生成的 `Layout` 里 `cached == false` 的次数 |
| 叶子布局执行次数 | 实际调用 `material.Body1(...).Layout` 的次数 |
| （Flex 内部录制） | 由 Gio 机制决定，无法直接插桩，但可从叶子数推断 |

### 实测矩阵

| 场景 | 帧数 | 录制分支 | 叶子布局 |
|---|---:|---:|---:|
| 单节点 | 3 | **1** | **1** |
| Column + 3 静态 Text | 3 | **1** | **3** |
| Column 套 Row（全静态） | 3 | **1** | **3** |
| 同 key 3 帧 | 3 | 1 | 2 |
| 约束变化 1 帧 | 1 | 2 | 4 |
| 回到原约束 2 帧 | 2 | 3 | 6 |

### 结论 1：回放分支不执行任何叶子布局

单节点 3 帧中叶子布局只执行 **1 次**；Column 3 子节点 3 帧中只执行 **3 次**（每个子节点一次，全在首帧）。

**没有重复工作。** 第 2、3 帧完全跳过布局计算，只做 `CallOp.Add`。

### 结论 2：每次 key 变化都重录，即使恢复到旧 key

「约束变化 1 帧」使录制分支从 1 增到 2；「回到原约束 2 帧」又增到 3。

因为 §16.4 只保留**最新一份**缓存，不维护历史 key 的多份缓存。这是已知设计取舍，不是缺陷。

## 二、A5.2 Ops 归属与绘制正确性

**不看尺寸，用像素比对。**

用 `headless` 离屏渲染三个来源并比较非零像素数：

| 来源 | 非零像素 |
|---|---:|
| 直接布局（无缓存） | 681 |
| 首帧（录制路径） | 681 |
| 次帧（回放路径） | 681 |

场景：`<Column><Text>AAA</Text><Row><Text>BBB</Text><Text>CCC</Text></Row></Column>`

### 结论 3：Ops 归属正确，无吞掉/覆盖/重复提交

三层绘制（外层 Flex、内层 Row、三个叶子）在缓存与不缓存两条路径上产出一致。

首帧与回放帧的像素有**细微浮点差异**（抗锯齿），但非零像素数完全相同——与 ADR-0009 §A1 的观察一致。

## 三、A5.4 嵌套缓存收益

与 A6a 同环境、同布局输入，三个场景并列：

| 场景 | NoCache ns/op | FirstRecord ns/op | **CacheHit ns/op** | 加速比 |
|---|---:|---:|---:|---:|
| 单节点 | 688.9 | 2237 | **30.37** | 22.7× |
| Column 3 子节点 | 1654 | 4248 | **33.59** | 49.2× |
| Column 套 Row | 1685 | 5620 | **29.00** | 58.1× |

### 结论 4：缓存命中时长几乎不随节点数增长

`30.37 → 33.59 → 29.00 ns`——三个场景在误差范围内相同。

这是**预期的**：命中路径只执行一次 `CallOp.Add`，回放的是同一份录制内容，
与录制时包含多少节点无关。

而 `NoCache` 从 689 涨到 1685 ns（2.4×），`FirstRecord` 从 2237 涨到 5620 ns（2.5×），
都随节点数线性增长。

**这意味着节点越多，缓存收益越大**——嵌套场景的加速比（58×）显著高于单节点（23×）。

### allocs/op

三个场景的 `CacheHit` 均为 **0 B/op, 0 allocs/op**，满足契约 §15.1 与 §16.8。

`FirstRecord` 的一次性成本随节点数增长（1184 → 3471 → 3464 B），摊销后趋近零。

## 五、决策：保留当前实现

按 A5 的四类证据：

| 检查项 | 结果 |
|---|---|
| 是否存在重复录制 | **否**——回放不执行叶子布局 |
| Ops 归属是否正确 | **是**——像素与非缓存一致 |
| 缓存是否有收益 | **是**——23×~58×，且节点越多收益越大 |
| 是否需要调整粒度 | **否** |

因此**不改变契约 §16 的缓存所有权或嵌套语义**。

### 特别说明：为什么「外层已缓存、Flex 内部又录制」不是问题

`layout.Flex.Layout` 确实对每个 `Rigid` 子节点执行 `op.Record`/`Stop`（源码确认）。

但这发生在**录制阶段**（首次 Layout），产物被外层的大 `CallOp` 完整包住。
稳定帧回放时，这些内层 `CallOp` 作为录制内容的一部分被一起回放，
**不会重新执行**——A5.1 的叶子计数证明了这一点。

所以「重复录制」只在首帧发生一次（这是构建操作列表的必然过程），
不构成每帧开销。
