# BUG-013：Lazy提前请求可能丢失终态唤醒

- 状态：2026-10-30 已修复并通过受控事件泵与两包/全仓逻辑回归；真实空闲原生窗口 smoke 尚未执行，不升级 FONT 正式验收。原初判 P1。
- 基线：35dc6a1；相关异步接线来自9f3ab8e。
- 触发：先对未绑定notify的Lazy调用Request，再交给NewLazyApp；首帧仍Loading，后续窗口空闲。

## 证据与机制

`pkg/runtime/theme/lazy.go:335`附近捕获当时notify到worker；`pkg/runtime/app/app.go:287`附近SetNotify失败后仅在构造器补一次Invalidate。Gio v0.10.3 app/window.go:284附近在mayInvalidate=false时不投递，该时刻窗口驱动可能尚未创建。若worker之后没有有效回调、也无其它帧，最终主题可能无法显示。

实现符合当前任务卡的单次补偿条文；待审的是设计中“以后还会有帧”的假设，不能直接称实现违背冻结条文。正常先绑定再Request不受此路径影响。StrictFontFailure按现有契约在窗口关闭后返回，不能把“没立即返回严格错误”列为本缺陷证据。

## 复现与关闭条件

用channel控制先Request/首帧/加载完成的顺序，不用sleep猜时序；验证实际最终主题应用而非仅回调计数。另覆盖已有notify、已Ready、失败重试与正常路径。源码修复不得用永久轮询或放宽断言替代。旧实现红→候选绿、两包回归/vet及独立复核后才关闭。真实窗口未执行，不升级正式验收。

来源：[代码审查记录](../05-开发/2026-10-29-代码审查记录.md)。

## 2026-10-30 修复与实测

- 基线 `f5297bf`；红基线只增加私有可观察回调字段，不增加完成调度。受控 Read 卡住后台，提前 Request 后构造 App，首帧使用临时字体；放行后台后，事件泵收不到终态唤醒，`bug013-instrumented-baseline-red` rc1。测试未通过定时器或持续驱帧掩盖缺口。
- 新增 `Lazy.Done()` 尝试快照。三处终态出口在同锁发布状态/报告/pending 后关闭信号；显式失败重试换新通道。NewLazyApp 在绑定失败时于首帧后注册完成等待，完成仅 Invalidate；窗口循环退出取消等待。
- 保留旧 SetNotify 的早绑定/一次性规则和已有回调。正常路径不分配完成通道；晚绑定稳定观察实测 `AllocsPerRun=0`。帧外不换 Shaper，首帧不等待最终字体，M1 不移动。
- 覆盖已有/无旧回调、失败后显式重试、已 Ready、默认/选面成功和失败、并发观察、Take 一次性、帧内交换与提交；专项、两包和全仓测试均 rc0。
- 设计修正在 [ADR-0014](../03-架构/adr/ADR-0014-Lazy晚绑定的终态观察与帧内交接.md)，命令、原始日志及未验证项见 [10月30日回归记录](../06-测试/2026-10-30-两项遗留修复回归记录.md)。原“先调用正确顺序则不受影响”的结论保留。
