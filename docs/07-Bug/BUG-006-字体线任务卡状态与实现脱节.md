## 现象

文档台账与真实实现**互相矛盾**，且矛盾已经存在了一段多天：

| 文档写的 | 真实情况 |
|---|---|
| `TASK-FONT-001-D`：「设计已冻结，**实现未开始**」 | `IMPL-1` 已实现，产物 `pkg/runtime/theme/lazy.go` 存在 |
| 「占位用例**仍是 `t.Skip`**」 | 占位已被替换，实跑 `-run TestFontLazyLoad -v` → 17 PASS / **0 SKIP** |
| `TASK-FONT-001-D-IMPL-1`：「实现提交：见 §11（**提交后补记 SHA**）」 | 提交 SHA 始终没补（`948c406`） |
| `TASK-FONT-001` 父卡：「状态：进行中（A、B、C 已完成；**D 未开始**）」 | 同上 |
| `WBS总表.md` 两行：「D 仍为**显式 skip 占位用例**」 | 同上 |

这些都是抽查者一眼就能发现的问题：**卡片说没做，代码里已经做完了。**

## 根因

两个各自成立的原因叠加：

1. **台账状态没有与实现做机械校验**。没有门禁把"卡片写未开始"与"文件/测试已存在"对起来，
   于是状态更新完全依赖人记得改。
2. **实现落在一次混合提交里**：`948c406` 同时包含 C1 命名预检（`naming.go` / `naming_test.go`）
   与字体交付物（`lazy.go` / `theme_build.go` / `lazy_test.go`）。
   按提交主题去更新台账时，很容易漏掉提交里那一半"顺路带走"的内容。

在 FF 后的主干上，修正四处文档的过时表述并把证据补进去：

- 写明"IMPL-2/3 未开工"的 grep 判据，防止反向漂移到"全都做完了"。

```bash

# → 仅 pkg/runtime/theme/lazy.go:233 的一行**注释**（不是实现）
grep -rn "StrictFontFailure" --include=*.go pkg/
# → 零命中
```

即：只有 `IMPL-1` 真的做完了，`IMPL-2` / `IMPL-3` 确实未开工——卡片的"未开工"部分是对的，
要修的只有"实现未开始"这部分。

## 这条 Bug 揭示的问题

**"文档状态"与"事实"之间没有自动耦合。** 一旦某次更新漏掉，文档就会停在旧结论上，
并且因为"它看起来很整齐"而不会被怀疑。凡是作为验收依据的台账，都应同时写清
**用什么命令可以当场验证它**——把判据写进卡片，比把结论写进卡片更可靠。

与之相邻的一条：混合提交是台账漂移的高发源；若一次提交跨越两条任务线，
应至少在其中一张卡上登记另一半的归属，避免两边都以为"对方会更新"。
