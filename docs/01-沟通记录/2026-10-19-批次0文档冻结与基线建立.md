## 1. 目标

在开始后续分批开发前，建立一套准确、互相一致、可追踪、可验收的项目文档基线。
文档冻结不代表功能已实现，也不代表发布验收通过。

批次 0 的预期结果：

- 项目目标、架构边界和关键设计决策只有一套当前有效表述；
- 需求能够追踪到规范、实现任务和验收证据；
- 任务依赖与开发批次顺序清楚，批次之间有可检验的进入/退出条件；
- 文档质量门禁可重复执行，过时事实、断链和状态漂移能被发现；
- 记录冻结版本和验证结果，后续批次从明确基线开始。

## 2. 已确认的项目约束

项目所有者确认：

1. 当前优先级是完成文档，不提前扩大产品开发范围。
2. 文档完成后按批次推进开发。
3. 每批开发应有明确的任务、依赖、验收条件和证据。
4. 批次 0 冻结的是经过事实审计、相互一致的文档基线，不表示所有功能已经完成。
5. 文档冻结不替代代码验收或发布验收。

## 5. 批次 0 退出门槛

以下均为必须通过项：

1. 核心术语、接口和架构决策之间不存在未处理的规范冲突。
2. 每项 P0 需求均可追踪到规范、实现任务和可执行验收条件。
3. 状态准确区分已实现、已测试、已验收、未验证和环境受限。
4. 活跃任务均有任务卡，依赖完整且无循环。
5. Markdown 本地链接检查无断链。
6. 自动文档门禁的实际行为与脚本、Makefile 和 CI 一致；显式失败的占位目标不得算作通过。
7. 验收证据可追溯到具体提交、执行环境、命令和结果。
8. 至少抽样验证一条完整追踪链：`需求 -> 架构契约/ADR -> 实现任务 -> 验收用例 -> 验收证据`。
9. 冻结报告记录自动检查结果、人工审查结论、基线和允许带出的未决项。

允许带入后续批次的事项：

| 类型 | 带出条件 |
|---|---|
| 当前环境无法验证的平台或真实 GUI 行为 | 标明环境限制，关联后续任务和验证阶段 |
| 尚未进入当前开发批次的功能或性能验证 | 关联对应任务与未来验收阶段 |
| 非 P0 且不阻塞文档基线的问题 | 有明确归属、影响和后续处理位置 |

若未验证事项影响 P0 承诺、接口正确性或冻结结论，不得仅凭登记为遗留项放行。
