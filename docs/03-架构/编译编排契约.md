# 编译编排契约

- 状态：冻结
- 冻结日期：2026-10-19
- 适用范围：编译管线驱动（Parser → Expander → Analyzer → Codegen）、失败门禁、产物提交
- 关联：`代码生成输出契约.md` §2.1–§2.3（入口与两层门禁，§13 第 20 条）、`Analyzer输入输出契约.md` §6.10（凭证）

## 1. 为什么需要单独一层

Codegen 的入口只接受 `*analyzer.VerifiedDoc`，从**类型层面**挡住了未验证的 IR。
但这不足以保证管线安全：

| 缺口 | 后果 |
|---|---|
| 谁决定「分析失败时不要调用 Codegen」 | 没有这一层，调用方可能拿到 `Result` 后自行判断，也可能判断错 |
| 谁决定「生成成功后是否写盘」 | Codegen 只返回 `[]byte`（契约 §4.4），写入方未定义 |
| Parser / Expander 失败如何中止 | 它们的诊断不是 `VerifiedDoc`，需要统一成同一个结果形态 |

因此编排层是**控制流**的归属，Codegen 是**生成**的归属。两者分开建模（契约 §2.2 的两层职责）。

## 2. 流程与中止点

```text
.gxml 源文件
  │
  ▼
Parser ──── 有诊断 ──▶ 返回诊断，不进入后续阶段
  │
  ▼
Expander ── 有诊断 ──▶ 返回诊断，不进入后续阶段
  │
  ▼
Analyzer ── StatusPartial / StatusBlocked / 有诊断 ──▶ 不调用 Codegen，不产出产物
  │
  ▼
Verified() ── 失败 ──▶ 不调用 Codegen
  │
  ▼
Codegen ──── 返回错误 ──▶ 不产出产物
  │
  ▼
Artifact（内存中的完整结果）
  │
  ▼
Commit ──── 失败 ──▶ 目标文件保持原样
```

**中止即返回**：每个中止点之后不再执行任何后续阶段。

## 3. 必须满足的行为

| 情况 | 期望行为 |
|---|---|
| Parser 有诊断 | 返回解析诊断，**不调用** Expander / Analyzer / Codegen |
| Expander 有诊断 | 返回展开诊断，**不调用** Analyzer / Codegen |
| Analyzer 为 `StatusPartial` | 不调用 Codegen，`Artifact == nil` |
| Analyzer 为 `StatusBlocked` | 不调用 Codegen，`Artifact == nil` |
| Analyzer 为 `StatusOK` 但有诊断 | 视为**内部不变量违反**，拒绝生成（`Verified()` 本应拒绝，这里再加一道） |
| `Verified()` 构造失败 | 不调用 Codegen |
| Codegen 返回错误 | `Artifact == nil`，不写盘 |
| 全部成功 | 返回完整 `Artifact`，允许提交 |

最后两行是本契约最容易被遗漏的边界：

- **生成失败不留下部分产物**：Codegen 已保证「失败时返回 `nil` 而非部分字节」（契约 §2.3）。
- **分析成功 ≠ 提交成功**：`Artifact` 只是「允许提交」的凭据，写盘可能仍然失败。

## 4. 产物与提交分开建模

```go
// Artifact 是内存中的完整生成结果。
//
// 它的存在意味着「全部阶段成功、允许提交」，不代表已写入磁盘。
type Artifact struct {
	// PackageName 是生成文件的 package 子句。
	PackageName string
	// SourcePath 是 .gxml 相对目标包目录的路径。
	SourcePath string
	// Source 是已格式化的 Go 源码。
	Source []byte
	// OutputName 是生成文件的文件名，由 SourcePath 推导。
	OutputName string
}
```

`Commit` 负责写盘：

1. 在目标目录写临时文件；
2. 重新读取并解析校验（防止写入过程出错）；
3. 原子替换目标文件；
4. 失败时删除临时文件，**目标文件保持原样**。

**v1 暂不实现**：manifest 与孤儿文件清理（契约 §10）、增量缓存（§11）。它们在独立任务中处理；
在此之前 `Commit` 只覆盖「单个文件原子替换 + 失败不留残骸」。

## 5. 可测试性

门禁的验收证据必须是「Codegen 没有被调用」，而不是「返回了一个错误」。

因此编排层允许**替换阶段实现**用于测试：

```go
// Hooks 是阶段钩子。零值表示使用真实实现。
//
// 存在目的：让测试能观察「某阶段是否被调用」，而不必改造生产架构。
type Hooks struct {
	// Generate 替换 Codegen 阶段。
	Generate func(*analyzer.VerifiedDoc, codegen.Options) ([]byte, error)
	// Load 替换 Parser/Expander/Analyzer 前端的类型环境构造。
	Load func(cfg Config) (*analyzer.TypeEnv, error)
}
```

钩子只在测试中设置；生产调用传零值。

> 这是最小的可测试边界，不是插件体系。不要为了测试扩展成通用的阶段注册机制。

## 6. 与契约 §13 第 20 条的关系

第 20 条要求：

> 用 `StatusPartial` 与 `StatusBlocked` 的输入各跑一次完整管线，
> 断言 Codegen **未被调用**且工作目录中**没有产生任何文件**。

本契约的 `Run` 就是「完整管线」。第 20 条由 `internal/compiler/pipeline` 的测试关闭。

**关闭前的状态**：该验收项标为「设计已定义、实现待完成」，不得标记为通过。
