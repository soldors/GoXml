# GXML 诊断码目录

本文件是 GXML 诊断码的**唯一权威清单**。规范、ADR、任务卡、CLI 输出与测试都必须以本文件为准。

- 适用版本：v1（未发布）
- 最后核对：2026-10-22
- 当前实现：Parser、Expander、Analyzer 已分配的诊断码均有源码发射点；Analyzer 11 个码已全部进入实现态；Codegen 的 2 个 `CODEGEN-NAME-*` 码自 C3 起实现、自 **C4 起接线**（CLI 在写盘前调用 `codegen.CheckNamingConflicts`，冲突即整批放弃），**生产链路已可达**。
- 一致性由 `internal/compiler/diagdoc` 的测试自动校验

## 1. 分配约定

### 1.1 号段

| 前缀 | 含义 | 责任阶段 |
|---|---|---|
| `GXML-ROOT` | 文档结构与根节点 | Parser |
| `GXML-SYNTAX` | XML 语法、标签结构 | Parser |
| `GXML-ATTR` | 属性名、属性值与布局属性用法 | Parser + Expander |
| `GXML-EVENT` | 事件语法与实参 | Expander |
| `GXML-DEF` | `<Def>`/`<Slot>` 契约与宏展开 | Parser + Expander |
| `GXML-BIND` | 绑定路径与类型兼容 | Analyzer |
| `GXML-SCOPE` | `<If>`/`<For>` 结构与作用域 | Parser + Analyzer |
| `CODEGEN-NAME` | 生成符号与目标 Go 包的包级声明冲突 | Codegen |

号段分两族，**不得混用**：

- `GXML-*`：`.gxml` **源文本**写得对不对，由前端阶段（Parser/Expander/Analyzer）发射；
- `CODEGEN-*`：**生成物**放进目标 Go 包会不会撞名，由 Codegen 在生成前发射。

两者的修复动作不同（改源文本 vs 改目标包布局），因此不共用号段。
前缀常量见 `contracts/ir_schema.go` 的 `CodePrefix*`。

### 1.2 规则

1. **一个码只有一个含义。** 禁止两个常量共用一个码——历史上 `GXML-EVENT-002` 曾被 `CodeEvent` 与 `CodeEventSyntax` 同时占用。
2. **码一经发布不复用。** 删除某个检测后，其码保留为空置，不得分配给新语义，否则旧日志与搜索结果会指向错误含义。
3. **号段内从 `001` 起递增分配**，按加入顺序，不追求语义分组。
4. **`000` 专用于内部不变式违反**，表示「不是用户源码的问题」。当前仅 `GXML-DEF-000` 使用。
5. **新增码必须同时更新**：本文件、规范中引用该码的位置、至少一个锁定该码的测试。
6. **前缀不得混用。** 属性值错误不得报成 `SYNTAX`，结构错误不得报成 `ATTR`。
7. **不追求为每种失败单独编号。** `GXML-ATTR-003` 是刻意保留的归集码，见 §3。

### 1.3 三种状态

本目录的码可能处于三种状态之一，必须明确区分：

| 状态 | 含义 | 目录中的表现 | 门禁 |
|---|---|---|---|
| **实现态** | 代码中有常量且会被发射 | 记录了触发条件与代表消息 | `internal/compiler/diagdoc` 的 `implementedCodes` |
| **定稿态** | 语义已定稿，但实现属于尚未开始的阶段 | 同样记录完整语义 | 同文件的 `frozenCodes` |
| **空置态** | 保留号码，禁止重新分配 | 在 §4 列出并说明原因 | 同文件的 `vacantCodes` |

区分「定稿态」与「空置态」很重要：前者是「语义已定、只是没写」，后者是「这个号不要用」。混为一谈会丢失信息——把 Analyzer 的码标为空置，会让后续实现者以为这些语义还需重新设计。

当前**没有定稿态的码**。`GXML-SCOPE-005`（`<For>` 内含 `<Input>` 的 v1 拒绝）
已于 2026-10-20 由 Parser 实现并发射（`parser.CodeInputInFor`），
语义见 [Input输出契约.md](Input输出契约.md) §7。

实现态 37 个，定稿态 0 个。

> 状态会漂移，因此不能只靠人工维护三张清单。`diagdoc` 的
> `emission_test.go` 直接解析源码验证：每个 `Code*` 常量都必须有
> 发射点、都必须登记、且登记的符号必须真实存在。这条门禁曾发现
> 清单声称「Analyzer 未实现」而代码早已发射的情况。

### 1.4 阶段归属

诊断由**单一阶段**负责，避免同一错误被两层各报一次：

```text
Parser    语法与结构（不加载 Go 类型）
   ↓
Expander  组件 Schema 分类、<Def>/<Slot> 展开
   ↓
Analyzer  绑定路径、类型兼容、事件方法签名（需要 go/types）
   ↓
Codegen   生成 Go 代码
```

组件调用点的属性由 Expander 校验（报 `GXML-DEF-007`），Parser 不再重复报 `GXML-ATTR-004`。这是刻意的分工：调用点的合法性依赖 `Props` 声明，只有 Expander 知道。

#### 为什么把「不存在」与「未导出」拆成两个码

两者的**修复动作完全不同**：

| 场景 | 用户该做什么 |
|---|---|
| 字段不存在 | 检查拼写，或确认 ViewModel 是否真的定义了该字段 |
| 字段存在但未导出 | 把字段名改为大写开头 |

合并成一个「路径不可用」会浪费最有价值的提示——后者最常被误判为前者，用户会反复检查拼写却找不到问题。

#### `GXML-BIND-001` 的历史承诺调整（需记录）

该码在此之前被标为「预留」，目录原文的规划含义是：

> 绑定路径不存在**或不可访问**（如 `User.Nmae` 拼写错误）

这条承诺**同时包含两种语义**。定稿时按「根本语义是否不同」拆分，`BIND-001` 收窄为首段无法解析，`BIND-002`/`BIND-003` 承载中间段与不可访问。

这是一次**语义收窄**，不是简单启用预留码。记录于此，避免历史语义被悄悄改变。

**`EVENT-004` 的计数规则**见 `Analyzer输入输出契约.md` §8.4：

```text
方法形参 = 事件声明参数 ++ 调用点实参
```

因此 `ValueChanged="OnNameChanged"`（不写实参）对应 `OnNameChanged(value string)` 是合法的——载荷 `value` 已占 1 个形参。`GXML-EVENT-001`、`-008` 至 `-010` 空置。

### 2.8 `CODEGEN-NAME`（2 个）

生成层的命名冲突，属于 **Codegen 阶段**（生成前预检，见
`TASK-CODEGEN-NAMING-001` 卡 §10.5.2 冻结）。与前 7 组不同，这一组的修复动作是
**改目标包的布局**（移走 `.gxml`、改名、或调整用户声明），而不是改 `.gxml` 源文本。

**发射路径（C4 起）**：CLI 在**写盘之前**调用 `codegen.CheckNamingConflicts`
（只对本次未命中的输入），有诊断即整批放弃——不写产物、不改 Manifest、
不写缓存，退出码 2。卡 §10.7.3。

| 码 | 常量 | 阶段 | 触发条件 | 代表消息 |
|---|---|---|---|---|
| `CODEGEN-NAME-001` | `codegen.CodeNamingExisting` | Codegen | 生成符号与目标包**已有**包级声明冲突，包括用户声明或其他生成物（自家上一版产物不算，仍按 `isOwnArtifact` 排除） | `generated symbol "goxmlRenderKeyHome" (from /path/to/home.gxml) is already declared in package: /path/to/user.go` |
| `CODEGEN-NAME-002` | `codegen.CodeNamingSameBatch` | Codegen | 不同源文件派生出相同生成符号，例如 Pascal 归一化后发生碰撞（`a-b.gxml` 与 `a_b.gxml`） | `sources "/path/to/a-b.gxml" and "/path/to/a_b.gxml" both generate symbol "GoxmlA_BView"` |

**位置字段为零值**：命名冲突是包级事实，不落在 `.gxml` 的某个行列，
`CompilerError.Error()` 输出形如 `file:0:0: CODE: message`。
上表代表消息里的 `/path/to/...` 是占位：两个 `%s` 实参实际是**绝对路径**
（源的 `.gxml` 与占用者文件），不是裸文件名。

**已知边界（不在本码范围内修）**：

- **`goxmlTextCache<Source>` 自 C5 起按槽位收窄**：预检只在 `bindSlots > 0`
  时把它计入占用符号。静态页、纯事件页（有 VM 有事件但无绑定）、以及绑定
  全部位于 `<For>` 体内的页面都不声明该类型，因此不再被过度报告
  （C4 及以前的误报已消除）。
  收窄后的残余边界是**槽位未知**：源的前端未通过（语法/绑定错误）时，
  预检无从判断产物会不会声明该类型 → **回退为保守上界**（计入）。
  这类源的正确报错点是阶段一的编译诊断，命名预检不与之争抢。
  判据与规则见卡 §10.7.4；实现见 `codegen/slots.go`，
  一致性护栏是 `TestSlotCountAgreesWithDeclaredTextCache`。
- 冲突来自「包内既有声明」时，Analyzer 也会报 `GXML-ROOT-002`（它加载目标包
  时看到 `redeclared`），但要等阶段一跑完才出现。当前以本码为准（更早、
  语义更明确）；`002`（批内冲突）场景 Analyzer 不会报——那时两个产物都还没
  写盘，磁盘上没有冲突可加载。是否去重仍留待后续。

## 3. `GXML-ATTR-003` 为什么是归集码

`GXML-ATTR-003` 覆盖 40 余处检查，包括取值格式、布局属性位置约束、`<Grid>` 结构约束。

**保留归集而非拆分的理由**：

- 这些错误的修复动作高度一致——「改属性值」或「挪到正确的元素」。拆成几十个码会增加记忆负担而不增加可操作性。
- 拆分会让码表变成实现的镜像，实现一动就要新增码，与 §1.2 规则 2「不复用」叠加后会迅速耗尽号段。

**什么时候应该拆分**：当某类错误需要**不同的修复路径**或**需要被工具自动修复**时。例如 `GXML-ATTR-004`（未知名称）之所以独立，是因为它需要「拼写建议」这类专门处理。

## 5. 维护流程

新增或修改诊断码时：

1. **先定语义**：这个错误是否需要与现有码区分？是否需要不同的修复路径？（§3）
2. **确认阶段**：由 Parser、Expander 还是 Analyzer 负责？一个错误只能有一个归属阶段。
3. **取号**：在对应前缀内取最小的空置号；`000` 保留给内部错误。
4. **改代码**：定义常量（不得内联拼接），在发射点使用常量。
5. **写测试**：至少一个用例锁定「该输入产生该码」。
6. **更新本文件**：全表、空置清单、必要时的归集码说明。
7. **更新规范**：若规范正文引用了该码，同步修改。
8. **跑一致性测试**：`go test ./internal/compiler/diagdoc/`。

删除某个检测时，**保留其码为空置**，并在 §4 记录，不要重新分配。
