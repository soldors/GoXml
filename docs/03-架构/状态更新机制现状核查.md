## 一、Gio v0.10.3 的关键语义（源码证据）

### 1.1 `w.Invalidate()` 并发安全，且语义正对状态变更场景

`gioui.org/app/window.go:276-284`：

```go
// Invalidate the window such that a [FrameEvent] will be generated immediately.
// If the window is inactive, an unspecified event is sent instead.
//
// Note that Invalidate is intended for externally triggered updates, such as a
// response from a network request. ...
//
// Invalidate is safe for concurrent use.
func (w *Window) Invalidate() {
    w.invMu.Lock()
    ...
}
```

三条事实：

1. **立即产生一个 `FrameEvent`**；
2. **并发安全**（内部有 `invMu` 锁）——任意 goroutine 可调用；
3. 文档点名它的用途就是「外部触发的更新」——与状态变更场景**完全吻合**。

### 1.2 `w.Event()` 会被 Invalidate 唤醒

`window.go:729`：

```go
// Event blocks until an event is received from the window, such as [FrameEvent],
// or until [Invalidate] is called.
```

即：`Event()` 阻塞 → `Invalidate()` 唤醒 → 下一轮 `Event()` 返回 `FrameEvent`。
**这就是最短可靠路径的机制基础。**

### 1.3 `headless.Window` 不是完整窗口（实测）

`headless.Window` **没有** `Event()` 与 `Invalidate()` 方法（实测编译失败）。
它是离屏渲染器，只提供 `Frame`/`Screenshot`。

**结论**：S3 的端到端验证**不能**用 headless，必须用真实 `app.Window`
（进程内驱动事件循环，与现有 `TestRunWindowCallsLayout` 同模式）。

## 二、本项目现状

### 2.1 App 事件循环（`pkg/runtime/app/app.go`）

```go
func loop(w *app.Window, view View, th *material.Theme) {
    var ops op.Ops
    for {
        e := w.Event()
        switch e := e.(type) {
        case app.DestroyEvent: return
        case app.FrameEvent:
            gtx := app.NewContext(&ops, e)
            view.Layout(gtx, th)
            e.Frame(gtx.Ops)
        }
    }
}
```

现状：**被动循环**。只有 Gio 主动产生事件（输入、窗口事件）才会重新布局。
没有任何「状态变化 → 重新布局」的路径。

`RunWindow` 已有一处 `w.Invalidate()`（:147），但仅用于**关闭流程**，
与状态无关。

### 2.2 `View` 接口与绑定视图不兼容（关键断层）

| 侧 | 签名 |
|---|---|
| `View` 接口 | `Layout(gtx, th)` |
| 绑定视图生成 | `Layout(gtx, th, vm *fixture.ViewModel)` |

**绑定视图无法接入当前 App**。这是 S1 契约必须解决的第一个问题：
需要一种让 App 拿到 vm 的机制（泛型 View、闭包适配、或 vm 由 View 内部持有）。

### 2.3 ViewModel 所有权（问题 1 的答案：**未定义**）

现状：

- `View` 接口不含 vm；
- App 不持有任何状态；
- vm 由调用方传给 `Layout`——**所有权完全在调用方**，框架无约定。

多页面共用同一 vm 时的通知责任**无人定义**。

### 2.4 绑定缓存对状态变化无感知（问题 4 的现状）

当前绑定缓存只靠 `Layout` 被调用时读值比较。**状态变了但没人调用 Layout →
画面永远陈旧**。这正是本任务要解决的核心。

### 2.5 测试能力（问题：能否模拟完整刷新链路）

- `TestRunWindowCallsLayout`：真窗口 + 帧计数 + 「无图形环境 Skip」；
- 已验证 RunWindow 能启动、收帧、干净退出。

**缺**：还没有「改状态 → 自动出现新帧」的测试。S3 需要新建。

## 四、最短可靠路径（S0 候选方案，供 S1 决策）

基于以上证据，最短路径是：

```text
goroutine 修改 ViewModel
  → 调用 w.Invalidate()（并发安全，实测机制成立）
  → 事件循环的 Event() 被唤醒 → FrameEvent
  → view.Layout 读到新 vm → 绑定缓存比较显示串 → 更新
```

这条路径**不需要**：

- AOT Diff（状态对比在绑定缓存里已按显示串做了）
- Deps / 细粒度失效（先整窗失效）
- 新的通知协议（Gio 的 Invalidate 就是通知机制）

**待 S1 决策的接口问题**：App 如何拿到 vm（View 接口扩展？适配器？vm 由 View 持有？）。
