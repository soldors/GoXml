# GXML 语言规范 v1

- 状态：冻结
- 冻结日期：2026-10-18
- 适用范围：Goxml 编译器、Analyzer、Codegen、运行时生成代码
- 变更规则：v1 语义冻结；新增语法必须进入 v2，并通过新的 ADR 批准

## 1. 设计目标

GXML 是面向 Gio 的声明式 UI DSL。v1 必须满足以下约束：

1. 所有 GXML 在编译期解析、校验、宏展开并生成 Go 代码。
2. 运行时不解析 XML、CSS 或 GXML 表达式。
3. 绑定路径可以由 Analyzer 使用 Go 类型信息静态验证。
4. 相同输入和相同编译上下文必须产生确定性的输出。
5. 语法保持有限，避免引入需要运行时解释器的通用表达式语言。

## 2. 文件与文档结构

### 2.1 文件规则

- 文件编码必须为 UTF-8。
- 一个文件只能包含一个 XML 根节点。
- v1 不使用 XML namespace。
- XML 注释允许，处理指令禁止。
- 仅由缩进产生的空白文本会被忽略。
- 布局节点中禁止出现普通文本节点；文本必须使用 `<Text>`。
- 根节点、标签名和属性名区分大小写。

### 2.2 根节点

根节点必须是 `<Goxml>`，并且必须包含 `Version="1"`。

```xml
<Goxml Version="1" ViewModel="demo.ViewModel">
  <Defs>
    <!-- 可选的编译期组件定义 -->
  </Defs>
  <Page Route="/">
    <!-- 页面内容 -->
  </Page>
</Goxml>
```

根节点允许的属性：

| 属性 | 类型 | 必选 | 说明 |
|---|---|---|---|
| `Version` | 静态字符串 | 是 | v1 必须为 `1` |
| `ViewModel` | Go 类型路径 | 否 | 页面绑定的 ViewModel；纯静态页面可以省略 |

`Package` 不属于 GXML 语义。Go 包名由目标项目、输出目录或 CLI 参数确定；编译器内部可以保留 `DocumentIR.Package` 作为生成上下文，但不得从 GXML 推导业务语义。

`<Goxml>` 只能包含以下两个直接子节点，并且顺序固定：

1. 可选的 `<Defs>`，最多一个。
2. 必选的 `<Page>`，只能一个。

未知的直接子节点、缺少 `<Page>`、重复 `<Defs>` 或重复 `<Page>` 都是编译错误。

## 3. 标签分类

### 3.1 布局标签

v1 内置布局标签：

- `<Column>`：纵向布局。
- `<Row>`：横向布局。
- `<Grid>`：按列定义组织的二维网格（见 §3.1.6）。
- `<Spacer>`：占用剩余空间的弹性空白。
- `<Expanded>`：将子节点作为一个弹性布局项。

#### 3.1.1 通用属性

| 属性 | 类型 | 适用标签 | 说明 |
|---|---|---|---|
| `Padding` | EdgeInsets | 全部 | 1、2 或 4 个非负 dp 数值 |
| `Gap` | 非负数 | `Column`/`Row`/`Grid` | 相邻子节点之间的 dp 间距 |
| `Background` | Color | 全部 | 静态颜色或主题引用 |
| `Width` | `Fill` / 非负 dp | 全部 | 缺省为内容自然尺寸（见 §3.1.4） |
| `Height` | `Fill` / 非负 dp | 全部 | 缺省为内容自然尺寸 |

`<Spacer>` 不允许包含子节点。`<Expanded>` 必须且只能包含一个渲染子节点。

> `Gap` 在 v1 早期草案中曾命名为 `Spacing`，为避免与 Gio 的空间分配语义混淆而更名，见 ADR-0008 §4。

#### 3.1.2 对齐与分布

`<Column>`、`<Row>` 支持交叉轴对齐与主轴分布：

| 属性 | 作用对象 | 取值 | 适用标签 |
|---|---|---|---|
| `Align` | 容器对**所有直接子项**的交叉轴对齐 | `Start` / `Center` / `End` / `Baseline` | `Row` / `Column`（`Grid` 见 §3.1.6） |
| `Justify` | 容器主轴剩余空间的分布 | `Start` / `Center` / `End` / `SpaceBetween` / `SpaceAround` / `SpaceEvenly` | `Column` / `Row` |

**v1 只提供容器级对齐，不提供子项级覆盖（没有 `AlignSelf`）。** 若某个子项需要不同的交叉轴对齐，用嵌套的 `<Row>` 或 `<Column>` 表达。

这样取舍的原因：

- Gio 的 `layout.Flex` 只有容器级 `Alignment`，`FlexChild` 没有对齐字段，子项级对齐必须额外包一层 `Stack` 才能实现；
- 而那一层包装本身等价于「多写一层嵌套」——用嵌套换嵌套，净收益接近零，还破坏了静态子树的整体固化（影响 `INV-PERF-1`）。

**默认对齐是轴向感知的**：

| 标签 | 默认 `Align` | 依据 |
|---|---|---|
| `<Row>` | **`Center`** | 一行元素类比一行文字，垂直居中为最自然状态 |
| `<Column>` | **`Start`** | 一列内容类比一页文档，左对齐为最自然状态 |

`Justify` 缺省为 `Start`（剩余空间留在末尾）。

#### 3.1.3 Baseline 的适用范围

`Baseline` 只在**存在文字基线的水平排列**中有意义，因此 v1 严格限定其适用面：

| 位置 | 是否允许 `Baseline` |
|---|---|
| `<Row Align="Baseline">` | ✅ 允许 |
| `<Column Align="Baseline">` | ❌ 编译错误 `GXML-ATTR-003` |
| `<Grid Align="Baseline">` | ❌ 编译错误 `GXML-ATTR-003`（v1 不支持） |

**基线的定义**：子项在布局时通过 `Dimensions.Baseline` 返回基线位置，其含义是**从子项的底边到基线的距离**（沿用 Gio 的定义，见 `layout.Dimensions`）。

换算成「从顶边到基线」的距离是 `Size.Y - Baseline`，容器用所有子项中该距离的最大值作为对齐参考线。

**零基线的语义**：`Baseline == 0` 是**合法值**，表示基线落在子项的**底边**（即「从顶边到基线」等于整个高度）。这**不等于**「未提供基线」——Gio 的 `Dimensions` 没有额外标志位可区分二者。

因此 v1 的契约是：

- 参与 `Baseline` 对齐的子项必须自行返回有意义的基线；内置文本控件已正确返回。
- 自绘控件若不设置 `Baseline`，其值为 0，会被当作「基线在底边」参与对齐，可能造成视觉错位。
- **Codegen 不对零基线做任何改写**（不生成 `if d.Baseline == 0 { ... }`）：既然 0 是合法值，任何「猜一个默认基线」的兜底都会把合法输入改错，而且是比原始问题更隐蔽的错误。

需要基线对齐的场景，正确做法是让控件实现方返回真实基线，而不是让编译器猜。


#### 3.1.4 尺寸

`Width` 与 `Height` 各有两个显式取值，缺省表示内容自然尺寸：

| 取值 | 语义 |
|---|---|
| （缺省） | 由内容决定，不施加额外约束 |
| `Fill` | **占满父容器在对应方向上可用的空间**（详见 §3.1.5） |
| 非负 dp 数值 | 固定尺寸 |

v1 **不提供** `Auto` 取值或内容测量语义：Gio 为立即模式，无两遍布局协议，内容测量会产生每帧额外分配，违反 `INV-PERF-2`（稳定帧 `allocs/op == 0`）。见 ADR-0008 §2.2。

#### 3.1.5 Fill 与固定尺寸的语义

**`Fill` 是语言层的尺寸语义，不是某个具体布局调用的别名。** 它表示「在指定方向上占满父容器提供的可用空间」，具体实现取决于该方向相对父容器是主轴还是交叉轴。

轴向判定、`Fill` 的分配规则、无界退化的完整规则见 **§3.1.7**（本节的唯一权威来源）。

一句话概括：

| 该方向是 | `Fill` 的行为 |
|---|---|
| 主轴 | 参与弹性分配，与其他 `Fill` 兄弟等权均分剩余空间 |
| 交叉轴 | 填充父容器传入的交叉轴上限；上限无界时退化为自然尺寸 |

**因此 `Fill` 不能一律翻译为「主轴弹性」，必须按上表区分轴向。** 具体到 Gio 的映射由 Codegen 决定，属于实现细节，不属于本规范承诺（见 `代码生成输出契约` §15）。

##### 约束冲突规则

尺寸语义在以下边界情况下的行为是**确定的**，不依赖底层库的偶然行为：

| 情况 | 行为 |
|---|---|
| **固定尺寸超出父容器可用空间** | **不裁剪、不报错**，按固定值布局并允许溢出父容器边界。若父容器 `Padding` 非零，溢出部分可能被绘制到父容器之外。是否裁剪由使用方的祖先容器决定。 |
| **同一节点同时设置 `Width` 与 `Height`** | 两者独立生效，分别作用于对应方向，不冲突（组合矩阵见 §3.1.7）。 |
| **`Fill` 与固定值混合（如 `Width="Fill"` + `Height="32"`）** | 两个方向独立处理，互不影响。 |
| **多个 `Fill` 兄弟节点** | 均分剩余空间；若剩余空间为负（固定尺寸子项已超出），按 0 处理，不产生负尺寸。 |
| **无界约束下的 `Fill`** | 主轴仍参与弹性分配；**交叉轴退化为内容自然尺寸**。理由与检测方式见 §3.1.7。 |
| **`<Grid>` 单元格内** | `Width` 不允许设置（§3.1.6）；`Height="Fill"` 退化为自然高度（§3.1.7）。 |

##### 数值格式

| 项目 | 规则 |
|---|---|
| 单位 | 严格为 **dp**（device-independent pixel），由 `gtx.Metric` 换算为物理像素 |
| 数值范围 | 非负有限小数；拒绝负值与 `NaN`/`Inf` |
| 小数 | 允许（如 `Width="80.5"`），实现精度为 `float32` |
| 语法 | 十进制表示，不接受指数形式、单位后缀（`px`/`em`）或百分号 |
| `0` | 合法，表示该方向尺寸为零 |


#### 3.1.6 Grid

`<Grid>` 在容器上声明列定义，子节点按**行优先**顺序自动填充：

```xml
<Grid Columns="72 * 96" Gap="8">
  <Text Value="姓名"/> <Input Value="{User.Name}"/> <Button Text="保存"/>
  <Text Value="年龄"/> <Input Value="{User.Age}"/>  <Button Text="保存"/>
</Grid>
```

##### 排列

| 规则 | 内容 |
|---|---|
| 方向 | 行优先：从左到右填满一行，再换到下一行 |
| 换行 | 填满 `Columns` 声明的列数后自动换行 |
| 最后一行 | **按列定义补齐剩余列**，使每列宽度在所有行中完全一致（见下） |
| 空 `<Grid>` | 至少要有一个渲染子节点，否则编译错误 `GXML-ATTR-003` |

##### 列定义

`Columns` 必填，空格分隔：

| 写法 | 含义 |
|---|---|
| 非负 dp 数值 | 固定列宽 |
| `*` | 弹性列，权重 1 |
| `N*`（N 为正数） | 弹性列，权重 N |

**弹性空间的计算**：

```text
弹性空间 = 容器可用宽度 − Σ(固定列宽) − Gap × (列数 − 1)
```

若结果 ≤ 0，所有弹性列宽按 **0** 处理；不产生负尺寸，不报错。

##### 整数像素的取整规则

弹性列的「理想宽度」是浮点值，最终必须落到整数像素。取整**从左到右依次进行，并把舍入误差结转到下一列**：

```text
fraction = 0
对每个弹性列（按列顺序）：
    理想 = 弹性空间 × 权重 / Σ权重
    实际 = floor(理想 + fraction + 0.5)      // 四舍五入，含上次余数
    fraction = 理想 − 实际                    // 余数结转到下一列
```

**示例**：容器 100px，`Columns="* * *"`，无 Gap。

| 列 | 理想宽度 | 计算 | 实际宽度 | 结转 |
|---|---|---|---|---|
| 0 | 33.3333 | floor(33.3333 + 0 + 0.5) | **33** | +0.3333 |
| 1 | 33.3333 | floor(33.3333 + 0.3333 + 0.5) | **34** | −0.6667 |
| 2 | 33.3333 | floor(33.3333 − 0.6667 + 0.5) | **33** | +0.3333 |

合计 100，不多不少。

**但这条「用满」不是普遍保证**：当理想宽度的小数部分使结转值无法累积到进位阈值时，每列都向下取整，合计会少 1px。例如 116px、`Columns="* * * * *"`（5 个等权列，理想值 23.2）实测得到 `[23 23 23 23 23]`，合计 115。

因此规范只承诺两条硬约束：

| 承诺 | 内容 |
|---|---|
| ✅ 不超过 | 列宽合计 **永远不超过** 可用宽度（扣除 Gap 后） |
| ❌ 不保证用满 | 可能留下未分配像素（每轮至多 1 个） |

v1 **不做事后补偿**：补偿需要额外一轮扫描把余数塞给某一列，会让规范描述与真实渲染不一致。这一点与 Gio 的 `layout.Flex` 行为完全一致。

**这条规则必须由所有行共享同一结果**：不能因为某行是最后一行而重新计算。因为每一行的列顺序、权重、固定列宽都相同，且固定列被强制为精确宽度，所以逐行独立计算也会得到**完全相同**的宽度——但这依赖实现严格满足下面三条前提：

1. 固定列强制为精确宽度，不允许子项改变；
2. 最后一行的补位列使用与原列**相同的固定宽度或权重**；
3. 补位列参与 `Gap` 计数（见下）。

违反任意一条，最后一行就会与前面的行错位。

##### Gap

| 规则 | 内容 |
|---|---|
| 轴向 | **一个 `Gap` 值同时控制列间距与行间距** |
| 列间距 | 映射到每行横向 `Flex.Gap` |
| 行间距 | 映射到外层纵向 `Flex.Gap` |
| 计算顺序 | **先从可用宽度中扣除全部列间距**，再分配固定列与弹性列 |

Gap 在分配前扣除意味着：`Columns="72 * 96"` + `Gap="10"` 在 600px 容器中，弹性列得到 `600 − 72 − 96 − 10×2 = 412`。

补位列必须计入 Gap 计数：若最后一行只有 2 个真实单元格却按 2 个而非 3 个计算 `Gap`，会少扣一个列间距，导致弹性列变宽——这是补位的第二个理由。

##### 单元格

| 规则 | 内容 |
|---|---|
| 宽度来源 | **列定义是单元格宽度的唯一来源** |
| 子项 `Width` | `<Grid>` 的**直接子项**不得设置 `Width`，否则编译错误 `GXML-ATTR-003`（不忽略、不降级） |
| 子项 `Height` | 允许；行高由该行内容的自然高度决定 |
| 对齐 | `Grid Align` 映射到**每行**横向 `Flex.Alignment`，控制单元格在该行内的垂直对齐 |
| 内容溢出 | 子项内容超出单元格宽度时，按 §3.1.5 的溢出规则处理：不裁剪、不报错 |

禁止 `Width` 的理由不是「优先级低」，而是布局会被破坏：单元格宽度确定后，若子项返回更小的尺寸，同一行后续单元格会分到本不属于它的空间，整列错位。因此必须在编译期拒绝，而不是运行时容忍。

需要在新窗口/子区域内控制宽度时，在单元格内再嵌套 `<Row>` 或 `<Column>`，由它们承担宽度语义。

##### 补位不是虚拟子项

最后一行的补位由 **Codegen 生成的内部布局占位**实现，其边界是：

| 项目 | 是否涉及 |
|---|---|
| 进入用户 IR | ❌ 否 |
| 创建控件实例 | ❌ 否 |
| 参与状态 Diff | ❌ 否 |
| 产生事件或绑定 | ❌ 否 |
| 参与 `Layout` 的宽度计算与 `Gap` 计数 | ✅ 是 |

补位只服务于布局计算，不得作为节点回写进 AST 或 `NodeIR`。

##### 非法用法汇总

| 用法 | 诊断 |
|---|---|
| `<Grid>` 无 `Columns` | `GXML-ATTR-003` |
| `<Grid>` 无子节点 | `GXML-ATTR-003` |
| `<Grid Columns="">` | `GXML-ATTR-003` |
| `Columns` 为 `0*` 或负数权重 | `GXML-ATTR-003` |
| `<Grid>` 直接子项设置 `Width` | `GXML-ATTR-003` |
| `<Grid Align="Baseline">` | `GXML-ATTR-003`（见 §3.1.3） |

##### 不支持的能力

- **不提供坐标属性**：没有 `Grid.Column` / `Grid.Row`，位置完全由行优先顺序决定。
- **不提供跨行跨列**：没有 `ColumnSpan` / `RowSpan`。
- **不提供 `Auto` 列**：理由同 §3.1.4（内容测量破坏零分配）。
- **不提供列对齐**：`Align` 只作用于行内交叉轴，不控制列与列之间的水平分布。

见 §9。


#### 3.1.7 尺寸组合与约束传递

##### 主轴与交叉轴的判定

尺寸语义依赖父容器。任何节点的两个方向先按父容器归类：

| 父容器 | 主轴 | 交叉轴 | 说明 |
|---|---|---|---|
| `<Row>` | 水平 | 垂直 | |
| `<Column>` | 垂直 | 水平 | |
| `<Page>` | 垂直 | 水平 | **等价于一个没有 `Gap`/`Padding` 的 `<Column>`** |
| `<Grid>` 单元格内 | 水平 | 垂直 | 单元格本身是行内 Flex 项 |
| `<If>` / `<For>` | — | — | 不产生新轴，透传父容器的主轴/交叉轴 |

`<Page>` 之所以等价于 `<Column>`：它不接受布局属性，但如果按 `Stack` 叠放，多子节点会互相覆盖而不报错；按垂直排列既符合「一页文档」的直觉，也与 `<Column>` 的默认交叉轴对齐（`Start`）一致。若需要间距或内边距，在 `<Page>` 内显式写一层 `<Column>`。

##### 单个方向的解析

`Width` 与 `Height` **各自独立解析，互不影响**。每个方向按所在轴的角色处理：

| 该方向的取值 | 主轴 | 交叉轴 |
|---|---|---|
| 缺省（自然） | 内容决定，不参与弹性分配 | 内容决定 |
| `Fill` | 参与弹性分配，权重 1 | 填充父容器传入的交叉轴上限 |
| 固定 dp | 精确该值 | 精确该值 |

因此 `Width` 与 `Height` 同时设置不会冲突：它们在各自的轴上独立生效。

**主轴 `Fill` 的分配规则**：

- 容器内的所有主轴 `Fill` 子项**等权**（各为权重 1），均分扣除固定尺寸与 `Gap` 后的剩余空间。
- 例：容器 600，`固定 100 + Fill + Fill` → 两个 `Fill` 各得 250。

**交叉轴 `Fill` 的基准**：父容器传给该节点的交叉轴可用上限（`Max`）。

- 该上限有限时，填充到该上限。
- 该上限**无界**时，退化为内容自然尺寸（见下）。
- 若父容器的交叉轴尺寸本身由内容决定（例如 `<Row>` 的高度由最高的子项决定），则该上限通常远大于实际内容，填充结果可能不符合直觉。需要「与兄弟等高」时应改用外层固定高度或 `<Grid>`。

##### 无界约束

**语义要求**：某个方向的可用空间没有上限时，交叉轴 `Fill` 不得试图填充它。

不填充的理由：交叉轴 `Fill` 的实现方式是把 `Min` 抬到 `Max`。若 `Max` 代表「无穷」，就会得到天文数字的布局尺寸——实测 `Max = 1<<30` 时产生 1073741824 px 的高度。这不是能靠 clamping 收场的错误，而是必须避免的。

**识别无界是编译器的责任，且只有一处**：由布局语义层（`internal/compiler/sizelayout`）统一判定。Parser 与 Codegen 不得各自判断。

**规范不规定识别的具体阈值**，只要求满足两条性质：

1. 真实设备的可用尺寸永不被判为无界。现实显示设备单边像素数远低于百万量级（8K 宽 7680），任何合理阈值都不会误判。
2. 明显的「无穷」标记必然被判为无界。

实现层面（Gio 适配）当前采用「`Max >= 1 << 20` 视为无界」作为**适配策略**，理由与边界见 ADR-0008 §2.8.2。该数值是可调整的实现参数，不是语言规范的一部分——若将来支持的目标平台或尺寸单位发生变化，适配层可以改。

无界时的行为：

| 取值 | 无界时的行为 |
|---|---|
| 缺省（自然） | 内容决定 |
| `Fill`（交叉轴） | **退化为内容自然尺寸**，不报错 |
| `Fill`（主轴） | 仍参与弹性分配（见 §3.1.7「单个方向的解析」） |
| 固定 dp | 仍精确该值（80dp 就是 80dp，与可用空间无关） |

**关于实际发生频率**：Gio 的窗口始终给出有界约束，其内置滚动容器也不产生无界约束。因此这条规则是**防御性回退**，用于自定义容器或测试把某方向放开的情形，而非日常路径。


##### 嵌套容器的约束传递

规律只有两条：

1. **主轴尺寸**由父容器的分配决定（`Fill` 参与弹性分配，固定值精确，自然值按内容）。
2. **交叉轴约束原样向下传递**：父容器收到的交叉轴 `Min`/`Max` 就是子节点收到的交叉轴 `Min`/`Max`。

由此可得嵌套时的实际效果：

```xml
<Column Padding="16">            <!-- 主轴垂直，交叉轴水平 -->
  <Row Height="Fill">             <!-- 在 Column 内 Height 是主轴 → 弹性分配 -->
    <Text Width="Fill"/>          <!-- 在 Row 内 Width 是主轴 → 弹性分配 -->
  </Row>
</Column>
```

- `<Row>` 的 `Height="Fill"` 让它参与 `<Column>` 的纵向弹性分配。
- `<Text>` 的 `Width="Fill"` 让它参与 `<Row>` 的横向弹性分配。
- 同一个 `Fill` 在不同层级承担不同轴的角色，这是嵌套时最容易出错的地方。

**固定尺寸超出可用空间**：一律允许溢出，不裁剪、不报错、不压缩。已实测：父容器 `Max` 为 150 时，子项把约束置为 `Exact(200)` 仍得到 200。

**多个 `Fill` 与固定值混合**：固定值先占用，剩余再均分给 `Fill`；剩余为负时所有 `Fill` 按 0 处理。

##### `<Grid>` 单元格内的尺寸限制

| 情况 | 行为 |
|---|---|
| 子项设置 `Width` | 编译错误 `GXML-ATTR-003`（列定义拥有宽度，见 §3.1.6） |
| 子项 `Height="Fill"` | **退化为自然高度**：行高本身由该行内容决定，用它作为填充基准会形成循环 |

需要与同行其他单元格等高时，应显式给该单元格内的内容设定高度，而不是依赖 `Fill`。

##### 完整组合矩阵

以 `<Row>` 为父容器（主轴=水平、交叉轴=垂直）、交叉轴有界为例：

| `Width` | `Height` | 水平（主轴） | 垂直（交叉轴） |
|---|---|---|---|
| 自然 | 自然 | 内容宽度 | 内容高度 |
| 自然 | `Fill` | 内容宽度 | 填满可用高度 |
| 自然 | 固定 | 内容宽度 | 固定高度 |
| `Fill` | 自然 | 弹性分配 | 内容高度 |
| `Fill` | `Fill` | 弹性分配 | 填满可用高度 |
| `Fill` | 固定 | 弹性分配 | 固定高度 |
| 固定 | 自然 | 固定宽度 | 内容高度 |
| 固定 | `Fill` | 固定宽度 | 填满可用高度 |
| 固定 | 固定 | 固定宽度 | 固定高度 |

父容器为 `<Column>` 时，逐项把「水平/垂直」互换即可；规则本身不变。


### 3.2 基础控件标签

v1 内置基础控件标签：

- `<Text>`
- `<Button>`
- `<Input>`
- `<Image>`

基础控件的属性由编译器内置组件注册表定义。未知属性、未知事件和不匹配的属性类型必须在编译期报错。

最小属性约定如下：

| 标签 | 必选属性 | 常用属性 |
|---|---|---|
| `Text` | `Value` | `Color` |
| `Button` | `Text` | `Enabled` |
| `Input` | 无 | `Value`、`Hint`、`ReadOnly`、`SingleLine`、`Submit`、`MaxLen`、`Filter`（`Enabled` 见下） |
| `Image` | `Src` | `Width`、`Height` |

控件的具体绘制实现属于组件库，不改变 GXML 语义。

#### 3.2.1 `<Input>` 的属性与语义

`<Input>` 的输入语义、状态同步与事件分派由
[`Input输出契约.md`](Input输出契约.md)（v1 冻结）唯一定义。本规范只列语言面：

| 属性 | 类型 | 默认值 | 说明 |
|---|---|---|---|
| `Value` | 绑定或字面量 | 空串 | **外部值**：把 ViewModel 的值显示到编辑器 |
| `Hint` | 字面量 | 空串 | 占位提示 |
| `ReadOnly` | 静态 bool | `false` | 只读 |
| `SingleLine` | 静态 bool | `true` | 单行模式 |
| `Submit` | 静态 bool | `false` | 启用回车提交（声明 `Submit` 事件时自动为 `true`） |
| `MaxLen` | 静态 int | `0`（不限） | 最大字符数 |
| `Filter` | 字面量 | 空串 | 允许的字符集 |
| `Enabled` | 静态 bool | — | **v1 不支持**：Schema 可识别，但生成阶段报错（与 `<Button Enabled>` 同一裁决） |

> **`Enabled` 的区分**：「Schema 可识别」与「可被成功编译」是两件事。
> `Enabled` 能被解析与校验，但 v1 的 Input 生成不实现禁用语义，
> 编译期显式报错而非静默忽略。

**绑定方向**：`Value="{Path}"` 是**单向**的（ViewModel → 编辑器）。
GXML v1 **不存在自动双向绑定**（见 §9）；回写只能经 `ValueChanged`
或 `Submit` 事件方法显式完成。

**两条事件的区别**：

| 事件 | 触发时机 | 载荷 |
|---|---|---|
| `ValueChanged` | 用户**编辑过程中**文本变化 | 编辑器的当前文本 |
| `Submit` | 用户**明确提交**（回车，且 `Submit=true`） | 提交时的文本 |

两者**互不回退**：只声明 `Submit` 时不会有值回写；只声明 `ValueChanged`
时回车不产生 `Submit` 事件。

**`<For>` 内禁止使用**：见 §6.2。

### 3.3 控制流标签

控制流标签只在编译期存在，运行时不会保留 XML 节点：

- `<If>`、`<Then>`、`<Else>`
- `<For>`

### 3.4 宏标签

宏标签只在编译期存在：

- `<Defs>`
- `<Def>`
- `<Slot>`

## 4. 属性值语法

### 4.1 静态值与绑定值

属性值只有两种语义：静态字面量或完整绑定。

合法示例：

```xml
<Text Value="欢迎"/>
<Text Value="{User.Name}"/>
<Button Enabled="{User.CanSave}"/>
```

v1 禁止在一个属性中混合静态文本和绑定：

```xml
<!-- 禁止 -->
<Text Value="你好，{User.Name}"/>
```

需要组合文本时，应在 Go ViewModel 中提供计算字段，或在后续版本增加明确的格式化节点。

### 4.2 绑定路径

绑定的规范形式为：

```text
{Path}
{!Path}
```

其中 `Path` 为一个或多个标识符，以 `.` 分隔：

```text
Identifier ("." Identifier)*
```

标识符规则：

```text
[_A-Za-z][_A-Za-z0-9]*
```

v1 允许：

- ViewModel 字段或方法结果字段的路径访问。
- 当前 `<For>` 作用域中的局部变量路径。
- `!` 前缀表示布尔取反。

v1 禁止：

- 函数调用。
- 算术、比较、三元和逻辑表达式。
- 数组或 map 下标。
- 任意 Go 代码。
- 运行时脚本或动态求值。

绑定路径必须由 Analyzer 在编译期校验。路径不存在、不可访问、类型不匹配或在当前作用域无效时，编译失败。

### 4.3 EdgeInsets

`Padding` 使用 1、2 或 4 个非负十进制数值，单位统一为 dp：

```text
Padding="10"          // 四边 10
Padding="10 20"       // 上下 10，左右 20
Padding="1 2 3 4"     // 上、右、下、左
```

负数、空值、超过 float32 可表示范围的数值和超过 4 个数值都是编译错误。

### 4.4 Color

颜色支持以下格式：

```text
#RRGGBB
#RRGGBBAA
$Theme.Field
```

主题引用只允许出现在颜色属性中。`$Theme.Field` 不属于 ViewModel 绑定，不能写成 `{Theme.Field}`。

### 4.5 布尔和数值

- 布尔值只接受小写 `true` 和 `false`。
- 数值使用十进制表示，默认单位为 dp。
- 不进行隐式类型转换。
- `"1"` 不能自动转换为整数，`"true"` 不能自动转换为布尔值。

## 5. 事件语法

### 5.1 事件绑定

事件**不使用 `@` 前缀**，与普通属性写法一致：

```xml
<Button Text="保存" Click="Save"/>
<Button Text="删除" Click="Delete(item.ID)"/>
```

> `@` 不是合法的 XML 属性名字符，`encoding/xml` 会直接报语法错误。因此事件与属性在语法层没有区分符号，改由组件契约区分（见 §5.2）。

事件处理器语法为：

```text
Method
Method(Argument, Argument, ...)
```

事件参数只能是：

- 字符串（单引号）、数字和布尔字面量。
- ViewModel 绑定路径。
- 当前 `<For>` 作用域中的局部变量路径。

以下形式禁止：

```xml
Click="Save(User.Name + '!')"
Click="func() { ... }"
Click="{Save}"
```

### 5.2 属性与事件的区分：由组件契约声明，绝不推断

语法层无法区分 `Click="Save"` 是事件还是普通字符串属性：`Save` 在两种位置都是合法文本。因此区分完全依赖**组件的类型化声明**。

分类按以下顺序进行，**顺序固定**：

| 顺序 | 类别 | 来源 |
|---|---|---|
| 1 | 全局布局属性 | 编译器内置表（`Padding`/`Gap`/`Background`/`Width`/`Height`/`Align`/`Justify`/`Columns`） |
| 2 | 组件属性 | 组件 Schema 的 `Properties` |
| 3 | 组件事件 | 组件 Schema 的 `Events` |
| 4 | 都不匹配 | 编译错误 `GXML-ATTR-004: unknown attribute or event` |

**规则 4 绝不退化为事件。** 否则 `Clik="Save"`（`Click` 的拼写错误）会被静默当作事件绑定，把一个应立即发现的错误变成看似合法的代码。

布局属性不进入任何组件的 Schema：它们对所有元素通用，若逐个组件声明会导致每新增一个布局属性都要修改全部 Schema。

**分类与适用性是两项独立检查**，不得混为一谈：

| 情况 | 诊断 |
|---|---|
| 名称不属于任何类别 | `GXML-ATTR-004` 未知属性或事件 |
| 名称是布局属性，但不适用于当前元素（如 `Columns` 出现在 `<Button>` 上） | `GXML-ATTR-005` 属性不适用于该元素 |
| 组件属性缺失且无默认值 | `GXML-ATTR-004` 缺少必填属性 |

### 5.3 内置控件的事件契约

| 标签 | 属性 | 事件 |
|---|---|---|
| `Text` | `Value`（必填）、`Color` | — |
| `Button` | `Text`、`Enabled` | `Click` |
| `Input` | `Value`、`Hint`、`ReadOnly`、`SingleLine`、`Submit`、`MaxLen`、`Filter` | `ValueChanged(value:string)`、`Submit(text:string)` |
| `Image` | `Src` | — |

### 5.4 自定义组件必须显式声明事件

`<Def>` 用 `Events` 声明组件可发出的事件，**不能通过「未在 `Props` 中出现」推断**：

```xml
<Def Name="UserCard"
     Props="Name:string; Accent:color=$Theme.Primary"
     Events="Click; Open(id:string)">
  <Column Padding="12">
    <Text Value="{Name}" Color="{Accent}"/>
    <Slot/>
  </Column>
</Def>
```

`Events` 语法：

```text
EventName
EventName()
EventName(ParamName:Type, ParamName:Type)
```

参数类型取 `string`/`bool`/`int`/`float`/`color`/`insets`，与 `Props` 一致。

调用时未声明的事件名是编译错误：

```xml
<UserCard Name="{User.Name}" Click="Open"/>  <!-- Click 已在 Events 中声明，合法 -->
<UserCard Name="{User.Name}" Clik="Open"/>   <!-- GXML-ATTR-004 未知 -->
```

### 5.5 事件契约与处理器调用是两件事

二者**不得共用同一份声明**：

| 概念 | 含义 | 声明位置 |
|---|---|---|
| **事件契约** | 组件能发出什么事件、携带什么数据 | `<Def Events="Open(id:string)">` |
| **处理器调用** | 事件触发时调用哪个方法、传入哪些实参 | `Click="Save(item.ID)"` |

即使事件本身不携带任何参数，处理器仍可读取当前作用域并传参：

```xml
<!-- Button 的 Click 事件不带参数 -->
<For Each="item" In="{Items}" Key="{item.ID}">
  <Button Text="删除" Click="Delete(item.ID)"/>
</For>
```

反之，声明了事件参数也不代表任意处理器调用都合法。

**方法形参由两部分按序拼接而成**：

```text
方法形参 = 事件声明参数 ++ 调用点实参
```

| XML | 事件载荷 | 调用点实参 | 处理方法签名 |
|---|---|---|---|
| `Click="Delete(item.ID)"` | 无 | `item.ID` | `Delete(id int)` |
| `ValueChanged="OnNameChanged"` | `value string` | 无 | `OnNameChanged(value string)` |

规则（由 Analyzer 校验）：

- **顺序固定**：载荷在前，实参在后；不根据方法签名反向猜测归属。
- **数量精确**：两部分之和恰好等于方法形参数量，不忽略载荷、不自动补参、不丢弃多余参数。
- **类型逐项**：先按事件声明顺序校验载荷类型，再按实参顺序校验实参类型；不做隐式转换。
- **载荷属于组件契约**：内置事件与自定义组件事件统一适用。

注意 `ValueChanged="OnNameChanged"` 不写任何实参，但方法仍必须接收 `value string`——事件触发时由组件提供载荷。完整论证见 [`Analyzer输入输出契约.md`](Analyzer输入输出契约.md) §8.4。

事件回调可以修改 ViewModel，但渲染刷新由生成代码和运行时生命周期负责；GXML 不定义隐式双向绑定。

### 5.6 名称冲突规则

- 同一组件的属性名与事件名不得重复：定义处报 `GXML-DEF-003`。
- 同一组件内重复声明属性或事件：定义处报 `GXML-DEF-004`。
- 组件属性或事件名不得与全局布局属性同名：定义处报 `GXML-DEF-005`。否则 `Width` 等名称的语义会随组件变化。
- 新增内置属性或事件**不得改变既有名称的语义**，见 §11。


## 6. 条件与循环

### 6.1 If

`<If>` 必须包含一个 `<Then>`，可以包含一个 `<Else>`：

```xml
<If Condition="{User.LoggedIn}">
  <Then>
    <Text Value="已登录"/>
  </Then>
  <Else>
    <Text Value="未登录"/>
  </Else>
</If>
```

规则：

- `Condition` 必须是布尔绑定。
- `<Then>` 和 `<Else>` 只能作为 `<If>` 的直接子节点。
- `<Then>` 必须存在且只能一个。
- `<Else>` 最多一个。
- `<If>` 不允许出现直接渲染子节点。

### 6.2 For

`<For>` 的基本形式为：

```xml
<For Each="item" In="{Items}" Index="i" Key="{item.ID}">
  <Text Value="{item.Name}"/>
</For>
```

属性规则：

| 属性 | 必选 | 说明 |
|---|---|---|
| `Each` | 是 | 循环变量名 |
| `In` | 是 | 可迭代绑定，必须是集合或数组 |
| `Index` | 否 | 当前索引变量 |
| `Key` | 条件必选 | 用于稳定保留子控件状态 |
| `Virtualize` | 否 | v1.1 扩展，`true` 时启用虚拟化，缺省 `false`（见 ADR-0006） |
| `ItemExtent` | 条件必选 | v1.1 扩展，固定行高（dp），启用虚拟化时使用 |

当循环体包含 `<Button>` 或声明为有状态的自定义组件时，`Key` 必须存在。`Key` 必须是稳定且可比较的绑定路径。

> **`<Input>` 是例外**：v1 的 `<Input>` **不得出现在 `<For>` 内**
> （行内编辑器的生命周期尚未裁决，见
> [`Input输出契约.md`](Input输出契约.md) §7）。
>
> 与 `Key` 规则的关系：`Key` 是**通用身份规则**，`<Input>` 的限制是
> **v1 能力边界**，后者优先。两种输入各自命中不同诊断码：
>
> | 输入 | 命中码 |
> |---|---|
> | `<For>` 无 `Key` + 含 `<Input>` | `GXML-SCOPE-003`（缺 Key，既有规则先命中） |
> | `<For>` 有 `Key` + 含 `<Input>` | `GXML-SCOPE-005`（v1 不支持行内 Input） |
>
> 两条规则不叠加——同一处只报一条。

`Virtualize` 与 `ItemExtent` 是对 v1 基线的**向后兼容扩展**：未指定时行为与 v1 完全一致。启用虚拟化后的行状态生命周期设计以 `docs/03-架构/AOT状态Diff语义.md` §5.1.1 为参考，待对应列表实现批次重新验证；决策依据见 `docs/03-架构/adr/ADR-0006-列表虚拟化与静态子树宏固化.md`。

循环状态协调、`nil`/空 Slice 语义、行状态生命周期和 Macro 缓存边界在 AOT Diff 尚未引入前不构成当前运行时承诺；未来启用该方案时以 `docs/03-架构/AOT状态Diff语义.md` 为准。

`Each` 和 `Index` 只能在循环体内使用。循环变量不得覆盖 ViewModel 根名称或外层同名变量。

## 7. Def 与 Slot

### 7.1 Def

组件定义只能放在 `<Defs>` 中：

```xml
<Defs>
  <Def Name="UserCard" Props="Name:string; Accent:color=$Theme.Primary">
    <Column Padding="12">
      <Text Value="{Name}" Color="{Accent}"/>
      <Slot/>
    </Column>
  </Def>
</Defs>
```

`Props` 语法为：

```text
Name:Type
Name:Type=Default
```

多个属性使用分号分隔。v1 类型名为：

- `string`
- `bool`
- `int`
- `float`
- `color`
- `insets`

没有默认值的属性为必填属性。默认值必须是对应类型的静态值或主题颜色引用，不能是任意绑定。

规则：

- `Name` 必须唯一且符合标识符规则。
- `Def` 必须有且只能有一个渲染根节点。
- `<Slot/>` 最多出现一次，只表示默认插槽。
- `<Slot/>` 只能出现在 `<Def>` 内。
- `<Def>` 不得直接或间接递归引用自身。
- 宏展开顺序和结果必须确定。

### 7.2 组件调用

自定义组件使用与 `Def.Name` 相同的标签名：

```xml
<UserCard Name="{User.Name}" Accent="$Theme.Primary">
  <Text Value="{User.Email}"/>
</UserCard>
```

调用方传入的属性必须通过 `Props` 声明并完成类型检查。没有 `<Slot/>` 的组件不能接收子节点。

#### 7.2.1 Props 的展开语义

`<Def>` 是编译期宏：调用点被**内联展开**为 Def 体的渲染子树，运行时不保留组件边界，也不产生任何注册表。

Prop 引用采用**值替换**而非文本替换：

| Def 体内写法 | 调用点传值 | 展开结果 |
|---|---|---|
| `<Text Value="{Name}"/>` | `Name="{User.Name}"` | `<Text Value="{User.Name}"/>` |
| `<Text Value="{Name}"/>` | `Name="张三"` | `<Text Value="张三"/>`（静态字面量） |
| `<Text Value="{User.Name}"/>` | `User="{Account}"` | `<Text Value="{Account.Name}"/>`（路径拼接） |
| `<Column Background="{Accent}">` | `Accent="#FF0000"` | 背景色为 `#FF0000` |

规则：

- 替换只匹配绑定路径的**首段**，`{UserName}` 不会被 `User` 误伤。
- 未传入且有默认值的 Prop 使用默认值；无默认值且必填时报告缺失。
- 同一 `<Def>` 可被多次调用，每次展开产生**独立副本**，互不影响。

#### 7.2.2 Slot 的展开语义

- 调用点的子节点替换 Def 体内的 `<Slot/>`。
- 未声明 `<Slot/>` 的组件**不能接收子节点**，报 `GXML-DEF-009`。
- 单个 `<Slot/>` 位置**只能被一个子节点替换**；多个子节点会报 `GXML-DEF-009`。

##### 为什么限制为单子节点（不自动包裹）

GXML 没有 React Fragment 那样的虚拟多节点容器。当调用点传入多个子节点而 `<Slot/>` 只有一个位置时，编译器只有两条路：报错，或自行套一层容器。**v1 选择报错**，理由有三条：

**① 插槽可能处于任意布局上下文，自动包裹会改变布局语义。**

`<Slot/>` 不由自己决定所处环境。考虑一个组件：

```xml
<Def Name="Toolbar">
  <Row Gap="8"><Icon/><Slot/></Row>
</Def>
```

调用方传入两个按钮：

```xml
<Toolbar>
  <Button Text="保存"/>
  <Button Text="取消"/>
</Toolbar>
```

若编译器自动把它们包进 `<Column>`，两个按钮会**垂直堆叠**，而作者的意图显然是 `<Row>` 中的水平并排。这个结果无法从调用点覆盖——调用方只能选择「不传两个子节点」。

相比之下，`<Page>` 是视窗的绝对根节点，没有外层布局上下文，给它一个默认的垂直流向不会产生歧义。这是两者唯一的区别，也是两者规则不同的原因。

**② 插槽的职责是内容替换，不应自行决定多个节点的排列方向。**

排列方向是布局决策，属于调用方或组件作者的职责。让编译器替他们决定，等于在布局树里插入一个「隐形层」——它不体现在 `.gxml` 里，却影响着测量、对齐与间距，出问题时极难定位。

**③ 明确错误优于静默改变语义。**

`GXML-DEF-009` 会在编译期立即告诉开发者「这里需要一个明确的布局容器」，并给出修复方式。而静默套一层非预期的 `<Column>`，会让界面「看起来能跑但位置全错」，把编译期问题推迟成人工排查。

**代价**：多子节点场景需要显式写一层容器。对一个需要精确控制布局的 GUI 框架，这个代价换来的可预测性更值得。


#### 7.2.3 v1 限制：自定义组件事件不参与展开

`<Def Events="...">` 在 v1 中**只做契约声明与调用点校验**，不产生事件传播：

- Def 体内没有语法能"发出"事件，因此组件的 `Events` 声明目前没有运行时可观察的效果。
- 调用点传入的处理器会被校验（语法、名称是否已声明），但不会出现在展开结果中。

真正的事件转发需要新的语言机制（事件冒泡、回调插槽或事件参数传递），属于 v2。之所以先在 v1 保留 `Events` 声明，是为了让契约、诊断与向前兼容现在就稳定下来，避免后续改动既有属性语义。

除 `<Def>` 外，编译器也可以解析目标 Go package 中通过 `//goxml:component` 注解声明的 Go 自定义组件。该解析发生在编译期并直接生成 Go 调用，不创建运行时注册表；注解、Props 类型和 Layout 签名以 `docs/03-架构/代码生成输出契约.md` 为准。

命名插槽、动态组件名、运行时组件注册和组件递归均不属于 v1。

## 8. 名称、属性和错误规则

- 标签名、属性名、事件名均区分大小写。
- 同一个元素中属性不能重复。
- 同一个元素中同名事件不能重复。
- 未知标签、未知属性和未知事件必须报错。
- 不允许通过大小写变化绕过重复检查。
- 保留名称 `Goxml`、`Page`、`Defs`、`Def`、`Slot`、`If`、`Then`、`Else`、`For`，用户组件不能覆盖这些名称。

编译器应按源码顺序返回诊断。XML 结构错误可以立即终止；结构正确后的属性、绑定和组件错误应尽可能一次收集并报告。

诊断格式统一为：

```text
file.gxml:12:18: GXML-BIND-001: unknown binding path "User.Nmae"
```

错误至少包含：文件、起始行、起始列、错误码和消息。建议同时保留结束位置，供编辑器标记源码范围。

> 上述示例中的 `GXML-BIND-001` 仅用于说明**格式**。该码的语义见诊断码目录（绑定路径首段无法解析），已由 Analyzer 实现并发射。
>
> 全部诊断码的含义、归属阶段与空置号码以 [`诊断码目录.md`](诊断码目录.md) 为唯一权威。

## 9. v1 明确不支持的内容

- 运行时 XML、CSS 或 GXML 解析。
- CSS 选择器、级联和继承样式。
- 任意表达式和 Go 代码内联。
- 隐式双向绑定。
- 运行时反射状态比较。
- 动态组件名和运行时宏查找。
- 命名插槽。
- Map 作为 `<For In>` 数据源或自动 Diff 的直接绑定值。
- 通过属性自动推断复杂布局行为。
- **尺寸的内容测量语义**（`Auto`、`Intrinsic`、`Measure`）：`Width`/`Height` 缺省即自然尺寸，不提供测量型取值（见 §3.1.4）。
- **`Grid` 的坐标定位与跨行跨列**：不支持 `Grid.Column`、`Grid.Row`、`ColumnSpan`、`RowSpan`（见 §3.1.6）。
- **`Auto` 列宽**：`Columns` 只接受固定 dp、`*`、`N*`。

> 说明：字体族、字号、CJK fallback 与 IME 支持**不属于 GXML 语法**，由主题与运行时负责，见
> `docs/03-架构/字体与文本渲染策略.md`。GXML 不引入字体相关标签或属性。

## 10. 对编译器契约的要求

为了实现本规范，IR 至少需要具备以下信息：

- `NodeKind`，不能只依赖 `Tag string`。
- 每个节点和属性的 `SourceSpan`。
- 结构化的 `If`、`For`、`Def` 和 `Slot` 节点。
- 绑定路径的分段表示，而不是只保存原始字符串。
- Def 属性的名称、类型和默认值。
- 事件名称、方法名、参数列表和源码位置。

`DocumentIR.Package` 可以作为生成上下文保留，但不应作为 GXML 语义字段；`ViewModel` 只描述绑定类型来源。

## 11. 版本演进

任何以下变更都必须进入 v2 或新的 ADR：

- 增加新的表达式能力。
- 改变绑定路径规则。
- 改变 `<For>` 状态身份规则。
- 增加双向绑定。
- 增加命名插槽或动态组件。
- 改变静态属性的单位和类型转换规则。
- **改变布局标签的默认 `Align`**（`<Row>` 默认 `Center`、`<Column>` 默认 `Start`，见 §3.1.2）。这是唯一难以回退的决定：修改默认值会改变所有既有文档的视觉行为。
- **改变 `Width`/`Height` 的取值集合**，或引入内容测量语义。
- **改变 `Columns` 语法**，或为 `<Grid>` 引入坐标与跨行跨列。
- **重命名布局属性**（如 `Gap`）。
