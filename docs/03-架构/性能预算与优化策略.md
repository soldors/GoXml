# 性能预算与优化策略

- 状态：设计冻结，基线实测完成（单机），CI 复测待完成
- 冻结日期：2026-10-18
- 关联需求：REQ-002、REQ-003、REQ-004
- 关联 ADR：ADR-0001、ADR-0003、ADR-0006
- 适用范围：Codegen、Analyzer、Runtime、Widgets、Benchmark、发布门禁

## 1. 本文件解决什么问题

`AGENT.md` 原先只声明「单帧渲染 CPU 耗时相比纯手写 Gio 损耗 < 5%」这一条相对指标。该指标有两个实践缺陷：

1. **不可证伪**：两个都慢的实现之间也能满足 5% 的比值。
2. **抓不住真凶**：Goxml 的性能风险主要不是「单帧多花几微秒」，而是「每帧产生堆分配导致 GC 周期性打断渲染」。

本文件把性能目标改写为**可执行、可断言、可复现**的不变量，并记录支撑这些决策的实测数据。凡本文件与旧表述冲突，以本文件为准。

## 2. 实测基线数据

### 2.1 测试环境

| 项目 | 值 |
|---|---|
| CPU | 12th Gen Intel Core i7-12700H |
| 操作系统 | Windows（amd64） |
| Go | 1.26.1 |
| Gio | gioui.org v0.10.3 |
| CGO_ENABLED | 0 |
| 采样 | `-benchtime 200~300ms -count 2~3`，取稳定值 |

> 本表是**单机初步基线**，用于确立量级与排序，不作为发布证据。发布数值必须在 `docs/06-测试/测试与质量门禁规范.md` §2.7 规定的固定 CI 环境复测，并写入 `docs/06-测试/ 下的里程碑验收报告` §7。

### 2.2 渲染规模：全量渲染 vs 虚拟滚动

场景：10,000 行文本，800×600 窗口，`layout.Flex` 逐行生成闭包。

| 实现 | ns/op | allocs/op | B/op |
|---|---:|---:|---:|
| 全量渲染（每行一个 `layout.Rigid` 闭包） | 6,438,000 | 10,010 | 1,511,672 |
| 虚拟滚动（`layout.List`，仅可见行） | **19,200** | **0** | **7** |

**结论：相差 335 倍。** 全量渲染单帧 6.4ms，已超出 60fps 的 16.67ms 预算的 38%，且每帧 1.5MB 分配会持续触发 GC。这是 Goxml 可能遇到的**最大性能风险**，远大于任何指令级优化。

### 2.3 静态子树：闭包分配 vs 编译期展开

场景：50 个子节点的纵向 `layout.Flex`，节点内容完全相同。

| 实现 | ns/op | allocs/op | B/op |
|---|---:|---:|---:|
| 每帧 `append` 构造 `[]FlexChild` | 28,000 | 51 | 6,172 |
| 预分配并复用 `[]FlexChild` 缓冲区 | 27,000 | 51 | 4,012 |
| **编译期完全展开（无循环、无切片、无闭包）** | **2,550** | **0** | **0** |

**结论：相差 11 倍。** 注意第二个结果：**预分配复用只省下约 4% 的时间和 35% 的字节数，几乎不解决问题**。真正的开销来自「闭包本身逃逸」而不是「切片容量」。因此 Codegen 不能只做「复用缓冲区」，必须把静态子树**展开为直接调用并固化 `op.CallOp`**。

### 2.4 文本 shaping：字符串稳定性决定开销

场景：单个 `<Text>` 节点的布局。

| 实现 | ns/op | allocs/op | B/op |
|---|---:|---:|---:|
| 每帧传入同一字符串 | **876** | 0 | 0 |
| 每帧 `fmt.Sprintf` 短字符串 | 1,079 | 1 | 16 |
| **每帧变化的较长字符串** | **82,053** | **270** | **137,461** |

**结论：相差 94 倍。** 原因是 `text.Shaper` 以字符串为缓存键；字符串每帧变化会令整条 glyph 布局缓存失效。**每帧 137KB 分配意味着 60fps 下每秒 8.2MB**，GC 必然被频繁触发。这是 Goxml 极易踩中、且文档此前完全未覆盖的陷阱。

### 2.5 抽象开销：接口派发 vs 具体调用

场景：200,000 个节点遍历并调用 `Measure()`。

| 实现 | ns/op |
|---|---:|
| `[]Node` 接口派发 | 361,000 |
| `[]box` 具体类型调用 | **61,000** |

**结论：相差 5.9 倍。** 该数据支撑 `AGENT.md` 的「零抽象开销」红线：Codegen 必须生成**具体类型调用**，不得在渲染树规模上引入接口。

### 2.6 附录：像素级优化（非帧热路径）

场景：1M 像素填充与 alpha 混合。此数据**仅用于说明边界**，不与帧预算混用。

| 实现 | ns/op | 相对 |
|---|---:|---:|
| `image.RGBA.Set()`（接口 + 坐标计算） | 5,475,139 | 1.0× |
| 直接写 `[]byte` | 211,349 | 25.9× |
| `[]uint64`（一次两像素） | 132,254 | 41.4× |
| 逐像素 alpha 混合 | 2,764,000 | 1.0× |
| SWAR64 位运算混合 | 354,000 | 7.8× |

浮点累加：朴素串行求和 577,000 ns/op；手动 4 路展开 **240,000 ns/op（2.4×）**，差异来源是 Go 不做自动向量化、不打破依赖链。

**重要边界**：Gio 的像素由 GPU 绘制（Windows 走 D3D11），CPU 侧**不存在逐像素热路径**。上述优化手法只适用于图标/位图预处理、CPU 侧大数组计算等非帧路径，**不得作为帧性能优化的主要手段**。

### 2.7 静态子树缓存（2026-10-19 实测）

**这是本项目第一次有可复现的缓存性能基线。** 此前 ADR-0001 的 11×/5.9×
一直标注为不可复现——仓库当时没有任何 `Benchmark`。

测量对象是**真实生成的代码**，不是生成器本身。

| 场景 | NoCache ns/op | FirstRecord ns/op | CacheHit ns/op | 加速比 |
|---|---:|---:|---:|---:|
| 单节点 `<Text>` | 688.9 | 2237 | **30.37** | 22.7× |
| `<Column>` 3 子节点 | 1654 | 4248 | **33.59** | 49.2× |
| `<Column>` 套 `<Row>` | 1685 | 5620 | **29.00** | 58.1× |

`CacheHit` 三场景均 **0 B/op, 0 allocs/op**。

#### 三条结论

1. **命中时长几乎不随节点数增长**（30 / 34 / 29 ns）。回放的是同一份
   `op.CallOp`，与录制内容包含多少节点无关。
2. **NoCache 随节点数线性增长**（689 → 1654 → 1685 ns）。
   因此**节点越多，缓存收益越大**。
3. **回放不执行任何叶子布局**：3 帧中叶子布局只执行 3 次（全在首帧，
   与子节点数相等），第 2、3 帧完全跳过布局计算。

#### 边界与限制（必须同时引用）

- **只适用于静态树**。静态/动态混合树的缓存边界尚未运行时验证
  （动态节点未实现，契约 §16.7 目前只有设计规则）。
- **不可换算为 FPS**。这是单帧布局成本，不含 GPU 提交与合成。
- **单机基线**，不作为发布证据。

#### 生成器自身基准

测量的是**代码生成阶段**（Parser/Expander/Analyzer 开销不计入）：

| 输入 | ns/op | B/op | allocs/op | 产物 |
|---|---:|---:|---:|---:|
| 单节点 | 253,183 | 62,007 | 1,103 | 2,685 字节 |
| Column 3 子节点 | 382,443 | 73,763 | 1,339 | 3,046 字节 |
| 嵌套 | 509,810 | 77,654 | 1,428 | 3,189 字节 |

**成本构成**：单独测 `go/format.Source` 为 208,039 ns/op，占 `Generate` 的
**约 78%**。格式化是契约 §7 的强制要求（生成输出必须经 `format.Source`），
因此这不是可优化项，而是既定成本。

> 编译期成本（数百微秒/文件）相对运行时收益（每帧省 600+ ns）
> 可忽略——只要文件生成一次、渲染多帧。

go test -bench BenchmarkGenerate -benchmem -run '^$' ./internal/compiler/codegen/

## 3. 性能不变量（强制）

以下为设计阶段的**硬约束**，违反按 P0 缺陷处理。每条都必须能被自动化断言，而不是靠人工评审。

### 3.1 INV-PERF-1：静态子树必须编译期固化

- 定义：一个子树若不含任何绑定、事件、条件或循环，其布局与绘制结果恒定。
- 要求：Codegen 必须为其生成 `op.Record` + `op.CallOp` 缓存槽位，稳定帧只回放 `CallOp.Add(gtx.Ops)`。
- 断言：Golden 测试检查生成源码包含对应 `CallOp` 字段；基准测试确认该子树在 `DirtyPaint == 0` 时不重新记录宏。

### 3.2 INV-PERF-2：热路径零分配

- 定义：热路径 = 一帧内因数据刷新而执行的 `Layout` 路径。
- 要求：**静态页面在稳定帧的 `allocs/op` 必须为 0**；有绑定变化的页面，每帧分配量必须与「实际变化的节点数」线性相关，不得与「总节点数」相关。
- 断言：`go test -bench` 断言 `b.ReportAllocs()` 输出的 `allocs/op == 0`。

### 3.3 INV-PERF-3：列表不得全量渲染

- 定义：视口外元素不参与布局与绘制。
- 要求：`<For>` 在开启虚拟化时，单帧工作量只与可见元素数相关，与集合长度无关。
- 断言：10,000 行与 100,000 行的基准耗时差异必须在常数倍以内（建议 ≤ 1.5×）。

### 3.4 INV-PERF-4：文本缓存不得被无条件击穿

- 要求：`<Text>` 的绑定值未变化时，不得重建字符串、不得重新 shaping。
- 要求：由多个字段拼装的显示文本，必须在 ViewModel 侧或框架侧缓存字符串化结果，禁止在 `Layout` 内每帧 `fmt.Sprintf`。
- 断言：稳定帧下文本节点的 `allocs/op == 0`。

#### 责任主体（绑定系统契约 §05）

| 层 | 职责 |
|---|---|
| 绑定读取层 | 从 ViewModel 取当前值并完成显示值转换；不得每帧无条件重建字符串 |
| 绑定缓存层 | 记住上次有效值；值未变化时复用，避免重复 shaping |
| 状态更新层 | 变化时确保 UI 有机会重新读取（具体机制由 `TASK-STATE-001` 定义） |

#### 五个必须验证的场景

| # | 场景 | 期望 |
|---|---|---|
| 1 | 绑定值稳定 | 不反复重建显示字符串，不重复整形 |
| 2 | 绑定值变化 | 缓存失效，显示更新（**正确性优先于零分配**） |
| 3 | 原始值变但显示字符串不变 | 由绑定契约明确是否允许复用 shaping |
| 4 | 字体/约束/主题变化 | 不得错误复用旧 shaping 结果 |
| 5 | 读取失败 | 不留部分结果，缓存可恢复 |

#### 两个必须区分的指标

- **稳定帧零分配**：初始化后、绑定值不变时，文本路径 `allocs/op == 0`。
- **避免重复 shaping**：需用**可观察的 shaping 调用计数**或等效证据验证，
  **不能只凭分配数推断**。

> ⚠️ 当前 `text.Shaper` 的缓存字段未导出，shaping 无法直接计数；
> 实现阶段需先设计可替换的测试 seam（见绑定系统契约 §05.3）。

#### 当前验证状态

**尚未验证。** 直接调用 Codegen 已能为部分 `<Text Value>` 字段绑定生成读取表达式，
但绑定值缓存、显示值复用和 shaping 计数尚未实现。A1–A6 的静态树测试**不覆盖**本条；
静态页面的 `0 allocs/op` 不能外推到动态绑定。

### 3.5 INV-PERF-5：交互控件必须每帧处理输入

- 该条与 INV-PERF-1 互为边界：`Button`、`Input` 等交互控件**不得**把「事件处理 + 绘制」整体缓存为永久回放宏。
- 依据：`docs/03-架构/AOT状态Diff语义.md` §6.2。
- 断言：连续两帧回放宏后，点击与输入事件仍能被消费。

### 3.6 INV-PERF-6：渲染上下文变化必须使宏失效

- 依据：`docs/03-架构/AOT状态Diff语义.md` §9。ViewModel 未变不代表宏有效。
- 断言：DPI/约束尺寸/主题/字体变化后，受影响宏必须重录。

## 4. 性能预算

以 60fps（16.67ms/帧）为基准，Goxml 生成代码的预算分配如下。

| 项目 | 预算 | 依据 |
|---|---:|---|
| 整帧总时间 | 16.67 ms | 60fps |
| Gio 布局 + 绘制（合理界面） | ≤ 2 ms | 实测合理界面量级 |
| Goxml 运行时开销（Diff + 协调 + 回放） | **≤ 0.5 ms** | 不超过 Gio 侧 25% |
| 万行表格单帧 | **≤ 1 ms** | 虚拟滚动实测 0.019ms，留 50× 余量 |
| 稳定帧 `allocs/op` | **0** | INV-PERF-2 |
| 冷启动 | ≤ 50 ms | `AGENT.md` 原有目标 |
| 常驻内存（空窗） | 15–30 MB | `AGENT.md` 原有目标 |

单帧 CPU 相对手写 Gio 的损耗 **≤ 5%** 目标保留，但改为**必须同时报告绝对 ns/op 与 allocs/op**，避免相对指标掩盖绝对退化。

## 5. 反模式清单（Codegen 与 Runtime 必须避免）

| 编号 | 反模式 | 后果 | 正确做法 |
|---|---|---|---|
| AP-1 | 无条件把 `<Column>` 翻译成 `layout.Rigid(func(...))` 闭包 | 每节点每帧一次堆逃逸，~11× 退化 | 静态子树展开为直接调用 + `CallOp` |
| AP-2 | `<For>` 一次性渲染全部元素 | 万行列表 6.4ms/帧，~335× 退化 | 虚拟化，只渲染可见区 |
| AP-3 | 在 `Layout` 内 `fmt.Sprintf` 拼接显示文本 | 文本缓存全失效，~94× 退化、每帧上百 KB 分配 | 缓存字符串化结果，仅在依赖字段变化时重建 |
| AP-4 | 为「零抽象」引入通用接口/容器承载节点 | 接口派发 ~5.9× 退化 | 生成具体类型代码 |
| AP-5 | 保存整份 ViewModel 快照做比较 | 每帧复制，分配随数据量增长 | 只存绑定叶子字段（AOT Diff §2.1） |
| AP-6 | 把交互控件的「事件+绘制」整体缓存为永久宏 | 点击/输入事件丢失 | 每帧处理输入，仅回放绘制宏 |
| AP-7 | 用全局锁包住 `Layout` 掩盖跨线程访问 | 渲染阻塞、抖动 | 单一 UI 状态所有者 + Dispatcher |
| AP-8 | 在帧热路径使用逐像素 CPU 处理 | 与 GPU 重复工作，且无收益 | 交给 Gio/GPU；CPU 仅做预处理 |

## 6. 门禁与验收

### 6.1 必须新增的门禁

```text
make benchmark                      # 生成版 vs 手写 Gio 对照，输出 ns/op、allocs/op
make bench-assert                   # 断言 INV-PERF-1/2/3 的机器可判定部分
```

`make bench-assert` 至少包含：

1. 静态页面稳定帧 `allocs/op == 0`。
2. 10,000 行虚拟列表单帧 ≤ 1ms。
3. 生成源码包含静态子树的 `CallOp` 缓存字段。
4. 生成源码不含 `import "reflect"`（与既有门禁合并）。

### 6.2 性能回归处理

| 情况 | 处理 |
|---|---|
| `allocs/op` 由 0 变为非 0 | 阻断合并，必须定位到具体节点 |
| 帧耗时回退 > 20% | 阻断合并，需说明原因并更新基线 |
| 基线整体上调 | 必须写入 ADR 并在验收报告记录新旧数值 |

## 8. 版本演进边界

以下变更必须更新本文件并通过新的 ADR：

- 改变性能不变量或预算数值；
- 放宽 `allocs/op == 0` 要求；
- 改变虚拟化的判定规则或默认行为；
- 引入新的帧热路径 CPU 计算。

## 9. 复现方法

```text
# 渲染规模对照
go test -run '^$' -bench 'Naive|Virtual' -benchtime 300ms -count 3 ./benchmarks/...

# 分配与静态展开
go test -run '^$' -bench 'NoPrealloc|PreallocReuse|StaticUnrolled' -benchmem ./benchmarks/...

# 文本 shaping
go test -run '^$' -bench 'Text_' -benchmem ./benchmarks/...

# 抽象开销
go test -run '^$' -bench 'Dispatch' ./benchmarks/...
```

基准必须固定窗口尺寸、DPI、数据量、预热次数与采样次数，并把环境写入验收报告。
