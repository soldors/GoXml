## 1. 控件状态持有（冻结）

### 1.1 生成位置

交互控件需要跨帧存活的状态（`widget.Clickable` 内部记录按下/悬停/指针捕获）。
因此为每个**声明了事件的控件**在生成视图结构体中分配私有字段：

```go
type GoxmlDashboardView struct {
	vm     *demo.ViewModel
	click0 widget.Clickable // 第 1 个带 Click 的控件
	click1 widget.Clickable // 第 2 个
	slots  []textCache
}
```

### 1.2 命名与顺序

- 按**深度优先遍历顺序**编号：`click0`、`click1`、…；
- 顺序由 `NodeIR` 子节点声明顺序决定（与 `§4.7.1` 布局顺序一致）；
- MVP 不涉及循环 Key，因此**不需要**字典映射或 Key 查找。

### 1.3 稳定性要求

字段位于 View 结构体，**跨帧地址不变**——这是 Gio 控件状态机的前提。
禁止把 `Clickable` 放在 `Layout` 局部变量或闭包捕获中（每帧重置 → 点击永不完成）。

## 2. 事件轮询位置与绘制时序（冻结）

### 2.1 轮询统一放在 `Layout` **开头**

```go
func (v *GoxmlDashboardView) Layout(gtx layout.Context, th *material.Theme) layout.Dimensions {
	// ① 事件消费：在所有布局/绘制之前
	for v.click0.Clicked(gtx) {
		v.vm.OnSave()
		gtx.Execute(op.InvalidateCmd{})
	}

	// ② 绘制
	return layout.Flex{Axis: layout.Vertical}.Layout(gtx, ...)
}
```

### 2.2 为什么必须在绘制之前（不是"更优雅"，是正确性）

若轮询放在控件自身位置：

```text
兄弟 A 已用旧状态绘制 → Button 轮询到点击并改状态 → 兄弟 B 用新状态绘制
```

**布局顺序在控件之前的节点这一帧仍是旧值**，而点击处理完成后若没有新输入事件，
Gio 不再产生帧——它们会**永久陈旧**（不是差一帧）。

把轮询提前到 `Layout` 顶部后，**本帧所有绘制都发生在状态更新之后**，
同帧即一致。`gtx.Execute(op.InvalidateCmd{})` 在此之上再保证后续帧，
属于**冗余保险**（防止未来实现把轮询移回树内）。

【外部事实】`op.InvalidateCmd{At time.Time}`，零值 = 立即重绘 —— `op/op.go:98`；
`gtx.Execute(Command)` 来自 `layout.Context` 内嵌的 `input.Source`
（`io/input/router.go:493`）；Gio 自身用法见 `widget/editor.go:778`。

### 2.3 控件自持事件类别（补充，2026-10-20）

> **修订记录**：本节为**限定适用范围**，不推翻 §2.1/§2.2。
> `<Button>` 的 `Click` 仍然遵循「置于 `Layout` 顶部」。
> 新增类别的原因是 `<Input>` 的事件消费依赖控件自身的布局上下文
> （焦点 tag、输入区域、IME 状态），提到顶部会失效。
> 依据：[`Input输出契约.md`](Input输出契约.md) §6、[ADR-0011](adr/ADR-0011-Input受控输入与事件分派.md) 决策 3。

#### 分类标准

| 类别 | 消费位置 | 判断标准 | 当前成员 |
|---|---|---|---|
| **顶部轮询事件** | `Layout` 开头，所有绘制之前（§2.1） | 消费只需输入区域命中，**不依赖控件的布局上下文** | `<Button>` 的 `Click` |
| **控件自持事件** | 控件自身的 `Update`/`Layout` 调用内 | 消费需要控件**自身的布局上下文**：焦点 tag、输入区域注册、IME 组合状态 | `<Input>` 的 `ValueChanged`、`Submit` |

#### 为什么 Editor 必须自持

【外部事实】`widget.Editor.Update(gtx)` 依赖：

- 本帧 `Layout` 注册的**焦点 tag**（写在 `gtx.Ops` 的 input op 中）；
- `gtx.Source` 的事件队列；
- IME 组合状态与布局上下文的对应关系。

若按 §2.1 提到 `Layout` 顶部，则焦点 tag 尚未由本帧 Layout 注册 →
事件无法路由到该 Editor；IME 状态与布局上下文错位。

**这不是"控件位置更自然"的风格问题，而是事件能否被投递的正确性问题。**

#### 对既有规则的影响边界

| 规则 | 是否受影响 |
|---|---|
| §2.1 轮询置于 `Layout` 顶部 | 对**顶部轮询事件**继续有效（Button 不变） |
| §2.2 同帧强一致（避免陈旧帧） | 对自持事件**由控件自身保证**：Editor 在 `Update` 后同一帧内 `Layout`，消费与绘制同帧 |
| §3 失效策略（`InvalidateCmd`） | 不变，两类事件共用 |

#### 覆盖方式

| 层 | 断言 |
|---|---|
| 结构 | 生成代码中 `<Input>` 的 `Update`/`Layout` 在控件位置；`Layout` 顶部**不出现** Editor 轮询 |
| 真实交互 | `input.Router` 合成按键 → `ValueChanged`/`Submit` 触发；焦点与 IME 走人工验收 |

> **IME 边界如实声明**：Gio 无合成 IME 的测试 API，组合输入行为
> 只能人工验收，不得标记为自动化覆盖。

## 3. 失效策略（冻结）

| 场景 | 机制 | 位置 |
|---|---|---|
| 同步事件（点击改状态） | `gtx.Execute(op.InvalidateCmd{})` | **帧内**（生成代码） |
| 异步任务（网络回调、ticker） | `App.Invalidate()` | **帧外**（调用方） |

### 3.1 为什么不用注入 `Invalidator`

| 路径 | 代价 |
|---|---|
| 生成代码持 `app.Invalidator` | 生成产物耦合 `pkg/runtime/app`；需 Setter 注入 + 测试期 nil 守卫；View 生命周期与 App 绑定 |
| **`gtx.Execute(op.InvalidateCmd{})`** | **零新增依赖**（`gioui.org/op` 生成代码已 import）；测试期同样可用 |

【设计判断】帧内失效由生成代码自理，帧外失效由调用方用 `App.Invalidate()`——
两者互补、不重叠。

## 4. 动态节点判定（冻结，含一处必修隐患）

### 4.1 判定规则

节点为**动态**，当且仅当满足任一：

```text
len(node.Events) > 0          // 携带事件
存在属性绑定 {Path}            // 已有规则（BindingVal.IsBinding）
任一子节点为动态
```

### 4.2 后果

动态节点**禁止**进入整页 / 子树静态固化（`op.Record`/`CallOp`）。

### 4.3 必修隐患

当前 `hasBinding()` **只看属性绑定**。若事件页不判为动态，会被整页录进 `CallOp`：

```text
录制时 Clicked(gtx) 轮询一次（无人点击）
后续每帧只回放宏 → Clicked 永不再执行 → 按钮"永久冻结"
```

表现为：**编译通过、界面正常、点击无反应**——最难定位的一类缺陷。

**实现要求**：判定函数改为 `hasDynamic()`（绑定 ∨ 事件 ∨ 子节点动态），
且必须有一条回归测试断言「含 `Click` 的页面生成结果中不含整页 `cacheCall` 回放」。

## 5. 处理器调用

### 5.0 修订记录

| 版本 | 范围 | 说明 |
|---|---|---|
| v1（MVP） | 仅无参 | 因 `ResolvedParam` 不含实参值（见 §5.2 原文），带参明确报错 |
| **v2（本版）** | **支持带参** | Facts 扩展 `ResolvedArg`（§5.4），Codegen 按类型化实参渲染 |

§5.2 保留为**历史阻断点记录**（它解释了 v1 为何收窄）；当前实现按 v2。

### 5.1 支持范围（v2 冻结）

| 写法 | 状态 |
|---|---|
| `<Button Click="Save"/>` → `v.vm.Save()` | ✅ |
| `<Button Click="OnLiteral(42)"/>` | ✅ 整数字面量 |
| `<Button Click="OnEcho('draft')"/>` | ✅ 字符串字面量（单引号或双引号） |
| `<Button Click="OnToggle(true)"/>` | ✅ 布尔字面量 |
| `<Button Click="Delete(User.Age)"/>` | ✅ ViewModel 路径实参 |
| `<Button Click="OnWeight(1.5)"/>` | ✅ 浮点字面量 |

多实参按 XML 声明顺序传入；类型兼容性由 Analyzer 的 EVENT-006 保证，Codegen 不再校验。

### 5.2 v1 的历史阻断点（保留记录）

【项目证据】`analyzer.ResolvedParam` 只有 `Name` / `Type` / `Span`，**不含实参值**：

```go
type ResolvedParam struct { Name string; Type TypeInfo; Span contracts.SourceSpan }
```

原始实参保存在 `contracts.EventArg{Kind, Literal, Binding}`（DocumentIR 层）。
即：**Codegen 无法只凭 `Facts` 生成带参调用**，必须回到 DocumentIR 读原始实参——
与「Codegen 不得自行解析绑定路径」的红线冲突。

v1 因此收窄为无参；v2 通过 §5.4 的事实扩展解决。

### 5.3 失败行为

- 实参形式非法 → Expander 的 EVENT-005（已有）；
- 实参类型与形参不兼容 → Analyzer 的 EVENT-006（已有）；
- 数量不匹配 → Analyzer 的 EVENT-004（已有）；
- **Codegen 不再为实参单独报错**：能走到生成阶段的实参必然已通过上述校验。

### 5.4 Facts 扩展：`ResolvedArg`（v2 冻结）

#### 5.4.1 结构

```go
// ResolvedArg 是一个已校验的事件调用实参。
type ResolvedArg struct {
	Kind    ArgKind      // ArgLiteral | ArgPath
	Literal LiteralValue // Kind == ArgLiteral 时有效
	Path    *ResolvedPath// Kind == ArgPath 时有效（复用既有路径类型）
	Type    TypeInfo     // 最终类型（Analyzer 已与形参兼容）
	Span    contracts.SourceSpan
}

type LiteralValue struct {
	Kind  LiteralKind // LiteralString|LiteralInt|LiteralFloat|LiteralBool
	Str   string
	Int   int64
	Float float64
	Bool  bool
	Raw   string // 原始文本，仅用于诊断回显
}
```

`ResolvedEvent.CallArgs` 的元素类型从 `ResolvedParam` 改为 `ResolvedArg`。
因 `ResolvedArg` 仍含 `Type` 字段，现有读取 `.Type` / `len()` 的断言不受影响。

#### 5.4.2 为什么存**类型化值**而不是 Go 表达式字符串

有人会倾向让 Analyzer 直接产出 `"draft"`（含引号）或 `v.vm.CurrentID`。
本契约**不采纳**，理由：

| 若存表达式字符串 | 后果 |
|---|---|
| 需要 Go 字符串转义规则（`strconv.Quote`） | Analyzer 承担 Codegen 语法 |
| 需要 `v.vm.` 根前缀约定 | **把生成代码的命名约定写进语义事实层**，未来改根名要动 Analyzer |
| 数字格式（`42` vs `42.0`、浮点精度） | 语法决策散落到两层 |

改为：Facts 存**类型化的值/路径**，Codegen 单点负责渲染语法
（它已有 `quote()` 处理属性字面量，转义规则只存在一处）。

这同样满足「Codegen 不自行解析原始文本」的红线——`Raw` 只用于诊断回显，
生成只用结构化的 `Kind/Literal/Path`。

#### 5.4.3 Codegen 渲染规则

| 实参 | 渲染 |
|---|---|
| `LiteralString` | `quote(Str)`（与属性字面量同一套转义） |
| `LiteralInt` | `strconv.FormatInt(Int, 10)` |
| `LiteralFloat` | `strconv.FormatFloat(Float, 'g', -1, 64)` |
| `LiteralBool` | `"true"` / `"false"` |
| `Path`（`RootViewModel`） | `"v.vm"` + `.` + 各段名（方法段加 `()`，与绑定取值同规则） |
| `Path`（`RootForVar`） | v2 **明确报错**：`<For>` 未实现，无可引用的循环变量 |

## 6. `<Button>` 生成形态（冻结）

【项目证据】`expander.builtinSchemas["Button"]`（`schema.go:134`）：

```go
Properties: Text(PropString), Enabled(PropBool)   // Text 非必选
Events:     Click                                 // 无载荷参数
```

### 6.1 生成

```go
material.Button(th, &v.click0, <label>).Layout(gtx)
```

| 属性 | MVP 处理 |
|---|---|
| `Text`（静态） | `"文字"` 字符串字面量 |
| `Text="{Path}"` | 经绑定取值表达式（复用既有绑定生成路径） |
| `Text` 缺省 | 空标签（Schema 允许非必选） |
| `Enabled` | ❌ **MVP 明确报错**（Gio 无直接参数，需 `gtx.Disabled()` 语义，留后续） |

### 6.2 文本与 shaping

`Text` 作为按钮标签传入 `material.Button`，**不**经 `bindText` 槽位缓存：
按钮标签由 `material.Button` 内部布局处理。若需复用显示缓存，属后续优化，
本轮**不宣称**按钮标签享有 `INV-PERF-4` 的缓存保证。

## 7. 与既有缓存的关系（冻结）

| 页面类型 | 静态整页固化 | 绑定显示槽位 |
|---|---|---|
| 纯静态（无绑定、无事件） | ✅ 保留（29 ns/op） | — |
| 含绑定、无事件 | ❌（§16.7） | ✅ `bindText` |
| **含事件** | ❌（本节 §4） | ✅ 仍可用 |
| 绑定 + 事件 | ❌ | ✅ |

事件页**不失去**绑定显示缓存——两者正交：事件控制「何时改状态」，
显示缓存控制「值未变时不重复工作」。

## 11. 本契约发现的两个既有缺陷

### 11.1 `pipeline` 未传 `Options.ModulePath`（阻断跨包 ViewModel）

【项目证据】`pipeline.go:143`：

```go
opts := codegen.Options{PackageName: cfg.PackageName, SourcePath: cfg.SourcePath}
```

demo 未暴露该问题（同包 ViewModel，`PkgDir == ""` 不需要 ModulePath）。

### 11.2 `hasBinding` 判定不含事件

见 §4.3。事件实现必须先修，否则事件页被固化。
