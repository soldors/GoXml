# ADR-0004：采用双进程 Live Reload 与独立静态预览器方案

- 状态：已接受，v1 协议已补充，实现验证待完成
- 冻结日期：2026-10-18
- 关联需求：REQ-005
- 关联文档：[运行时线程模型.md](../运行时线程模型.md)、[代码生成输出契约.md](../代码生成输出契约.md)、[测试与质量门禁规范.md](../../06-测试/测试与质量门禁规范.md)

## 1. 背景

Goxml 的 `.gxml` 必须在编译期转换为 Go 源码，运行时不能依赖 XML 解释器或虚拟 DOM。因此，开发期热更新不能通过替换运行时组件树实现，而必须重新生成、构建并启动应用进程。

## 2. 决策

v1 采用两个相互隔离的进程：

1. **Watch 主进程**：监听源文件、执行防抖、调用 `goxml generate` 和 Go 构建、管理子进程、保存和恢复状态。
2. **应用子进程**：运行生成后的 Gio 应用，只负责渲染和业务运行时，不负责监听文件或生成代码。
3. **Preview 进程**：独立运行 GXML 解析、宏展开和静态布局预览，不启动完整应用热重载链路。

Watch 进程崩溃或退出时，应用子进程必须收到取消信号并退出；应用子进程异常退出不能反向阻塞 Watch 进程。

## 3. 进程状态机

```text
Idle
  -> Debouncing       收到文件事件
  -> Building         防抖窗口结束
  -> StoppingChild    构建成功，准备替换应用
  -> StartingChild    旧进程已退出
  -> Restoring        新进程建立控制连接
  -> Running          状态恢复完成
```

任一阶段失败都进入 `Failed`：保留当前可运行的旧进程（如果它仍健康），记录诊断，等待下一次文件事件。构建失败不能启动半成品，也不能删除旧生成文件。

## 4. 文件监听与防抖

- 监听 `.gxml`、相关 Go 类型文件、主题和静态资源。
- 防抖窗口固定为 100ms；窗口内多个事件合并为一次构建。
- 事件必须按项目相对路径去重，并在构建前重新读取文件内容。
- 临时文件、`.goxml/` 缓存和生成文件的变化不得触发自身无限重启。
- 构建过程中再次到达的事件进入队列，当前构建结束后只保留最后一次变更集合。

## 5. 控制协议

Watch 与应用子进程之间使用独立的本机控制通道，业务 stdout/stderr 不得混入控制数据。v1 消息采用 UTF-8 JSON Lines，每行一个对象：

```json
{"type":"hello","protocol":1,"token":"..."}
{"type":"restore","schemaVersion":1,"stateFile":".goxml_state.json"}
{"type":"shutdown","reason":"source_changed"}
{"type":"ready","pid":1234}
{"type":"error","code":"HYDRATION-VERSION","message":"..."}
```

规则：

- 通道只监听 loopback 或等价的进程私有管道，并使用一次性随机 token；不得暴露到公共网络。
- `hello` 必须在超时内完成，否则 Watch 将子进程视为启动失败。
- `ready` 之前发生的状态恢复错误只能影响恢复，不得让 Watch 永久等待。
- 未知消息类型被记录并忽略；协议版本不兼容时关闭连接并进入失败流程。
- 控制通道关闭时，应用必须取消生命周期 Context 并释放平台 worker。

## 6. 状态保存与恢复

状态文件默认名为 `.goxml_state.json`，写入项目运行目录，采用临时文件加原子替换。最小结构为：

```json
{
  "schemaVersion": 1,
  "appVersion": "...",
  "sourceRevision": "...",
  "createdAt": "...",
  "payload": {}
}
```

- `schemaVersion` 不兼容时丢弃整个 payload，并记录 `HYDRATION-VERSION`。
- JSON 损坏、文件过期、页面不存在或字段类型不匹配时只丢弃受影响状态，不阻塞新进程启动。
- 状态只包含显式声明可恢复的 ViewModel 和控件状态，不保存指针、Gio 操作对象、平台句柄或 Goroutine。
- 恢复必须在页面挂载和控件状态创建之后、首次稳定布局之前完成。
- 状态恢复失败不得覆盖新进程刚建立的默认状态。

## 7. 重启时序

1. Watch 收集并合并文件事件。
2. 执行生成、格式化、解析和构建检查。
3. 构建失败：保留旧进程和旧生成文件，报告诊断。
4. 构建成功：请求旧进程优雅退出并等待超时。
5. 超时后按平台规则清理整个进程树；Windows 必须处理残留句柄。
6. 启动新进程，建立控制通道并发送 `restore`。
7. 收到 `ready` 后将新进程设为当前进程，清理过期状态文件。
8. 任一步骤失败：记录失败原因；如果旧进程仍可用则恢复其运行状态。

## 8. Preview 行为

`goxml preview <file.gxml>` 使用同一 Parser、Analyzer 和主题契约，但输出为只读静态预览：

- 不启动目标应用的 ViewModel 生命周期；
- 不执行平台弹窗、剪贴板、托盘或菜单调用；
- 不写入项目生成文件和 Manifest；
- 诊断必须显示文件、行、列、错误码和消息；
- 退出时关闭文件监听、控制通道和临时资源。

## 9. 失败与资源策略

- 构建失败：旧应用继续运行，Watch 显示最新错误。
- 新应用启动失败：保留失败日志；旧应用若仍存活则继续提供服务。
- 状态恢复失败：以默认状态启动，不重复重试损坏状态。
- Watch 退出：先发送 `shutdown`，再按超时和平台规则清理进程树。
- 用户主动停止：不生成新的状态文件，不删除用户源码和非 Manifest 文件。

## 10. 验收要求

必须通过 AC-005-01 至 AC-005-03，以及以下专项验证：

- 100ms 内连续文件事件只触发一次构建；
- 构建失败不覆盖旧生成文件且旧进程保持可用；
- Windows 多次重启无残留子进程和文件句柄；
- 状态版本不兼容、JSON 损坏和页面卸载都能安全降级；
- Watch、应用和 Preview 退出后无监听器、临时文件和 Goroutine 泄漏。

## 11. 版本演进边界

改变控制协议、状态文件路径或格式、重启时序、防抖窗口、进程清理策略和 Preview 隔离边界，必须新增 ADR 或更新本 ADR，并同步验收用例和测试报告格式。
