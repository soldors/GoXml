## 1. 现状：在 `0e4b693` 上实测（相对合并稿的行号更新已就地标注）

### 1.1 静态颜色背景已经真的绘制（B2-P §1.6 已过期）

`internal/compiler/codegen/decoration.go:45-77` 的 `leafDecorationExpr` 为叶子节点
（Text/Button/Input）叠加静态 Background：`op.Record` 包住 Padding 外框 →
`clip.Rect.Push` → `paint.Fill(gtx.Ops, color.NRGBA{...})` → `call.Add`。
`background_alpha_review_test.go` / `background_candB_test.go` /
`background_candB_interact_test.go` / `background_input_review_test.go` 覆盖
alpha、事件不被吞、输入事件三类。`decoration.go` 是已提交文件。
**`#RRGGBB` 静态色不需要本 ADR 再接线。**

### 1.2 仍然断开的，只剩一条分支

`decoration.go:50` 的守卫 `if bg == nil || bg.IsThemeRef` —— `Background`
为主题引用时只加 Padding、不画背景，**不报错、不警告**。且全仓 codegen 测试
`IsThemeRef` 0 命中：**「主题引用被静默丢弃」这一当前行为没有被任何测试固定**。

### 1.3 Analyzer 契约的推理链前提

`Analyzer输入输出契约.md:893`：

> 主题引用是静态的：`$Theme.Primary` 在编译期解析为具体颜色，不是运行时绑定。
> 因此绑定到 `color` 属性的值只可能是具体颜色，不需要 `IsThemeRef` 那种表示。

这是**推理链前提**（静态 → 绑定值只能是具体色 → 绑定不需要 IsThemeRef）。
若改运行时解析，前提被推翻，结论是否仍成立须重新给理由，不能只改前半句。

### 1.4 主题切换链路：换了主题，Palette 不会跟着换

`pkg/runtime/app/app.go:519` `swapPending` 只做 `a.th.Shaper = next.Shaper`
（合并稿时为 :497，行号已更新）；`pkg/runtime/` 非测试源码 `.Palette =` 赋值 0 处。
**只做 codegen 不做 Palette 刷新，交付的是「代码正确但切换无效」。**

### 1.5 `Accent` 不是主题字段（B1 C.4 前提已判非）

`GXML语言规范.md` 中 `$Theme.` 的全部出现：`$Theme.Field`（:650 语法占位、
:653 规则说明）；`$Theme.Primary`（:736、:888、:929）**全部是 `<Def>` 的
Props 用法**。`Accent` 出现 6 处（:736、:739、:888、:890、:929、:947）**全部
是组件属性名**，无任何 `$Theme.Accent`。首版字段集候选据此收窄：**只有
`Primary`**（`Bg`/`Fg` 是否公开是新的开放项，见 Q-2）。

- `Text.Color`：`codegen.go` 非测试源码 `.Color` 0 处，Text 只读 `Value`
  ——`Text.Color` 属独立任务，不进本 ADR。

## 3. 合并方案判断

两份原稿与 B2-A 结论一致：**推荐方案 B（运行时解析）**——与输出契约「主题逐帧
传入」、Gio `Palette` 可变惯例单轨；字段错误仍在编译期暴露；通知机制零新增。

在当前基线上该结论**更强也更窄**：

- 更强：静态色已跑通（§1.1），方案 A 会造成同一页面两种语义——静态背景按常量
  烘焙、material 控件按 `Palette` 运行时取；这是代码里已存在的分界线。
- 更窄：要改的只有 `decoration.go:50` 那条 `IsThemeRef` 分支 + 未知字段校验 +
  `swapPending` 的 Palette 刷新，不涉及静态色路径、`Text.Color`、IR。

**「选方案 B」不等于「能交付」**：§1.4 的 Palette 不刷新会让方案 B 表现为
「改了主题没反应」。本稿主张把 Palette 刷新从乙的 B4 阶段**前置**为方案 B 的
组成部分，不允许拆成「先交付后补」。
