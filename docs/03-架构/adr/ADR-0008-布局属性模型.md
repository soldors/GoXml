# ADR-0008：布局属性模型——对齐、分布、间距与 Grid

- 状态：已接受
- 决策日期：2026-10-18
- 关联需求：REQ-001、REQ-002
- 关联文档：[GXML语言规范](../GXML语言规范.md)、[性能预算与优化策略](../性能预算与优化策略.md)、[代码生成输出契约](../代码生成输出契约.md)
- 取代：无（新增能力，但含一处属性重命名，见 §4）

## 1. 背景

GXML v1 冻结时只有 4 个布局标签（`Column`/`Row`/`Spacer`/`Expanded`）和 3 个通用属性（`Padding`/`Spacing`/`Background`），没有暴露交叉轴对齐、主轴分布与显式尺寸。

Gio 的 `layout.Flex` 实际上**已提供**这些能力（`Alignment`、`Spacing`、`Gap`、`Flexed` 权重、`Constraints.Exact`），缺口纯粹在语法映射层，不需要发明任何布局算法。

### 1.1 先行验证的结论

在决策前已完成四项实测（i7-12700H / Go 1.26.1 / Gio v0.10.3）：

| 对照 | 结果 |
|---|---|
| `Gap` 用原生 `Flex.Gap` vs 逐项 `Inset` | 分配完全相同（3,153 B / 17 allocs），性能无差异 |
| `Auto` 尺寸每帧两遍测量 vs 缓存一次 | 2,035 vs 1,346 ns/op；**两者都有分配（14 / 11 allocs），均无法达成 `allocs/op == 0`** |
| Grid 嵌套 Cell vs 固定宽度 Flex | 分配完全相同（11,219 B / 23 allocs），性能无差异 |
| `Baseline` 作用于 `<Column>` | 源码确认**仅 `Axis == Horizontal` 生效**，纵向静默无效 |

**因此性能不构成这四组取舍的依据**，决策依据转为开发舒适度、代码量、错误可发现性与长期成本。

## 2. 决策

### 2.1 新增 6 个属性

| 属性 | 取值 | 适用标签 | Gio 映射 |
|---|---|---|---|
| `Align` | `Start` / `Center` / `End` / `Baseline` | `Row` / `Column` | `Flex.Alignment`（Center→Middle） |
| `Justify` | `Start` / `Center` / `End` / `SpaceBetween` / `SpaceAround` / `SpaceEvenly` | `Column`/`Row` | `Flex.Spacing`（见 §2.4 映射表） |
| `Gap` | 非负 dp | `Column`/`Row`/`Grid` | `Flex.Gap` |
| `Width` | 缺省（自然）/ `Fill` / `<dp>` | 任意元素 | 按轴向决定：主轴 `Flexed`，交叉轴填充约束；`<dp>` → `Constraints.Exact` |
| `Height` | 同上 | 任意元素 | 同上 |
| `Columns` | `数字` / `*` / `N*`，空格分隔 | 仅 `Grid` | `Rigid+Exact` / `Flexed(N)` |

### 2.2 不引入 `Auto` 取值

`Width`/`Height` **缺省即为内容自然尺寸**，不设 `Auto` 这个取值。

理由：

1. Gio 在宽松约束下本来返回内容自然尺寸，`Auto` 是多余概念。
2. 引入 `Auto` 会诱发"容器按内容撑开"的测量需求，实测每次测量产生额外分配，无法满足 `INV-PERF-2`（稳定帧 `allocs/op == 0`）。
3. 三个取值（缺省/`Fill`/`<dp>`）已覆盖布局需求；`Measure` 语义留待 v2，且须显式 opt-in。

### 2.2.1 `Fill` 是语言层语义，不是 `Flexed(1)` 的别名

早期草案把 `Fill` 直接定义为「生成 `Flexed(1)`」。这是错的：`Flexed` 只作用于**主轴**，而 `Width`/`Height` 相对父容器的轴向是不固定的。

| 父容器 | 方向 | 相对父容器的角色 | 正确行为 |
|---|---|---|---|
| `Row` | `Width` | 主轴 | 参与主轴弹性分配 |
| `Row` | `Height` | 交叉轴 | 填充交叉轴可用高度 |
| `Column` | `Height` | 主轴 | 参与主轴弹性分配 |
| `Column` | `Width` | 交叉轴 | 填充交叉轴可用宽度 |

因此在 `Column` 内写 `Width="Fill"`，用 `Flexed(1)` 是**无效的**（`Flexed` 影响纵向），必须改为填充交叉轴约束。

**决策**：`Fill` 在规范中只定义语义（「占满父容器在对应方向上的可用空间」），具体映射由 Codegen 按轴向决定。这样规范不承诺某个具体的 Gio 调用，避免把底层库的偶然行为固化成语言契约。

**边界行为**（规范 §3.1.5 已冻结）：

- 无界约束下的 `Fill` → 退化为内容自然尺寸，不报错。
- 固定尺寸超出父容器 → 不裁剪、不报错，允许溢出。
- 多个 `Fill` 兄弟 → 均分剩余空间；剩余为负时按 0 处理。

### 2.3 轴向感知的默认对齐（唯一不可逆决定）

| 标签 | 默认 `Align` | 依据 |
|---|---|---|
| `<Row>` | **`Center`** | 一行元素类比一行文字，垂直居中是最自然状态（同 Flutter `Row` 默认） |
| `<Column>` | **`Start`** | 一列内容类比一页文档，左对齐是最自然状态（同 Compose `Column` 默认） |
| `<Grid>` | `Start` | 单元格内默认左对齐；列宽由 `Columns` 决定 |

**为何 GXML 可以做轴向感知默认值**：`<Row>` 与 `<Column>` 是两个独立标签，而非同一组件的参数，因此按标签给不同默认值不会显得"魔法"。Flutter 因 `Flex` 单组件无法区分；Compose 区分了（Row 默认 Top、Column 默认 Start），但都不是最常见的视觉期望。

**代价**：与 Gio 零值（`Start`）不一致，Codegen 必须显式写出 `<Row>` 的默认 `Middle`。这是生成代码的字符成本，**无运行时成本**。

**v1 不提供子项级覆盖（无 `AlignSelf`）**：需要时用嵌套 `<Row>`/`<Column>` 表达，理由见 §2.6.1。

### 2.4 `Justify` 到 `Flex.Spacing` 的精确映射

Gio 的 `Spacing` 枚举语义与名称不对称，必须逐项映射（源码已核实）：

| GXML `Justify` | Gio `Spacing` | 语义 |
|---|---|---|
| `Start`（默认） | `SpaceEnd` | 剩余空间全部留在末尾 |
| `Center` | `SpaceSides` | 剩余空间平分到首尾 |
| `End` | `SpaceStart` | 剩余空间全部留在开头 |
| `SpaceBetween` | `SpaceBetween` | 子项间均分，首尾不留 |
| `SpaceAround` | `SpaceAround` | 子项间均分，首尾各留一半 |
| `SpaceEvenly` | `SpaceEvenly` | 含首尾在内完全均分 |

> ⚠️ 实现注意：`Start` 对应的是 `SpaceEnd`，`End` 对应 `SpaceStart`，命名方向相反。Codegen 必须有此映射表，不可直接同名字段赋值。

### 2.5 `<Grid>` 采用容器声明列 + 行优先自动流，无坐标属性

```xml
<Grid Columns="72 * 96" Gap="8">
  <Text Value="姓名"/> <Input Value="{User.Name}"/> <Button Text="保存"/>
</Grid>
```

- 列宽在容器上声明**一次**，所有行自动对齐——这是 Grid 相对 `<Row>` 的**唯一不可替代价值**（用 `<Row>` 拼表格需每行重复写宽度）。
- 子项按行优先顺序自动填充，**不引入 `Grid.Column` / `Grid.Row` 坐标属性**，避免与 `<Row>`/`<Column>` 标签名冲突。
- 跨行跨列（`ColumnSpan`/`RowSpan`）**不属于 v1**：一旦需要跨度就必须引入坐标，成本陡增且与行优先流冲突。
- `Columns` **不含 `Auto`**，理由同 §2.2。

`<Grid>` 是**语言内置标签**而非 `//goxml:component` 组件：组件机制的 `slot` 只能接收整棵子树，无法按单元格逐个布局。

本节只定「方向」；补位规则、列宽计算、Gap 轴向、取整与非保证项见 §2.7。

### 2.6 `Baseline`：收紧适用范围，不做零值兜底

`Baseline` 在 Gio 层有两个固有约束：

1. 仅 `Axis == Horizontal` 生效，纵向静默无效；
2. 子项返回 `Baseline == 0` 时，表示基线落在元素**底边**（Gio 定义为「从底边到基线的距离」）。

**v1 的处理是收紧范围 + 明确契约，而不是编译器兜底：**

| 情况 | 处理 | 实现位置 |
|---|---|---|
| `<Row Align="Baseline">` | ✅ 允许 | — |
| `<Column Align="Baseline">` | 编译错误 `GXML-ATTR-003` | Analyzer |
| `<Grid Align="Baseline">` | 编译错误 `GXML-ATTR-003`（v1 不支持） | Analyzer |
| 子项 `Baseline == 0` | **视为合法的「基线在底边」，不做任何改写** | Codegen 不生成兜底代码 |

**为什么放弃原先的零值兜底方案**：

早期草案打算让 Codegen 生成 `if d.Baseline == 0 { d.Baseline = d.Size.Y }`，把零基线当作「未提供」并补成底部基线。这个方案是错的：

- Gio 的 `Dimensions` 没有额外标志位区分「未提供基线」与「基线恰好在底边」。
- 一旦兜底，**真正想表达「基线在底边」的控件会被错误改写**，而且这种错误在视觉上比原始问题更隐蔽。
- 兜底让「提供正确基线」的责任从控件实现方转嫁给了编译器，掩盖而非解决契约缺失。

**正确做法**：把「参与 `Baseline` 对齐的子项必须返回有意义的基线」写进控件契约，内置文本控件已正确返回；自绘控件若需参与基线对齐，由实现方负责。

### 2.6.1 不提供 `AlignSelf`（子项级对齐）

v1 **只提供容器级 `Align`，不提供 `AlignSelf`**。

原因是一条实现约束：Gio 的 `layout.Flex` 只有容器级 `Alignment`，`FlexChild` 结构体只有 `flex`/`weight`/`widget` 三个字段，**没有子项级对齐能力**。

实现 `AlignSelf` 只能给每个子项额外包一层：

```go
gtx.Constraints = layout.Exact(image.Pt(width, gtx.Constraints.Max.Y))
layout.Stack{Alignment: dir}.Layout(gtx, ...)  // 撑满交叉轴 + 定位
```

代价是：

| 代价 | 说明 |
|---|---|
| 额外嵌套层 | 子项从 Flex 的直接子项变成 Stack 的孙节点 |
| 破坏静态子树固化 | 包装层成为 `CallOp` 固化的判定边界，可能让本该整体固化的子树退化为每帧重算 |
| 每帧闭包分配 | 实测每帧新建闭包约 11× 慢（28,000 → 2,550 ns/op），与 `INV-PERF-1/2` 冲突 |

**而 `AlignSelf` 的全部价值是「省掉一层嵌套」——实现它却要多一层包装。用嵌套换嵌套，净收益接近零。**

因此 v1 选择不提供。需要子项独立对齐时用嵌套表达：

```xml
<Row Gap="8">
  <Row Justify="End" Width="72"><Text Value="标签"/></Row>
  <Text Value="值" Width="Fill"/>
</Row>
```

该决定不排斥未来重新引入：若将来 Gio 支持子项级对齐，或静态子树固化能安全穿过包装层，可另行提案。


### 2.7 Grid 布局模型

`<Grid>` 是**语言内置标签**而非 `//goxml:component` 组件：组件机制的 `<Slot/>` 只能接收整棵子树，无法按单元格逐个布局。

#### 实现结构

`<Grid>` 编译为「外层纵向 Flex + 每行一个横向 Flex」：

```text
Column{ Gap: rowGap }                 ← 行间距
├── Row{ Gap: colGap, Alignment }     ← 列间距 + 行内垂直对齐
│   ├── Rigid(Exact(72))   → 单元格
│   ├── Flexed(1)          → 单元格
│   └── Rigid(Exact(96))   → 单元格
└── Row{ ... }
```

不引入任何新的布局原语，全部由 Gio 已有的 `Flex`/`Rigid`/`Flexed` 组合而成。

#### 实测证据（Gio v0.10.3）

以下数据由直接调用 `layout.Flex` 测得，是冻结规范的依据：

| 场景 | 实测输出 | 结论 |
|---|---|---|
| 600px，`2* 1* 3*` | `200 / 100 / 300` | 权重按比例精确分配 |
| 600px，`72 * 96`，Gap=10 | 固定 72、弹性 **412**、固定 96 | 弹性空间 = 600−72−96−10×2 |
| 600px，3 列，5 个单元格（最后一行缺 1 列） | 第 2 行弹性列 **500**（应为 400） | **不补位则列错位** |
| 同上，补位后 | 第 2 行弹性列 **400** | 补位使列宽一致 |
| 100px，3 等权列 | `33 / 34 / 33` | 结转式取整，多出的像素不总在末列 |
| 116px，5 等权列 | `23 / 23 / 23 / 23 / 23`，合计 **115** | 可能丢失 1px |
| 单元格 200，子项只返回 100 | 下一格实得 **300** | 子项变窄会破坏整行列宽 |
| `Flexed` 子项收到的约束 | `Min == Max == 分配宽度` | 单元格宽度先于子项布局确定 |
| 固定列 200+200，容器 300 | 两列仍各 200 | 固定列不被压缩，允许溢出 |
| 固定列吃满后，弹性列 | `Min = Max = 0` | 弹性列归零，不产生负值 |

#### 决策与理由

| 决策 | 理由 | 被拒方案 |
|---|---|---|
| **最后一行补列占位** | 不补位时缺失列的宽度被弹性列吸收，同一列在不同行宽度不同；且 `Gap` 计数少一个，进一步放大偏差。列对齐是 `<Grid>` 唯一不可替代的价值。 | 「不补位，允许最后一行自然铺开」——实测列错位，见上表 |
| **补位只做布局占位** | 补位若变成 IR 节点，会污染状态 Diff、事件绑定与控件实例化，且用户能在调试器里看到不存在的节点。 | 「把虚构节点写回 IR 再统一处理」——语义边界被破坏 |
| **子项 `Width` 直接报错** | 单元格宽度先于子项确定；子项返回更小尺寸会让后续单元格分到额外空间，整行错位。这不是「优先级」问题，是布局被破坏。 | 「列定义优先，忽略子项 Width」——静默忽略违反「非法必须明确失败」；「允许子项覆盖」——实测导致错位 |
| **一个 `Gap` 同时控制两个轴向** | 属性数量优先；实测 `Flex.Gap` 在 `Horizontal` 与 `Vertical` 上都生效，一个值可同时喂给两个 Flex。 | 「`ColumnGap` + `RowGap` 两个属性」——多数场景两个值相同，属重复劳动 |
| **`Align` 映射到每行 `Flex.Alignment`** | 移除 `AlignSelf` 后只剩容器级对齐；映射到每行 `Alignment` 恰好表达「单元格在行内的垂直对齐」，零额外层级。 | 「`Align` 控制整个 Grid 的内容分布」——与 Row 语义不一致，且需要额外的分布计算 |
| **取整完全交给 Gio，不做补偿** | 补偿会让规范描述与真实渲染不一致；Gio 的行为可预测（已实测并写入规范）。 | 「自行计算像素并全部用 `Rigid(Exact)`」——需运行时逐帧计算列宽，破坏零分配目标 |

#### 非保证项

弹性分配**不保证用满可用宽度**：116px 五等分实测合计 115。规范只承诺「不超过可用宽度」。v1 不做补偿，理由见上表最后一行。

#### 输入约束

| 用法 | 结果 |
|---|---|
| 无 `Columns` | `GXML-ATTR-003` |
| 无子节点 | `GXML-ATTR-003` |
| `Columns=""` / `0*` / 负数权重 | `GXML-ATTR-003` |
| 直接子项设置 `Width` | `GXML-ATTR-003` |
| `Align="Baseline"` | `GXML-ATTR-003` |


### 2.8 尺寸组合与约束传递

`Width` 与 `Height` 各自独立解析，规则由 §3.1.7 定义。本节只记录三条**需要选项依据**的决定。

#### 2.8.1 `<Page>` 等价于没有 `Gap`/`Padding` 的 `<Column>`

规范原本没有定义 `<Page>` 如何排列多个子节点。

| 方案 | 否决理由 |
|---|---|
| 用 `Stack` 叠放 | 多个子节点会静默互相覆盖，不报错——这是最难排查的一类问题 |
| 强制只允许一个子节点 | 破坏既有文档结构（`<Page>` 已被允许包含多个子节点），且与 `<Column>` 能力重复 |
| **按垂直排列（采用）** | 符合「一页文档」的直觉；与 `<Column>` 的默认交叉轴对齐（`Start`）一致；需要间距时显式写一层 `<Column>` |

因此 `<Page>` 接受 `Route`/`ViewModel`，不接受布局属性，其子节点按垂直方向依次排列。

#### 2.8.2 无界判定：规范只定义语义，阈值属适配策略

**规范层面**（§3.1.7）只要求两件事：

1. 交叉轴 `Fill` 在无界时必须退化为自然尺寸；
2. 无界的识别由布局语义层统一负责，Parser 与 Codegen 不得各自判断。

规范**不规定具体阈值**，只要求识别策略满足两条性质：真实设备的尺寸永不被误判；明显的无穷标记必然触发。

**实现层面**：Gio 适配当前采用 `Max >= 1 << 20`（1,048,576 个布局单位）。

这条阈值是**可调整的实现参数**，不是永久规范常量。支持的设备、尺寸单位或后端约定变化时，适配层可以改，只需满足上述两条性质。

#### 为什么是「适配策略」而不是「规范常量」

一个未经验证的数值不应该凝固成语言承诺。支持它是当前最合理策略的依据：

| 依据 | 数据 |
|---|---|
| 现实设备远低于阈值 | 8K 宽 7680，余量约 136 倍 |
| 明显的无穷必然触发 | `math.MaxInt` 远大于阈值 |
| Gio 不产生无界约束 | 窗口始终有界；`widget.List` 用 `Constraints.Max` 作视口 |

最后一条尤其重要：**无界在 Gio 中不是常见路径**，而是自定义容器或测试放开某方向时的情形。因此这条规则是**防御性回退**，其阈值精度要求不高——即使偏差几个数量级，也不影响正常布局。

#### 已知局限

现有数据只能证明「不应把 `math.MaxInt` 当作正常布局上限」，**不足以证明 `1 << 20` 对所有目标平台都合适**。若将来引入高 DPI 缩放下的超大虚拟画布、或改用更细的尺寸单位，该阈值需要重新评估。届时改动点只有一处：`sizelayout.UnboundedThreshold` 及其边界测试。

#### 被拒方案

| 方案 | 否决理由 |
|---|---|
| 判断 `Max == math.MaxInt` | 精确匹配 Gio 内部约定；Gio 若改用有限大值表示无界即失效。且把实现细节写进规范 |
| 不检测，直接填满 | 产生上亿像素布局，无法靠 clamping 收场 |
| 无界时禁止 `Fill` 并报错 | 同一份 `.gxml` 在可滚动与不可滚动容器中的合法性会不同，无法在编译期判定 |
| 把 `1 << 20` 写进语言规范 | 一个未经验证的数值变成永久承诺，后续调整会被视为破坏性变更 |


#### 2.8.3 主轴 `Fill` 在无界时不退化

无界约束通常意味着容器在该方向可滚动，主轴弹性分配仍然有意义（剩余空间由内容撑开，`Fill` 参与比例分配）。只有**交叉轴** `Fill` 在无界时缺乏基准，需要退化为自然尺寸。

这条区分很重要：若统一按「无界即退化」处理，可滚动列表里的主轴 `Fill` 会全部失效。

#### 2.8.4 决策规则的可执行形式

规范表格容易在实现时被各自解释，因此把决策规则实现为纯函数
`internal/compiler/sizelayout`（`Resolve` / `ResolveMainCross`），
输入「尺寸规格 + 轴向 + 可用上限」，输出「自然 / 弹性 / 填充交叉轴 / 精确」。

它与 `grid` 包的区别：

| 包 | 定位 |
|---|---|
| `grid` | 规范的 **oracle**，只用于测试与验证，不进入生产路径 |
| `sizelayout` | 规范的**可执行决策表**，Codegen 应直接调用，避免各处自行解释 |


## 3. 替代方案与否决理由

| 方案 | 否决理由 |
|---|---|
| 维持 v1 现状（仅 `Spacer` 硬凑间距） | 六行表单需 18 个 `<Spacer/>` 标签，改间距要动 18 处；用占位标签模拟布局属性是重复劳动的真正来源 |
| 引入 `Auto` 尺寸 | Gio 立即模式无两遍布局协议；实测每帧测量多 4 allocs，破坏 `INV-PERF-2` |
| `<Grid>` 放组件层 | `slot` 无法按单元格拆分；且无法与 `<For>` 自然嵌套 |
| `<Grid>` 用坐标属性 | `Grid.Column` 需附加属性语法（改 Parser）；普通属性 `Column="1"` 与 `<Column>` 标签撞名 |
| `<Grid>` 用 `<GridRow>`/`<Cell>` 嵌套 | 结构字符最多（3×3 网格约 144 字符），且跨行列宽无法共享 |
| `Baseline` 不暴露 | 文字混排是通用需求；限定在 `<Row>` 内后风险可控 |
| `Justify` 不提供 | 映射 Gio 已有 6 个枚举值，零运行时成本；缺失会导致"按钮组靠右"必须用 `<Spacer/>` |

## 4. 一处破坏性变更：`Spacing` → `Gap` 重命名

v1 规范中已存在属性 `Spacing`，含义为「子节点之间的 dp 间距」。该语义与本次新增的 `Gap` **完全相同**，但名称与 Gio 的 `Spacing`（空间分配）冲突——若保留，GXML 的 `Spacing`（间距）与 `Justify`（映射到 Gio `Spacing`）将长期混淆。

**决策：将 `Spacing` 重命名为 `Gap`**，与 CSS、Tailwind、Flutter 3.27+、Compose `spacedBy` 的生态惯例一致。

**执行时机说明**：该重命名是破坏性的，但当前仓库 **0 行解析器实现、0 个 `.gxml` 用户文件**，此刻变更成本为零。若推迟到实现之后，将造成真实迁移负担。

## 6. 验收要求

1. `Align` 四个取值均正确映射，`Center` 映射到 `Flex.Alignment = Middle`。
2. `Justify` 六个取值按 §2.4 映射表正确，特别验证 `Start→SpaceEnd`、`End→SpaceStart` 方向相反。
3. `<Row>` 未写 `Align` 时默认居中，`<Column>` 未写时默认左对齐。
4. `Width="Fill"` 在 `Row`（主轴）内参与主轴弹性分配；在 `Column`（交叉轴）内填充交叉轴宽度。**不得一律生成 `Flexed(1)`**。`Width="80"` 生成 `Constraints.Exact`，缺省不生成尺寸约束。
5. `<Grid Columns="72 * 96">` 在三行列宽一致，且与手写 `Flex` 输出性能一致。
6. `<Column Align="Baseline">` 与 `<Grid Align="Baseline">` 均在 Analyzer 阶段报错。
7. 子项 `Baseline == 0` 时 **Codegen 不生成任何兜底代码**（AST 断言无 `d.Baseline = ...` 赋值）。
8. `Gap` 使用原生 `Flex.Gap`，不生成逐项 `Inset`。
9. 未使用任何新属性的既有 `.gxml` Golden 输出保持不变（除 `Spacing→Gap` 重命名）。

## 7. 版本演进边界

改变以下任一项必须新增 ADR：

- 默认对齐值（**唯一难以回退的决定**）；
- `Width`/`Height` 增加取值，或引入测量型语义；
- `<Grid>` 引入坐标属性或跨行跨列；
- `Columns` 语法；
- 属性重命名。
