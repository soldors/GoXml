## 1. 背景

`$Theme.Field` 自 v1 起就是合法语法（`GXML语言规范.md:634`、`:637`），Parser 与 Expander 已把它解析为 `contracts.NRGBAColor{IsThemeRef: true, ThemeField: ...}`（`parser/attrs.go:259-265`、`expander/color.go:47-52`），并写入 `NodeIR.Background`（`ir_schema.go:717`）。

但**下游完全未接通**：

| 层 | 证据 | 现状 |
|---|---|---|
| Analyzer | `internal/compiler/analyzer/*.go` 检索 `IsThemeRef`/`ThemeField`/`Background` → 0 处 | 不校验、不消费 |
| Codegen | `internal/compiler/codegen/*.go` 检索 `Background` → 0 处 | 不消费 |

即：写 `Background="$Theme.Primary"` 会被**静默忽略**，生成代码完全不设置背景色——既不报错，也不产生无效代码。

同时存在语义冲突：`Analyzer输入输出契约.md:891` 规定「`$Theme.Primary` 在**编译期解析为具体颜色**，不是运行时绑定」。

## 2. 待决问题

1. 主题引用应在**编译期**钉成常量，还是**运行时**从当前主题读取？
2. 若运行时读取，`Primary` 等字段的**正式定义**是什么？
3. `Analyzer输入输出契约.md:891-892` 如何处置？
4. 未知主题字段在哪一阶段报错？

## 3. 决策（提案）

### 3.1 采用运行时解析（方案 B）

`$Theme.X` 由 Codegen 生成为对 `th` 参数的**字段读取**，`th` 是 `Layout(gtx, th *material.Theme)` 的既有参数。

**理由**：
1. 用户需求是「主题变化后 UI 更新」；编译期固化在定义上无法满足（`TRACE §3`）；
2. IR **无需扩展**——`NRGBAColor` 的 `IsThemeRef` 二态已能无歧义区分常量与引用（`ir_schema.go:130-132`）；
3. 生成代码保持只依赖 Gio `*material.Theme`，符合 `代码生成输出契约.md:214-227` 与 ADR-0012 的边界。

### 3.2 字段清单（**待负责人批准，本节不构成冻结**）

首版**只接受规范中已出现的主题字段名**。当前规范中主题引用的实际用词只有一个：`$Theme.Primary`（`GXML语言规范.md:720`、`:872`、`:913`）。

| GXML 字段 | 类型 | 语义 | 运行时来源 | 状态 |
|---|---|---|---|---|
| `Primary` | `color.NRGBA` | 主强调色（组件强调/激活态） | 待定（见 §3.3） | **提案** |

**明确不纳入**（无规范依据，不得擅自新增）：
- `Foreground`（规范 0 处）
- `AccentForeground`（规范 0 处）
- `Accent` —— **不是主题字段**，而是 `<Def>` 的 `Props` 名（`GXML语言规范.md:720`、`:872`、`:913`、`:931`，6 处全为组件属性用法）

### 3.3 `Primary` 的运行时来源（**未决，需负责人裁决**）

这是本提案**唯一无法由代码事实决定的点**。Gio `material.Palette` 只有 4 个字段（外部事实：Gio v0.10.3 `widget/material/theme.go:21/24/28/32`：`Bg`/`Fg`/`ContrastBg`/`ContrastFg`），**没有 `Primary`**。

候选：

| 选项 | 做法 | 代价 |
|---|---|---|
| **F1** | `Primary` → `th.Palette.ContrastBg` | 语义近似（Gio 注释：ContrastBg 用于 "active"/强调态），但把语言语义绑到工具包实现细节 |
| **F2** | 在 `pkg/runtime/theme` 增加 GXML 自有调色板（映射表） | 需改运行时包，超出 `TASK-STYLE-001-1` 授权 |
| **F3** | 修订规范样例，改用 Gio 既有名（如 `$Theme.ContrastBg`） | 需改冻结的 v1 规范文本 |

**本 ADR 不替负责人选择。**

### 3.4 契约修改（**需批准**）

若采纳 3.1，则 `Analyzer输入输出契约.md:891-892` 必须修订。

**评审已确认的事实**：该段位于 `§11.5 「color 与 insets：精确类型身份」`（`:877`），全节讨论**绑定类型兼容矩阵**（`:883-886`）。原句主语是「**绑定**到 `color` 属性的值」——即在说「`{Path}` 绑定不可能产生主题引用」。

但原句同时以肯定语气断言「`$Theme.Primary` 在编译期解析为具体颜色」，这是**独立于绑定的完整语义陈述**。

因此本提案**不宣称这是"澄清"**：是否属于澄清、还是修改 v1 语义，**由负责人定性**。若认定为后者，需走 v1 语义变更流程。

## 4. 后果

### 4.1 正面

- 主题引用从「静默忽略」变为**真实生效**；
- 不新增 IR 字段，不引入反射/字符串运行期解析；
- 生成代码仍只依赖 `*material.Theme`。

### 4.2 负面 / 风险

| 风险 | 证据 | 说明 |
|---|---|---|
| **R1：运行时切换当前不生效** | `pkg/runtime/app/app.go:436` 的 `swapPending` 仅 `a.th.Shaper = next.Shaper`；全仓 `a.th.Palette` 赋值 **0 处** | 即使生成 `th.Palette.X`，主题替换后 Palette 仍是构造期值。**必须由 B4 补 Palette 刷新**，否则本 ADR 交付的是「代码正确但切换无效」 |
| **R2：与字体线冲突** | `app.go` 当前为未提交修改（字体 Agent 在制），`swapPending` 是字体线新增函数 | B4 要改**同一函数**，必须与字体 Agent 协调 |
| **R3：`Text.Color` 仍不可实现** | `codegen.go:578-603`（Text 生成全文）只读 `Value`，不读 `Color`；`GXML语言规范.md:709` 却把 `Color` 列为 Text 正式属性 | 本 ADR 只覆盖 `Background`；`Color` 需独立任务 |
| **R4：未知字段当前无校验** | `parser/attrs.go:261-264` 只校验标识符形态 | `$Theme.NotARealField` 会被静默接受 |

## 5. 替代方案（未采纳）

**方案 A：编译期解析**——把 `$Theme.X` 在生成期钉成常量色值。

- 需定义「用哪个主题解析」（编译期无窗口主题）；
- 生成后调色板变更**不会**反映到界面，与需求冲突；
- 与 `:891` 一致，但代价是功能不成立。
