## A1. Gio 录制/回放语义验证

### A1.1 验证方法

用 `gioui.org/gpu/headless` 做离屏渲染，通过**像素比对**判断回放是否真正生效。

为什么不用更简单的方法：

| 尝试 | 结果 |
|---|---|
| 读 `ops.Data` 字节数 | `ops.Ops.data` 未导出，包外无法访问 |
| `op.NewReader` 解码计数 | `NewReader` 不在 `op` 公开 API 中 |
| `call.Add()` 不 panic 即算成功 | **不成立**——空操作也能不 panic，无法区分 |

最终使用 `headless.NewWindow` + `Screenshot` + 像素差分。这是唯一能证明
「回放产生了正确绘制」的手段。

### A1.2 实测结论

| # | 结论 | 证据 |
|---|---|---|
| 1 | 录制过程**不改变**布局结果 | 直接布局与录制内布局均返回 `(100,50)` |
| 2 | 同一 `CallOp` 可**重复回放**，前提是源 `Ops` 未被 `Reset` | 连续两次 `call.Add` 像素完全一致 |
| 3 | **源 `Ops` 一旦 `Reset`，`CallOp` 立即失效（panic）** | `slice bounds out of range [9:0]` |
| 4 | `op.Defer` **不复制**数据，仍引用源 `Ops` | `Defer` 后 `Reset` 源 → 同样 panic |
| 5 | `Flex.Layout` 内部**确实**对每个 `Rigid` 子节点调用 `op.Record` | `flex.go` 中 `macro := op.Record(gtx.Ops)`；且其 `scratchSpace.call` 是**函数局部变量**，从不跨帧 |
| 6 | 同帧「录制+回放」与直接布局的像素**实质一致** | 7200 像素中非零像素数均为 229；仅 4 个字节的浮点差异 |

### A1.3 最关键的一条

**结论 3 推翻了「把 `CallOp` 存进结构体、跨帧回放」的直觉方案。**

根因在 `internal/ops/ops.go`：

```go
func Reset(o *Ops) {
    ...
    o.data = o.data[:0]     // 截断数据
    ...
}
```

而 `CallOp` 保存的是 `[start, end)` 区间：

```go
type CallOp struct {
    ops   *ops.Ops
    start ops.PC
    end   ops.PC
}
```

`Reset` 之后 `data` 被截断，`[start,end)` 指向已不存在的区间 → 回放越界。

**Gio 自身从不跨帧保存 `CallOp`**：`flex.go` 的 `scratchSpace` 是函数内局部变量，
每次 `Layout` 重新创建。这印证了该约束是设计性的，不是偶然。

### A1.4 A3 期间补充的两项实测

在把决策升格为契约时，又发现两个实现必然撞上的事实：

| # | 事实 | 证据 | 后果 |
|---|---|---|---|
| 7 | `CallOp.Add` **返回 void** | `func (c CallOp) Add(o *Ops)` 无返回值 | 缓存必须**同时保存 `layout.Dimensions`**，否则 `Layout` 无法返回 |
| 8 | 布局尺寸**强依赖约束** | Exact(200×100)→(200,100)；Exact(50×20)→(50,20) | `Constraints` 必须进 `renderKey` |
| 9 | DPI 显著影响渲染 | 同文本 DPI=1 非零像素 510，DPI=3 为 1653 | `Metric` 必须进 `renderKey` |

第 7 条是最容易漏的：直觉上「缓存绘制指令」就够了，但 `Add` 不返回尺寸，
而 `Layout` 的返回值是缓存的**另一个必要组成**。

## A2. 8 个待澄清问题的决策

### Q1：何时判定为静态子树

**结论**：严格引用 ADR-0006 §2.1 的 4 条标准，**不另立定义**。

```text
不含 {Binding}、事件绑定
不含 <If>、<For>
不含交互控件（Button / Input / 有状态自定义组件）
布局结果只依赖 renderContextKey 已纳入的上下文
```

代码中引用 ADR 编号，不复制文字——避免第二份定义漂移。

### Q2：首次录制在何时发生

**结论**：**首次 `Layout` 调用时惰性录制**，不在构造函数中。

理由：

- 构造函数不知道 `gtx`（约束、DPI），而布局结果依赖它；
- 首帧的 `gtx` 才是真实的渲染上下文。

实现形态：View 结构体持有一个 `recorded bool` + `op.CallOp` + 录制时的 key。

### Q3：缓存槽位存在哪

**结论**：存在**生成代码的 View 结构体字段**中，且必须配套一个**专用的持久 `op.Ops`**。

这是 A1 结论 3 的直接后果：

```go
type GoxmlDashboardView struct {
    // 持久源：录制内容存于此，永不 Reset
    cacheOps op.Ops
    // 回放句柄
    cacheCall op.CallOp
    // 是否已录制
    cached bool
    // 录制时的上下文指纹
    cachedKey renderKey
}
```

**关键**：`cacheOps` 必须与帧 `Ops` 分离。每帧的 `Ops` 由 Gio 提供并被 `Reset`，
而 `cacheOps` 由 View 自己持有、从不 `Reset`。

> ⚠️ 这一条是本文档最重要的设计决定。若把录制内容留在帧 `Ops` 里，
> 下一帧 `Reset` 后 `cacheCall` 立即失效（实测 panic）。

### Q4：何时回放、何时重录

| 时机 | 行为 |
|---|---|
| 首帧 | 录制 → 回放 |
| 后续帧，key 未变 | **只回放**：`cacheCall.Add(gtx.Ops)` |
| 后续帧，key 变化 | 清空 `cacheOps` → 重录 → 回放 |

### Q5：失效条件（`renderContextKey` 包含什么）

**结论**（保守起步，可后续放宽）：

| 输入 | 是否纳入 | 理由 |
|---|---|---|
| `gtx.Constraints` | ✅ | 布局结果直接依赖 |
| DPI / `gtx.Metric` | ✅ | 影响所有像素尺寸 |
| 主题指针 | ✅ | 影响字体与颜色 |
| 布局方向 / Locale | ✅ | 影响文本排布 |
| 时间、动画状态 | ❌ | 静态子树按定义不含 |

**判定原则：宁可多失效，不可少失效。** 少失效会导致画面不更新（功能缺陷），
多失效只是损失性能（可测量、可优化）。首次实现取保守集合。

### Q6：嵌套静态容器怎么办

**结论**：**只固化最外层静态子树，内部不再单独固化。**

理由（A1 结论 5）：

`layout.Flex.Layout` 内部**已经**对每个 `Rigid` 子节点调用 `op.Record`。
如果生成代码再为每个子节点额外录制一层，会形成「Flex 录一次 + 我们录一次」的
**重复录制**，性能反而更差。

因此规则是：**找到最大的静态子树边界，只在边界处录制一次。**
子树内部无论嵌套多少层容器，都不再生成额外缓存槽位。

> 这条待 A6 基准实测确认：需对比「只外层录制」与「不录制」的实际开销。

### Q7：静态与动态混合的边界

**结论**：**缓存边界必须切在动态节点之上，不能把动态节点包进缓存。**

```text
<Column>                          ← 含动态子节点，不固化
  <Column>  （纯静态）             ← 可固化为一个 CallOp
    <Text/> <Text/>
  </Column>
  <Text Value="{Name}"/>          ← 动态，每帧重算
</Column>
```

判定方法：自底向上标记每个节点「是否静态」，静态且父节点非静态的节点即为固化边界。

**禁止**：把父容器整体固化后再指望动态子节点更新——那会把本应每帧变化的内容
永久冻结。

### Q8：`op.Record` / `op.CallOp` 的实际语义

**结论**：见 A1 的 6 条实测结论。核心三条：

1. 录制不改变布局结果；
2. `CallOp` 可重复回放，但**有效期绑定源 `Ops` 的数据**；
3. 源 `Ops` `Reset` 后 `CallOp` 失效（panic），`Defer` 不能规避。

## A3. 待冻结的固化契约（草案）

```text
1. 静态子树判定：引用 ADR-0006，不另立定义。
2. 缓存所有权：View 结构体持有 cacheOps（持久，永不 Reset）+ cacheCall + key。
3. 录制时机：首次 Layout 惰性录制。
4. 回放：key 未变时只执行 cacheCall.Add(gtx.Ops)。
5. 失效：key 变化时清空 cacheOps 并重录；key 纳入 Constraints/Metric/主题/Locale。
6. 嵌套：只固化最外层静态边界，内部不重复录制。
7. 混合：缓存边界切在动态节点之上，禁止冻结动态内容。
```

## A4–A6 的验收前提

| 阶段 | 关键验收 |
|---|---|
| A4 单节点 | `<Text>` 固化后，第二帧**不重录**（计数断言），渲染像素与首帧一致 |
| A5 嵌套 | 多层静态树只产生**一个**缓存槽位；混合树中动态节点每帧更新 |
| A6 性能 | `allocs/op == 0`；且**不劣于**不缓存的基线（防重复录制导致退化） |

### 验收原则（承接任务卡 §4.1）

**不得**将以下任一条件单独视为完成：

- 生成代码中出现 `op.Record`；
- 生成代码中出现 `op.CallOp`；
- 某次基准恰好得到 `0 allocs/op`。

必须同时证明：缓存槽位存在且被正确使用、布局结果符合语义、失效后能正确更新、
性能满足要求。

## 附：A1 的复现方法

```go
// 1. 准备持久源 Ops 与帧 Ops
var src op.Ops          // 永不 Reset
var frame op.Ops        // 每帧 Reset

// 2. 录制
m := op.Record(&src)
material.Body1(th, "hello").Layout(gtxOnSrc)
call := m.Stop()

// 3. 每帧回放
call.Add(&frame)
win.Frame(&frame)
```

**错误做法**（会 panic）：对 `src` 调用 `Reset()` 之后再 `call.Add`。
