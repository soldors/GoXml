## 1. 背景与真实问题

语言层已有 `$Theme.Field` 语法且 v1 冻结（`GXML语言规范.md:630-637`：仅限颜色属性、非绑定；示例使用 `$Theme.Primary`），IR 表示已产出（`contracts/ir_schema.go:129-136` `NRGBAColor{IsThemeRef, ThemeField, R,G,B,A}`，由 `parser/attrs.go:257-265` 与 `expander/color.go:41-53` 构造）。但本轮全引用普查证实：**颜色渲染链在 Codegen 侧整体缺失**——`NodeIR.Background`（`ir_schema.go:717`）除 parser/expander 外零消费者，Codegen 无任何颜色绘制调用（`paint./color.NRGBA/op.ColorOp` 零命中），`Text` 组件虽在 Schema 声明了 `Color` Prop（`expander/schema.go:131`）却无任何颜色发射（Text 渲染为 `material.Body1(th, …)`，`codegen.go:589/603`）。同时存在**三方解析时机矛盾**：Analyzer 契约 :891 称"编译期解析为具体颜色"；`ThemeProvider.GetColor`（`runtime_api.go:46-48`，0 调用方）是运行时接口；代码生成输出契约 §4.3.1 与 Gio 惯例是"主题逐帧传入、Palette 可变"（`pkg/runtime/theme/theme.go:68-69`）。字段集从未被任何文档或代码枚举（`"Primary"` 在 compiler/contracts 生产代码零命中）。本 ADR 需要一次性裁决：**字段集、解析时机、颜色值来源、与既有契约的措辞对齐**。

## 3. 两种方案及优缺点

### 方案 A：编译期固化

`$Theme.Field` 在 Codegen 阶段解析为具体颜色常量写入生成代码；运行时不再查表。

- **颜色值唯一来源**：必须新增一份**构建期主题颜色表**（建议位置：`pkg/runtime/theme` 的导出常量表或独立配置文件，由负责人定义初值）。当前仓库不存在任何来源——这是方案 A 的前置成本。
- **字段定义**：字段集 = 颜色表条目，编译期封闭；新增字段 = 改表 + 重编译。
- **未知字段报错**：Analyzer 新增诊断（**需新诊断码，须先核对 `诊断码目录.md` 号段与三态规则**——本提案不分配编号）。
- **运行时切换**：**不影响**已烘焙颜色；主题切换 = 修改颜色表 + 重新编译。与双进程 Live Reload（改码即重建）兼容，但与"逐帧改 `Palette`"的运行时玩法互斥。
- **与 Analyzer 契约 :891 一致性**：完全一致，无需改字。
- **优点**：生成代码零运行时查表（合 ADR-0001 零抽象开销精神）；字段错误编译期暴露；无新运行时 API。
- **缺点**：① 与代码生成输出契约 §4.3.1"主题可逐帧变化"冲突，需修订表述；② 与 material 控件**双轨不一致**——`<Button>` 底色运行时取 `Palette.ContrastBg`，GXML 背景色却烘焙，同屏两种主题语义；③ 运行时换肤（改 `Palette`）失效；④ 需要新建颜色值来源并定义初值。

### 方案 B：运行时解析（含编译期字段校验）

`$Theme.Field` 在编译期**只校验字段合法性**，生成代码按字段在运行时解析颜色。

- **IR 表达**：不变（`NRGBAColor{IsThemeRef, ThemeField}` 已足够）。
- **Codegen 输出**：按裁决 D-3 二选一——(i) string key：生成 `theme.GetColor("Primary")`（`ThemeProvider` 接线）；(ii) 强类型：为每个字段生成具名访问（如 `theme.Primary()`），并**替换** `ThemeProvider`、同步 `ThemeField` 语义（runtime_api.go:43 的替换规则）。
- **运行时接口**：`pkg/runtime/theme` 新增解析函数，数据源 = `th.Palette`（+ 项目扩展表）；经 `pkg/runtime/theme` 装配以守住 docgate 门禁。
- **失败语义**：字段不存在 → **编译期诊断**（字段集封闭后运行时不存在"未知字段"）；运行时取色不失败（`Palette` 恒有值：`material.NewTheme` 默认 `Fg:#000000, Bg:#ffffff, ContrastBg:#3f51b5, ContrastFg:#ffffff`，gio 源码实测）。
- **主题切换刷新**：调用方在帧内改 `Palette`（或换注入主题）→ 既有 `Invalidate` 通知机制 → 下一帧生效——与状态更新契约 §2 的职责链完全一致，无需新机制。
- **Palette 与 Shaper 更新一致性**：两者同属 `*material.Theme`，更新都必须发生在帧内 UI 线程（Shaper 已有 IMPL-2 六步门禁先例）；本 ADR 要求 Palette 更新遵守同一线程约束（写进生成代码注释与文档）。
- **对冻结契约的影响**：:891 措辞需精确化（"编译期校验 + 运行时解析"）；§4.3.1/§4.3.2 完全一致；规范语法不变。
- **优点**：与 Gio 惯例、material 控件单轨（Button 与 GXML 背景色同源）、热切换体验、通知机制零新增。
- **缺点**：① 需修订 :891 措辞（受控契约变更，须负责人批准）；② 生成代码多一次查表（可在 ADR-0001 意义下论证为零抽象：直接字段访问）；③ 需要裁决 string key vs 强类型（D-3）。

### 混合方案（明确陈述，不模糊）

方案 B 的完备形态**本身就是混合**：编译期做字段集封闭与诊断，运行时做取值。方案 A 与 B 的本质区别只有一条——**颜色的运行时可变性是否存在**。本提案不提供第三种"部分烘焙"的折中（那会造成同屏双轨，见方案 A 缺点②）。

## 4. 推荐方案及依据

**推荐方案 B（运行时解析 + 编译期字段校验）**，依据：① 与代码生成输出契约 §4.3.1"主题逐帧传入"及 Gio"Palette 可变"惯例单轨一致（material 控件本就运行时取 `Palette`，方案 A 会造成同屏双主题语义）；② 与状态更新契约 §2 通知职责链零新增；③ 字段错误仍在编译期暴露（保留方案 A 的核心收益）；④ D-006"强类型 $Theme Struct"在运行时形态下依然成立（字段集封闭 + 强类型访问器）。**最终选择权在负责人。**

## 6. 迁移与兼容性策略

1. 字段集以**最小集起步**（见评估报告 §3 候选表），只收负责人批准的字段；后续加字段 = 改 ADR 附录（颜色表），不需新 ADR。
2. 既有文档兼容：规范示例（`Accent:color=$Theme.Primary` 等）在两种方案下均合法；`Accent` 作为 Prop 名的既有用法不受字段集影响（命名空间不同）。
3. 未接线资产处置：`ThemeProvider` 按 D-3 使用或替换；`NRGBAColor` 语义不变。
4. 生成代码从"无颜色发射"到"有颜色发射"是**纯增量**，无存量迁移；唯一回归风险是新增渲染改变既有示例视觉——验收时用 examples/demo 人工比对。

## 7. 失败语义与诊断要求

- 未知 `$Theme.Field`：**编译期诊断**（Analyzer/Expander 报出，含字段名与 Span）；不得静默渲染为零色。
- 字段合法但值未配置：按 D-4 裁决（建议：要求颜色表封闭完备，构建期断言，杜绝运行时缺值路径）。
- 运行时：`Palette` 恒有默认值（gio 实测 `#3f51b5` 等），取色不失败；调用方改 Palette 属正常路径非错误。
- 诊断码：**本提案不分配编号**，实现前按 `诊断码目录.md` 号段与三态规则另行登记。

## 9. 尚未解决的风险

1. 颜色值来源缺失：无论何种方案都需要负责人定义初值（方案 A 是构建期颜色表，方案 B 是初始 Palette 约定）。
2. 与未来 `TASK-STYLE-001` 剩余范围的归属耦合（评估报告 §5）。
3. `Palette` 运行时可变带来的"视觉一致性"测试成本（逐帧取色难以做像素级断言，需探针形态验证——B3 阶段设计）。
4. 若选方案 A：双轨不一致风险（material 控件 vs GXML 背景色）需在文档中显式声明为已知取舍。
5. 诊断码号段占用需在实现前核对（避免与 Analyzer 现有码冲突）。
