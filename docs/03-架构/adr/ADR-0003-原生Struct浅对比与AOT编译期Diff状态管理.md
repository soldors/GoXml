# ADR-0003：采用原生 Struct 浅对比与 AOT 编译期 Diff 状态管理

- 状态：已接受，v1 语义已冻结
- 冻结日期：2026-10-18（论证于 2026-10-18 补全）
- 规范正文：`docs/03-架构/AOT状态Diff语义.md`
- 相关：ADR-0001（AOT 架构）、ADR-0006（列表虚拟化与静态子树宏固化）

| 标记 | 含义 |

## 1. 背景与问题

GUI 框架必须回答两个问题：

1. **状态放在哪里？** 框架管理的响应式对象，还是用户自己的数据结构？
2. **如何判断「要不要重绘」？** 每帧全量重绘、深度比较、还是变更通知？

这两个问题的答案决定了运行时开销的量级。

若引入框架管理的响应式系统（Signals、Observable），则需要：包装每个字段、拦截每次写入、维护订阅关系图。若引入单向数据流（Redux/TEA），则需要：消息类型、reducer、状态不可变替换。

Goxml 的约束来自 ADR-0001：**运行时不得有反射、不得有深比较**。这直接排除了「反射式深度比较」与「运行时依赖收集」。

## 2. 决策

**业务层使用纯 Go Struct；编译器根据绑定路径生成 ShadowState、硬编码字段对比与节点级 Dirty Mask，配合 Gio 的 `op.CallOp` 局部失效。**

四条具体规则：

| 规则 | 含义 |
|---|---|
| **纯 Go Struct** | ViewModel 是用户自己定义的结构体，不继承框架基类、不实现接口、不使用特殊标签（除 JSON 序列化） |
| **ShadowState** | 生成的代码保存上一帧用到的字段的副本，用于对比 |
| **硬编码对比** | 每个被绑定的字段生成一条显式比较语句，不遍历、不反射 |
| **节点级 Dirty Mask** | 只标记实际依赖变化字段的节点，其余节点复用上一帧的 `op.CallOp` |

附加约束：

- 有状态 `<For>` 必须使用稳定 `Key`。
- Map 不参与 v1 自动 Diff。
- 交互控件的输入处理不得整体缓存为绘制 Macro。

## 3. 已有项目证据

### 3.1 为什么不能深比较：来自渲染规模的证据

【项目实测】`性能预算与优化策略.md` §2.2，10,000 行文本列表：

| 实现 | ns/op | allocs/op |
|---|---:|---:|
| 全量渲染（每行一个 `layout.Rigid` 闭包） | 6,438,000 | 10,010 |
| 虚拟滚动（仅可见行） | **19,200** | **0** |

差距 335×。这条数据的用途是说明：**每帧的工作量必须只与可见元素相关**。

深度比较的问题结构相同——它的成本与**状态树规模**成正比，而不是与「实际变化的字段数」成正比。一个含 10,000 个元素的 ViewModel，深比较每帧都要遍历全部字段，即使只有 1 个字段变化。

⚠️ 说明：上表测的是**渲染**规模，不是**比较**规模。它支撑的是「规模必须受控」这一设计方向，不是「深比较慢 N 倍」的直接测量。深比较与本方案的对比如**未进行统一基准测试**。

### 3.2 为什么硬编码比较可行：绑定路径在编译期已知

【项目证据】`contracts.BindingVal` 保存的是**分段路径**而非整串：

```go
type BindingVal struct {
    IsBinding bool
    IsNegated bool
    Raw       string    // 保留原文，用于诊断回显
    Segments  []string  // 按 "." 切分，供 Analyzer 逐段解析类型
}
```

契约注释明确要求「不允许保存整串路径后再在运行时切分」。

这使得编译期能沿路径逐段解析类型（Analyzer 阶段），并为每段生成具体的字段访问代码。字段一旦具体，比较就能写成：

```go
if vm.User.Name != shadow.User.Name { dirty |= dirtyUserName }
```

而不是运行时反射遍历。**这条能力完全来自「绑定路径是编译期常量」这个语言约束**（ADR-0002 §3.1 禁止表达式与混合绑定）。

### 3.3 已实现的约束

【项目证据】当前编译器已强制：

| 约束 | 实现位置 | 状态 |
|---|---|---|
| `<For>` 含状态控件必须给 `Key` | `parser.CodeKey`（`GXML-SCOPE-003`） | 已实现并有测试 |
| `Key` 用于维持每项状态稳定 | 规范 §6 | 已冻结，Codegen 待实现 |
| Map 不参与自动 Diff | `AOT状态Diff语义.md` | 已冻结 |

`GXML-SCOPE-003` 的实测触发：`<For>` 内含 `<Button>` 等状态控件却未写 `Key` 时拒绝编译。

### 3.4 尚未实现的证据

**ShadowState、Dirty Mask、`op.CallOp` 固化目前都还没有实现代码。** 它们属于 `TASK-STATE-001`（依赖 `TASK-CODEGEN-001`）。

本 ADR 记录的是**已冻结的设计**与**支持该设计的既有证据**，不是已完成的性能结论。

## 4. 外部事实：其它状态管理方案

以下仅描述各方案的官方定位。它们的性能与本方案不可直接横向比较（不同语言、不同运行时、不同职责）。

### 4.1 Signals（细粒度响应式）

【外部事实】Signals 被 Angular、Solid、Vue（`ref`/`reactive`）、Preact Signals 等采用，核心特性是「读取时自动追踪依赖，写入时精确通知订阅者」。

它对 GXML 的启示是：**「精确知道谁依赖谁」确实能避免全量比较**。本方案用编译期分析达到同样目的（绑定路径即依赖声明），而不引入运行时依赖图。

### 4.2 TEA（The Elm Architecture）

【外部事实】Elm 的架构是 `Model → Update(Msg) → Model`，状态不可变，视图是纯函数；Redux 沿用同一模式。

它对 GXML 的启示是：**不可变状态天然适合比较**（引用相等即可判定未变，无需逐字段）。但 Go 没有内置的不可变数据结构，强制不可变需要大量复制，或引入持久化数据结构库。

### 4.3 保留式组件 + 脏标记

【外部事实】多数保留式 GUI 框架（含 Flutter 的 `setState`、Qt 的 `update()`）采用「组件持有状态 + 显式请求重绘」。

它与 GXML 的立即模式前提不同：立即模式没有可持有的组件实例，每帧重新执行布局代码。

### 4.4 明确不做的比较

| 不采用的比较 | 原因 |
|---|---|
| 「Signals 比浅对比快」 | 不同语言、不同运行时，**无统一基准** |
| 「Redux 太重」 | 它对大型团队的可预测性是其设计目标；不是能力缺陷 |
| 「浅对比是最优方案」 | 它有明确的失效场景（§5.2），不是普适最优 |

## 5. 设计判断与适用边界

### 5.1 为什么选原生 Struct + 浅对比

| 理由 | 说明 |
|---|---|
| 与 ADR-0001 一致 | 运行时零反射、零深比较是硬约束；浅对比（`!=` 比较具体字段）恰好不需要反射 |
| 用户零侵入 | ViewModel 是普通 Go 结构体，可以直接 JSON 序列化、可以传给任何 Go 库、可以在测试里字面量构造 |
| 依赖关系编译期已知 | 绑定路径是编译期常量（§3.2），不需要运行时依赖收集 |
| 与 Go 的类型系统天然契合 | `==` 对可比较类型是编译期保证的，不需要运行时类型检查 |

### 5.2 浅对比依赖的条件（这是它的边界）

浅对比**只在以下条件成立时正确**：

| 条件 | 说明 | 违反的后果 |
|---|---|---|
| **被绑定字段本身可比较** | `string`/`int`/`bool`/指针/接口。切片、Map、函数**不可用 `==` 比较** | 编译失败（Go 语言层面）。已知：Map 不参与 v1 Diff |
| **嵌套对象的修改是引用替换** | 修改 `vm.User.Name` 时，代码写的是 `vm.User = newUser` 或字段直接赋值 | 若通过指针在**别处**改了共享对象，ShadowState 的副本仍是旧值，对比会误判「未变」 |
| **切片内容变更需替换切片或改变元素** | 元素级绑定依赖元素字段变化 | 原地 `sort` 或原地修改指针指向的对象可能漏检 |

### 5.3 哪些修改会导致漏更新

这是本 ADR 最重要的部分——**必须写成明确清单，而不是含糊承诺**。

| 修改方式 | 是否被检测 | 说明与规避 |
|---|---|---|
| `vm.Name = "x"` | ✅ 检测 | 直接字段赋值 |
| `vm.User.Name = "x"` | ✅ 检测 | 嵌套字段赋值，路径上的段都被绑定 |
| `vm.User = otherUser` | ✅ 检测 | 引用替换 |
| `vm.Items[i].Name = "x"` | ✅ 检测（元素被绑定） | 元素字段赋值 |
| `vm.Items = newSlice` | ✅ 检测 | 切片引用替换 |
| **原地修改切片元素但元素是指针** | ⚠️ **可能漏检** | `*vm.Items[i]` 与 ShadowState 保存的是同一指针。规避：不要保存指向 ViewModel 内部的指针，或改为值类型 |
| **通过另一个指针别名修改绑定字段** | ⚠️ **可能漏检** | ShadowState 存的是值副本，别名修改不经过 Diff 路径 |
| **原地 `append` 未改变长度且复用底层数组** | ⚠️ 需注意 | 长度变化可检测；长度不变而内容变化需依赖元素字段绑定 |
| **Map 内容变更** | ❌ 不检测 | v1 明确不支持，需替换整个 Map 或改用切片 |
| 未绑定字段的修改 | 不触发重绘 | 属预期行为，不是缺陷 |

**防漏更新的设计原则**：

1. **不要在 ViewModel 中保存指向自身内部的指针**，否则值副本失效。
2. **Map 不作为绑定源**，需要有序集合时用切片。
3. `<For>` 必须有 `Key`，否则元素重排会导致状态错位（这已由 `GXML-SCOPE-003` 强制）。
4. 若确实需要原地修改指针指向的对象，显式触发重绘。

### 5.4 AOT Diff 的收益与代价

【设计判断】

| 收益 | 代价 |
|---|---|
| 运行时无反射、无深比较，开销与**变化字段数**成正比 | 编译器必须为每个绑定路径生成对比代码，代码量随绑定数线性增长 |
| 依赖关系在编译期确定，不需要运行时订阅图 | 绑定路径的语义必须是「可静态解析的字段路径」（ADR-0002 §3.1），牺牲了表达式灵活性 |
| Dirty Mask 可精确到节点，复用 `op.CallOp` | 静态子树的识别与固化逻辑复杂（ADR-0006） |
| 用户数据结构零侵入 | 用户必须遵守 §5.2 的三条约定，否则出现**静默漏更新** |

最后一项是最重要的代价：**漏更新不会报错，只表现为界面不刷新**。因此测试责任显著增加——每个 ViewModel 变更路径都需要有可见性测试。

## 6. 被拒方案与否决理由

| 方案 | 否决理由 |
|---|---|
| 每帧全量重绘，不做 Diff | 渲染规模的成本与元素数成正比（§3.1），10k 元素已不可接受 |
| 反射式深度比较 | 违反 ADR-0001 的「运行时零反射」；且成本与状态树规模成正比而非变化数 |
| 框架管理的响应式对象（Signals 式） | 需要包装每个字段并拦截写入，与「用户用纯 Go Struct」的目标冲突；Go 无法拦截字段赋值 |
| TEA/Redux 单向数据流 | 需要不可变状态与消息类型，Go 无内置不可变结构，强制造型成本高；且对「直接改结构体字段」这种 Go 惯用法不友好 |
| 手动 `Invalidate()`（用户自己声明何时重绘） | 把正确性责任完全推给用户，且无法做节点级精确失效，容易退化成全量重绘 |

## 7. 版本演进边界

- 支持 Map 参与 Diff 需新 ADR：它需要定义 Map 的稳定顺序与比较方式。
- 引入框架管理的响应式对象需新 ADR：它推翻「纯 Go Struct」前提。
- 放宽 §5.2 的可比较条件（如允许切片内容 diff）需新 ADR 并给出实测。
- `TASK-STATE-001` 完成后，§5.3 的漏更新清单必须逐条写成测试用例；若发现清单不完整，应回改本节。
