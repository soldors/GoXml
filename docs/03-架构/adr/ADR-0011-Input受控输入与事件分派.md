# ADR-0011：Input 受控输入与事件分派

- 状态：**已接受（2026-10-20）**
- 决策依据：[Input输出契约.md](../Input输出契约.md)（v1 冻结）、
  [INPUT-001-B-决策记录.md](../../04-WBS/任务卡/INPUT-001-B-决策记录.md)
- 关联：ADR-0002（声明式语法）、ADR-0010（统一 View 接口）、
  ADR-0009（静态子树固化）

---

## 背景

`<Input>` 在 Schema 里早有定义（`Value` + `ValueChanged(value:string)`），
但 Codegen 从未支持——因为缺少四个前置决策：

1. `{Path}` 对 Input 是不是双向绑定？
2. 用户输入何时、如何回写？
3. 外部改值如何同步而不打断输入？
4. 事件在哪里消费？

这些不是纯 UI 问题：它们同时触及语言语义（绑定方向）、事件系统（载荷）、
状态机制（失效与同步）与运行时（Gio Editor 的事件/焦点/IME 模型）。
若不先裁决，实现必然反复返工。

---

## 决策 1：`Value` 是外部值绑定，**不提供自动双向绑定**

### 决策

`Value="{Path}"` 只表达 vm → Editor 一个方向；回写只能经显式事件方法。

### 理由

- v1 规范 §9 已明确「不支持隐式双向绑定」——自动双向会引入**可写性**
  问题：Analyzer 必须知道哪些字段可写、哪些路径是方法调用（不可赋值），
  这需要一套全新的写路径语义，超出 Input 范围；
- 双向绑定把「值变化」与「用户意图」混为一谈，会使 Submit/Validate
  这类明确语义无处安放；
- 显式回写让"何时写、写什么"成为可审计的代码（`v.vm.M(...)`），
  而不是编译器的隐式行为。

### 代价

用户必须为每个需要回写的 Input 声明 `ValueChanged`；漏声明时 Input
不把编辑写回模型；编辑器可保留本地草稿，直到绑定外部值实际变化后应用新值。
这不等于 ReadOnly，也不属于 MaxLen/Filter 投影例外；本轮修订按 Input 契约 §5.4 明确。

### 未采纳的方案

| 方案 | 为什么不采纳 |
|---|---|
| 自动双向（`Value="{x}"` 即可写回 `x`） | 需要可写性模型；与规范 §9 冲突 |
| 字段直写（`vm.Name = text`） | 破坏"写入必须经方法"的既有生成形态，且无法拦截副作用 |

## 决策 2：同步镜像两条更新路径（2026-11-02 负责人修订）

原2026-10-20决策曾规定处理器后 A=V；该规则造成归一化模型与显示永久分歧。
负责人在完整行为表（含同帧优先级、光标复位、Submit原文、共享字段边界）说明后，
明确选择“采用该方案，更新契约和回归后再验收”。本修订替代原决策2的A更新规则。

- 路径1：事件消费之后求值V，V!=A时SetText(V)，成功后A=V。
- 路径2：真实事件处理器执行后A=Editor.Text()，而非重求值模型或原始输入企图。
- 本次Layout事件处理末尾按需同步模型；程序化写的回显由Gio布局内部排空，静默。
- 同帧冲突用户编辑优先，外部新值可能被覆盖。模型归一化后显示追随，SetText可能复位光标。
- Submit保留确认事件原文；同帧UpperText+Return可出现payload=abc、帧末E/V=ABC。
- 共享字段按布局顺序更新，前控件可能下一帧才收敛；无处理器draft、不可表示投影按Input契约§5保留。

不新增字段、跨帧来源标志或整帧丢弃。精确算法以[Input输出契约](../Input输出契约.md)§5为唯一权威。
原生IME、物理焦点、跨平台运行仍未验证；本修订不把自动化通过替代人工验收。

## 决策 3：Editor 在**控件自身布局上下文**中消费事件

### 决策

`<Input>` 的事件属于新增的**「控件自持事件」类别**：在控件位置调用
`Editor.Update(gtx)` 与 `Layout`，**不**提到 `Layout` 顶部。

### 理由

【外部事实】`widget.Editor.Update(gtx)` 依赖：

- 本帧 `Layout` 注册的**焦点 tag**（`gtx.Ops` 中的 input op）；
- `gtx.Source` 的事件队列；
- IME 组合状态与布局上下文的对应关系。

把它们提到 `Layout` 顶部会导致焦点 tag 尚未注册 → 事件无法路由；
IME 状态错位。这与 `<Button>` 的 `Click` 有本质差异：Clickable 只需要
输入区域命中，Editor 需要**完整的编辑上下文**。

### 代价

事件消费位置不再统一——`Layout` 顶部规则必须新增例外类别。
本 ADR 要求把该类别写进事件契约（C 阶段），而不是留作 Input 的实现备注。

### 未采纳的方案

| 方案 | 为什么不采纳 |
|---|---|
| 也提到顶部（统一规则） | 实测会破坏焦点与 IME |
| 由框架代持焦点/IME | 重复实现 Gio 已有的编辑状态机，且更难正确 |

## 决策 4：v1 **明确拒绝** `<For>` 内 `<Input>`

### 决策

`<For>` 子树内出现 `<Input>` → Parser 报 `GXML-SCOPE-005`（不论有无 Key）。

### 理由

- `widget.Editor` 是**重量级状态**（文本缓冲、光标、选区、IME、撤销历史），
  与轻量 `Clickable` 不同量级；
- 行状态生命周期有一整套未决问题：键重复如何检测、重排后 Editor 归属、
  删除后何时清理、缓存重放时状态归谁；
- 在未裁决这些问题前允许使用，会产生**难以诊断的状态串位**——
  比明确拒绝更糟；
- `<For>` 已有稳定 Key（SCOPE-003 强制），但 Key 只解决"身份"，
  不解决"重量级状态的生命周期"。

### 代价

v1 无法做"表单行内编辑"这类界面。这是**有意的能力边界**，
不是遗漏——生命周期设计列为独立门槛。

### 未采纳的方案

| 方案 | 为什么不采纳 |
|---|---|
| `map[K]*widget.Editor`（照搬 Clickable 池） | 键语义/清理/重放归属均未裁决，属于临时发明不完整机制 |
| 按索引池 | 重排即串位（与 Clickable 同理，且 Editor 代价更高） |

## 决策 5：`FromPayload` 是**通用 Codegen 能力**，不是 Input 专属

### 决策

载荷渲染的实现归属**通用事件生成**：由 `ResolvedEvent.Payload` +
`Mapping` 决定实参来源，控件只需为每个已声明事件提供一个"载荷值表达式"。

### 理由

- Schema 的事件载荷是**通用概念**（`Input.ValueChanged` 只是第一个使用者；
  未来的 `Select.ValueChanged`、`Slider.ValueChanged` 同构）；
- 若把载荷实现塞进 Input 分支，第二个带载荷控件必须复制一遍——
  这正是 `<For>` 阶段"池按 For 组织"被证明错误后的同类教训；
- 通用能力可以**独立于 Input 测试**（构造一个带载荷的 `ResolvedEvent`
  即可），因此能先于 Input 交付。

### 代价

需要先定义"控件侧义务"接口（每个事件提供一个载荷表达式）——
对只有一个成员的当前状态略重，但避免第二次返工。

### 未采纳的方案

| 方案 | 为什么不采纳 |
|---|---|
| Input 分支内特判（`if tag == "Input"`） | 第二个控件就要复制；且 Analyzer 的 `FromPayload` 语义被绕过 |
| 方法自取值（处理器无参，内部调 `Editor.Text()`） | 把编辑器状态泄漏进 ViewModel 调用约定 |

## 影响

| 方面 | 影响 |
|---|---|
| 语言语义 | `Value` 单向；无新表达式运算 |
| 事件系统 | 新增"控件自持事件"类别；`FromPayload` 成为通用能力 |
| 状态机制 | `lastApplied` 两条路径算法；复用既有失效双轨 |
| 诊断 | 新增 `GXML-SCOPE-005`（待 C 阶段登记） |
| Codegen | 新增 Input 分支 + 通用载荷渲染；Input 为动态节点 |
