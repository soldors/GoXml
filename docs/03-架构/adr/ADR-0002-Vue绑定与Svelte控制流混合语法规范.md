# ADR-0002：采用 Vue 绑定与 Svelte 控制流混合的 GXML 语法规范

- 状态：已接受，v1 语义已冻结
- 冻结日期：2026-10-18（论证于 2026-10-18 补全）
- 规范正文：`docs/03-架构/GXML语言规范.md`
- 相关：ADR-0001（AOT 架构）、ADR-0003（状态与 Diff）、ADR-0008（布局模型）

## 0. 证据分级

| 标记 | 含义 |
|---|---|
| **【项目证据】** | 已冻结的规范条款、已实现的编译器行为 |
| **【外部事实】** | Vue/Svelte/XAML 官方文档的表述，附来源 |
| **【设计判断】** | 基于项目约束的取舍，**不是**对来源框架的评价 |

本 ADR 的核心不是证明 Vue 或 Svelte 不好，而是说明 **GXML 为什么不直接复制任何一个框架的完整语法**。

## 1. 背景与问题

声明式 UI 语法已有多个成熟范式，各有明确的适用场景：

| 范式 | 代表 | 语法重心 |
|---|---|---|
| 模板 + 指令 | Vue、Angular | 属性绑定、指令前缀、表达式 |
| 编译期模板 | Svelte | 编译期消解响应式，接近原生 JS |
| 标记 + 代码隐藏 | WPF/UWP XAML | 强类型标记 + 单独的代码文件 |
| 函数式组合 | Compose、SwiftUI | 全 Go/Kotlin/Swift 代码，无标记 |

GXML 需要在这几种范式之间取一组具体规则，同时满足一个硬约束：**所有语法必须能在编译期静态分析并翻译为 Go 代码**（ADR-0001）。

这条约束直接排除了「任意表达式」类语法——任意表达式需要完整的表达式解析器与类型推导，其代价远超一个标记语言应有的复杂度。

## 2. 决策

四组决议：

| 维度 | 决议 | 规范条款 |
|---|---|---|
| 属性绑定 | 完整绑定 `{Path}` / 取反 `{!Path}` / 静态字面量，**禁止混合** | §4 |
| 事件绑定 | `Click="Save"` 或 `Click="Delete(item.ID)"`（无 `@` 前缀） | §5.1 |
| 控制流 | `<If>/<Then>/<Else>`、`<For>` 标签，**不是属性指令** | §6 |
| 组件 | 编译期 `<Def>/<Slot>` 宏展开，无运行时注册表 | §7 |

并明确禁止：任意 Go 表达式、函数字面量、隐式双向绑定、动态组件名、命名插槽。

## 3. 已有项目证据

### 3.1 绑定语法：为什么要求「完整」或「静态」，不允许混合

【项目证据】规范 §4 规定属性值只有三种形态：

```text
静态字面量            保存
完整绑定              {User.Name}
取反绑定              {!ReadOnly}
```

**禁止**的形态：

```text
Hello, {User.Name}        <!-- 静态文本与绑定混合 -->
{User.Age + 1}            <!-- 表达式 -->
{format(User.Name)}       <!-- 函数调用 -->
```

理由是可静态分析：`{Path}` 只需按 `.` 切分成段，每段做标识符校验；混合文本与表达式则需要词法分析、求值顺序、类型推导与错误定位。

已实现证据：`parser/attrs.go` 对混合形态报 `GXML-ATTR-003`，测试锁定在 `diagcode_test.go`。

### 3.2 事件语法：`@` 前缀不可行

【项目证据】规范 §5.1 记录了这次修正。初版设计用 `@Click="Save"`，但 **`@` 不是合法的 XML 属性名字符**，`encoding/xml` 直接报语法错误：

```text
<Button @Click="Save"/>  →  XML syntax error: expected attribute name in element
```

因此改为无前缀的 `Click="Save"`。这带来一个问题：语法层无法区分「事件」与「普通属性」，因为 `Click` 与 `Text` 在 XML 里是同类东西。

**解法是把区分移出语法层**，交给组件契约（§3.3）。

### 3.3 属性与事件的区分：由组件契约声明，绝不推断

【项目证据】规范 §5.2 规定四层分类顺序，且**顺序固定**：

| 顺序 | 类别 | 来源 |
|---|---|---|
| 1 | 全局布局属性 | 编译器内置表 |
| 2 | 组件属性 | 组件 Schema 的 `Properties` |
| 3 | 组件事件 | 组件 Schema 的 `Events` |
| 4 | 都不匹配 | 编译错误 `GXML-ATTR-004` |

**规则 4 绝不退化为事件。** 否则 `Clik="Save"`（`Click` 的拼写错误）会被静默当作事件绑定，把一个应立即发现的错误变成看似合法的代码。该用例已收入 `examples/gxml/invalid/attr004-misspelled.gxml` 并由测试锁定。

### 3.4 为什么 Parser / Expander / Analyzer 分层

【项目证据】分层不是学术偏好，而是被两个具体发现逼出来的：

**发现一：Parser 不能知道组件白名单。**
最初 Parser 试图识别事件属性，结果是 Parser 必须内置控件名列表——每新增一个控件或第三方组件，语法层就多一处耦合。

现结构：Parser 只做 XML 语法与属性值形态，所有属性进 `RawAttrs`，**不判断属性还是事件**。

**发现二：适用性检查需要 Schema 知识，放在 Parser 会与值校验打架。**
`Columns` 是合法布局属性（Parser 能解析其值），但它只适用于 `<Grid>`。若 Parser 消费了布局属性，Expander 就再看不到 `Columns`，无法报「不适用」。

现结构：Parser 解析布局属性的值形态，**同时保留在 `RawAttrs`**；Expander 完成分类与适用性检查后清空。

因此三层的职责边界是：

| 阶段 | 职责 | 是否需要 Go 类型 |
|---|---|---|
| Parser | XML 语法、属性值形态、结构规则 | ❌ |
| Expander | 组件契约分类、`<Def>`/`<Slot>` 展开 | ❌（只看文档内声明） |
| Analyzer | 绑定路径存在性、事件方法签名 | ✅ `go/types` |

Analyzer 之所以必须独立，是因为它需要加载目标 Go 包——这是前两层都不愿承担的依赖。

## 4. 外部事实：来源范式的特征

以下仅描述各范式的官方定位，不构成评价。这些框架的**性能与其语法设计无关**，本 ADR 不引用任何跨框架性能数字。

### 4.1 Vue

【外部事实】Vue 官方文档将模板语法描述为「基于 HTML 的模板语法，允许你声明式地将 DOM 绑定至底层组件实例的数据」，支持插值、指令（`v-if`、`v-for` 等）与表达式。

GXML 采用了它的**属性绑定外形**（`{Path}` 接近 Vue 的插值/绑定直觉），但没有采用指令系统与模板表达式。

### 4.2 Svelte

【外部事实】Svelte 官方文档强调其在**编译期**把组件转换为高度优化的原生 JS，而不是在浏览器中解释框架代码。

GXML 采用了它的**编译期消解**思路（这也是 ADR-0001 的基础），但没有采用它的响应式赋值语法（那需要语言级赋值重写，配合 Go 的语法不可行）。

### 4.3 XAML

【外部事实】XAML 是标记 + 代码隐藏（code-behind）模型，标记中声明控件树与属性，逻辑写在配对的代码文件中。

GXML 采用了它的**强类型属性**直觉（属性值按类型解析，不合法即编译错误），但没有采用代码隐藏——GXML 把事件处理指向 ViewModel 的方法，而不是生成代码里的 partial 类。

### 4.4 明确不做的比较

| 不采用的比较 | 原因 |
|---|---|
| 「GXML 比 Vue 快 / 比 Svelte 慢」 | 三者解决的是不同问题（浏览器 DOM / 编译期 JS / 原生绘制），**没有可比基准** |
| 「Vue 的表达式能力是缺点」 | 在浏览器环境里它是特性；只是在「必须静态分析并生成 Go」这一约束下不适用 |
| 「Svelte 的响应式赋值可以照搬」 | Go 没有可被编译器拦截的赋值语法，语言机制不支持 |

## 5. 设计判断

### 5.1 为什么把静态结构、绑定、控制流分开处理

三种东西的**失败模式不同**，混在一起会让诊断失焦：

| 类别 | 典型错误 | 应该在哪个阶段发现 |
|---|---|---|
| 静态结构（标签、嵌套） | `<Else>` 出现在 `<If>` 外 | Parser（纯语法） |
| 绑定 | `{User.Nmae}` 拼写错误 | Analyzer（需要类型信息） |
| 控制流 | `<For>` 缺 `Key` 导致状态串位 | Parser（结构规则） |

如果用一个「万能表达式」把它们统一，那么所有错误都会退化成同一种「表达式非法」，用户无法知道该去查类型还是查结构。

### 5.2 为什么控制流用标签而不是属性

Vue 的 `v-if` / `v-for` 是属性，Svelte 的 `{#if}` / `{#each}` 是块语法。GXML 选择标签：

| 理由 | 说明 |
|---|---|
| XML 属性无法自然表达「块」 | `<If>` 需要一个明确的子句边界，属性形式只能靠包裹元素，反而更绕 |
| `<Then>`/`<Else>` 让分支显式 | 避免「没有 else 时语法该怎么办」的歧义 |
| 与 `<Def>`/`<Slot>` 一致 | 结构性的东西都用标签表达，规则统一 |
| 错误定位更准 | `<Then>` 缺失可以直接指向 `<If>` 的范围，而不是某个属性 |

### 5.3 为什么组件用编译期宏而不是运行时组件

`<Def>/<Slot>` 在 Expander 阶段内联展开（规范 §7.2），不产生运行时组件实例、注册表或边界。

理由与 ADR-0001 同源：运行时组件意味着每帧创建组件对象与生命周期调用，而宏展开后的结果与手写的嵌套代码完全一致。

代价见 §6。

## 6. 混合语法的代价

| 代价 | 具体表现与缓解 |
|---|---|
| **学习成本是复合的** | 用户要同时理解「XML 结构 + `{Path}` 绑定 + 标签式控制流 + 宏组件」四套概念。缓解：`GXML语言规范.md` 按这四块组织，`examples/gxml/` 提供 6 个可编译示例 |
| **语法边界需要反复解释** | 最常被问的是「为什么 `{User.Age + 1}` 不行」。缓解：规范 §4 明确列出禁止形态并给出理由；诊断码 `GXML-ATTR-003` 的消息直接说明「use either a literal or a single {Path}」 |
| **诊断数量与维护成本** | 25 个激活诊断码需要统一维护，历史上曾出现文档与代码不一致。缓解：`诊断码目录.md` + `internal/compiler/diagdoc` 自动一致性门禁 |
| **分层带来跨阶段追踪成本** | 一个错误可能由 Parser 或 Expander 报出，用户需要知道去哪查。缓解：诊断码目录明确标注每个码的归属阶段 |
| **混合范式的「缝合感」** | 来自不同框架的元素放在一起，可能显得不统一。这是刻意的取舍——优先复用已被验证的心智模型，而不是发明一套全新的语法 |

## 7. 被拒方案与否决理由

| 方案 | 否决理由 |
|---|---|
| 纯 Vue 模板（含 `v-if`/`v-for`/表达式） | 需要完整的表达式解析与求值，且指令系统无法在编译期确定最终代码结构 |
| 纯 Svelte（`{#if}`/响应式赋值） | 响应式赋值依赖语言级语法拦截，Go 不支持；`{#...}` 块语法在 XML 中不合法 |
| 纯 XAML（代码隐藏） | 代码隐藏意味着生成 partial 类与生命周期方法，与「事件指向 ViewModel 方法」的轻量模型冲突；且 XAML 的附加属性机制过于复杂 |
| 全 Go 代码（Compose/SwiftUI 式） | 失去标记语言的可读性与非程序员可编辑性——这是 Goxml 存在的理由之一 |
| 事件用 `@Event` 前缀 | `@` 非合法 XML 属性名字符，实测直接被 `encoding/xml` 拒绝（§3.2） |

## 8. 版本演进边界

- 引入表达式求值（哪怕受限）必须新 ADR：它会改变 Parser/Analyzer 的职责边界与诊断体系。
- 引入运行时组件或动态组件名必须新 ADR：它推翻 AOT 宏展开的前提。
- 事件语法再变更（如恢复前缀）：需先验证 XML 合法性，并同步更新 `诊断码目录.md` 中 `GXML-EVENT-*` 的触发条件。
- v1 明确不支持的内容清单以规范 §9 为准，缩减该清单需新 ADR。
