# ADR-0001：采用编译期 GXML 转 Gio 的零抽象开销架构

- 状态：已接受，输出契约已冻结
- 冻结日期：2026-10-18（论证于 2026-10-18 补全）
- 输出契约：`docs/03-架构/代码生成输出契约.md`
- 相关：ADR-0007（Zero-CGO 平台约束）、ADR-0008（布局模型）、`性能预算与优化策略.md`

## 0. 证据分级

本 ADR 严格区分三类内容，请按标记阅读：

| 标记 | 含义 | 可信度 |
|---|---|---|
| **【项目实测】** | 本项目在记录环境下测得的数字 | 量级可信；部分**尚不可复现**，见 §3.2 |
| **【项目证据】** | 已实现的代码、已冻结的规范 | 可直接核验 |
| **【外部事实】** | 其他框架官方文档的表述，附来源 | 可查证，但不构成适用性判断 |
| **【设计判断】** | 基于项目约束做出的取舍 | 是**选择**，不是对别人的优劣评价 |

## 1. 背景与问题

Goxml 的目标是用声明式标记写桌面 GUI，Go 做逻辑，并要求「性能不因使用框架而显著下降」。

核心选择：**运行时解释，还是编译期生成？**

若 `.gxml` 在运行时解析、反射绑定、动态构建渲染树，则每帧都要付出解析与反射代价，且大量错误只能在运行期暴露。若在编译期转成普通 Go 源码，运行时便没有任何框架痕迹——代价是编译器必须承担全部语义校验与代码生成。

## 2. 决策

**在构建前将 GXML 编译为纯 Go 代码，运行时无 XML 解析与虚拟 DOM。**

三条具体要求：

1. **运行时零 XML 解析、零反射、零状态深比较。** 生成的代码只含具体类型调用。
2. **静态子树在编译期展开为直接调用并固化 `op.CallOp`**，不得每帧重建闭包。
3. **渲染底座使用 Gio**，生成代码调用其 `layout`/`op`/`widget`。

生成文件、包名、导入、组件接入、失败保护、清理和缓存行为以 `代码生成输出契约.md` 为准。

## 3. 已有项目证据

### 3.1 构建实测：Gio 在各平台的依赖形态

【项目实测】来自 ADR-0007，在 Windows 与真实 Linux（WSL2 Debian 13）上验证：

| 平台 | `CGO_ENABLED=0` | 依据 |
|---|---|---|
| Windows | ✅ 可行 | Gio 的 Windows 后端是纯 Go（`x/sys/windows` + 手写 D3D11 绑定） |
| Linux | ❌ 不可行 | `internal/vk`、`internal/gl/gl_unix.go`、`internal/egl/egl_unix.go`、`app/os_x11.go`、`app/os_wayland.go` 均 `import "C"` |
| macOS | ❌ 不可行 | `app/os_macos.go`、`metal_macos.go` 依赖 CGO |

Linux 上穷举 5 种构建标签组合均失败；`CGO_ENABLED=1` 可构建（11 MB），`readelf -d` 显示需要 10 个系统动态库。

**用途限定**：「Gio = 纯 Go、零依赖」**只在 Windows 成立**，不得扩展到全平台（详见 ADR-0007）。

### 3.2 性能实测：AOT 相对解释式构造的差距

#### 静态子树：闭包 vs 编译期展开

【项目实测】

| 项目 | 值 |
|---|---|
| 场景 | 50 个子节点的纵向 `layout.Flex`，节点内容完全相同 |
| 对比 A | 每帧 `append` 构造 `[]FlexChild`（即解释式重建渲染树） |
| 对比 B | 编译期完全展开为直接调用（无循环、无切片、无闭包） |
| 结果 A | 28,000 ns/op，51 allocs/op，6,172 B/op |
| 结果 B | **2,550 ns/op，0 allocs/op，0 B/op** |
| 差距 | 约 **11×** |

同一实验的第三个数据点更关键：**预分配并复用 `[]FlexChild` 缓冲区只省约 4% 时间**（27,000 ns/op，51 allocs/op，4,012 B/op）。

这说明开销来源是**闭包本身逃逸**，不是切片容量。因此 Codegen 不能只做「复用缓冲区」，必须消除闭包。

#### 抽象开销：接口派发 vs 具体调用

【项目实测】

| 项目 | 值 |
|---|---|
| 场景 | 200,000 个节点遍历并调用 `Measure()` |
| 对比 A | `[]Node` 接口派发 |
| 对比 B | `[]box` 具体类型调用 |
| 结果 A | 361,000 ns/op |
| 结果 B | 61,000 ns/op |
| 差距 | 约 **5.9×** |

#### 测试环境（两组共用）

| 项目 | 值 |
|---|---|
| CPU | 12th Gen Intel Core i7-12700H |
| 操作系统 | Windows（amd64） |
| Go | 1.26.1 |
| Gio | gioui.org v0.10.3 |
| CGO_ENABLED | 0 |
| 采样 | `-benchtime 200~300ms -count 2~3`，取稳定值 |

#### ⚠️ 证据完整性声明

**这两组数字目前不可复现。** 仓库中**没有任何 `Benchmark` 函数**，也没有 `benchmarks/` 目录——它们来自开发期的一次性测量程序，程序本身未入库。

因此：

- 本 ADR 只用它们确立**量级与排序**（「闭包重建比展开慢一个数量级」这个判断是稳的）。
- **不得**把 28,000 / 2,550 / 361,000 / 61,000 作为对外发布数据或跨项目比较依据。
- 复现任务：`TASK-BENCH-001-5`（静态子树）、`TASK-BENCH-001-9`（抽象开销）。
- 正式发布数值必须在固定 CI 环境复测，写入 `测试报告.md` §7。

`性能预算与优化策略.md` §2 对这批数据有同样限定：「单机初步基线，用于确立量级与排序，不作为发布证据」。

> **本表是 2026-10-18 的历史快照，不维护实时状态。**
> 覆盖率与测试数会随实现推进变化；权威来源是各任务的验收报告与任务卡。
> 表中只保留「某包是否已存在」这一稳定事实。

【项目证据】当前仓库已具备前端管线：

| 包 | 作用 | 状态 |
|---|---|---|
| `contracts` | IR 契约、`CompilerError` | 已实现（快照值） |

| `internal/compiler/grid` | Grid 列宽计算（规范 oracle） | 已实现，100% 覆盖 |
| `internal/compiler/sizelayout` | 尺寸决策表 | 已实现，94.4% 覆盖 |
| `internal/compiler/diagdoc` | 诊断码目录一致性门禁 | 已实现 |
| `internal/compiler/analyzer` | 绑定路径、类型兼容与事件签名校验 | 已实现（本表为 2026-10-18 的快照，**当前状态以 `TASK-ANALYZER-001` 任务卡为准**） |

## 4. 外部事实：候选方案的架构特征

以下为其他框架官方文档的表述，仅描述**它们是什么**，不构成优劣评价。

### 4.1 Gio

【外部事实】官方 README：

> Immediate mode GUI programs in Go for Android, iOS, macOS, Linux, FreeBSD, OpenBSD, Windows, and WebAssembly (experimental).

对本项目的意义：

- 立即模式意味着「每帧重新执行布局与绘制代码」，没有保留式组件树，与 AOT 生成直接调用代码的思路契合——生成的就是普通函数调用。
- 布局原语足够底层（`layout.Flex`/`Rigid`/`Flexed`/`Stack`），可被语言层精确映射（ADR-0008 已逐项验证）。
- 构建依赖形态已由本项目实测（§3.1），不依赖宣传口径。

### 4.2 Fyne

【外部事实】官方 Quick Start（<https://docs.fyne.io/started/quick/>）：

> Fyne requires 3 basic elements to be present, the Go tools (at least version 1.19), a C compiler (to connect with system graphics drivers) and a system graphics driver.

同页紧接着限定：

> Note that these steps are just required for development - your Fyne applications will not require any setup or dependency installation for end users!

对本项目的意义：Fyne 的**开发工具链**需要 C 编译器与系统图形驱动。**这不等于最终用户需要安装 C 编译器**——发布的应用不需要。

因此本文只在「贡献者环境准备」维度使用该事实，**不用它论证部署复杂度**。

### 4.3 Wails

【外部事实】官方 How does it work（<https://wails.io/docs/howdoesitwork>）：

> A Wails application is a standard Go application, with a webkit frontend. [...] The frontend is a webkit window that will display the frontend assets.

且：

> The `Assets` option is mandatory as you can't have a Wails application without frontend assets.

即：Go 后端 + Web 前端（HTML/JS/CSS 资产必填），Go 方法通过绑定暴露为 JavaScript 方法，渲染由系统 WebView 承担。

对本项目的意义：Wails 的架构是「复用 Web 技术栈」——前端是真正的网页。这与 GXML 的目标不同：GXML 用声明式标记生成**原生绘制调用**，不引入浏览器引擎。

### 4.4 明确不做的比较

| 不采用的比较 | 原因 |
|---|---|
| 「Fyne/Wails 性能不如 Gio」 | **没有任何统一基准测试**。公开数字来自不同硬件、不同任务、不同版本，横向比较无意义 |
| 「Wails 因为用 WebView 所以慢」 | 缺乏本项目环境下的实测；WebView 性能取决于具体引擎与用法 |
| 「Fyne 需要用户装 C 编译器」 | 与官方文档矛盾（§4.2） |
| 「Gio 零依赖」 | 只在 Windows 成立；Linux/macOS 需要 10 个系统库（§3.1） |
| 启动时间、内存占用的框架排名 | **未进行统一基准测试**，不做推测 |

## 5. 设计判断

以下不是「别的框架做不到」，而是**本项目在自己约束下的选择**。

### 5.1 为什么选 Gio 作为渲染底座

| 项目约束 | Gio 的契合点 |
|---|---|
| 需要把声明式语法**精确映射**为绘制调用 | 立即模式 + 底层布局原语，语法层可直接翻译，无需适配保留式组件模型 |
| 要求运行时无框架痕迹 | 生成代码就是普通 Gio 调用，可逐行对照手写实现 |
| 要求 Windows 侧单文件产物 | Windows 后端纯 Go（§3.1 实测），可得单文件静态二进制 |
| 要求语言层能控制分配 | 布局 API 不含隐式分配，闭包/切片是否逃逸完全由生成代码决定（§3.2 的前提） |

### 5.2 为什么采用 AOT 而不是运行时解释

决定性的是 §3.2 的量级差：**10 倍量级**的差距不是微优化能抹平的，它来自「是否每帧重建渲染树」这个结构性选择。

附带收益：所有语法与语义错误在编译期暴露，而不是在用户点击某个界面时才发现。

### 5.3 为什么不选 Fyne / Wails

这是**目标差异**，不是能力差异：

| 方案 | 它的擅长 | 与本项目目标的差异 |
|---|---|---|
| Fyne | 完整的保留式组件库与主题系统，开箱即用 | Goxml 要做的是**语言与编译器**，渲染层需要尽量薄、可被精确映射；保留式组件模型会引入编译器无法静态掌握的中间层 |
| Wails | 复用成熟的 Web 前端生态（HTML/CSS/JS 与全部前端框架） | Goxml 的出发点之一正是「不用 Web 技术栈」；若目标是复用 Web，Wails 是更直接的选择 |

两者都能构建桌面应用，也都能实现相近界面。选择 Gio 是因为它更贴合「薄渲染层 + 编译期映射」，而不是因为它们做不到。

## 6. 代价与已知局限

| 代价 | 具体表现 |
|---|---|
| **复杂度从运行时转移到编译期** | 编译器必须自行承担语法校验、语义分类、绑定路径检查、代码生成、诊断与位置报告。当前已实现 7 个前端包（含 `contracts`）约 5,600 行生产代码，Codegen 尚未开始 |
| **诊断质量成为核心责任** | 运行时框架可「先跑起来再说」，AOT 不行——未被静态检查覆盖的错误会变成生成代码里的类型错误。诊断码体系因此需专门维护（`诊断码目录.md`） |
| **布局语义必须自己定义** | Gio 只给原语，`Fill` 的轴向、Grid 的补位、Baseline 的适用面都须在语言层定义（ADR-0008） |
| **平台依赖不由本项目决定** | Linux/macOS 必须 CGO，放弃一键三端交叉编译（ADR-0007） |
| **性能收益尚未端到端证实** | §3.2 是量级推断，全链路对照要等 Codegen（§3.3） |

## 7. 被拒方案与否决理由

| 方案 | 否决理由 |
|---|---|
| 运行时解析 `.gxml` + 反射绑定 | 每帧重建渲染树，实测退化约 10×（§3.2）；错误推迟到运行期 |
| 保留式组件树（Fyne 路线）+ 声明式语法糖 | 编译器无法静态掌握组件内部布局，AOT「生成即最终代码」的前提被破坏 |
| 基于 WebView 渲染（Wails 路线） | 与项目出发点相反——Goxml 存在的前提之一就是避开 Web 技术栈的性能与体积特征 |
| 直接用 Gio 手写（不做框架） | 可行，但放弃了声明式语法的可读性与编译期校验，等于取消这个项目 |

## 8. 版本演进边界

- 更换渲染底座（离开 Gio）属于推翻本 ADR，必须新 ADR。
- 引入运行时组件树、动态布局测量或反射驱动更新，同样必须新 ADR。
- 性能不变量（`性能预算与优化策略.md` §3）一旦放宽，必须记录理由与实测依据。
- 复现 `TASK-BENCH-001` 后，若量级结论与 §3.2 出入较大，应回改本节并注明。
