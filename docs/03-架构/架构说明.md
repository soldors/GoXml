# 架构说明

## 1. 编译与运行双态管线
- 编译期：.gxml -> Parser (带行列号) -> Expander (宏展开) -> Analyzer (AST校验) -> VerifiedDoc -> Codegen -> Artifact -> 提交 *_gen.go
  - 阶段串联与失败门禁由 `internal/compiler/pipeline` 负责：任一阶段失败即中止；分析未通过**不调用** Codegen；生成失败不写文件。详见 [编译编排契约](编译编排契约.md)
- 运行期：go build -> 原生二进制 -> Gio 立即模式 GPU 循环（显式 Invalidate 驱动重布局，绑定显示缓存与静态 CallOp 负责复用；AOT Diff 暂为设计储备）
  - Windows：`CGO_ENABLED=0`，纯 Go，单文件静态产物
  - Linux / macOS：`CGO_ENABLED=1`，动态链接平台库（Gio 后端所需）
- GXML 语义唯一依据：docs/03-架构/GXML语言规范.md（v1，状态：冻结）
- AOT 状态 Diff 设计储备：docs/03-架构/AOT状态Diff语义.md（v1 语义稿；当前阶段推迟，是否引入以 S5 评估记录为准）
- Codegen 输出唯一依据：docs/03-架构/代码生成输出契约.md（v1，状态：冻结）
- 编译编排唯一依据：docs/03-架构/编译编排契约.md（v1，状态：冻结）
- 运行时入口唯一依据：docs/03-架构/运行时入口契约.md（v1，状态：冻结）
- 平台与依赖唯一依据：docs/03-架构/平台与平台依赖矩阵.md（v1，状态：设计冻结，Linux 编译已验证）
- 运行时线程唯一依据：docs/03-架构/运行时线程模型.md（v1，状态：冻结）
- 性能不变量唯一依据：docs/03-架构/性能预算与优化策略.md（v1，状态：设计冻结）
- 字体与文本唯一依据：docs/03-架构/字体与文本渲染策略.md（v1，状态：设计冻结）

## 2. 模块拓扑与职责划分
- contracts/: 编译器与运行时唯一依赖的基础契约。
- internal/compiler/: 编译器套件，最终用户二进制不包含此部分。
  - `parser` / `expander` / `analyzer` / `codegen`：各编译阶段
  - `pipeline`：阶段串联与失败门禁（不生成代码，只决定是否调用、是否产出可提交产物）
  - `grid` / `sizelayout`：布局语义的可执行参考实现
  - `diagdoc`：诊断码目录一致性门禁
- pkg/runtime/: 运行时核心（路由、主题、生命周期、状态序列化）。**当前仅 `app/` 已实现，其余为规划**。
  - `app`：窗口创建与 Gio 主循环入口（最小实现，见 运行时入口契约.md）
- pkg/platform/: 平台调用层（**规划，未创建**）。**Windows 侧纯 Go（Zero-CGO）；Linux/macOS 允许 CGO**。
- cmd/goxml/: CLI 工具链（generate, watch, preview）。（**规划，未创建**）

## 3. 语法与契约边界
- GXML v1 只允许静态值、完整绑定路径、受限事件调用和编译期控制流。
- 布局属性（`Align`/`Justify`/`Gap`/`Width`/`Height`/`Columns`）与 `<Grid>` 标签见 ADR-0008；`<Row>` 默认 `Align=Center`，`<Column>` 默认 `Start`。
- 若未来批准 AOT Diff v1，则按该设计稿比较生成的 ShadowState；当前版本只冻结稳定 Key、绑定缓存和交互控件逐帧处理等已采用的边界，Map 不作为自动 Diff 输入。
- Codegen 默认在 `.gxml` 同目录生成 `<basename>_gen.go`，失败时保留旧产物，清理只允许通过 Manifest 执行。
- Platform 能力通过专用 worker 执行，UI 状态由 UI 线程单一所有；跨线程结果必须经 Dispatcher 和 `window.Invalidate()` 返回。
- 任意表达式、运行时 XML/CSS 解析、隐式双向绑定、动态组件和命名插槽不属于 v1。
- Parser、Analyzer、Codegen 必须共同遵守冻结规范；语义变更必须新增版本并通过 ADR。

## 4. 性能边界（设计约束摘要）
- 静态子树（无绑定/事件/条件/循环）必须在编译期固化为 `op.CallOp`，禁止每帧新建布局闭包。
- 大列表必须虚拟化，单帧工作量只与可见元素数相关，与集合长度无关。
- 禁止在 `Layout` 内拼接显示字符串；文本 shaping 缓存依赖字符串稳定。
- 稳定帧 `allocs/op` 必须为 0；判定与阈值见 `docs/03-架构/性能预算与优化策略.md`。
- 像素级 CPU 处理（SWAR、[]uint64）只适用于图标/位图预处理，**不构成帧热路径优化手段**——Gio 的像素由 GPU 绘制。

## 5. 平台后端边界

Gio 内部把「渲染逻辑」与「平台窗口 + GPU 提交」分开，Goxml 的跨平台能力完全取决于后者：

| Gio 包 | 作用 | Windows | Linux | macOS | Goxml 是否直接依赖 |
|---|---|---|---|---|---|
| `op`、`layout`、`widget`、`material`、`text` | 布局与绘制指令 | 纯 Go | **纯 Go** | **纯 Go** | **是（Codegen 产物的目标）** |
| `gioui.org/app` | 窗口、事件循环、IME | 纯 Go | CGO | CGO | 是（入口） |
| `gioui.org/gpu` | GPU 提交 | 纯 Go | CGO（`internal/vk`） | CGO（`internal/gl`） | 间接 |

**关键结论**：Goxml 编译器的核心产出（布局与控件代码）所在的那一层是**三端纯 Go 的**；CGO 只集中在最后一层「窗口 + GPU 提交」。

这意味着：

1. **放弃三端 Zero-CGO 不影响 Goxml 的核心价值**（AOT 代码生成、零反射 Diff、声明式语法）。
2. 若将来要恢复某平台的 Zero-CGO，需要替换的是 `gioui.org/app`/`gpu` 的**平台后端**（约 6,400 行量级），而不是整个框架。

依据：[ADR-0007](adr/ADR-0007-Zero-CGO降级为Windows侧约束.md) §3。
