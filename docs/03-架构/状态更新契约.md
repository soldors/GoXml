## 1. 接口形态：统一 View 接口，View 持有 ViewModel 引用（冻结）

### 1.1 决策

**采用方案 A**：

- `View` 接口保持 `Layout(gtx, th)` **不变**；
- 绑定视图在**构造时接收 vm**，内部持有**引用**；
- `Layout` 签名不再随绑定需求变化。

### 1.2 为什么不是 B / C

| 方案 | 否决理由 |
|---|---|
| B 适配器 | 多一层类型与生命周期管理；适配器须处理 vm 更新、通知、视图替换，复杂度转嫁调用方 |
| C 扩展接口 | 所有静态页面被迫跟随接口变化，传播到 App、示例、测试；还需解决不同页面 vm 类型不同的泛型问题 |

**核心理由**：绑定只是页面读取状态的一种能力，不应改变 UI 框架的基本接口。
静态页面已统一在 `Layout(gtx, th)` 上。

### 1.3 持有语义：引用，不是所有权

- ViewModel 由**调用方创建与管理**；
- 生成的 View **只保存引用**，不拥有、不销毁；
- 第一版**不支持**隐式替换 vm——如需更换模型，重新构造 View。

### 1.4 构造 API（核查后确定）

现状：`NewXxxView()` 无参（静态页面）。

冻结规则：

| 页面类型 | 构造函数 |
|---|---|
| 纯静态页面 | `NewXxxView()` **不变**（不为 nil 校验复杂化静态路径） |
| 含绑定页面 | `NewXxxView(vm *T)`，**不接受 nil**（见 §4） |

**兼容性影响**：仅含绑定页面的构造签名变化。静态页面、demo、现有测试不受影响
（demo 的 `demoView` 是手写等价物，不是生成代码）。

## 2. 通知机制：Runtime 轻量封装 Gio Invalidate（冻结）

### 2.1 职责链

```text
外部状态修改（调用方负责）
  ↓
Runtime 失效入口（仅请求重新布局，不修改状态）
  ↓
app.Window.Invalidate()   ← 并发安全（S0 源码证据）
  ↓
FrameEvent
  ↓
View.Layout(gtx, th)      ← 统一签名
  ↓
绑定读取最新值 → 显示缓存判定命中/失效
```

### 2.2 冻结的职责边界

| 项 | 冻结 |
|---|---|
| 通知入口负责 | **请求窗口重新布局**，不负责修改 ViewModel |
| 失效范围（第一版） | **整窗**。不承诺节点级/绑定级失效 |
| 并发 | 通知入口遵守 Gio 并发安全语义，可从任意 goroutine 调用 |
| 连续通知 | 是否合并由事件循环行为决定，**契约不承诺**每次修改对应独立帧 |
| 多窗口 | **第一版不支持**。现有 Run/RunWith/RunWindow 均单窗口；契约写明该范围 |

### 2.3 关键诚实条款

**`w.Invalidate()` 并发安全 ≠ ViewModel 并发安全。**

- Invalidate 的锁保护的是窗口失效状态，**不保护**用户数据；
- 任意 goroutine 写普通 Go 字段后 UI 读取，**可能存在数据竞争**；
- ViewModel 数据访问的同步规则**由调用方负责**，本契约不提供自动同步；
- S2 实现时须在文档与生成注释中显式声明该边界。

## 3. 多页面共享 ViewModel：通知责任（冻结）

| 项 | 冻结 |
|---|---|
| 修改状态 | **调用方**负责 |
| 通知 | 按**窗口绑定关系**承担：每个展示该 vm 的窗口收到失效请求 |
| 管理方 | Runtime 承载窗口失效关系 |
| 解绑 | 窗口退出或页面替换后解除关系，不向已退出窗口发送通知 |
| 订阅管理器 | **不引入**通用事件总线；第一版单窗口下无此需求 |

第一版范围：**一个 ViewModel 服务一个窗口**。多窗口订阅是 S5+ 的评估项。

## 4. `vm == nil`：明确拒绝，不静默降级（冻结）

语义：

| 规则 | 冻结 |
|---|---|
| nil vm | **调用方配置错误** |
| 构造时 | `NewXxxView(nil)` 必须显式失败，**不得**生成可运行但语义错误的代码 |
| 不做 | 不自动转空串、不静默忽略绑定、不允许难以定位的深层 panic |
| 静态页面 | 构造方式**不变**，不为 nil 校验复杂化 |

实现方式（构造函数返回 error 还是 panic）**留给 S2**，按现有生成 API 约定决定；
S1 只冻结**语义**：明确拒绝。

## 5.1 受控输入控件的值同步：`lastApplied`（交叉引用，2026-10-20）

> **本文不复制算法**。`<Input>` 的同步算法由
> [`Input输出契约.md`](Input输出契约.md) §5 **唯一定义**；本节只声明
> 它在本契约中的**位置与责任边界**，避免两处各写一遍而日后分叉。

### 责任边界

| 项 | 归属 |
|---|---|
| 何时把 ViewModel 值写进编辑器（`SetText`） | Input 契约 §5.3（逐帧顺序） |
| 两条 `lastApplied` 更新路径 | Input 契约 §5.2 —— **外部应用**与**用户回写**是两条独立路径，不得合并 |
| 同帧冲突（外部值 vs 本地编辑） | Input 契约 §5.4（外部覆盖本地，v1 已接受） |
| 光标/选区/IME 保留 | Input 契约 §5.5（`V == A` 时不调用 `SetText`） |
| **回写后的重绘** | **本契约 §2**：复用既有双轨，无新机制 |

### 与 §2 通知机制的关系

输入回写（`ValueChanged`/`Submit` 的处理器）在帧内修改 ViewModel 后，
重绘**不需要**任何新入口：

```text
帧内：处理器改 vm → gtx.Execute(op.InvalidateCmd{})     （事件契约 §3）
帧外：其他 goroutine 改 vm → app.Invalidate()           （本契约 §2）
```

即：`lastApplied` 是**显示同步**机制，不是**通知**机制——它不参与
"何时重绘"的决策。

### 一条须与 §2.3 一致的前提

本节的同步算法成立的前提是「失效通知的并发安全 ≠ ViewModel 字段读写
的并发安全」（§2.3）：编辑器回写与外部改值若来自不同 goroutine，
同步由调用方负责。`lastApplied` 本身是 **View 状态**（UI 线程独占），
不跨 goroutine 共享。
