# 代码生成输出契约

- 状态：冻结
- 冻结日期：2026-10-18
- 关联需求：REQ-002
- 关联 ADR：ADR-0001
- 适用范围：`goxml generate`、Codegen、Analyzer、生成 Go 文件、用户自定义组件

## 1. 目标

代码生成器必须把 `.gxml` 编译为可审查、可重复、可直接参与 Go 构建的源码文件。输出契约必须保证：

1. 生成结果确定，同一输入不会因为时间、机器路径或遍历顺序产生差异。
2. 生成文件与用户手写代码严格分离。
3. 解析、分析、生成或校验失败时，已有生成文件保持不变。
4. 生成代码可重复执行，且不会产生重复声明或无主文件。
5. 导入、包名、符号名和文件路径都能被静态确定。
6. 增量缓存只用于提速，不能改变生成正确性。
7. 生成阶段不需要运行时 XML、CSS、模板或反射支持。

## 2. 输入与编译流水线

标准流水线为：

```text
发现 .gxml
  -> 确定 Go 包上下文
  -> Parser
  -> Def/Slot 编译期展开
  -> Analyzer 类型和绑定校验
  -> Codegen 生成 AST/源码
  -> go/format.Source
  -> 生成源码语法与包一致性校验
  -> 原子提交文件
  -> 更新 manifest 和增量缓存
```

任一步骤失败都不得提交新的生成文件。旧的生成文件只有在新结果完成全部校验后才允许被替换。

### 2.1 入口只接受已验证的语义 IR

Codegen 的公开入口签名为：

```go
// 位于 internal/compiler/codegen
func Generate(v *analyzer.VerifiedDoc, opts Options) ([]byte, error)
```

**不接收** `*contracts.DocumentIR`、`*analyzer.Result` 或任何未经验证的结构。

`VerifiedDoc` 的字段全部未导出，且只能由 `(*analyzer.Result).Verified()`
在下列条件**同时**成立时构造（见 `Analyzer输入输出契约.md` §6.10）：

- `Status == StatusOK`
- `len(Diags) == 0`
- `Doc != nil` 且 `Facts != nil`

因此 `StatusPartial` / `StatusBlocked` 的结果在**类型层面**无法传入 Codegen。

### 2.2 门禁由两层共同承担，缺一不可

| 层 | 职责 | 能保证什么 |
|---|---|---|
| **类型入口**（Codegen 签名） | 拒绝未验证的 IR | 编译期无法把 `Partial`/`Blocked` 传进来 |
| **编排层**（编译管线驱动） | 决定是否调用 Codegen、是否提交产物 | 失败时**不产生任何文件** |

两者不可互相替代：

- 只有类型入口，无法保证编排层不绕过它去写文件；
- 只有编排层检查，无法防止有人直接构造 IR 调用 Codegen。

> **验证状态**：类型入口已随 Analyzer 实现（`Verified()` 有测试）；
> **编排层门禁尚未验证**——Codegen 与编排层都不存在。在两者落地并有
> 实测前，不得声称「失败不会产生产物」已验证。

### 2.3 失败语义

| 情况 | 行为 |
|---|---|
| 未取得 `VerifiedDoc` | 不调用 Codegen，不写任何文件 |
| Codegen 内部出错 | 返回 error，**不返回部分代码** |
| 格式化或包一致性校验失败 | 丢弃本次结果，旧文件保持不变 |

「不返回部分代码」是硬要求：若允许返回不完整的字节流，
调用方可能误写出去，从而破坏「失败不覆盖旧产物」的保证。

## 3. 输出路径与文件命名

### 3.1 默认路径

每个 `.gxml` 默认在同一 Go 包目录生成一个同名文件：

```text
ui/dashboard.gxml -> ui/dashboard_gen.go
```

生成文件名规则固定为：

```text
<source-base>_gen.go
```

生成文件必须包含标准保护头：

```go
// Code generated by goxml. DO NOT EDIT.
// Source: ui/dashboard.gxml
// Goxml-Version: 1
```

`Source` 使用项目相对路径，统一使用 `/`，禁止写入绝对路径、机器用户名和时间戳。

### 3.2 输出目录

- 默认输出目录是 `.gxml` 文件所在目录。
- `--out-dir` 可以指定输出根目录；批量生成时必须保持输入相对路径结构。
- 输出目录必须属于当前 Go module，且能够解析为一个明确的 Go package。
- 如果输出目录存在多个非测试 package，生成失败。
- 如果输出目标已存在但没有 Goxml 生成保护头，生成失败，绝不覆盖用户文件。

## 4. Go 包与生成符号

### 4.1 包名

GXML 不声明 Go `package`。生成器从目标目录的 Go 源码或 `go/packages` 结果确定包名，并原样写入生成文件。

如果目录没有可识别的 Go package，必须报告错误并要求用户先初始化目标 package；不得猜测包名。

GXML 根节点的 `Package` 不属于 v1 语义。`DocumentIR.Package` 如需保留，只能表示生成上下文。

### 4.2 生成符号

页面根类型和构造函数根据源文件相对路径生成：

```go
type GoxmlDashboardView struct { /* generated state */ }

func NewGoxmlDashboardView() *GoxmlDashboardView
```

符号名规则：

1. 取源文件相对 package 目录的路径。
2. 每个路径段转为 PascalCase。
3. 非 Go 标识符字符转换为 `_`。
4. 以 `Goxml` 前缀避免与用户常规类型冲突。
5. 如果仍与同包符号冲突，生成失败并报告冲突来源，不静默改名。

例如：

```text
ui/settings/dashboard.gxml
-> GoxmlUiSettingsDashboardView
-> NewGoxmlUiSettingsDashboardView
```

### 4.3 页面 API

包含 `ViewModel` 的页面生成：

```go
func (v *GoxmlDashboardView) Layout(
	gtx layout.Context,
	th *material.Theme,
	vm *demo.ViewModel,
) layout.Dimensions
```

不包含 `ViewModel` 的静态页面生成：

```go
func (v *GoxmlDashboardView) Layout(
	gtx layout.Context,
	th *material.Theme,
) layout.Dimensions
```

构造函数只创建组件状态，不执行布局、不启动 Goroutine、不触发系统 I/O。

#### 4.3.1 为什么必须有主题参数

本节原冻结形态没有 `th` 参数，与 `字体与文本渲染策略.md` §6.2 存在冲突：那里规定
生成代码「只通过主题引用字体：`th.Fonts.Family`」——但 `th` 不在作用域内，无法成立。

渲染文本在 Gio 中必须经由主题（`material.Body1(th, ...)` 需要 `*material.Theme`），
因此主题是**布局的必要输入**，不能省略。

选择「作为 `Layout` 参数」而非「存进 View 结构」，理由：

| 方案 | 问题 |
|---|---|
| 存进 View（构造函数接收主题） | 切换主题需要重建整个 View，与其状态生命周期耦合；Gio 的惯例是逐帧传入 |
| **作为参数（本契约）** | 与 Gio 惯例一致；主题可逐帧变化；View 只持有自身状态 |

#### 4.3.2 参数类型固定为 `*material.Theme`

生成代码依赖的主题类型是 **Gio 的 `material.Theme`**，不是项目自有的主题封装。

理由：

1. **最大化稳定性**：`pkg/runtime/theme` 是面向使用者的便利层（字体探测、fallback 链、
   颜色语义），它会演进；而 `material.Theme` 是 Gio 的稳定 API。生成代码依赖后者，
   项目主题的演进不会改变已生成代码的签名。
2. **不泄漏字体细节**：`material.Theme` 携带字体集合，满足 §13 第 19 条
   「生成代码不包含字体路径、字号常量或 `text.Shaper` 构建逻辑」。
3. **不引入反向依赖**：生成代码只依赖 `gioui.org/*`，不依赖 `pkg/runtime/*`，
   避免「用户代码 → 生成代码 → 运行时包」的循环。

项目主题（`pkg/runtime/theme.Theme`）若要参与，由使用者取出其中的 `*material.Theme`
后传入，**不修改本签名**。

### 4.4 生成器入口与 `Options`

```go
// 位于 internal/compiler/codegen

// Options 是生成所需的全部外部输入。
//
// Codegen **不读取磁盘、不加载包**：它只消费已通过校验的语义 IR 和
// 调用方提供的上下文。包名与源路径由编排层确定后传入。
type Options struct {
	// PackageName 是生成文件的 package 子句。
	//
	// 由调用方按 §4.1 从目标目录的 Go package 解析得到。
	// Codegen 不推导、不猜测；为空时生成失败。
	PackageName string

	// SourcePath 是 .gxml 相对目标包目录的路径（如 "ui/dashboard.gxml"），
	// 用于按 §4.2 推导符号名。
	SourcePath string
}

// Generate 生成单个 Go 源文件。
//
// 成功时返回已格式化的源码；失败时返回 error 且**不返回部分代码**。
// 不写文件——写入与原子替换由编排层负责（§9）。
func Generate(v *analyzer.VerifiedDoc, opts Options) ([]byte, error)
```

`Options` 与 §4.1 的分工：§4.1 约束包名的**来源**（不得猜测），`Options` 只是
**传递通道**。两者不矛盾——猜测发生在 Codegen 里才是被禁止的。

### 4.5 最小纵向切片的结构

首个实现只覆盖 `<Page>` + 单个静态 `<Text>`，用于打通「IR → 源码 → 可编译」链路。

输出形态（`SourcePath = "dashboard.gxml"`，`PackageName = "demo"`）：

```go
// Code generated by gxml. DO NOT EDIT.

package demo

import (
	"gioui.org/layout"
	"gioui.org/widget/material"
)

// GoxmlDashboardView 是 dashboard.gxml 的生成视图。
type GoxmlDashboardView struct{}

// NewGoxmlDashboardView 创建视图状态。
func NewGoxmlDashboardView() *GoxmlDashboardView { return &GoxmlDashboardView{} }

// Layout 渲染页面。
func (v *GoxmlDashboardView) Layout(gtx layout.Context, th *material.Theme) layout.Dimensions {
	return material.Body1(th, "Hello").Layout(gtx)
}
```

约束：

| 项目 | 规则 |
|---|---|
| 文件数 | 单个 Go 源文件 |
| 保护头 | `// Code generated by gxml. DO NOT EDIT.` 后空一行 |
| 符号 | `Goxml<Path>View` / `NewGoxml<Path>View`（§4.2） |
| import | 按 §7：只为实际使用的符号生成，去重、确定性别名、AST 校验 |
| 格式化 | 一律经 `go/format.Source` |
| 写入 | **不写文件**，只返回 `[]byte` |

### 4.6 最小切片明确不做的事

- 数据绑定与类型转换
- 事件处理
- `<For>`、Grid 及其他布局
- 生成文件的磁盘写入与原子提交
- CLI 与完整编排
- 为未来功能预留的模板/插件体系

这些留给后续切片。提前设计会在真正需要时被推翻。

## 5. 用户代码与生成代码隔离

- 用户逻辑只能写在普通 `.go` 文件中。
- 生成文件只能包含编译器输出，不接受手工扩展点。
- 生成文件中的声明使用 `Goxml` 前缀和源路径派生名称。
- `goxml generate` 不修改、格式化或移动用户手写 `.go` 文件。
- 业务状态、事件方法和平台调用由用户代码或运行时 API 提供。
- 生成代码不得通过 `go:linkname`、反射或字符串查找调用用户逻辑。

## 6. 确定性输出

同一以下输入必须产生逐字节一致的生成结果：

- `.gxml` 文件内容。
- 所有被引用的 `<Def>` 内容。
- 目标 Go package 的类型和组件声明。
- Goxml 编译器版本。
- CLI 选项和输出上下文。

生成器必须遵守：

- 节点、属性、事件、绑定和导入按稳定规则排序。
- 不写入时间戳、随机数、绝对路径和进程信息。
- 使用 `go/format.Source` 最终格式化。
- 同一个输入重复生成时，不应产生无意义文件修改。
- Golden 测试比较完整生成文件，而不是只比较片段。

## 7. Import 处理

Codegen 只为实际使用的符号生成导入：

1. 按导入路径去重。
2. 读取 Go package 的真实默认包名。
3. 包名无冲突时使用默认名。
4. 包名冲突时按导入路径字典序分配确定性别名：`pkg`、`pkg_2`、`pkg_3`。
5. 导入路径和别名都必须经过 Go AST 校验。
6. 最终源码必须经过 `go/format.Source`。

用户手写文件中的 import 不影响生成文件；每个 Go 文件拥有独立的 import 区域。

## 8. 用户自定义组件注册

### 8.1 GXML Def

`<Def>` 是 v1 的首选自定义组件机制。它在编译期展开，不产生运行时注册表：

```xml
<Def Name="UserCard" Props="Name:string">
  <Column>
    <Text Value="{Name}"/>
    <Slot/>
  </Column>
</Def>
```

`Def` 名称、属性和插槽由 Analyzer 校验，展开结果直接进入 Codegen。

### 8.2 Go 自定义组件

需要保留独立 Go 绘制逻辑时，使用编译期注解注册，不使用运行时注册表：

```go
//goxml:component tag=UserCard props=UserCardProps
type UserCard struct{}

func (UserCard) Layout(
    gtx layout.Context,
    props UserCardProps,
    slot func(layout.Context) layout.Dimensions,
) layout.Dimensions {
    // user implementation
}
```

规则：

- `tag` 必须是唯一的 PascalCase 标签名。
- `props` 必须指向可由 Go 类型系统解析的 struct。
- Props 字段必须是导出字段，并与 GXML 属性完成静态类型匹配。
- `slot` 为空时表示调用方没有子节点。
- 注解只参与编译期发现和直接调用，不创建运行时注册表。
- 同一个 tag 不能同时被 `<Def>` 和 Go 组件声明。
- Go 组件必须位于目标 package，外部 package 通过目标 package 中的薄包装类型接入。

组件解析顺序固定为：内置标签 -> 当前文档 `<Def>` -> 当前 Go package 的 `goxml:component`。

## 9. 失败保护与原子提交

生成过程必须采用临时文件和原子替换：

1. 在内存中完成解析、分析、生成和格式化。
2. 写入目标目录下的临时文件。
3. 重新读取临时文件并执行 Go parser 校验。
4. 可选执行 package 类型校验或构建检查。
5. 校验成功后原子替换目标生成文件。
6. 更新 manifest。
7. 清理临时文件。

以下任一情况发生时，旧生成文件必须保持不变：

- GXML 解析失败。
- 绑定或组件分析失败。
- Go 源码格式化失败。
- import 或 package 校验失败。
- 磁盘写入失败。
- 构建检查失败。

错误分类至少包括：

- `CODEGEN-PACKAGE-*`
- `CODEGEN-NAME-*`
- `CODEGEN-IMPORT-*`
- `CODEGEN-OUTPUT-*`
- `CODEGEN-CHECK-*`
- `CODEGEN-IO-*`

## 10. Manifest、清理与孤儿文件

生成器在项目根目录维护：

```text
.goxml/generate-manifest.json
```

Manifest 记录：

```json
{
  "version": 1,
  "entries": [
    {
      "source": "ui/dashboard.gxml",
      "output": "ui/dashboard_gen.go",
      "inputHash": "...",
      "compilerVersion": "..."
    }
  ]
}
```

规则：

- 默认 `generate` 不删除任何文件。
- `generate --clean` 只删除 manifest 中登记且仍带 Goxml 保护头的文件。
- 未登记文件、无保护头文件和用户文件永远不删除。
- Source 被删除后，只有 `--clean` 才清理对应生成文件。
- Manifest 本身损坏时，生成失败并保留现有生成文件。

## 11. 增量生成与缓存

缓存目录为：

```text
.goxml/cache/
```

缓存键至少包含：

- 当前 `.gxml` 内容。
- 传递引用的 `<Def>` 内容。
- 目标 Go package 的相关源码或类型指纹。
- 编译器版本。
- CLI 选项。
- 输出 package 路径。

缓存命中必须同时满足：

1. 输入哈希完全一致。
2. 目标生成文件存在。
3. 目标文件保护头和 Source 一致。
4. Manifest 记录一致。

缓存命中时可以跳过写文件，但不能跳过必要的错误诊断。缓存可以通过 `--no-cache` 禁用，删除缓存不会改变生成结果。

## 12. CLI 行为

推荐命令：

```text
goxml generate <path>
goxml generate <path> --check
goxml generate <path> --clean
goxml generate <path> --no-cache
```

- `generate`：生成并执行源码级校验。
- `--check`：在生成结果提交前执行 package 类型检查或构建检查。
- `--clean`：按 Manifest 清理已登记的孤儿产物。
- `--no-cache`：忽略增量缓存但仍更新 Manifest。
- 失败退出码必须非零。
- 成功但没有变更时仍返回零，并输出明确的 skipped 状态。

## 13. 验收测试

实现必须覆盖：

1. 同一输入连续生成两次，文件内容和 SHA-256 完全一致。
2. 生成文件包含保护头、Source 和版本信息。
3. 用户手写同名文件不会被覆盖。
4. 包名能从目标目录正确解析。
5. 包名缺失或冲突时返回明确错误。
6. import 重名时生成稳定别名。
7. `<Def>` 展开不产生运行时注册代码。
8. Go 自定义组件注解能被 Analyzer 发现并直接调用。
9. 解析、分析、格式化或构建失败时旧文件保持不变。
10. `--clean` 只删除 Manifest 登记的生成文件。
11. Manifest 损坏时不会删除文件。
12. 缓存命中不修改文件时间和内容。
13. `--no-cache` 生成结果与缓存生成结果一致。
14. 生成源码通过 Go parser、gofmt 和 package 检查。
15. 生成代码不包含 `import "reflect"`。
16. 静态子树被展开为直接调用，生成源码包含对应 `op.CallOp` 缓存字段（无每帧新建闭包）。
17. 启用 `Virtualize="true"` 的 `<For>` 生成虚拟化代码，未启用时与基线输出逐字节一致。
18. 稳定帧 `allocs/op == 0`（静态页面），万行虚拟列表单帧 ≤ 1ms。
19. 生成代码不包含字体路径、字号常量或 `text.Shaper` 构建逻辑（字体由主题提供）。
20. **编排层门禁**：用 `StatusPartial` 与 `StatusBlocked` 的输入各跑一次完整管线，
    断言 Codegen **未被调用**且工作目录中**没有产生任何文件**。

    这条不能用手动调用 `Verified()` 的单元测试代替——后者只验证 API 拒绝，
    不验证管线是否真的停在生成之前（见 §2.2 的两层职责）。

    注意：第 20 条在编排层与 Codegen 落地前**无法执行**。在此之前只能标注
    「设计已定义、实现待完成」，不得标记为通过。

## 14. 版本演进边界

以下变更必须进入新的 ADR：

- 改变生成文件命名或生成 API。
- 改变用户组件注册注解或方法签名。
- 改变 Manifest 格式。
- 改变失败保护和清理规则。
- 引入运行时组件注册、反射或动态模板。

v1 的 CLI、Codegen 和发布流程必须以本文件为输出行为唯一依据。

## 15. 生成代码的性能约束

除正确性外，生成输出必须满足以下性能要求（阈值与实测依据见 `docs/03-架构/性能预算与优化策略.md`）：

### 15.1 静态子树固化

不含绑定、事件、条件、循环的子树，必须展开为直接调用并生成 `op.Record`/`op.CallOp` 缓存槽位。禁止生成每帧新建的布局闭包。

理由：实测闭包方案 28,000 ns/op + 51 allocs/op，暴露为 2,550 ns/op + 0 allocs/op。

### 15.2 列表虚拟化

`<For>` 启用 `Virtualize="true"` 时，生成代码必须只对可见元素执行布局，不得遍历全部元素。决策见 [ADR-0006](adr/ADR-0006-列表虚拟化与静态子树宏固化.md)。

理由：实测 10,000 行全量渲染 6,438,000 ns/op + 10,010 allocs/op，虚拟化后 19,200 ns/op + 0 allocs/op。

### 15.3 文本节点

- 文本节点的 shaping 结果必须可缓存，绑定未变化时不得重录。
- 生成代码**禁止**在 `Layout` 内构造显示字符串（如 `fmt.Sprintf`）。组合文本必须由 ViewModel 字段或框架缓存提供。

理由：每帧变化字符串会击穿 shaping 缓存，实测 876 → 82,053 ns/op（94×），每帧 137KB 分配。

### 15.4 抽象开销

- 生成代码必须在节点层面使用具体类型调用。
- 禁止引入通用接口或反射型容器承载渲染节点。

理由：实测接口派发 361,000 ns/op vs 具体调用 61,000 ns/op（5.9×）。

### 15.5 字体

生成代码不包含字体路径、字号常量或字体集合构建逻辑。字体一律通过主题（`theme.Fonts`）引用，详见 `docs/03-架构/字体与文本渲染策略.md`。
