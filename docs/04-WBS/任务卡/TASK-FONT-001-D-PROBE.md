## 0. 定位：这是门禁，不是 D 的实现

本卡只回答一个问题：

> **后台 goroutine 调用 `Window.Invalidate()` 后，真实窗口的事件循环是否
> 可靠地产生后续 `FrameEvent`；在首帧前、首帧处理中、首帧后、突发重复、
> 关闭期间这五种情形下，是否出现丢帧、卡住或生命周期异常。**

不回答（明确排除，防止把范围做散）：

| 不做的事 | 归属 |
|---|---|
| 字体探测耗时、懒加载、首帧预算 | `TASK-FONT-001-D` 本体 |
| shaper 跨 goroutine 安全性 | 已由 `d7268e5` 的 `concurrencyprobe` 取证 |
| 帧内替换 `th.Shaper` | 已由 `d7268e5` 的 `lifecycleprobe` 取证 |
| 渲染正确性（像素比对） | codegen 离屏测试 |

**本卡不通过，`TASK-FONT-001-D` 的实现（§10 第 4 步）不得开工。**
理由：D 的核心机制是「后台加载完成后请求一次重绘」，该机制的唯一失效模式
就是"这次重绘请求丢了"。若丢了，懒加载实现了也表现为"加载完成后界面不更新"，
属于静默错误，比崩溃更难诊断。

### 1.1 环境可用性的判定方式（关键，防"假绿"）

探针**必须显式打印**本次是否真的产生了 `FrameEvent`：

- **0 帧** → 记录"环境阻塞"，本卡状态写 **BLOCKED**，
  **不得**把 Gio 源码注释（`app/window.go:284` "safe for concurrent use"）
  升级为通过证据。这是评审明确要求的边界。
- **≥1 帧** → 才允许进入 P1–P5 判定。

`go test` 在本仓库的相关用例里用 `t.Skip` 处理 0 帧（`state_e2e_cases_test.go:61`、
`app_test.go:116`），**skip 与 pass 在 CI 汇总里都是绿的**——所以本卡不用
`go test`，改用 `go run` + 显式退出码（0 通过 / 1 失败 / 3 超时或阻塞）。
这条差异本身就是本卡独立存在的理由之一。

## 3. 探针设计（冻结）

### 3.1 形态

单文件 `pkg/runtime/app/testdata/windowprobe/main.go`：

- 真实 `app.Window`，**一个 phase 一个全新窗口**（相互隔离，避免前一 phase
  的待处理帧污染后一 phase 的计数）；
- 主 goroutine 跑事件循环（与 `pkg/runtime/app/app.go:loop` 同构），
  driver goroutine 负责后台唤醒；
- 每个 phase 输出一行 `PHASE <id> PASS|FAIL <detail>`，供人工与脚本同时读；
- 退出码：`0` 全通过 / `1` 存在 FAIL / `3` 超时（卡住）。

### 3.2 判据表

| ID | 场景 | 动作 | 判据 | 失败意味着什么 |
|---|---|---|---|---|
| **P1** | 首帧**前**唤醒 | 窗口创建后、首次 `Event()` 之前连续 2 次 `Invalidate` | 不 panic、不阻塞；循环仍能产生 ≥1 帧 | 早期失效不能崩溃——`App.Invalidate` 的"安全丢弃"语义得靠它 |
| **P2** | 首帧**处理中**唤醒 | 第 1 个 `FrameEvent` 内 `sleep 30ms`，driver 在此期间 `Invalidate` | 2s 内出现第 2 帧 | 帧处理期间的请求被吞 → D 的"加载完成正好发生在一帧里"会丢更新 |
| **P3** | 首帧**后**（静默）唤醒 | 静默 300ms 无帧后 `Invalidate` 一次 | 2s 内出帧，且记录延迟 | 基本链路；同时给出延迟量级作 D 的参考 |
| **P4** | 突发重复唤醒 | 无间隔连发 50 次 `Invalidate` | (a) 500ms 内帧数 ∈ [1,50]；(b) **在最后一次 `Invalidate` 返回之后**仍出现新帧；(c) 随后单次唤醒仍出帧 | (a) 合并=允许，但不能 0 帧（全被吞）；(b) **最后一次唤醒丢失是致命错误**；(c) 突发事件后链路不僵死 |
| **P5** | 关闭期并发唤醒 | driver 每 1ms `Invalidate`，100ms 后 `Perform(system.ActionClose)` | 3s 内收到 `DestroyEvent`；无 panic；关闭后再 `Invalidate` 不 panic | 关闭与唤醒的竞态；若卡住，生产上表现为退出时挂死 |

### 3.3 判据的写法约束

- **P1 明确不判定"唤醒生效"**：Gio 的 `mayInvalidate` 零值为 false，
  driver 未创建时 `Invalidate` 会被静默跳过（源码依据）。因此 P1 只判定
  "安全 + 首帧仍会出现"，**不得**写成"首帧由 Invalidate 触发"。
- **P4(a) 用区间而非精确值**：合并次数取决于帧率、DPI、后端调度，
  不是确定的 1:1 或 1:N。承诺精确值等于把实现细节写进验收。
- 所有 phase 必须打印**实际数值**（帧数、延迟 ms），不接受只打印 PASS。

### 3.4 为什么不用 `go test`

| 原因 | 说明 |
|---|---|
| 0 帧环境会 `t.Skip`，而 skip 在汇总里是绿的 | 会把"没验"显示成"没问题" |
| 探针需要真实弹窗（5 个窗口，各约 1s） | 单元测试套件里弹窗不合适 |
| 需要在"帧处理过程中"插入 30ms 睡眠 | 在测试里是反模式，在探针里是必要手段 |

代价：本卡不能进 CI 自动门禁，只能手工执行并登记结果。**这一点如实登记，
不假装它是自动化门禁。**

## 5. 证据边界（不可外推，评审点名要求）

1. **单版本**：只在 Gio v0.10.3 上验证。`Invalidate` 的合并策略、`mayInvalidate`
   的时序都是实现细节，**升级 Gio 必须重跑本卡**（与 C 卡 `Glyph.ID`
   位布局的门禁同级别）。
2. **单平台单后端**：Windows D3D11。macOS（必须 `app.Main` 接管主线程）、
   X11/Wayland 的行为**未验证**，不得据此外推。
3. **无 `-race`**：本机缺 C 工具链，`-race` 不可用。"无 panic" ≠ "无数据竞争"。
   本卡给出的结论是**行为级**的（有没有丢帧、有没有卡住），不是**同步级**的。
4. **弹窗副作用**：执行时会在桌面短暂创建 5 个窗口（各约 1s）。
   这是真实窗口验证不可消除的代价，不是缺陷。
5. **P4 的区间与具体数值不可当承诺**：换机器/换 DPI/换显示器，合并次数会变。

## 6. 风险

| 风险 | 影响 | 处理 |
|---|---|---|
| 无交互式桌面 → 0 帧 | 全部 phase 无法判定 | 显式记录 BLOCKED，**不**降级为源码依据通过 |
| 帧处理中 `sleep 30ms` 过长触发后端卡死判定 | P2 假失败 | 30ms 远小于常见看门狗阈值（数百 ms）；若实测出现异常，记录实测值再调整，不直接放大 |
| 串行创建 5 个窗口受 DPI 缓存/首次创建开销影响 | P3 延迟读数偏大 | 记录每个 phase 的窗口创建耗时，P3 的读数单独看，不与 P1 混谈 |
| 探针进程被信号终止 | 结果不完整 | 逐 phase 输出（不缓冲到结尾统一打印），中断也能看到已完成的 phase |
