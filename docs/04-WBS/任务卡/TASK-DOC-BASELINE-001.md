## 1. 目标

建立一套经过事实审计、相互一致、可追踪且可复验的文档基线，为后续分批开发提供可靠入口。
本任务冻结的是文档基线，不代表产品功能全部完成，也不替代代码验收或发布验收。

## 2. 范围

### 允许

- 审计和修订工程文档、核对规范冲突、补齐需求到验收证据的追踪关系。
- 按任务依赖规划后续开发批次，明确每批的目标、前置条件、交付物、退出条件和排除项。
- 验证文档门禁；为验证其有效性，可单独修改文档检查脚本。
- 记录基线、门禁结果、人工审查结论、未决事项和验收证据。

### 脚本变更要求

任何文档检查脚本变更都必须记录变更范围、测试和回归证据，并提供负例证明门禁能检测目标问题。不得把门禁名称或绿色结果扩大解释为它未覆盖的人工判断。

### 排除

- 不扩展产品功能，不顺手重构或修复生产代码。
- 不以文档修订暗中改变尚未讨论或批准的架构决策。
- 发现代码问题时只登记独立任务，记录影响、优先级、依赖和后续归属；未经项目所有者另行批准，不在本任务中修复。

## 5. 退出门槛

以下项目必须全部通过，方可将本任务标记为完成：

1. 核心术语、接口和架构决策之间不存在未处理的规范冲突；争议有明确裁决，不以执行者自行取舍代替。
2. 每项 P0 需求均能追踪到适用规范、实现任务和可执行验收条件。
3. 文档准确区分已实现、已测试、已验收、未执行、执行失败和环境限制跳过。
4. 每项活跃任务均有任务卡；依赖关系无缺失且无循环。
5. Markdown 本地链接检查无断链。
6. 文档门禁的实测行为与仓库脚本、Makefile 和 CI 一致；未实现或显式失败的占位目标不计为通过。
7. 验收证据能够追溯到具体提交、执行环境、命令和结果。
8. 至少抽样核验一条完整链路：`需求 -> 架构契约/ADR -> 实现任务 -> 验收用例 -> 验收证据`。
9. 冻结报告记录自动检查结果、人工审查结论、基线提交、例外和允许带出的未决项。

允许带出的事项仅限当前环境无法验证的平台/真实 GUI 行为、尚未进入当前开发批次的功能或性能验证，以及有明确归属且不阻塞基线的非 P0 问题。任何影响 P0 承诺、接口正确性或冻结结论的未验证事项均阻塞退出。

## 6. 决策与变更规则

- 批次 0 的范围及 B0-01 至 B0-05 决议以沟通记录第 6 节为准。

- 任务范围外发现的代码问题另建任务卡；不纳入文档冻结的“允许带出项”而不留归属。

记录每项验证的提交、操作系统/环境、实际命令、退出码、结果和证据位置。未执行、失败、跳过和通过必须分别记录原因；环境限制跳过项必须关联后续任务和计划验证阶段。
