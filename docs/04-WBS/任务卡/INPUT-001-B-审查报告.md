## R2 lastApplied 与编辑器状态稳定性

### 核验过程

B 记录 I-05 的规则原文：
- View 持有 `lastApplied`；
- 绑定值 == lastApplied → 不 SetText；≠ → SetText 并更新；
- "lastApplied 同时记录是否来自用户回写：用户回写后 lastApplied=新值"。

### 发现

| # | 级别 | 问题 |
|---|---|---|
| **R2-1** | **阻断** | **lastApplied 的定义不完整**（审查清单挑战项 1 全部命中）：① 用户回写后 lastApplied 是否更新、更新成什么（Editor.Text() 还是回写方法的实参——两者在 MaxLen 截断/Filter 过滤下**可能不同**）；② SetText 后 lastApplied 更新的时机（Set 前还是 Set 后）；③ 外部更新与用户输入在同一帧的优先级未定义；④ 文本相同但光标不同——因为不调 SetText，光标天然保留，但这条**应写成显式规则**而非推导结论。四点缺任何一点，lastApplied 就只是字段名而非同步算法。 |
| R2-2 | 非阻断 | 时序五步（审查清单）中第 5 步「外部值变回先前值」依赖①的定义——若①用 Editor.Text()，回写后 lastApplied=用户文本，外部改回旧值 → 绑定值≠lastApplied → SetText ✓。若用实参，MaxLen 截断场景下两者不同 → 行为分叉。**必须在①中选定一个并给出理由**。 |

**R2-1 的建议修正方向**（供 B 修订，非最终裁决）：

```text
lastApplied := 最近一次成功应用到 Editor 的外部文本（= SetText 的实参）
更新时机 1：渲染时绑定值 != lastApplied → SetText(绑定值) → lastApplied = 绑定值
更新时机 2：用户 ChangeEvent 回写 → lastApplied = 绑定值*（*绑定值在该帧
            尚未包含用户新文本；下一帧绑定值若含之则相等）
同帧优先级：先处理事件轮询（用户回写改 vm），后渲染（读 vm）——
            单帧内顺序固定，无歧义
文本同、光标不同：不 SetText（光标保留）——写成显式规则
```

## R3 焦点/选区/IME 与稀疏同步

### 发现

| # | 级别 | 问题 |
|---|---|---|
| R3-1 | **阻断** | **`--check` 类比错误不存在，但轮询位置规则未声明适用**：事件契约 §2 冻结"轮询在 Layout 顶部"，但 Editor 的事件消费（`Update(gtx)`）**必须在 Layout 期间、Editor 自身位置附近调用**（Gio 的 editor.go:778 模式——Editor 事件与焦点/IME 状态依赖布局上下文），**不能**像 Button 一样提前到顶部。B 记录未声明 Input 的事件轮询**豁免**顶部规则——按现有契约字面实现会破坏焦点/IME。 |
| R3-2 | 非阻断 | IME 人工验收已标（I-08 分层表）✓；但"稀疏同步是 IME 正确性前提"这一定性应升级为**契约正文规则**（B 记录在 I-07 理由里，容易被当作背景说明）。 |

**R3-1 的建议修正方向**：Input 的事件消费跟随 `material.Editor(...).Layout(gtx)`（控件自身位置），轮询时机与 Button 不同——这是**控件类别差异**，需在事件契约中新增"控件自持事件"的类别（Editor 是第一个），并说明为什么它不适用顶部轮询。
