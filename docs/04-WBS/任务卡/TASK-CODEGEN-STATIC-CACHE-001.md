# TASK-CODEGEN-STATIC-CACHE-001：静态子树固化（`op.Record` / `op.CallOp`）

## 元信息

- 状态：**Done**（A1–A6 全部完成）| 优先级：P0 | 预计：4h | 实际：约 7h
- 依赖：TASK-CODEGEN-001（最小切片）
- 契约：`代码生成输出契约.md` §15.1（要求）、§4.7（容器结构）
- 决策依据：`ADR-0006` §2.1（静态子树判定标准）
- **关闭**：§15.1 的「未满足」状态

## 1. 为什么单独立项

多子节点生成（`§4.7`）与静态子树固化是两个**正交**问题：

| 问题 | 归属 |
|---|---|
| 容器如何排列子节点 | §4.7（结构） |
| 子树如何避免每帧重录 | 本任务（性能） |

捆在一起会让一个任务同时处理布局结构、子树识别、录制回放、失效条件四件事，
任何一环出错都难以定位。

## 2. 现状与缺口

Codegen 目前对所有输出都直接生成调用表达式，**不含任何缓存槽位**。实测：

```text
单个静态 <Text> 的生成结果：
  return material.Body1(th, "Hello").Layout(gtx)
  含 op.CallOp: false
  含 op.Record: false
```

按 ADR-0006 的判定标准，这个子树**完全符合静态子树条件**，因此当前的
不符合项是「实现落后于契约」，不是契约例外。

多子节点（§4.7.2）会引入 `layout.Rigid(func(...) ...)` 闭包，届时连
「不产生每帧闭包」也不满足。

## 2.1 A1/A2 已完成（2026-10-19）

设计决策与 Gio 语义验证已记录于
[`ADR-0009-静态子树固化机制.md`](../../03-架构/adr/ADR-0009-静态子树固化机制.md)。

**三项结论推翻了实现前的直觉推断**：

1. **`CallOp` 不能跨帧保存** —— 源 `Ops` 一旦 `Reset`，`CallOp` 立即失效并 panic
   （`slice bounds out of range`）。`op.Defer` 不能规避（它不复制数据）。
   → 缓存必须配套**专用的持久 `op.Ops`**，与每帧的帧 Ops 分离。
2. **`Flex` 内部已对每个 `Rigid` 子节点录制** —— 若生成代码再为子节点录制，
   会重复录制、性能更差。→ **只固化最外层静态边界**。
3. **`ops.Ops` 数据不可从包外观测** —— 无法用「字节数」「解码计数」验证回放，
   必须用 `headless` 离屏渲染 + 像素比对。

§3 的 8 个问题已在 ADR-0009 §A2 逐项给出结论。

## 2.2 A3 已完成（2026-10-19）

设计已升格为契约 [`代码生成输出契约.md` §16](../../03-架构/代码生成输出契约.md)，
共 8 个子节：判定边界、缓存所有权、录制时机、回放与失效、`renderKey` 构成、
嵌套与重复录制、静态动态边界、验收标准。

A3 期间补充三项实测，其中一项最容易漏：

**`CallOp.Add` 返回 void**，而 `Layout` 必须返回 `Dimensions`。
→ 缓存必须**同时保存布局尺寸**，不只是绘制指令。
`Constraints` 与 `Metric` 也因实测确认会改变结果而纳入 `renderKey`。

## 3. 必须搞清楚的问题（本任务的核心难点）

**静态子树固化不是「把闭包包进 `op.Record`」这么简单。** 以下每一项都需要明确契约：

| # | 问题 | 需要的结论 |
|---|---|---|
| 1 | 何时判定为静态子树 | 引用 ADR-0006 的 4 条标准，**不重复维护第二份定义** |
| 2 | 首次录制在何时发生 | 首帧？构造时？如何判定「首次」 |
| 3 | 缓存槽位存在哪 | View 结构体字段？其生命周期与 `Layout` 的调用关系 |
| 4 | 何时回放、何时重录 | 稳定帧只 `CallOp.Add`；什么变化会导致失效 |
| 5 | 失效条件 | 主题变化？尺寸约束变化？`renderContextKey` 包含什么 |
| 6 | 嵌套静态容器怎么办 | 内层已固化时，外层是否还要录制（避免重复录制） |
| 7 | 静态与动态混合 | 容器下部分子树静态、部分动态时的边界 |
| 8 | `op.Record` 与 `op.CallOp` 的实际语义 | 需要用测试确认，不能凭文档推断 |

### 3.1 已确认的 Gio 事实（实测）

- `layout.Flex.Layout` **内部已经对每个 `Rigid` 子节点调用 `op.Record`**
  （`flex.go` 中的 `macro := op.Record(gtx.Ops)`）。
- 因此「多子节点 + 固化」可能存在**重复录制**：Flex 自己录一次，
  生成的代码又录一次。这必须在设计时澄清，否则会得到更差的性能。

生成的 `<Text>` 视图已实现缓存闭环。契约 §16.8 的五项验收全部满足：

| # | 要求 | 证据 |

| 4 | key 变化正确重录 | `TestKeyChangesTriggerRerecord`：Constraints / Metric / Theme / Locale 分别变化均触发 |
| 5 | 生成确定性 | `TestCacheGenerationDeterministic` + `TestCacheImportsSorted` |

### 一个推翻测试方法的重要发现

最初用「`cacheCall` 是否变化」判断是否重录。**实测证明这不可靠**：

```text
cacheOps.Reset() 后重录相同内容 → CallOp 完全相同（start:9 end:192 一致）
```

因此 `cacheCall` 相同既可能是「回放了」，也可能是「重录了相同内容」。

改用 **`cacheKey` 是否被改写** 作为信号：回放分支根本不写 `cacheKey`，只有录制分支写。

`TestCacheCallIsNotARecordSignal` 专门锁定这个事实，防止后来者再犯。

## 3.3 A6a 单节点性能基线（2026-10-19）

在扩展 `<Column>` 之前先固定单节点基线，供后续判断嵌套缓存的额外成本。

**测量环境**：Windows amd64 / Go 1.26.1 / Gio v0.10.3 / `CGO_ENABLED=0` /
`-benchtime 200ms -benchmem` / 20 逻辑核（P）。

| 基准 | ns/op | B/op | allocs/op | 说明 |
|---|---:|---:|---:|---|
| `BenchmarkNoCache` | 643.6 | 3 | 0 | 对照组：每帧直接布局 |
| `BenchmarkFirstRecord` | 1720 | 1185 | 14 | 冷路径：新建 View + 首次录制 |
| `BenchmarkCacheHit` | **29.35** | **0** | **0** | 稳定命中：只 `CallOp.Add` |

**缓存命中比不缓存快约 21.9 倍**（29.35 vs 643.6 ns/op），且稳定帧零分配。

### 解读

- 「不缓存」的 643.6 ns/op 里，主要成本是文本 shaping 与布局计算——
  这些在命中路径被完全跳过。
- `FirstRecord` 的 1185 B/14 allocs 是**一次性**成本，摊销到 N 帧后趋近于零。
- 命中路径 0 B/0 allocs 满足契约 §15.1 与 §16.8 的性能要求。

### 这个基线的局限

**只代表单节点 `<Text>`，不能外推到嵌套容器。** `layout.Flex.Layout` 内部
已对每个 `Rigid` 子节点录制，嵌套场景的缓存边界与收益需要 A5/A6b 重新测量。

### 复现方式

```text
go test -run TestSingleNodeBaseline -v ./internal/compiler/codegen/
```

基准在临时模块中对**真实生成的代码**运行，不是测量生成器本身。

## 3.4 B1 `<Column>` / `<Row>` 多子节点（2026-10-19）

按契约 §4.7 实现。**只做结构，不调缓存边界**（缓存粒度评估留给 A5）。

### 实现要点

| 项 | 做法 |
|---|---|
| 生成形态 | `layout.Flex{Axis: ...}.Layout(ops, layout.Rigid(func(gtx) ...))` |
| 子节点顺序 | 严格按声明顺序遍历 `n.Children` |
| `Page` | 等价于垂直容器（规范 §3.1） |
| 嵌套容器 | 闭包内使用**闭包的 `gtx`**，不是外层 `rec` |
| 顶层容器 | 使用 `rec`（cacheOps），使录制发生在缓存 Ops 上 |

**一个实现细节**：`containerExpr` 需要 `ops` 参数区分顶层与嵌套。
顶层传 `rec`，嵌套传 `gtx`——否则内层的 `Rigid` 闭包会把绘制写进错误的 Ops。

### 运行时验证

| 测试 | 验证内容 |
|---|---|
| `TestColumnMultiChildRuntime` | 3 子节点 Column 在 Exact(200,300) 下返回 (200,300) |
| `TestNestedContainersRuntime` | Column 套 Row 的嵌套布局正确 |
| `TestMultiChildCacheReplay` | 多子节点下仍能正确回放 / 重录 |

### 兼容性

单节点生成结果**改变**了：`<Page><Text/></Page>` 现在也包一层垂直 Flex
（因为 Page ≡ 无 Gap/Padding 的 Column，契约 §4.7.1）。

这是契约要求的语义，不是回归。旧测试 `TestGenerateTextRendering` 已相应更新，
断言改为检查容器形态。

`Layout(gtx, th)` 签名未变。

### 明确未做

- 未调整缓存粒度（`Flex` 内部已录制 `Rigid` 子节点，外层再缓存是否重复录制——
  留给 A5 验证）
- 未实现 `Gap` / `Padding` / `Align` / `Justify` / 尺寸属性
- 未实现 `<Spacer>` / `<Expanded>` / `<If>` / `<For>` / `<Grid>`

## 3.5 A5 嵌套缓存验证（2026-10-19）

完整报告见 [`A5嵌套缓存验收报告.md`](../../06-测试/A5嵌套缓存验收报告.md)。

### 关键实测结果

| 场景 | 录制分支 | 叶子布局 | NoCache | CacheHit | 加速 |
|---|---:|---:|---:|---:|---:|
| 单节点 3 帧 | 1 | 1 | 688.9 ns | 30.37 ns | 22.7× |
| Column 3 子节点 | 1 | 3 | 1654 ns | 33.59 ns | 49.2× |
| Column 套 Row | 1 | 3 | 1685 ns | 29.00 ns | 58.1× |

### 三条结论

1. **回放不执行叶子布局**：3 帧中叶子只执行 3 次（全在首帧）。无重复工作。
2. **Ops 归属正确**：像素比对 681/681/681（直接 / 录制 / 回放）。
3. **命中时长几乎不随节点数增长**（30/34/29 ns）——回放的是同一份 CallOp，
   而 NoCache 随节点数线性增长（689→1685）。**节点越多收益越大。**

### 关于「Flex 内部也录制」

`layout.Flex.Layout` 确实对每个 Rigid 执行 `op.Record`/`Stop`。但这发生在
**录制阶段**（首帧），产物被外层大 CallOp 包住；稳定帧回放时内层 CallOp
作为录制内容的一部分被回放，**不重新执行**——叶子计数证明了这点。

因此「重复录制」只在首帧发生一次（构建操作列表的必然过程），不构成每帧开销。

### 决策：不改变缓存粒度

四类证据均支持保留当前实现。契约 §16 的缓存所有权与嵌套语义不变。

### 未验证

静态/动态混合边界（动态节点未实现）、>3 层嵌套、真实窗口帧时间。

## 3.6 A6b 性能基线归档与生成器基准（2026-10-19）

### 归档位置

基线数据已写入 [`性能预算与优化策略.md` §2.7](../../03-架构/性能预算与优化策略.md)，
含环境、命令、边界限制与成本构成。

**这是本项目第一次有可复现的缓存性能基线**——此前 ADR-0001 的 11×/5.9×
一直标注不可复现，因为仓库当时没有任何 `Benchmark`。

### 生成器基准

测的是**代码生成阶段**（Parser/Expander/Analyzer 开销不计入）：

| 输入 | ns/op | B/op | allocs/op | 产物 |
|---|---:|---:|---:|---:|
| 单节点 | 253,183 | 62,007 | 1,103 | 2,685 B |
| Column 3 子节点 | 382,443 | 73,763 | 1,339 | 3,046 B |
| 嵌套 | 509,810 | 77,654 | 1,428 | 3,189 B |

**成本构成分析**：单独测 `go/format.Source` 为 208,039 ns/op，
占 `Generate` 的约 **78%**。格式化是契约 §7 的强制要求，不是可优化项。

编译期数百微秒 vs 运行时每帧省 600+ ns——文件生成一次、渲染多帧，成本可忽略。

### 基准可复现性

- 循环内实际调用 `Generate` 并检查错误（避免测到快速失败）
- 输出写入 `genSink`，防止被优化掉
- 预热阶段验证产物非空
- 记录产物字节数

### 明确未做

未因基准结果调整任何缓存策略——A5 的四类证据已表明无需调整。

### 4.1 关于第 9 项的说明

字符串包含检查是**必要但不充分**的。真正的验收必须是：

- 首帧录制，第二帧**不重新录制**（计数断言，不是看代码）；
- 回放后的绘制结果与不缓存时一致（视觉/尺寸断言）；
- 稳定帧零分配（benchmark）。

## 5. 首个回归案例必须是单节点

按 ADR-0006 标准，**单个静态 `<Text>` 就属于静态子树**。

因此修复顺序是：

1. 单节点 `<Text>`（当前已存在的缺口）
2. 嵌套容器（`§4.7` 引入的新形态）

**不能只修新引入的多子节点代码**——那会留下「单节点仍不符合」的尾巴。

## 6. 明确不做

- 列表虚拟化（`<For Virtualize>`，属另一个任务）
- 绑定/事件的增量重录（依赖绑定实现，尚未开始）
- 跨帧的全局缓存（超出单页范围）

## 7. 风险

| 风险 | 说明 |
|---|---|
| 重复录制 | Flex 内部已录制，生成代码再录会劣化性能。需实测对比 |
| 失效判定过粗 | 主题或约束变化未纳入 key，会导致画面不更新 |
| 失效判定过细 | 每帧都重录，等于没优化 |
| 与 §4.7 耦合 | 容器结构变化会影响固化粒度，两任务需协调 |
