# TASK-EVENT-PAYLOAD-001：事件载荷的通用生成能力

## 元信息

- 状态：**Todo（契约已冻结，实现未开始）** | 优先级：P1
- 依赖：`TASK-BINDING-IMPLEMENT-001`（Facts 体系）、`TASK-CODEGEN-001`
- 被依赖：`TASK-INPUT-001` 的 D4（Input 事件生成**必须**等本卡通过独立验收）
- 规范依据：
  [`事件处理输出契约.md`](../../03-架构/事件处理输出契约.md) §5.4、
  [`Input输出契约.md`](../../03-架构/Input输出契约.md) §4
- 关联需求：REQ-002

## 1. 目标

把「事件载荷 → 生成代码实参」做成**通用 Codegen 能力**，而不是 `<Input>` 的
专属分支。`<Input>` 是第一个消费者，不是唯一一个。

## 2. 范围（冻结）

### 2.1 载荷来源：Schema 声明 + Mapping（**不是事件名特例**）

```text
ResolvedEvent.Payload   []ResolvedParam   ← Schema 的 EventSchema.Params
ResolvedEvent.Mapping   []ParamOrigin     ← 每个方法形参来自载荷还是调用点实参
```

- 载荷的存在与类型由 **Schema 声明**决定；
- 生成时**不得**按事件名（如 `ValueChanged`）或控件类型（如 `Input`）分支——
  那是特例实现，第二个带载荷控件就要复制一遍；
- `Mapping` 决定实参顺序：载荷在前、调用点实参在后（既有契约 §8.4 R1，
  Analyzer 已实现）。

### 2.2 事件分派：由已解析的事件声明决定，不允许隐式回退

| GXML 声明 | 运行时事件源（控件侧提供） | 生成 |
|---|---|---|
| `ValueChanged="M"` | `widget.ChangeEvent` | `v.vm.M(<载荷表达式>)` |
| `Submit="S"` | `widget.SubmitEvent` | `v.vm.S(<载荷表达式>)` |

- 两条路径**独立**：只声明 `Submit` 时不生成 ChangeEvent 处理；反之亦然；
- **不允许**「没声明 ValueChanged 就退回到 Submit」这类隐式回退。

### 2.3 v1 载荷数量上限：1

- 一个事件最多 **1 个载荷参数**；
- 多个载荷参数由 Analyzer 报 `GXML-EVENT-004`（数量不匹配），**Codegen 不重复诊断**。
  【项目证据】`EventSchema.Params` 当前均不超过 1 项；数量校验路径已存在。

### 2.4 责任划分（冻结）

| 角色 | 职责 | 不得做 |
|---|---|---|
| **控件侧**（Codegen 的控件分支） | 为每个已声明事件提供**一个 Go 表达式**表示该事件的载荷值 | 不得自行拼装完整调用、不得判断 `Mapping` |
| **Codegen 通用层** | 按 `Mapping` 组装实参列表，生成方法调用 | **不得**重复诊断载荷类型/数量错误 |
| **Analyzer** | 载荷与形参的数量、类别兼容、无返回值 | — |

控件侧义务的具体形状（不规定 Go 结构体，只规定语义）：

```text
输入：事件名 + 该事件的运行时事件值
输出：一个可内联到调用实参位置的 Go 表达式字符串
示例（Input）：
  ChangeEvent  → <Editor 当前文本表达式>
  SubmitEvent  → <该 SubmitEvent 的 Text 字段>
```

### 2.5 失败边界（不重复诊断）

| 情形 | 归属 | 码 |
|---|---|---|
| 载荷数量与形参数不符 | Analyzer | `GXML-EVENT-004` |
| 载荷类别与形参不兼容 | Analyzer | `GXML-EVENT-006` |
| 方法有返回值 | Analyzer | `GXML-EVENT-007` |
| 声明了 Schema 未定义的事件名 | Expander | `GXML-EVENT-002` |
| **Codegen** | 能走到生成阶段的载荷必然已校验 | **不报载荷错误** |

Codegen 只在**内部一致性被破坏**时 panic 或报内部错误（如 `Mapping` 长度
与形参数不符——那是 Analyzer 的缺陷，不是用户错误）。

## 3. 独立测试要求（冻结）

**必须不依赖 `<Input>` 即可测试**——否则无法先于 Input 交付。

| # | 测试 | 断言 |
|---|---|---|
| 1 | 零参数方法（`Click` 形态，无载荷） | 生成 `v.vm.M()`，无载荷实参 |
| 2 | 单载荷参数（由注入的载荷表达式提供） | 生成 `v.vm.M(<注入表达式>)` |
| 3 | 载荷 + 调用点实参 | 顺序为「载荷在前、实参在后」 |
| 4 | 两个不同事件映射到两个不同方法 | 各自独立生成，无隐式回退 |
| 5 | `Mapping` 长度与形参数不符 | Codegen 报**内部错误**（不伪装成用户诊断） |

测试载体：构造 `ResolvedEvent`（Facts 层），注入载荷表达式，断言生成的
调用形态；**不需要真实控件**。

## 4. 排除

- 不实现任何具体控件的事件；
- 不扩展多载荷参数；
- 不改 Analyzer 的校验逻辑（已完整）；
- 不引入表达式运算。

## 5. 退出条件

1. §3 的 5 项独立测试全部通过；
2. 生成的调用形态可编译（在仓库内临时包验证）；
3. `Mapping` 不一致时明确报内部错误，不静默生成错误代码；
4. 不修改 `<Button>` 的既有生成结果（回归）；
5. 六道门禁通过。

## 6. 与 `TASK-INPUT-001` 的关系

```text
TASK-EVENT-PAYLOAD-001（本卡）──独立验收通过──→ TASK-INPUT-001 D4 才可开始
```

且失去独立验收的可能。
