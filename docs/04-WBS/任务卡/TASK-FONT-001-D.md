## 0. 定位：D 不是「把字体加载丢进 goroutine」

架构评审（2026-10-21）明确：D 的核心目标是**确保字体探测与加载不阻塞首帧，
同时不破坏字体选择、诊断和布局的一致性**。单纯丢进 goroutine 会同时引入
三个新问题——首帧用什么字体、什么时候换、换了之后布局会不会跳——
而这三个问题**都必须有实测**，不能凭 API 名称推断安全性。

本卡冻结的就是这三个问题的答案与验收方式。

## 1. 两个预算必须分开计量（评审要求，勿合并）

| 预算 | 含义 | 来源 |
|---|---|---|
| **探测预算** | 系统字体探测耗时 | 规范 §3.2「字体加载耗时 ≤ 20ms（冷启动内）」 |
| **首帧预算** | 从进程启动到第一帧呈现的耗时 | D 的目标 |

二者**不是**同一件事，也不互相蕴含：

- 探测 < 20ms **不等于**首帧不阻塞（shaper 构建、首次 shaping 可能仍在关键路径上）；
- 探测 > 20ms **也不必然**违反首帧目标——只要首帧**不等待**探测即可。

因此 D1 分别测量，D6 分别验收。**不得用其中一个的达标冒充另一个达标。**

## 2. D1 基线实测（2026-10-21，Windows / amd64 / Go 1.26.x / Gio v0.10.3）

探针：`pkg/runtime/theme/testdata/coldstartprobe`（`testdata/` 不参与 `./...`）。
环境：`CGO_ENABLED=0`，系统命中 `msyh.ttc`，C 已落地。

| 阶段 | 冷（首次进程） | 进程内重复 | 说明 |
|---|---|---|---|
| `ResolveWithReport`（系统探测 + 覆盖判定） | **97.4 / 109.1 ms** | 81–101 ms | **每轮都重扫，无缓存** |
| `text.NewShaper`（系统字体索引） | **38.5 ms** | ~0.5 ms | 首次建索引写磁盘缓存，之后读缓存 |
| 首次 shaping（10 字符） | **53.7 ms** | 36–50 ms | **per-shaper 冷启动，热轮不下降** |
| **小计** | **~190 ms** | ~128 ms | — |
| 嵌入 `Load` + `ParseCollection` | 1.49–1.68 ms | — | 与 B 实测 1.58 ms 一致 |
| `NewShaper(NoSystemFonts())` | ~0 s | ~0 s | 完全不碰系统字体 |

三条直接影响设计的读数：

1. **探测 97–109 ms 已远超 20 ms 预算**——这正是 D 的动因，且它**没有**
   Provider 层缓存可依赖（每轮新建 Provider 都重扫）。
2. **首次 shaping 41–53 ms 是 per-shaper 的，且热轮不下降**。
   → D3「加载完成后换成真字体」会**重新付一次**这个成本，必须计入验收，
   不能只看"后台加载完成了"。
3. **零值 `&text.Shaper{}` 首次使用会同步建系统字体索引（38.5 ms）**。
   → 「首帧先用零值 shaper 顶着」**完全不能**省掉开销，等于没懒加载。
   首帧的临时 shaper **必须显式 `NoSystemFonts()`**（见 §5.2）。

> ⚠️ 本轮**未测到真实首帧**（那需要窗口环境）。上表最末一步是 shaping。
> 真实首帧数值列为 D2 的第一个待办，不得用 shaping 时长冒充首帧时长。

## 3. D2：冻结加载状态机

```
            ┌──────────┐
            │ Unloaded │  构造完成，未做任何 IO（规范 §3.3）
            └────┬─────┘
                 │ 首次请求 / 首帧
                 ▼
            ┌──────────┐
            │ Loading  │  后台 goroutine 探测 + 解析
            └────┬─────┘
          ┌──────┴──────┐
          ▼             ▼
     ┌─────────┐   ┌─────────┐
     │  Ready  │   │ Failed  │
     └─────────┘   └────┬────┘
          ▲             │ 显式请求重试（唯一入口）
          └─────────────┘
```

语义（逐条冻结，实现不得自行选择）：

- **Unloaded → Loading**：构造**不**做 IO。首帧请求拿到的是**临时字体**（§5.2），
  不是"等待加载完成"。
- **并发首次请求必须合并**：N 个并发请求只允许触发**一次**加载；
  所有在 `Loading` 状态下到达的请求都**立即返回临时字体，不等待同一结果**。
  加载完成后由 `Invalidate` 驱动后续帧取得真字体。用计数器可测（沿用 B 的 `countingLoader` 手法）。
- **Loading 期间重复请求 → 立即返回临时字体**（已冻结）。
  - **不等待**加载完成——等待会把"不阻塞首帧"退化成"阻塞，只是换了个地方等"；
  - **不重复触发**加载（与上一条的合并语义一致）；
  - 拿到临时字体的调用方通过后续 `Invalidate` 得到真字体，无需自己轮询。
- **Failed 后 → 不自动重试，只由显式请求触发重试**（已冻结）。
  - **不做后台轮询、不做每帧重试、不设自动退避重放**；
  - 重试的唯一入口是调用方显式发起（显式调用重试，或显式 `Invalidate` 后重新请求）；
  - 失败态**不缓存成功态**（失败就是失败，不得被读成可用），
    但也不得演变成"每次请求都自动重试一次"的隐式行为。

> **为什么选"立即返回 / 不自动重试"这一组**
>
> 两者是同一条原则的两面：**调用方永远不该为一个它没主动要求的加载等待或付代价。**
> "Loading 期间等待"会让首帧不阻塞的成果在第二个调用点被抵消；
> "失败自动重试"则把一个已明确报告的失败重新变成周期性后台工作，
> 且与 §6 D5 的要求冲突——失败必须在诊断里保持可见，
> 而自动重试倾向于把失败重新藏进"也许下次就好了"。
> 需要重试的场景由调用方决定，它需要的信息（失败原因）由 `Diagnostics()` 提供。

## 4. D3：不阻塞首帧

### 4.1 失效机制（依据 Gio v0.10.3 源码，非推断）

- `app/window.go:284` `func (w *Window) Invalidate()`，
  注释原文：**"Invalidate is safe for concurrent use."**
- 同段注释：**"intended for externally triggered updates, such as a response
  from a network request"** —— 正是异步加载完成的场景。
- `op.InvalidateCmd{At: time.Time}`（零值 = 立即重绘）用于帧内请求重绘。
- `material.Theme.Shaper` 是 `*text.Shaper`（`widget/material/theme.go:39`）。
- Gio 要求**每个顶层窗口有独立的 Theme/Shaper**
  （`widget/material/theme.go:36-37` 注释）。
- `text.Shaper` 内部有 map 缓存，**跨 goroutine 布局会 panic**
  （`text/shaper.go:210-216` 注释）。

### 4.2 加载期间的字体（评审问题 2）

候选与实测代价：

| 方案 | 首帧代价 | 问题 |
|---|---|---|
| (a) 零值 `&text.Shaper{}` | **38.5 ms**（冷） | 仍同步索引系统字体，**等于没懒加载**，否决 |
| (b) `NoSystemFonts()` + 内置 gofont（拉丁） | ~0 s | 中文/日文全部 notdef；换成真字体后**文本宽度变化** |
| (c) `NoSystemFonts()` + 嵌入子集 | ~1.5 ms（解析） | 中文可见；系统命中时仍会有一次度量变化 |
| (d) 首帧不渲染文本（占位） | ~0 s | 最保守、无跳动，但首帧无内容 |

**冻结决策：取 (c)**。理由：首帧代价可接受（1.5 ms）、中文**不是豆腐块**，
且与「最终可能就是嵌入兜底」的终态一致，跳动幅度小于 (b)。
(b)/(d) 留作备选，若 (c) 的跳动实测不可接受再评估。

**强制验收**：**文本宽度变化导致的控件跳动必须有测试覆盖**（D6）。
不允许以"跳动是正常的"为由跳过——评审点名的就是这一项。

## 5. D4：避免竞态（评审问题 1）

**冻结为「帧内替换」模型，禁止后台直接替换 shaper**：

1. 后台 goroutine 只做探测/解析，**不触碰** `th.Shaper`；
2. 完成后把结果写入受保护的位置（互斥量或 channel），然后
   `w.Invalidate()`（并发安全，且正是 Gio 为此设计的入口）；
3. 在**下一帧 `FrameEvent` 处理内**——即窗口事件循环的**同一个 goroutine**——
   完成 `th.Shaper` 的替换。

理由：替换与渲染因此**永不同时发生**，绕开 `text.Shaper` 非并发安全的限制，
也不需要给渲染路径加锁。

**不在共享对象里原地更新字体集合**：`text.Shaper` 的集合只在构造时由
`WithCollection` 给定，没有公开的"换集合"API，且内部缓存与新集合不一致会
产生难以诊断的结果。

> ✅ **已验证（2026-10-21，执行顺序第 2 步完成）**。实测结论见 §4.3。

### 4.3 生命周期独立验证结果（2026-10-21，Windows / headless D3D11）

#### 4.3.1 帧内替换 `th.Shaper`：被接受，生效，可回退

用 goregular（纯拉丁，无汉字）与嵌入子集（有汉字）渲染同一个汉字 `世`，
统计非白像素：

| 场景 | 结果 | 判定 |
|---|---|---|
| A. 同一 shaper 连续 3 帧 | `nonWhite=164` × 3 | ✅ 帧间稳定 |
| B. 帧间替换（拉丁 → 嵌入） | 164 → **579** | ✅ 替换**真的生效**（字形从 notdef 变成真实汉字） |
| C. 换回旧 shaper | 回到 **164**（与首次完全一致） | ✅ **无隐藏 per-shaper 状态/所有权** |
| D. 每帧交替替换 10 帧 | 无 panic、无错误 | ✅ 连续帧绘制稳定 |

→ **D4「帧内替换」模型成立**：Gio 没有把 shaper 绑在窗口或 ops 上，
`th.Shaper` 可在两帧之间自由替换，且旧实例换回后行为不变。

#### 4.3.2 跨 goroutine 共用 shaper：**必现崩溃**（比注释更严重）

`concurrencyprobe` 让 4 个 goroutine 共用**同一个** shaper 各做 300 次
`LayoutString`，连跑 6 次，**6/6 全部以退出码 2 终止**：

| 次数 | 错误 | 崩溃位置 |
|---|---|---|
| 1、4 | `index out of range [16] with length 16` | `bidi.(*Runs).Run` |
| 2、3 | `slice bounds out of range [:16] with capacity 0` | `bidi.(*Paragraph).prepareInput` |
| 5 | `concurrent map writes` | `fontscan.familyList.compileTo` |
| 6 | `concurrent map read and map write` | `fontscan.familyList.compileTo` |
| 另测 | `concurrent map read and map write` | `fontscan.runeLRU.Get` |

三条结论，比 Gio 注释的「会 panic」更具体：

1. **不是概率性警告，是必现**（6/6）。
2. **崩溃点不固定**：分布在 `bidi` 与 `fontscan` 的多个内部结构上
   （双向文本段落、字体族列表、runes LRU）。
   → 内部状态是**大面积被破坏**，不是"小心某个字段"就能绕开的单点问题。
3. **`recover()` 抓不住其中一部分**：`concurrent map ...` 是 Go 运行时的
   **fatal error**，进程直接终止，不是普通 panic。

**证据边界（评审 2026-10-21 点名，勿外推）**：上述"必现"是
**本机（Windows）+ Gio v0.10.3 + 本探针这一种调用方式**（多 goroutine
共用同一 shaper 做 `LayoutString`）的实测。它**足以支持**出台一条工程禁令
（异步路径不得借用渲染线程的 shaper）——因为代价是不可接受的；
但它**不等于**证明 Gio 所有版本、所有调用方式都会以同样方式崩溃。
例如：单 goroutine 交替使用、只读 `Shaper` 的某些字段、
或未来版本引入内部锁，都可能表现不同。
→ 结论**只用于定纪律，不用于断言 Gio 的实现性质**；升级 Gio 后需重跑
`concurrencyprobe` 复核，但**不得**因为某次重跑"没崩"就解除禁令。

#### 4.3.3 由此产生的一条新约束（C 的代码也受影响）

> **异步加载路径绝对不能用渲染线程的 shaper 做字形查询。**

C 的 `theme.Resolver.ResolveRune` 内部调用 `shaper.LayoutString`，
因此它和 `material.Label` 一样会触发上述崩溃。
D 的实现在后台 goroutine 里若需要字形信息（例如做覆盖判定），
**必须使用自己构造的独立 shaper**，不得借用 `th.Shaper`
（即使只是"读一下"也不安全——`ResolveFace` 会写 LRU 缓存）。

#### 4.3.5 2b 真实窗口验证结果（`TASK-FONT-001-D-PROBE`，2026-10-21）

探针：`pkg/runtime/app/testdata/windowprobe`（真实 `app.Window`，
Windows / D3D11 / Gio v0.10.3 / `CGO_ENABLED=0`，**非 BLOCKED**）。
4 次运行（1 次 `go run` + 3 次编译产物），**5/5 PASS × 4，退出码 0**。

| phase | 情形 | 实测（4 次范围） |
|---|---|---|
| P1 | 首帧**前**两次 `Invalidate` | 未 panic、未阻塞；1.2s 内 5 帧（首帧由窗口创建触发，**不归因**） |
| P2 | 首帧**处理中**唤醒 | 2s 内出帧；延迟 95.7–125.2 ms（扣 20 ms 人为睡眠后净 75.7–105.2 ms） |
| P3 | 静默 300 ms 后**单次**唤醒 | 新帧延迟 **0.0–1.0 ms** |
| P4 | **突发 50 次**（耗时 <10 µs） | 合并成 **1 帧**；`maxAckSeen=50`——最后一次请求之后确有帧读到序号 50 |
| P5 | **关闭期**并发唤醒（134–244 次） | 收到 `DestroyEvent` 35.3–152.2 ms；关闭后再 `Invalidate` 未 panic |

**三条对 D 有直接约束的结论**：

1. `Invalidate` **可作"加载完成"通知**：合并允许，但最后一次更新会被渲染
   （P4 的 `maxAckSeen=50` 是因果判据，不是时间戳巧合）。→ D4 的
   "加载完成后发一次 `Invalidate` 换 `th.Shaper`"成立。
2. **延迟分两档**：空闲态 <1 ms；**帧在途时净等待 75.7–105.2 ms**。
   若加载恰好在一帧处理中完成，用户可见更新要等本帧提交。
   → D 实现**不得**假设"发完 `Invalidate` 立即重绘"；诊断里若要记
   "加载完成时刻"与"首帧显示时刻"，两者必须分开记。
   **绝对值不作承诺**（探针窗口可能被遮挡，DWM 节流会放大该值）。
3. **静态窗口自带 3–4 帧**（P1 帧间距序列），所以"帧数增加"不能证明
   "唤醒生效"。→ 后续任何与 `Invalidate` 有关的验收，**必须用状态序号
   或内容变化做因果判据，不得数帧**。（这条是本轮踩出来后写死的。）

**本卡仍未覆盖**：窗口最小化/不可见时的唤醒；macOS/X11/Wayland；
`-race`；`present` 耗时与调度延迟的分离；长期运行的丢失率。
均登记在 `TASK-FONT-001-D-PROBE` §8.4，**不得**据此外推。

## 6. D5：诊断保持完整

- 异步失败**必须**能从 `theme.Diagnostics()` 观察到，与同步路径同样的字段
  （`Candidates` / `Embedded` / `Coverage` / `Err`）。
- 失败时错误链必须包含 `contracts.ErrFontNotFound`（沿用 B6），
  `app.Run` 的严格语义不得因为改成异步而丢失。
- **明令禁止的静默故障**：后台加载失败、UI 却永久停留在临时字体上，
  且诊断看不出原因。这比同步失败更糟——同步失败至少会立刻报错。
  → 必须有"失败后诊断可见 + 终态明确"的验收用例。

## 7. D6：性能与行为验收

| # | 验收点 | 方法 |
|---|---|---|
| 1 | 冷启动首帧不等待加载 | 首帧耗时与"完全不加载字体"的基线同量级 |
| 2 | 后台完成时间可观测 | 记录并断言不超过冷启动同步路径的总耗时 |
| 3 | 后续帧稳定 | 加载完成后连续 N 帧无新增分配/无重复解析 |
| 4 | **系统命中时不解析嵌入**（既有约束） | 计数器注入，沿用 B4/C 的手法，**不得因异步化失效** |
| 5 | 并发首次请求合并 | N 个并发请求只触发 1 次加载（计数器） |
| 5a | **Loading 期间重复请求立即返回临时字体**（§3 冻结） | 注入一个"永不完成"的加载器，断言请求**不阻塞**、
  返回临时字体，且加载器只被调用 1 次 |
| 5b | **Failed 后不自动重试**（§3 冻结） | 注入失败加载器，断言：失败后**不发起**第二次加载；
  只有显式重试请求才触发第二次（计数器 1 → 2） |
| 6 | 布局跳动可测 | 换字体前后同一段文本的度量差有断言，且**有明确接受阈值或修复** |
| 7 | 失败诊断可见 | 注入两条链路全失败，断言 `Diagnostics()` 能读到原因 |
| 8 | 两个预算分开报告 | 探测耗时与首帧耗时**分别**输出，不得只报一个 |

## 8. 三个设计问题的冻结答复

| 评审问题 | 冻结答复 | 依据 |
|---|---|---|

## 9. 风险

1. **真实首帧未测**（D1 只到 shaping）。首帧预算的阈值必须在拿到实测后
   再定，**不得**先拍一个数字再去找数据。
2. ~~帧内换 shaper 未被实测验证~~ → **已验证**（§4.3.1）：替换生效、可回退、
   连续帧稳定。剩余风险收敛为「真实窗口 `FrameEvent` 时序未验证」。
3. **换 shaper 会重新付 41–53 ms 的 shaping 冷启动**（§2 读数 2）。
   若不处理，"首帧不阻塞"达标但"加载完成后那一帧"卡顿。
4. **布局跳动**没有现成判据，需要 D 自己定义"可接受"的度量差阈值——
   这是判断不是事实，理由必须写进代码注释。
5. 首帧临时字体用嵌入子集，意味着**即使系统字体最终可用，嵌入也会被解析一次**，
   与 C 的"覆盖完整时不加载嵌入"约束**存在张力**。D 必须明确这一次的语义
   （属于"首帧临时字体"，不是"补充链"），并在诊断里可区分。
6. 跨平台：上述基线**仅 Windows 实测**；Linux 精简环境下探测可能更快
   （无字体可探）但嵌入解析占比更高。
7. **异步路径不得借用渲染线程的 shaper**（§4.3.3，实测得出）。
   C 的 `Resolver.ResolveRune` 会调用 `shaper.LayoutString`，
   与 `material.Label` 同样会触发必现崩溃。后台若需字形信息，
   **必须构造独立的 shaper**——"只是读一下"也不安全，
   因为 `ResolveFace` 会写 `fontscan` 的 LRU 缓存。
   **边界**：崩溃实测只覆盖本机 + v0.10.3 + 该调用方式（§4.3.2 末段）。
   禁令按「代价不可接受」立，不按「已证明所有情况都崩」立。
