## 1. 为什么需要这一项

Goxml 不是普通库：它在编译期做三件有安全含义的事。

| 行为 | 潜在风险 |
|---|---|
| 读取并解析 `.gxml` | 输入不可信时，解析器的资源消耗与错误处理成为攻击面 |
| **加载 Go 包类型信息** | `go/packages` 会读取模块、解析 `go.mod`、可能触发依赖下载 |
| **生成并写出 Go 源码** | 生成路径若不设边界，可能被诱导写到预期之外的位置 |

框架本身的信任模型没有文档化——这是本任务要补的。

## 2. 必须回答的问题

### 2.1 信任边界

| 问题 | 需要结论 |
|---|---|
| `.gxml` 是否被视为可信输入？ | 若不可信，解析必须防资源耗尽（超深嵌套、超大文件、属性数量爆炸） |
| `ViewModel` 声明是否可信？ | 它决定加载哪个包。当前已限制为模块内类型（契约 §4.2），需确认这足以防止加载任意包 |
| 生成代码的输出路径是否可被 `.gxml` 影响？ | 应不能。路径应由 CLI 参数或目录约定决定 |

### 2.2 `go/packages` 的副作用

必须明确：加载过程是否会**访问网络**、**修改模块缓存**、**执行任意代码**。

`go/packages` 底层调用 `go list`，可能解析依赖。若输入可控，需评估是否可能触发非预期下载。

### 2.3 生成代码的注入面

生成的 Go 源码包含来自 `.gxml` 的字符串。需要确认：

- 属性值、绑定路径、组件名在写入源码前是否经过正确的转义；
- 是否存在能被构造成「跳出字符串字面量」或「注入语句」的输入；
- 现有 Parser 的标识符校验是否足以覆盖（`isIdentifier`）。

这一项**必须在 Codegen 实现前**给出结论，否则可能在生成器里埋下注入漏洞。

### 2.4 热重启与进程管理

`TASK-DEVX-001` 会执行 `go build` 并清理进程树。需确认：

- 待构建的命令不来自 `.gxml`；
- 进程清理不会误杀非本项目进程。

## 2.5 审查结果（2026-10-19）

完整报告见 [`安全边界与威胁模型.md`](../../03-架构/安全边界与威胁模型.md)。

| 组件 | 结论 |
|---|---|
| Commit 路径校验 | ❌→✅ **发现并修复缺陷**：`OutputName` 可含 `../` 写到目标目录之外 |
| Parser 输入边界 | ⚠️ 无深度限制，10 万层不返回（已量化，未修） |
| Expander 展开规模 | ⚠️ `<Def>` 组合可指数膨胀，1098 字节 → 1.1 s（已量化，未修） |
| Analyzer / VerifiedDoc | ✅ 未发现绕过路径 |
| Codegen 字符串处理 | ✅ 6 类注入输入全部正确转义 |
| 运行时入口生命周期 | ✅ 无死锁、无泄漏 |

两项未修的风险都是**资源上限**，而上限取值属语义决策，应由规范定义而非实现随手拍。
当前 `.gxml` 视为可信输入时风险可接受。
