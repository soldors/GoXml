## A. `pkg/runtime/theme`：报告出口深拷贝（`copyProbeReport`）

### A1 ✅ 深拷贝**当前是完整的**（逐字段核对）

`ProbeReport` 的引用字段只有四个：`Candidates []CandidateResult`、`Embedded *EmbeddedResult`、`Coverage *CoverageResult`、`Err error`。
嵌套类型核查：

| 类型 | 引用字段 | `copyProbeReport` 是否处理 |
|---|---|---|
| `CandidateResult` | 无（全是值类型 + `Err`） | 外层切片已新建 ✅ |
| `EmbeddedResult` | **无**（`bool`/`string`/`int`/`error`/`Duration`） | `e := *r.Embedded` 即完整深拷贝 ✅ |
| `CoverageResult` | 仅 `Missing []rune` | `c.Missing = append([]rune(nil), …)` ✅ |

⇒ 对照当前类型定义，**三处出口的深拷贝是完备的**，`Lazy` 侧复用同一函数也避免了行为分叉。

### A2 ⚠ 风险：`Coverage.Missing` 的深拷贝**没有有效测试保护**（本轮发现）

变异取证（基线两个测试均绿）：

| 变异 | 改法 | 是否变红 |
|---|---|---|
| **M1** | `font.go` 系统命中路径 `copyProbeReport(rep)` → `rep`（不拷贝） | ✅ FAIL（`TestProviderReportOwnership`） |
| **M2** | `lazy.go` `Candidates` 改**浅拷贝** | ✅ FAIL（**两个测试都红**） |
| **M3** | `lazy.go` `Coverage.Missing` 改**浅拷贝** | ❌ **全 PASS，未变红** |

**根因**：`TestProviderReportOwnership` 用 `rep.Coverage.Missing = append(rep.Coverage.Missing, '中')` 做「污染」，
而 **Go 的 `append` 在容量不足时会重新分配底层数组**——此时写入根本碰不到被共享的那块内存，
污染自然不可见。断言又写成 `len(again.Coverage.Missing) != 0`（只能区分「空 vs 非空」），
在该测试路径下 `Missing` 本身为空，判据进一步失效。

**建议**：污染手段改为**就地写**，并对具体元素值断言：

```go
if len(rep.Coverage.Missing) > 0 {
    rep.Coverage.Missing[0] = 0xFFFD   // 就地写，必然命中共享底层数组
}
```

同时让 fixture 构造一个**非空**的 `Missing`（例如覆盖不足的字体），否则这段分支根本不执行。
另可补一个**元素值**断言而非只比 `len`。详见 [PIT-025](../08-踩坑/踩坑-025-用append污染切片无法证明深拷贝.md)。

### A3 ⚠ 风险：手工深拷贝缺少结构性守卫

`copyProbeReport` 是**手写**的深拷贝。今天完整（A1 已逐字段核对），但将来给 `ProbeReport` /
`EmbeddedResult` / `CoverageResult` 新增 slice / map / 指针字段时，**没有任何机制会提醒补拷贝**——
编译能过、现有测试也会绿，直到线上出现「改了调用方的报告、污染了缓存」。

**建议**（任选）：给三个类型各加 `Clone()` 方法由类型自己负责；或加一个反射守卫测试，
遍历结构体所有 slice/map/指针字段，断言副本的底层地址与原件不同——**新增字段时该测试会自动变红**。

### A4 观察：锁内分配，可忽略

`ResolveWithReport` 在持 `p.mu` 期间调用 `copyProbeReport`（4 处，本改动新增 3 次分配）。
相对同一把锁内 ~110 ms 的探测耗时，拷贝是百纳秒量级，**不是问题**。
> 顺带（**既有设计，非本改动引入**）：`p.mu` 跨越整个探测过程，探测期间查 `Scans()` / `Faces()` 会阻塞。
> 这是已知约束，本轮不评价其取舍。

### A5 ⚠ 风险（latent）：缓存命中分支取的是「全局最近一次」报告

```go
derived := copyProbeReport(p.last)   // font.go:332
```

`p.last` 是**最近一次**探测，不是 `family` 对应的报告。A 阶段只有 `FamilyCJK` 可探测
（`FamilyBody` / `FamilyMono` 在 341-347 行直接报错返回），因此**当前不可触发**。
但若将来多族探测，命中 B 族缓存时会返回 A 族的诊断历史。

**建议**：改为按 family 存报告（`p.reports map[string]*ProbeReport`），或至少在此处加注释锁住
「A 阶段仅 CJK 可探测」这个前提，并配一条断言，让前提失效时能变红。

## B. `pkg/runtime/app`：窗口事件循环与 `stop` 监听

### B1 ✅ goroutine 泄漏修复**有效**，且有测试保护

变异 **M4**：把 `watchWindowStop` 的第一个 select 改回纯 `<-stop`（重现「窗口已关、监听仍阻塞」）。

→ `TestWindowStopWatcherLifecycle` **FAIL**，报错：

```
window_lifecycle_test.go:47: window destroyed while its stop watcher remained blocked
```

⇒ 判别力成立，修复是真的被锁住的。

### B2 ⚠ 风险：双检的测试判别力约 **83%，不是 100%**

变异 **M5**：删掉第二个「双检」select。**单次运行 PASS**，一度让我误判为「无覆盖」。
重复跑 **12 次**后：

| 指标 | 结果 |
|---|---|
| 顶层用例 FAIL / PASS | **10 / 2** |
| 子用例 `both` FAIL | **10 / 12** |
| `destroy` / `stop` 子用例 | 12/12 PASS（不受影响） |

原因：第一个 select 在 `loopDone` 与 `stop` **同时就绪**时由 Go 运行时**随机选路**，
删掉双检后约 83% 概率向已退出的窗口发出 `ActionClose`。

⇒ 结论：**双检有覆盖，但判据是概率性的**。
**不得**用「跑一次通过」来判定此处是否改坏；若要在此加断言，应跑多次，或改成确定性判据
（例如 fixture 里先让 `stop` 就绪、再 `close(loopDone)`，强制走到双检分支）。

### B3 ✅ 接口抽取合理

`windowEvents` 只声明 `Event() event.Event` / `Perform(system.Action)` / `Invalidate()`，
`*app.Window` 满足该接口——场景 C 下 `go build ./...` rc=0 已实测。抽取后 `runWindowEvents`
可在无原生窗口的测试里驱动，代价只是一层接口。

### B4 观察：双检是**尽力而为**，不是确定性保证

两次 select 之间 `loopDone` 仍可能关闭，因此「向已退出窗口发 `ActionClose`」的竞态只能**减少、不能消除**。
代码注释已写明是 "Give an exited loop priority"，属有意取舍，**不算缺陷**。

**未验证项**：`w.Perform(system.ActionClose)` 打在**已 Destroy** 的窗口上是否无害，取决于 Gio 行为，
本轮**未验证**，不作为结论。
