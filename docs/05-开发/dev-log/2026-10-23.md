### 11.3 原逐帧判据为什么失效（D6-3）

原设计：切换后逐帧记录排版耗时，断言 `max(后续帧) <= 5 × min(后续帧) + 2ms`
（"无冷启动尖峰"）。

失效原因：本机单帧读数恒为 0（§11.2），于是 `min = max = 0`，不等式退化成
`0 <= 2ms`——**恒真的空判据**。它显示为绿色却不构成任何证据，比没有断言更危险。

实测取证：按该判据实现时 5 帧读数全是 `0s` 且测试 PASS；把帧数加到 200 后总耗时
仍读不出（200 × 1.65 µs ≈ 0.33 ms < 0.53 ms），触发护栏报"未验证"——
这条护栏正是为了**不让**这类空判据静默通过而设。

### 11.4 替代判据：2000 帧批量总量 + 两道护栏

```text
d_swap = 切换帧耗时（含 1 次冷启动）
T      = 其后 N = 2000 帧的总耗时
预算   = 10 × d_swap
断言   = T <= 预算
```

**设计理由**：

- N = 2000 使 T ≈ 4 ms ≈ 8 个计时粒度，读数才落在可分辨区间（200 帧时 T≈0.33 ms，读不出）。
- 冷启动与缓存命中相差约 5 个数量级（≈45 ms vs ≈1.4 µs/帧），"10 倍冷启动"的预算
  位于两者之间的巨大空档，**不属于需要精调的临界值**。
- 每 50 帧检查一次累计耗时并提前跳出，失败路径耗时有界（否则每帧冷启动要跑几十秒）。

**两道护栏（测不到就报"未验证"，不得假装通过）**：

- `d_swap <= 0` → `t.Fatalf`：冷启动量级测不出，D6-3 的耗时判据在本机**无法成立**。
- `T <= 0` → `t.Fatalf`：总量读不出，判据会在 0 上恒真。

**本轮实测**：切换帧 45.4705 ms；其后 2000 帧总 4.5533 ms；预算 454.705 ms → PASS。

### 11.5 一处测试自身竞态的发现与修正（重要）

**现象**：`TestFontLazyLoadNoFrameCounting/晚到` 在 `go test -run TestFontLazyLoad`
过滤跑时 PASS，在**整包跑**时 FAIL：

```text
Ready 之前跑了 235 帧, Shaper 却变化了 1 次：替换不是由状态驱动的
Ready 之前就写入了 FrameSubmittedAt：提交时刻早于产出
```

**根因（测试自身的 TOCTOU，不是生产缺陷）**：后台加载可能在**某一帧运行期间**
完成。那一帧开始时状态还不是 Ready、结束时已经是，"它算到达前还是到达后"
**无法判定**；把这种帧当成"到达前的帧"去断言"不得替换"，就是拿一个不可判定的
事实下结论，因此在不同时序下偶发失败。

**修正**：按**帧的起止状态是否一致**给每一帧分类——

- 起止一致（都未 Ready）：确定处于到达前，**可以**断言不得替换；
- 起止不一致：跨越到达时刻，**单列计数并跳过判定**，不强行下结论。

同时把"切换前抓到的 tempShaper"接入变化计数，消除"到达前跑 0 帧"
（加载极快时）导致变化次数算成 0 的漏计。

**复验**：`go test -count=3 ./pkg/runtime/app/` rc=0；
`go test -count=2 ./pkg/runtime/app/ ./pkg/runtime/theme/` rc=0。
