### 8.1 新发现：`TestFontLazyLoadDiagnosticsFields` 间歇失败（登记为 `D-ACCEPT-08`）

串行重跑 `./pkg/runtime/app/` 时出现失败：

```
--- FAIL: TestFontLazyLoadDiagnosticsFields (0.08s)
    font_lazy_strict_test.go:158: LoadElapsed = 0s, 期望 > 0
    成功路径：state=ready attempts=1 tempSource=embedded-subset loadElapsed=0s
```

**定性过程（没直接下结论）**：
1. 连跑该用例 6 次 → **6/6 通过**（单跑时文件读取是冷的，读得出）；
2. 连跑整包 3 次 → PASS、PASS、**FAIL**；
3. 追加整包 5 次 → 全 PASS；
⇒ **整包 10 次中 2 次失败（20%）**，与缓存预热相关。

**根因**：成功路径的加载耗时可能**低于本机 `time.Now()` 有效粒度（约 0.53 ms）**，
`LoadElapsed` 读成 0。失败路径早已注入 `failReadDelay = 50ms` 规避同类问题，
**成功路径没有同类保护**。

**归属与处置**：断言在 `pkg/runtime/app/font_lazy_strict_test.go:157-158`，
属**冻结候选**（哈希 `700edc28…` 未变）⇒ **不存在独立修复路径**，本轮**未修**。
已登记 `D-ACCEPT-08`：验收结论 `未验证`、复核状态 `待独立复核`；

### 08 根因（已证实，非假设）
上一轮写的"耗时低于计时粒度"**只是必要条件**。逐个排除四类后：

| 类别 | 判定 | 关键证据 |
|---|---|---|
| 生产逻辑错误 | 否 | 三时刻均写入、计算正确；命中缓存本就该快 |
| **测试时序（主因）** | 是 | `newTestLazy` → `theme.NewLazy(LazyOptions{})` → **共享 defaultProvider**；同进程预热后命中缓存 |
| **计时精度（放大器）** | 是 | 时钟步长独立实测 **504.9µs**（20000 次 back-to-back 中 19999 次差 0） |
| 环境波动 | 否 | 单跑 12 次 `LoadElapsed` 稳定 137–214ms |

决定性读数（临时诊断用例，同进程连续三次，**取证后已删除**）：

| 次序 | LoadElapsed | ProbeRan | ProbeElapsed |
|---|---|---|---|
| #1 冷 | **164.452ms** | true | 125.406ms |
| #2 热 | **1.01ms** | false | 0s |
| #3 热 | **538.5µs** | false | 0s |

⇒ 命中缓存后 0.5–1ms，落在 504.9µs 步长边界 ⇒ 有时恰好读成 0。
**修复不能只加延迟**（会掩盖共享 provider 的时序耦合），也不能放宽成 `>= 0`。
