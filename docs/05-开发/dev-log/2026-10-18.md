## 1. 文档补充：性能预算与字体策略

### 1.1 背景

在通读全部规范后发现两个系统性空白：

1. **性能只有相对指标**（「单帧损耗 < 5%」），不可证伪且抓不住真正的开销来源（每帧堆分配）。
2. **字体与 IME 完全没有覆盖**。Gio 自带 `gofont` 不含 CJK 字形，中文界面会静默渲染为空白。

### 1.2 实测结论（i7-12700H / Go 1.26.1 / Gio v0.10.3 / CGO_ENABLED=0）

| 对照 | 差距 |

| 50 节点静态子树：每帧闭包 28,000 ns/op vs 编译期展开 2,550 ns/op | **11×** |

### 3.1 `bdd299b` 绑定路径解析（第 2 步）

实现 `BIND-001/002/003` 与 `<For>` 作用域。范围限定在路径层面。

**踩到的坑**：`types.LookupFieldOrMethod` 在 `pkg == nil` 时**不返回未导出成员**。
若直接用它，`{User.note}` 会得到「字段不存在」（`BIND-002`），而不是「存在但未导出」
（`BIND-003`）——两者修复动作完全不同（改拼写 vs 改大小写）。

解法：先手动扫描直接字段（可见未导出成员），再回退到标准查找处理嵌入提升与方法。

**范围外的一处提前实现**：`SCOPE-004`。建立循环作用域依赖 `In` 的可迭代性，
不检查的话循环体内 `{item.X}` 会被误报成 `BIND-001`，掩盖真正原因。

**夹具修正**：15 个夹具原本写短名 `fixture.ViewModel`，但冻结文法要求模块根
相对路径，全部被判「包不存在」。改为完整相对路径。

### 3.2 `b077c81` 类型兼容契约与 `BIND-004`（第 3 步）

先冻结契约 §11（类型兼容），再实现。

**三层分开**：类型兼容 / 特殊表达式约束 / 值转换。合并会让「兼容」与「如何生成」纠缠。

**三条关键决定**：`int → string` 拒绝、`int → float` 拒绝、无符号整数一律拒绝。

**`color`/`insets` 按精确身份**（`types.Identical`），不接受「结构相似」的结构体。
类型选型：`color` ← `image/color`（标准库），`insets` ← `contracts.EdgeInsets`（本项目）。
**不引入 Gio 类型**：当时编译器只依赖 `x/tools`，把渲染库拖进编译器依赖图是不必要的耦合。

**前置修复**：内置 Schema 的属性此前只写 `Name`、`Type` 全为 `PropUnknown`，
`BIND-004` 无从判定。已补齐 Text/Button/Input/Image 全部属性类型。

**IR 补充**：`ValueKind` 新增 `ValueUint`。原实现把有符号与无符号都归为 `ValueInt`，
无法表达「`int` 属性拒绝 `uint`」。

### 3.3 `259033b` 事件签名校验（第 4 步）

按契约 §8.4：方法形参 = 事件载荷 ++ 调用点实参（载荷在前）。

**两处契约缺口，实现时才发现**：

1. **`EVENT-007` 从未被分配**。契约 §8.2（Q4）早已规定「事件方法不得有返回值」，
   但诊断码目录只到 `EVENT-006`。新增 `GXML-EVENT-007`，并同步目录、门禁与夹具期望。
2. **`EventArg.Literal` 违反自身契约**。注释写「保留原始字面量文本」，
   但 Expander 剥掉了字符串单引号，导致 `'42'` 与 `42` 在 IR 中无法区分。
   改为保留引号。

**载荷与实参用不同判定**：载荷无具体 Go 类型（Schema 只有 `PropType`）→ 按**类别**匹配；
实参有确定 Go 类型 → `types.AssignableTo` **严格**判定。若都用后者，
`OnX(v float32)` 会被错误拒绝。

**v1 限制已锁定**：`<Def Events>` 不传播事件（规范 §7.2.3），因此 Def 调用点的事件
处理器签名**不被校验**。`TestDefEventNotSignatureChecked` 固定该限制。

验证快照：137 个测试，92.6% 覆盖。

### 3.4 `9381542` Analyzer 整体验收
