### 1.1 双 `.gxml` 同包生成 + 真实编译（新增 `naming_samepkg_test.go`）

`TestGeneratedCompiles` 与 `TestBindingGeneratedCompiles` 都是**单文件**编译，
两者都不能证明"同包多源"——而 C2 修的正是同包多源重复声明。补的四个用例：

| 用例 | 组合 | 判据 |
|---|---|---|
| `TestTwoStaticSourcesSamePackage` | 静态 + 静态 | 同包 `go build` 通过；两侧符号互不相交；静态页不声明 `goxmlTextCache*` |
| `TestStaticAndBindingSourcesSamePackage` | 静态 + 含绑定（用户点名的混合组合） | 同上；含绑定侧声明 `goxmlTextCacheDetail`，静态侧不声明 |
| `TestTwoBindingSourcesSamePackage` | 含绑定 + 含绑定 | 同上；两侧各自声明自己的 textCache（最强重复声明面） |
| `TestSamePackageTwoSourcesUseDistinctTypeNames` | 纯逻辑，不启子进程 | 5 个源路径派生的包级类型名两两不同 |

实现要点（两处坑，都踩过并修）：

- **必须建在仓库内**，不能建独立模块：含绑定页的 ViewModel 在
  `internal/compiler/analyzer/testdata/fixture`，Go 的 internal 规则禁止外部模块
  import（与 `binding_compile_test.go` 顶部注释同源）。目录建在 `testdata/` 之下，
  避免被运行期 `./...` 枚举撞上（这是 `binding_runtime_test.go` 的老坑）。
- **产物开头是三行保护头**，断言 package 子句不能用 `HasPrefix(s, "package demo")`
  —— 首版因此 3 个用例全红，改为 `strings.Contains(s, "\npackage demo\n")` 才绿。

**变异取证**（先 `go build ./...` 退出码 0，再跑测试；`codegen.go` 的
`generatedTypeNames` 退回固定名 `renderKey`/`textCache`）：

```text
BUILD=0
--- FAIL: TestTwoStaticSourcesSamePackage
    gen_home.go:69:6: renderKey redeclared in this block
--- FAIL: TestStaticAndBindingSourcesSamePackage
    gen_home.go:69:6: renderKey redeclared in this block
--- FAIL: TestTwoBindingSourcesSamePackage
    gen_home.go:65:6: renderKey redeclared in this block
    gen_home.go:96:6: textCache redeclared in this block
--- FAIL: TestSamePackageTwoSourcesUseDistinctTypeNames
```

这直接把用户"缺少双文件真实编译回归测试"的顾虑转成机器判据：**退回旧实现时，
新测试会在 `go build` 层报 `redeclared`**，不是靠字符串巧合变红。
恢复后 SHA-256 与变异前一致（`9135cdb03a3776c522bbd0b071b115cf06c8af82557c1baedafb232911097185`），
四个用例复跑全绿（9.2s）。

### 1.3 text cache 保守预检的边界（新增 `naming_textcache_boundary_test.go`）

用户怀疑的"过度报告"经实测**属实**，且现在可复现：

- `bindCacheDecl`（声明 `goxmlTextCache<Source>`）只在 `usesVM` 为真时生成，
  **静态页产物不声明该类型**；
- 但 `generatedPackageSymbols` 无条件把它算进占用符号集合 → 包内恰好有同名
  用户符号时，预检报 `namingConflictExisting`；
- 同一组合放进真实包 `go build` **仍然通过** → 产物没真声明它 → 该冲突是**误报**。

反向对照（证明保守上界不能被整体删掉）：换成含绑定页，产物真声明该类型，
同名用户符号会让 `go build` 报 `redeclared` 真失败。

| 用例 | 钉住的事实 |
|---|---|
| `TestTextCacheIsDeclaredOnlyForBindingPages` | 静态页不声明 / 含绑定页声明 |
| `TestPrecheckIsConservativeForStaticTextCache` | 预检集合 ⊋ 静态页实际声明，多出的正是 textCache |
| `TestPrecheckOverreportsForStaticPageButBuildStillPasses` | 预检报冲突 **且** build 通过 → 误报可复现 |
| `TestPrecheckTextCacheConflictIsRealForBindingPage` | 含绑定页同名符号 → build 报 `redeclared` → 预检必要 |

符号名一律由 `generatedTypeNames` 派生，不硬编码字面量——否则将来改规则时
测试会静默失效。（首版把 `generatedTypeNames` 的返回值顺序写反——它是
`(keyType, cacheType)`，`_, keyType, _ :=` 取到的是 cacheType——已修并在注释里标注顺序。）

**变异取证**（`naming.go` 的 `generatedPackageSymbols` 去掉 `cacheType`）：

```text
BUILD=0
--- FAIL: TestPrecheckIsConservativeForStaticTextCache
    预检应保守地包含 "goxmlTextCacheHome"；实际=[GoxmlHomeView NewGoxmlHomeView goxmlRenderKeyHome]
--- FAIL: TestPrecheckOverreportsForStaticPageButBuildStillPasses   实际=[]
--- FAIL: TestPrecheckTextCacheConflictIsRealForBindingPage        实际=[]
```

恢复后 SHA-256 一致（`0e68308f9a51fbfd5b0e1487a9fb102a4b018725a70effdfd8cf357786417a43`），
四个用例复跑全绿（6.7s）。

**归属裁决：不在 C2 收窄，留给 C4/C5。** 三条理由已写进
`naming_textcache_boundary_test.go` 顶部注释：

1. 保守上界是 C1 的有意设计——误报的代价是"生成前被拦下并给出明确诊断"，
   漏报的代价是"生成成功、`go build` 才炸"，后者正是 C2 要消灭的失败模式；
2. 精确判定必须知道"该源是否含绑定"，而 C1 预检的契约输入只有 `SourcePath`
   （不读 `.gxml`、不跑前端）；引入内容判定等于改预检契约，超出 C2 范围；
3. C4（CLI 接线）才同时持有源内容与预检调用点，是收窄的自然时机；
   收窄时必须同步更新本文件，否则测试会红——这是防回归钩子，不是负担。
