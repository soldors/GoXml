### 1.1 双 `.gxml` 同包生成 + 真实编译（新增 `naming_samepkg_test.go`）

`TestGeneratedCompiles` 与 `TestBindingGeneratedCompiles` 都是**单文件**编译，
两者都不能证明"同包多源"——而 C2 修的正是同包多源重复声明。补的四个用例：

| 用例 | 组合 | 判据 |
|---|---|---|
| `TestTwoStaticSourcesSamePackage` | 静态 + 静态 | 同包 `go build` 通过；两侧符号互不相交；静态页不声明 `goxmlTextCache*` |
| `TestStaticAndBindingSourcesSamePackage` | 静态 + 含绑定（用户点名的混合组合） | 同上；含绑定侧声明 `goxmlTextCacheDetail`，静态侧不声明 |
| `TestTwoBindingSourcesSamePackage` | 含绑定 + 含绑定 | 同上；两侧各自声明自己的 textCache（最强重复声明面） |
| `TestSamePackageTwoSourcesUseDistinctTypeNames` | 纯逻辑，不启子进程 | 5 个源路径派生的包级类型名两两不同 |

实现要点（两处坑，都踩过并修）：

- **必须建在仓库内**，不能建独立模块：含绑定页的 ViewModel 在
  `internal/compiler/analyzer/testdata/fixture`，Go 的 internal 规则禁止外部模块
  import（与 `binding_compile_test.go` 顶部注释同源）。目录建在 `testdata/` 之下，
  避免被运行期 `./...` 枚举撞上（这是 `binding_runtime_test.go` 的老坑）。
- **产物开头是三行保护头**，断言 package 子句不能用 `HasPrefix(s, "package demo")`
  —— 首版因此 3 个用例全红，改为 `strings.Contains(s, "\npackage demo\n")` 才绿。

**变异取证**（先 `go build ./...` 退出码 0，再跑测试；`codegen.go` 的
`generatedTypeNames` 退回固定名 `renderKey`/`textCache`）：

```text

    gen_home.go:69:6: renderKey redeclared in this block
--- FAIL: TestStaticAndBindingSourcesSamePackage
    gen_home.go:69:6: renderKey redeclared in this block
--- FAIL: TestTwoBindingSourcesSamePackage
```

### 1.3 text cache 保守预检的边界（新增 `naming_textcache_boundary_test.go`）

用户怀疑的"过度报告"经实测**属实**，且现在可复现：

- `bindCacheDecl`（声明 `goxmlTextCache<Source>`）只在 `usesVM` 为真时生成，
  **静态页产物不声明该类型**；
- 但 `generatedPackageSymbols` 无条件把它算进占用符号集合 → 包内恰好有同名
  用户符号时，预检报 `namingConflictExisting`；
- 同一组合放进真实包 `go build` **仍然通过** → 产物没真声明它 → 该冲突是**误报**。

反向对照（证明保守上界不能被整体删掉）：换成含绑定页，产物真声明该类型，
同名用户符号会让 `go build` 报 `redeclared` 真失败。

| 用例 | 钉住的事实 |
|---|---|
| `TestTextCacheIsDeclaredOnlyForBindingPages` | 静态页不声明 / 含绑定页声明 |
| `TestPrecheckIsConservativeForStaticTextCache` | 预检集合 ⊋ 静态页实际声明，多出的正是 textCache |
| `TestPrecheckOverreportsForStaticPageButBuildStillPasses` | 预检报冲突 **且** build 通过 → 误报可复现 |
| `TestPrecheckTextCacheConflictIsRealForBindingPage` | 含绑定页同名符号 → build 报 `redeclared` → 预检必要 |

符号名一律由 `generatedTypeNames` 派生，不硬编码字面量——否则将来改规则时
测试会静默失效。（首版把 `generatedTypeNames` 的返回值顺序写反——它是
`(keyType, cacheType)`，`_, keyType, _ :=` 取到的是 cacheType——已修并在注释里标注顺序。）

**变异取证**（`naming.go` 的 `generatedPackageSymbols` 去掉 `cacheType`）：

```text
BUILD=0
--- FAIL: TestPrecheckIsConservativeForStaticTextCache
    预检应保守地包含 "goxmlTextCacheHome"；实际=[GoxmlHomeView NewGoxmlHomeView goxmlRenderKeyHome]
--- FAIL: TestPrecheckOverreportsForStaticPageButBuildStillPasses   实际=[]
--- FAIL: TestPrecheckTextCacheConflictIsRealForBindingPage        实际=[]
```

恢复后 SHA-256 一致（`0e68308f9a51fbfd5b0e1487a9fb102a4b018725a70effdfd8cf357786417a43`），
四个用例复跑全绿（6.7s）。

**归属裁决：不在 C2 收窄，留给 C4/C5。** 三条理由已写进
`naming_textcache_boundary_test.go` 顶部注释：

1. 保守上界是 C1 的有意设计——误报的代价是"生成前被拦下并给出明确诊断"，
   漏报的代价是"生成成功、`go build` 才炸"，后者正是 C2 要消灭的失败模式；
2. 精确判定必须知道"该源是否含绑定"，而 C1 预检的契约输入只有 `SourcePath`
   （不读 `.gxml`、不跑前端）；引入内容判定等于改预检契约，超出 C2 范围；
3. C4（CLI 接线）才同时持有源内容与预检调用点，是收窄的自然时机；
   收窄时必须同步更新本文件，否则测试会红——这是防回归钩子，不是负担。

### 5.1 C4-PRE-1：F-06 路径归一化（已修）

`isOwnArtifact` 拿**裸** `SourcePath` 去比保护头里的 `// Source:`，而保护头由
`headerFor` 写出、走 `normalizeSourcePath`（统一 `/`）。调用方给平台原生分隔符

> 当前 CLI 传的 `SourcePath` 是 `filepath.Base()`（不含分隔符），该缺陷在
> 现有调用形态下不会触发。修它是因为接线后预检进了失败路径，一次误报的成本
> 从"没人看见"变成"合法工程生成不了"。

### 5.2 接线暴露的既有缺陷：批内冲突没有按目标包分组

接线后第一批红灯**不是**新代码写错：

```text
alpha/row.gxml: CODEGEN-NAME-002: sources "…/alpha/row.gxml" and
"…/beta/row.gxml" both generate symbol "GoxmlRowView"
goxml generate: 包级符号冲突（4 条）——批次全部放弃，磁盘无任何变更
```

- 根因：`detectNamingConflicts` 第 1 段用**全局** `firstOwner` 比较符号，
  没有按 `TargetDir` 分组 → 不同目录（不同 Go 包）的同名源被判冲突；
- 这正是验收矩阵 **A3** 要防的误报；C1/C2 阶段预检零接线，缺陷不显形；
- 修法：第 1 段改为按 `filepath.Clean(TargetDir)` 分组后再比较（同组内才比）；
- 证据：既有 CLI 用例 `TestGenerateNestedDirsRun` /
  `TestGenerateNestedDirsDeterministic` / `TestGenerationDeterministicAcrossCreationOrder`
  由红转绿（它们是 A3 的天然回归），另补 `naming_batch_group_test.go`（3 用例，
  含"同目录塌缩仍要报"的反向对照）；
- 变异：退回全局比较（`key := strings.Repeat("", len(t.TargetDir))`，
  build 退出 0）→ **2 红**。

> 教训：一个"检测已实现、测试全绿"的检测器，可能从未被真正调用过。
> 接线本身就是一次验收——这类缺陷只有在调用点存在时才显形。

### 5.3 接线实现（冻结于卡 §10.7.3）

### 6.4 实现 1/3：`slots.go` 的单一派生（并立刻抓出真分叉）

新增 `internal/compiler/codegen/slots.go`：

- `textBindSlot(n, facts, inFor) (ra, isBinding, takesSlot)` —— **唯一**的
  「哪个 `<Text>` 占槽」规则；
- `CountBindSlots(v *analyzer.VerifiedDoc) (int, error)` —— 纯遍历统计。

生成器 `nodeExpr` 的 Text 分支改为调用 `textBindSlot`，与预检共用同一条规则
（不再各写一份 `lookupAttr(...).Path != nil` 判断）。

护栏测试 `TestSlotCountAgreesWithDeclaredTextCache` 断言
**「槽位数为零 ⟺ 产物不声明 TextCache」互为充要**。它第一次运行就红了：

```
If 内绑定：CountBindSlots = 0，期望 1
```

根因：`<If>` 的分支**不在 `Children` 里**，而在 `If.Then` / `If.Else`
（`contracts.IfClause`）。我的计数遍历只走 `Children`，漏了分支；而发射侧
`emitIfChildren` 会进去，所以生成器真的分配了槽位 → 预检会低估槽位数 →
**该报的冲突漏报**。修正为同时遍历 `Children` 与 `If.Then/Else`。

这条正是该护栏存在的理由：规则单一不代表**遍历形状**一致，而两处遍历分叉
的后果就是漏报。

### 6.5 实现 2/3：前端复用（避免 +285 ms/文件的真实回归）

先按最朴素的实现接上（预检 `SlotsFor` + 阶段一 `pipeline.Run` 各跑一次前端），
然后做**受控 A/B**：同一工程（2 静态 + 1 绑定，`--no-cache` 强制未命中），
两个二进制的差异只有收窄逻辑。

| 版本 | 3 次实测（ms） | 中位数 |
|---|---|---|
| 收窄前（`28fecae`，保守上界） | 1996 / 2258 / 2162 | 2162 |
| 收窄后（双跑前端） | 3017 / 2853 / 3017 | 3017 |
| **收窄 + 前端复用** | 1787 / 1770 / 1757 | **1770** |

也就是说"多跑一遍前端"让生成慢了 **+0.86 s/3 文件（≈+285 ms/文件，+40%）**，
主要成本是 `loadEnv` 构造 `go/types` 类型环境。这个量级不能接受，于是改成复用：

- `pipeline.Prepare(...)` → `*Prepared`（只跑 parse→expand→analyze→verify）
- `Prepared.Slots()` → 槽位数（前端失败时返回 error）
- `pipeline.RunPrepared(...)` → Codegen + Artifact
- `pipeline.Run(...)` 保留原签名，内部即 `RunPrepared(Prepare(...))`

CLI 在**阶段零 C** 为每个未命中输入准备一次，存进 `preparedFE`，
阶段一直接复用 —— 前端总次数与 C4 相同。

复用后中位数 1770 ms **不高于**收窄前 2162 ms。**不主张"更快"**：
两者工作量相同，差异在测量噪声（Windows 计时、磁盘缓存）量级。

### 6.6 实现 3/3：CLI 接线与保守回退

`precheckPackageSymbols(rs, moduleRoot, preparedFE, stderr)`：

- 每个输入 `Prepare` 一次 → `Prepared.Slots()`；
- `Slots()` 成功 → `BindSlotsKnown = true`；
- **失败 → `BindSlotsKnown = false`**（槽位未知 → 保守上界）。

失败回退是刻意的：前端未通过时无从判断产物会不会声明该类型，而那种情况的
正确报错点是阶段一的编译诊断。**不得**让预检把语法错误伪装成命名冲突——
由 `TestNamingDoesNotMaskCompileErrors` 钉住（断言 stderr 含 `GXML-*`
且**不含** `CODEGEN-NAME-*`，且零产物）。

### 7.1 P1-1：槽位「绝对数」确实从未被断言（缺口成立，已闭合）

复审原话的意思是：既有护栏只断言「零 ⟺ 不声明 TextCache」，只能证明**零与非零**
一致；3 个绑定被统计成 2 个时它仍然是绿的，而 `CountBindSlots` 这个名字承诺的是
「统计槽位数」。

**这个判断是对的。** 处理：

1. `Generate` 拆出 `generateWithSlots`（不导出），把发射时**实际累加**的
   `g.bindSlots` 暴露给同包测试——基准是真值，不是再数一遍。
2. 新增 `TestSlotCountEqualsEmittedSlots`：**13** 种页面形态，断言
   `CountBindSlots(v) == 发射实际累加值`，并附期望绝对值。覆盖
   两层容器嵌套、If 两分支、嵌套 If、For 内 If、For 内外混排、三绑定等。
3. 变异 M8（跳过 `If.Else` 遍历）下对比两条护栏：

| 护栏 | M8 下结果 |
|---|---|
| `TestSlotCountAgreesWithDeclaredTextCache`（旧的零/非零） | **ok（绿）** |
| `TestSlotCountEqualsEmittedSlots`（新的绝对数） | **FAIL**：「If 两分支各一」CountBindSlots=1，发射=2 |

这就是缺口的实证：**旧护栏对"非零但数量错"完全不敏感**。

**IR 子节点字段枚举**（回答"计数是否可能漏掉某类节点"）：
`grep '\[\]\*NodeIR' contracts/` 只有三处——`Children`、`IfClause.Then/Else`、
`DocumentIR.Defs`。计数遍历覆盖前两处；`Defs` 不被遍历是**与发射口径一致**的
（`Generate` 只走 `Document().Page`，`<Def>` 已由 Expander 内联）。

### 7.2 P1-2：`Prepare/RunPrepared` 行为等价（可执行 A/B，未发现回归）

不读代码下结论，做三二进制对照，差异只在被测项上：

| 二进制 | 代码状态 |
|---|---|
| `B0` | `28fecae`（重构前：`Run` 内部 frontEnd + codegen） |
| `B1N` | 当前 + **收窄关闭**（`BindSlotsKnown` 恒 false）→ 只含重构 |
| `B1` | 当前（重构 + 收窄） |

9 个用例：单文件静态、单文件绑定、同包两文件、语法错误、未知 ViewModel、
批内塌缩冲突、静态页+同名 textCache 符号、缓存命中（连跑两次）、
`--out-dir` 指向不存在目录 + 冲突。每个用例记录 **退出码 + stdout + stderr +
目录内每个文件的 sha256 前 12 位**。

结果：

| 对照 | 结果 |
|---|---|
| **B0 vs B1N** | **9/9 完全一致（零差异）** → 前端拆分未改变任何可观测行为 |
| B0 vs B1 | 仅 `c7statictc` 不同：B0 `EXIT=2` + `CODEGEN-NAME-001`；B1 `EXIT=0` 并生成产物 —— 正是收窄的预期效果 |
| c6 塌缩冲突 / c9 out-dir | 逐字节一致（c9 两边都 `--outdir-exists-- no`） |

**采集过程的一个坑（如实记录）**：第一次跑的 `c8cache`（缓存命中）出现差异，
排查后确认是**采集污染**——脚本用 `rm -rf .goxml` 复位缓存，而沙箱的批量删除护栏
在达到阈值后开始拦截，导致上一轮二进制的缓存残留到下一轮，于是"未命中"变"命中"。
证据是三份采集里产物 `a_gen.go` 的哈希完全相同（`1313093ad68f`），只有 miss/hit
那一行不同。改用 `mv` 替代 `rm` 清态重做后，B0 与 B1 的缓存行为完全一致
（首次 `cache-missing` → 二次 `缓存命中 / 命中 1，生成 0`）。
**教训**：A/B 对照里，采集脚本自身的副作用也会伪造差异，必须先证明差异来自被测项。

**Hooks 与状态隔离**（静态核对）：

- `frontEnd` 仍用 `hooks.Load` / `hooks.Analyze`，`RunPrepared` 仍用 `hooks.Generate`；
  pipeline 包内的 Hooks 用例（`pipeline_test.go` 3 处、`modulepath_test.go` 2 处）全绿。
- `preparedFE` 是 `runPipeline` 内的**局部 map**，键是 `*resolvedInput`，
  每次调用新建 → 不存在跨文件/跨运行共享同一个 `Prepared`。
- **`Prepared` 的配置充分性**：`pipeline.Config` 只有 4 个字段
  （`ModuleRoot`/`SourceDir`/`PackageName`/`SourcePath`），预检与阶段一的兜底
  构造**逐字段相同**；`Prepared` 存的是整份 `cfg` 加 `file`，`RunPrepared`
  只用到 `PackageName`/`SourcePath` + 前端带出的 `modulePath`。
  即：复用一个 `Prepared` 与「阶段一重新 Prepare 一次」在入参上等价——
  差别只有耗时，这也正是 M9 变异能被单独观测到的原因。
- 前端失败时 `Prepare` 只返回 nil 文档 + 诊断，**不返回 error**，
  预检据此回退保守上界；编译错误仍由阶段一报出（`TestNamingDoesNotMaskCompileErrors`）。
