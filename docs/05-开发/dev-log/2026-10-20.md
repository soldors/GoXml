### 0.2 安全准入第 1 项（必须先满足）

出处：`TASK-CODEGEN-001` §3.5（契约 §4.7.5 的「安全准入第 1 项」指的就是它）：

§3.5 明确要求：**第 1、2 项必须由测试证明，不能只靠代码审查**——故本轮补了注入测试。

### 0.3 核对中发现的一处单位差异（不是文档冲突，但会致错）

| 来源 | 单位 |
|---|---|
| GXML `Gap` 语义 | **dp** |
| Gio v0.10.3 `layout.Flex.Gap` | **int（像素）**——`go doc gioui.org/layout.Flex` 实测 |

两者不是同一单位。若图省事直接写 `Gap: 8`，在 DPI ≠ 1 的屏幕上间距整体偏小，
且症状随设备变化——**单一开发机上不会暴露**。因此实现必须经 `gtx.Dp` 换算，
测试也明确禁止「裸整数字面量」通过。

这一条没有两份文档互相矛盾，属「规范语义 vs 底层 API」的单位差异，
按规范语义（dp）+ 显式换算处理，不擅自改动任一份文档。

## 4. TASK-CODEGEN-001-8：`Align` 交叉轴对齐（阶段 0–2）

### 4.1 契约核对（开工前）

同 §0 的做法：契约与规范从 Git 已提交版本读取（基线 `8013d49`），不推断验收条件。

| 核对项 | 结论 | 出处 |
|---|---|---|
| 取值 | `Start` / `Center` / `End` / `Baseline`，**大小写敏感** | 规范 §3.1.2；`contracts.ParseCrossAlign` |
| 适用标签 | `Column` / `Row` / `Grid`；**`<Page>` 不在内** | `expander/schema.go:45`；ADR-0008 §2.8.1 |
| Gio 映射 | `Flex.Alignment`；**`Center` → `Middle`** | ADR-0008 §2.1 |
| Gio 常量实测 | `Start / End / Middle / Baseline`（**无 `Center`**） | `go doc -all gioui.org/layout` |
| 轴向感知默认值 | `<Row>`=Center、`<Column>`/`<Grid>`=Start | 规范 §3.1.2；ADR-0008 §2.3 |
| 默认值归谁补 | **Codegen**；IR 保持 `AlignUnset` | `ir_schema.go:298-299,711-713`；任务卡 §1.3 |
| `Baseline` 限定 | 仅 `<Row>`；其余由 Parser 报错 | 规范 §3.1.3；`parser/layout.go:78` |
| 子项级对齐 | v1 **没有 `AlignSelf`**，不生成包装层 | ADR-0008 §2.6.1 |
| 生成归属 | 「后续切片」（**不**触发安全准入第 1 项——枚举不是数值） | 契约 §4.7.5 |

### 4.2 两处最容易写错的地方

1. **Gio 没有 `Center`，居中叫 `Middle`。** 按名字直觉写 `layout.Center` 会编译失败（还好，能被发现）；
   真正的危险是有人为了「先跑起来」改用 `layout.Start` 兜底——编译通过、只断言「字段存在」的测试也通过，
   但居中静默变成左对齐。因此测试断言的是**成员名**，不是字段是否存在。
2. **`<Row>` 的默认值与 Gio 零值不一致。** `Start` 是 `Alignment` 的零值，所以 `<Column>` 省略字段
   与显式写 `layout.Start` 等价；但 `<Row>` 默认 `Center`，省略就会静默变成顶部对齐。
   ADR-0008 §2.3 称这是「唯一难以回退的决定」，并明确要求 Codegen 显式写出默认的 `Middle`。
   故本轮对两个标签**都**显式生成默认值（任务卡 §1.3 亦如此要求）。

### 4.3 发现的一处文档冲突（已于 2026-10-20 由用户裁决，已修正）

| 来源 | 记载的诊断码 |
|---|---|
| 规范 §3.1.3、ADR-0008 §2.6 | `GXML-ATTR-003` |
| `contracts/ir_schema.go:311` 注释（原文） | `GXML-ATTR-002` |

**裁决：以 `GXML-ATTR-003` 为唯一正确事实。** 依据：规范 §3.1.3、ADR-0008 §2.6 与
`parser/diagcode_test.go` 的真实断言三者一致，且 `diagdoc` 门禁早已将 `002` 列为空置码
（`TestAttr002StaysVacant`）；`ir_schema.go` 的 `002` 系早期草案笔误残留。

已按裁决把 `ir_schema.go:311` 的注释改为 `GXML-ATTR-003`。**代码与诊断逻辑无需改动**
（发码处一直是 003）。

顺带修正同一文件的另一处笔误：`NodeIR.Justify` 的注释原写「`AlignUnset` 之外只对
Column/Row 有效」，把 `Justify` 字段的默认值错写成了 `Align` 的枚举名，已改为
`JustifyUnset` 并补充说明由 Codegen 显式写出默认值。两处均只改注释，不改逻辑。

### 4.4 实现（集中在 `layout.go`）

| 文件 | 改动 |
|---|---|
| `internal/compiler/codegen/layout.go` | 新增 `defaultCrossAlign`（轴向感知默认值）、`gioAlignment`（枚举→Gio 标识符，非法枚举返回 error）、`flexFieldsExpr`（拼 `, Alignment: ...` + Gap） |
| `internal/compiler/codegen/codegen.go` | 仅接线：`containerExpr`/`dynamicContainerExpr` 的 `gap` 参数改名为 `fields`（类型不变）、Column/Row 改调 `flexFieldsExpr` 并处理 error、`<Page>` 保持传空串 |

字段顺序按 Gio 结构体声明顺序（`Axis` → `Alignment` → `Gap`），后续接入 `Justify`（`Spacing`）时插在 `Alignment` 前即可。

`<Page>` 不消费 `Align`：契约 §3.1/§4.7.2 定义它等价「无布局属性的 Column」，而 Page 按
ADR-0008 §2.8.1 沿用 Column 的默认对齐 `Start`，**恰好等于 Gio 零值**，故省略字段视觉等价。

非法枚举（`AlignUnset` 之外的未知取值）返回 error 而非静默退回 `Start`——
契约 §2.3 的失败语义要求 Codegen 出错时返回 error 且不返回部分代码。

### 6.2 唯一的坑：方向相反，且同名常量确实存在

Gio 的 `Spacing` 描述**空白留在哪**，GXML 的 `Justify` 描述**元素靠哪**，因此：

- `Start` → `SpaceEnd`（元素靠前，空白在末尾）
- `End` → `SpaceStart`（元素靠后，空白在开头）
- `Center` → `SpaceSides`（元素居中，空白在两边）

**危险之处**：`layout.SpaceStart` 与 `layout.SpaceEnd` 两个常量**确实存在**。
按名字直译（`layout.` + GXML 取值）能编译、也能跑，「字段存在」型断言同样通过——
只有视觉上前后颠倒，且在一个元素占满容器时完全看不出来。

因此除主映射测试外，另加 `TestJustifySpacingDirectionIsReversed`：
对 `Start`/`End`/`Center` 断言生成值**不等于**按名字直译会得到的错值。
这条与 `TestJustifyMapping` 的分工是：那条证明「映射正确」，这条证明「不是同名赋值」。

### 6.3 一处取舍：默认值显式写出，尽管它等于 Gio 零值

`SpaceEnd` 是 `Spacing` 的 `iota` 首项，即**零值**。所以缺省时省略字段在行为上完全等价。

仍然选择显式写出，与 `Align` 保持同一规则：不把「默认分布是什么」这一语言语义
藏进「碰巧等于零值」的实现细节里，也让生成代码能自解释。

代价与 §4.2 第 2 点同源：生成代码多一个字段；与 ADR-0008 §6 第 9 条「既有 Golden 不变」
存在张力。该条与 §2.3「`<Row>` 必须显式写出默认 Middle」本身就冲突，
而默认对齐/分布是规范 §11 已登记的 v1.1 语义变更，故按语义变更处理。

## 7. TASK-CODEGEN-001-10 / -22 尺寸接入：核对结论与一个必须先裁决的接口断层

按「先核对契约与解析器接口，再实现」的要求，本节只记录核对结果，未写实现代码。

### 7.1 `-10` 与 `-22` 的关系（先厘清，避免重复实现）

| 子任务 | 字面内容 | 实际职责 |
|---|---|---|
| `-10` | `Width`/`Height` 三取值映射，`Fill` 按主轴/交叉轴分别处理 | **属性 → Gio 调用**的生成 |
| `-22` | 尺寸决策统一走 `sizelayout.ResolveMainCross`（AST 断言无自行判断轴向的代码） | **决策来源**的归属 |

二者不是两个实现，而是**同一切片的两个验收面**：`-10` 验「生成对不对」，`-22` 验「判断从哪来」。
因此不重复实现，只保留一套完成标准，两个验收命令分别覆盖。
（`-23`/`-24`/`-25` 是更细的行为断言，其中 `-23` 交叉轴 Fill 抬 `Min` 正是下面断层所在。）

### 7.2 核对结论

| 核对项 | 结论 | 出处 |
|---|---|---|
| 三取值 | 缺省=自然 / `Fill` / 非负 dp 固定 | 规范 §3.1.4 |
| 单位 | **dp**，经 `gtx.Metric` 换算；`float32` 精度 | 规范 §3.1.5「数值格式」 |
| 非法值 | 拒绝负值、`NaN`/`Inf`、指数形式、单位后缀、百分号、绑定 | 规范 §3.1.5；`parser.parseSize` |
| 轴向判定 | `Row`：主轴水平、交叉轴垂直；`Column`/`Page`：主轴垂直；`Grid` 单元格：主轴水平 | 规范 §3.1.7「主轴与交叉轴的判定」 |
| 主轴 `Fill` | 参与弹性分配，权重 1，与其他 `Fill` 兄弟等权均分 | 规范 §3.1.7 |
| 交叉轴 `Fill` | 填充父容器传入的该方向 `Max`；**无界时退化为自然尺寸** | 规范 §3.1.7 |
| 固定尺寸 | 精确该值；**超出父容器不裁剪、不报错** | 规范 §3.1.5「约束冲突规则」 |
| IR 形态 | `SizeSpec{Mode, Value}`；`Mode` 缺省为 `SizeNatural`(=0)，`IsSet()` 区分是否显式 | `contracts/ir_schema.go:407-431` |
| 决策函数 | `sizelayout.Resolve(spec, axis, max) Directive` / `ResolveMainCross(w, h, mainIsHorizontal, availW, availH)` | `sizelayout.go:92-127` |

### 7.3 断层：`ResolveMainCross` 的入口需要运行时值，而生成代码无法 import `internal`

这是本次核对唯一的阻塞项，必须先说清楚：

1. 规范 §3.1.7 明确：**「识别无界是编译器的责任，且只有一处：由布局语义层（`internal/compiler/sizelayout`）统一判定。Parser 与 Codegen 不得各自判断。」**
2. 但 `ResolveMainCross` 的签名要求 `availWidth, availHeight int`——它们是**运行时**的 `gtx.Constraints`，Codegen 在编译期拿不到。
3. 因此「让生成代码调用 `sizelayout`」这条路走不通：生成代码落在**用户的独立 module**（`buildInTempModule` 用 `example.com/miniproj` 构建，已验证），Go 语言禁止跨 module import `internal/`。
4. `pkg/runtime` 下目前只有 `app`，**没有任何布局辅助包**；全仓 `ResolveMainCross` 在生产路径零调用（只有它自己的测试）。

**断层一句话**：契约要求「判定只有一处」，但那一处（`internal`）在生成的代码里不可达。

### 7.4 两个可行方案（需要裁决）

| | 方案 A：编译期决策 + 生成运行时检查 | 方案 B：把运行时判定提升为公开包 |
|---|---|---|
| 做法 | Codegen 编译期调用 `sizelayout.Resolve`（传已知有解的 `max`）拿到 Directive；对 `Cross+Fill` 生成 `if gtx.Constraints.Max.Y < <阈值> { ... }`，阈值取自 `sizelayout.UnboundedThreshold` | 新建 `pkg/runtime/layoutx`（公开），把 `Resolve`/`IsUnbounded`/`Directive` 的运行时部分搬过去；生成代码 import 它 |
| 是否满足 §3.1.7「只有一处判定」 | 判定**逻辑**唯一（阈值与分支条件都来自 `sizelayout`），但**执行位置**在生成代码里 | 完全满足 |
| 生成代码是否含轴向分支 | **不含**（轴向在编译期已确定，天然满足 `-22` 的 AST 断言） | 不含 |
| 代价 | 无界检查的 `if` 出现在生成代码里，与 §3.1.7「Codegen 不得自行判断」**字面有张力**（可论证：Codegen 不判断，只把 sizelayout 的判定输出为代码） | 新增公开包 + 契约变更 + 影响所有生成代码的 import；明显超出 `-10` 切片范围 |
| 影响面 | 仅 `layout.go` + 生成模板 | `pkg/runtime/layoutx`（新）、`sizelayout`（可能变薄壳）、契约 §15、所有尺寸相关生成 |

**我的推荐是 A**：`-10` 是属性生成切片，方案 B 等于在做架构迁移；而 A 的「字面张力」可以用一句约束消解——
**阈值必须是 `sizelayout.UnboundedThreshold` 的引用（编译期读取后写为字面量），禁止在 layout.go 里另写魔法数字**，
这样「无界」这个概念在仓库里仍然只有一个定义处。

但按项目「契约冲突不自行选一份作准绳」的规则，**这一条需要你点头我才动手**。

### 7.5 已确定、与方案无关的部分（裁决后可立即实现）

  因此只有 `Fill` 需要分轴——这缩小了方案 A/B 的分歧面。

## 8. 方案 A 的契约草案（第一阶段产出，未写实现）

### 8.1 Gio 约束行为的实测结果（v0.10.3，非推导）

探针 `zz_probe_test.go`（跑完即删）用 `layout.Context{Ops, Constraints, Metric}` 直接测量：

| 场景 | 实测 |
|---|---|
| 父 `Max=(300,200)`，`Flex{Horizontal}`，`Rigid` 子项 | 收到 `Min=(0,0) Max=(300,200)` |
| 同上，`Flexed(1)` 子项 | 收到 `Min=(200,0) Max=(200,200)`（主轴 `Min==Max` = 300−100） |
| 父交叉轴 `Max.Y=1<<30`，`Rigid` 子项 | 收到 `Max=(300, 1073741824)` |
| 闭包内执行 `Min.Y = Max.Y`（有界 200） | `Min` 变 `(0,200)` |
| 同上但在无界 1<<30 下 | `Min` 变 `(0,1073741824)` —— 规范 §3.1.7 所述灾难得到证实 |
| 两个 `Rigid` 尺寸 `(100,30)`/`(50,120)` | `Flex` 返回 `(150,120)`：主轴累加、交叉轴取最大 |

由此确定四件与实现直接相关的事实：

1. **交叉轴约束原样向下传递**，与规范 §3.1.7「嵌套容器的约束传递」第 2 条一致；因此「父容器交叉轴是否有界」与「本节点收到的是否有界」是同一件事，**判断位置可以放在子项闭包内**。
2. `Flexed` 子项的**主轴** `Min==Max`，已被父容器锁定，子项不得再改主轴约束；只有交叉轴可动。
3. 抬 `Min` 到 `Max` 在无界时确实产生 `2^30` 量级尺寸，**必须在抬之前判断**，事后的 clamping 无法收场。
4. 交叉轴的「轴」随容器方向变化：`Horizontal` 容器的交叉轴是 **Y**，`Vertical` 容器是 **X**。该轴在**编译期**即可确定，不需要生成代码推断。

### 8.2 规范 §3.1.7「只有一处」的准确含义

原文：

> **识别无界是编译器的责任，且只有一处**：由布局语义层（`internal/compiler/sizelayout`）统一判定。Parser 与 Codegen 不得各自判断。

按字面，「不得各自判断」排除的是：**Parser 判一套、Codegen 再判一套**（两处独立实现会各自漂移）。
它要求的不是「判断表达式只能出现在一个源文件里」——那样连内联展开都算违规，而任何代码生成器都必须展开。

因此本方案把它读作：**无界的概念定义（阈值 + 比较方向 + 作用轴）只能有一个来源**；
生成代码里的 `if` 是该定义的**内联展开**，不是第二处定义。

这个读法要在契约里成立，必须同时满足三条（缺一即回退到方案 B）：

| # | 约束 | 如何保证 |
|---|---|---|
| 1 | 阈值只有一个来源 | 生成的字面量**只能**来自 `sizelayout.Plan(...)` 的返回值，禁止 `layout.go` 出现任何数字常量 |
| 2 | 轴与比较方向也来自同一处 | `Plan` 返回 `CrossAxis`（X/Y）；比较方向由模板固定为「不小于阈值即视为无界」，与 `IsUnbounded` 同义 |
| 3 | 生成器只有一处模板 | 四个生成点（静态/动态容器、For/If 子项）**共用同一个** `sizeWrap`，不复制 |

第 3 条同时是用户「统一生成辅助逻辑」要求的落点。

### 8.3 契约修订草案（建议并入 `代码生成输出契约.md` §15.6）

> **§15.6 尺寸属性的生成**
>
> #### 15.6.1 职责边界
>
> `sizelayout` 是尺寸语义的**唯一**定义处：
> - 编译期：`sizelayout.Plan(width, height, mainIsHorizontal)` 返回「主轴/交叉轴各用什么指令、交叉轴是哪一维、无界阈值是多少」。它**不读取任何运行时尺寸**。
> - 运行时：生成代码按指令执行约束转换；其中 `FillCross` 指令附带一次「有界性检查」。
>
> Codegen **不得**重新解释 `SizeSpec`，也不得自行决定轴、阈值或比较方向；它只把 `Plan` 的结果翻译成 Gio 调用。
>
> #### 15.6.2 轴向映射（编译期确定，生成代码不推断）
>
> | 父容器 | 主轴 | 交叉轴 | 主轴对应属性 | 交叉轴对应属性 |
> |---|---|---|---|---|
> | `<Row>` | 水平 | 垂直 | `Width` | `Height` |
> | `<Column>` | 垂直 | 水平 | `Height` | `Width` |
> | `<Page>` | 垂直 | 水平 | `Height` | `Width` |
> | `<Grid>` 单元格 | 水平 | 垂直 | `Width`（禁止） | `Height` |
>
> `<If>` / `<For>` 不产生新轴，透传父容器的轴（规范 §3.1.7）。
>
> #### 15.6.3 四种指令的生成模板
>
> | 指令 | 生成 |
> |---|---|
> | `Natural` | 子项照原样，**不生成任何约束代码** |
> | `Flex`（仅主轴） | `layout.Flexed(1, func(gtx) {...})` 取代 `layout.Rigid(...)` |
> | `Exact` | 闭包首行：`gtx.Constraints.Min.<A> = gtx.Dp(<v>)`、`gtx.Constraints.Max.<A> = gtx.Constraints.Min.<A>` |
> | `FillCross` | 闭包首行：`if gtx.Constraints.Max.<A> < <阈值> { gtx.Constraints.Min.<A> = gtx.Constraints.Max.<A> }` |
>
> 其中 `<A>` 是 `Plan.CrossAxis` 给出的 `X`/`Y` **字面量**，`<v>` 是 `formatDp` 后的数值字面量，
> `<阈值>` 是 `Plan.Threshold` 的十进制字面量。三者都不得由生成器自行决定。
>
> #### 15.6.4 固定尺寸溢出
>
> `Exact` 指令直接写精确约束，**不生成** `Clip`、不生成 `Min` 修正、不与父 `Max` 取小。
> 规范 §3.1.5 明确「不裁剪、不报错」，实现必须保留该行为。
>
> #### 15.6.5 与无界判定的关系
>
> `FillCross` 模板中的 `if` 是 `sizelayout.IsUnbounded` 的**内联展开**，不是第二处判定：
> 阈值、轴、比较方向均来自 `Plan`；展开模板在生成器中只有一处。
> 若将来 `sizelayout` 的判定方式变化（例如改用别的表示无界的约定），只需改 `Plan` 与 `IsUnbounded`，
> 生成器模板随之重生成，无需在生成器内二次判断。
>

### 8.4 为什么 `Plan` 不构成「第二个 Resolve」

`PlanFor` 内部仍调用既有的 `ResolveMainCross(w, h, mainIsHorizontal, 0, 0)`——
传 `0` 表示「假定有界」，只取语义分支（`Cross+Fill → FillCross`），
再补上 `CrossAxis` 与 `Threshold` 两项**编译期元信息**。

因此：语义判定仍只有 `Resolve` 一处；`PlanFor` 是它的**编译期视图**，不复制任何判断分支。
这一点需要在实现时用测试锁住：`PlanFor` 的 `Main/Cross` 必须与 `Resolve` 在「有界」输入下的结果逐项相等。
