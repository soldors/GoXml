## 3. `3cd258b` Codegen 输出契约冻结与最小纵向切片

### 3.1 先冻结，再编码

按「先定结构再实现」的原则，先解决三处冲突：

| 冲突 | 处理 |
|---|---|
| 草稿用 `func UI(...)`，契约 §4.3 已冻结 `Goxml<Path>View.Layout` | 以契约为准 |
| 草稿称包名由 `Options` 提供，契约 §4.1 要求从目标目录解析 | 分工：§4.1 管**来源**，`Options` 只是**传递通道** |
| **契约 §4.3 的 `Layout` 没有主题参数**，但渲染文本必须有 `material.Theme`；而字体文档 §6.2 规定生成代码用 `th.Fonts.Family` | 两份冻结文档互相矛盾 → 新增 §4.3.1/§4.3.2 |

主题决策：作为 `Layout` 参数，类型固定为 `*material.Theme`（Gio 的），
不是项目自有主题封装。理由：`pkg/runtime/theme` 会演进，`material.Theme` 是稳定 API；
生成代码依赖后者，项目主题怎么改都不会反向改动已生成代码的签名。

### 3.2 实现

`internal/compiler/codegen`：`Generate(*analyzer.VerifiedDoc, Options) ([]byte, error)`。

- 支持 `<Page>` + 单个静态 `<Text>`
- import 按需收集、去重、冲突别名（契约 §7 早已定义，未新造）
- 一律经 `go/format.Source`；失败返回 error 且**不返回部分代码**

### 3.3 依赖变更

`gioui.org v0.10.3` 加入 `go.mod`。此前约定的「仅在 Codegen 接入时加入」即此刻。

验证离线可复现：`GOFLAGS=-mod=readonly` + `GOPROXY=off` 下 `go build ./...` 通过。

期间踩过一个坑：`go mod tidy` 会因 Gio 的**测试依赖**（`x/image`、`x/text`、`x/sys`）
未缓存而失败；用 `go get` 拉齐后缓存完备。

- `Run`：四阶段串联，任一失败即返回
- `Commit`：临时文件 → 复读校验 → 原子替换；失败删临时文件、旧文件不变
- `Hooks`：可替换 `Generate` / `Load` / `Analyze`，只为观察「是否被调用」

### 4.4 关闭第 20 条的证据

**不是**「返回了错误」，而是：

| `TestCommitFailureLeavesTargetUntouched` | 旧文件字节不变、无临时残留 |

## 10. `d4f3e38` 安全审查：发现并修复路径穿越（高危）

### 10.1 方法：实证探针，不写通用安全说明

沿真实数据流逐组件做探针，每条结论附可复现测试。**先盘实现，再写报告**。

### 10.2 唯一确认缺陷：`Commit` 路径穿越

修复前 `Commit` 直接 `filepath.Join(dir, a.OutputName)`，无任何校验。探针实测：

```text
OutputName = "../<outside>/evil.go"
→ 返回 err=<nil>，文件被写到目标目录之外
```

**根因是信任假设错误**：`Artifact` 字段是导出的，调用方可直接构造，
因此 `Commit` 不能假设它来自 Codegen。

修复 `validateOutputName`：纯文件名、不含分隔符、非 `.`/`..`、不以 `.` 开头、
以 `.go` 结尾。回归测试覆盖 9 种非法名，并断言「目标目录之外不得出现任何文件」。

### 10.3 两处已量化但未修的资源风险

**Parser 无嵌套深度限制**：

| 深度 | 耗时 |
|---:|---|
| 5,000 | 0.23 s |
| 20,000 | 3.26 s |
| 100,000 | **> 20 s 未返回** |

**`<Def>` 组合指数膨胀**（每层调用下一层两次）：

| 层数 | 源码 | 耗时 |
|---:|---:|---:|
| 8 | 490 B | 0.5 ms |
| 16 | 894 B | 68 ms |
| 20 | 1,098 B | **1.11 s** |

源码增加 204 字节，耗时增加约 1000 倍。现有 `DEF-010` 只拦**递归**，
拦不住有向无环的爆炸。

## 14. `ae3cf0f` 静态子树固化 A1/A2：三项实测推翻直觉（09:52–10:20）

### 14.1 为什么先用 headless 做像素验证

直觉方案是「把 `CallOp` 存进结构体，后续帧 `Add` 回放」。但 `ops.Ops` 的数据不可从包外观测：

| 尝试 | 结果 |
|---|---|
| 读字节数 | `ops.Ops.data` 未导出 |
| `op.NewReader` 解码计数 | 不在 `op` 公开 API |
| `call.Add()` 不 panic 就算成功 | **不成立**——空操作也不 panic |

最终用 `gpu/headless` 离屏渲染 + 像素差分。这是唯一能证明「回放真的画出了东西」的方法。

### 14.2 结论 1：`CallOp` 不能跨帧保存

实测：源 `Ops` 上录制 → `srcOps.Reset()` → `call.Add(newOps)` 再 `Frame`：

```text
panic: runtime error: slice bounds out of range [9:0]
  gioui.org/internal/ops.(*Reader).Decode
```

根因：

```go
func Reset(o *Ops) { ... o.data = o.data[:0] ... }
type CallOp struct { ops *ops.Ops; start, end ops.PC }
```

`Reset` 截断 `data`，`[start,end)` 指向已不存在的区间。

`op.Defer` **不能**规避——它不是复制数据，仍引用源 `Ops`（实测同样 panic）。

**Gio 自己从不跨帧保存 `CallOp`**：`flex.go` 的 `scratchSpace.call` 是函数局部变量，
每次 `Layout` 重建。这印证约束是设计性的。

→ **设计结论**：缓存必须配套**专用的持久 `op.Ops`**，与每帧的帧 Ops 分离。

### 14.3 结论 2：`Flex` 内部已经录制，再录会重复

`layout.Flex.Layout` 对每个 `Rigid` 子节点执行 `macro := op.Record(gtx.Ops)`。
若生成代码再为子节点额外录制，就是「Flex 录一次 + 我们录一次」。

→ **设计结论**：只固化**最外层**静态边界，内部不再生成缓存槽位。
该结论待 A6 基准实测确认。

### 14.4 结论 3：像素比对的正确判据

同帧「录制+回放」vs 直接布局：7200 像素中非零像素数**均为 229**，
仅 4 个字节差异（浮点抗锯齿）。说明渲染实质一致。

这也说明：**像素级「完全相等」不是可靠判据**，应比对非零像素数或容忍极小差异。

### 14.5 产出

- `ADR-0009-静态子树固化机制.md`：8 个待澄清问题逐项结论 + A3 契约草案

与「Codegen 不得自行解析绑定路径」冲突。

因此 MVP 明确收窄为**无参事件**，带参事件需先扩展 Facts（独立任务）。

`ResolvedFor` 只有 Each/Elem/Index/IndexType/Key，**没有 In 数据源路径**。
与之前 `ResolvedParam` 不含实参值是同类缺口：Codegen 拿不到

- **内联展开**：含 For 的容器改为「立即调用闭包」表达式，运行时组装

1. **`op` 导入变成未使用**：展示型 For 页面既无 Record 也无 InvalidateCmd，

## 39. `451272c` `<If>` 条件渲染：契约 + 实现（08:57–09:40）

### 39.1 一个意外的好消息：Facts 不需要扩展

`<For>` 需要补 `ResolvedFor.In`，但 `<If>` **不用**——Analyzer 早已把
`Condition` 解析成 `ResolvedAttr{Target: PropBool}`（与普通属性同构），
Codegen 直接用 `lookupAttr(n, "Condition", facts)` 即可。
Analyzer 也已递归遍历 `Then`/`Else` 子树。

### 39.2 六处实现 + 一处语义修正

1. `hasDynamic` 覆盖 `KindIf` —— 漏判会让分支冻进整页宏
2. 容器分流：`hasIfChild` 与 For 一起走动态组装
3. `emitIfChildren`：`cond := <expr>; if cond { append... } else { append... }`
   —— **内联展开**，`<Then>`/`<Else>` 本身不产生节点
4. `emitBranchAppends` 里再分派嵌套 For/If（支持 §4.3 的任意组合）
5. `clickSlot.guards` / `rowClickSlot.guards`：按钮记录所处分支条件
6. 轮询守卫：Then 用条件本身，Else 用 `!(cond)`
7. `emitForChildren` 加 If 分派（循环体里的 If）

### 39.3 语义修正：行级条件不能用于整池清理

第一版把守卫直接拼到清理条件里：

```go
if rowItem.Done && len(v.rowClicks0) > len(rowItems) {   // rowItem 未定义！
```

`rowItem` 在循环外不可见 → 编译失败。**但更深的问题是语义**：
清理是「键集合」的函数，与某一行是否渲染无关。

修正：`guardCond{expr, rowScoped}` 区分两类守卫——
轮询用全部守卫（行级条件改写 item→rowItem），清理只用非行级守卫。
若外层 If 隐藏，则跳过清理（条件恢复后行状态仍可用）。

## 48. `0b07a18` 1-5：两阶段事务提交（G4 冻结落地）（13:00–13:30）

### 48.1 G4 冻结语义（与用户确认）

- **全或无（策略 A）**：批次是原子单元；
- **回滚对象 = 本批次目标文件**；已有文件在批次成功前不被触碰；
- 回滚本身失败必须报错，不得静默。

理由（评审补充）：同包内混新旧两代生成文件会造成符号冲突，
`go build` 报重定义——比「全部回滚」更难诊断。

### 48.2 实现（commit.go）

| 函数 | 职责 |
|---|---|
| `stageBatch` | 阶段一：全部产物写入各自目标目录的临时文件（`.goxml-*.tmp`，同目录保证 rename 原子性）；任一失败即清理已写入的并返回 |
| `commitBatch` | 阶段二：全部成功后逐个 `os.Rename` 覆盖落盘 |
| `cleanup` | 删临时文件；失败收集为错误（不静默） |

runPipeline 改造：阶段一先**全部**跑管线（不碰磁盘），全过后才 stage →
commit。生成失败发生在阶段一 → 「批次全部放弃，磁盘无任何变更」。

### 48.3 一个如实标注的边界

阶段二 rename 失败时，已 rename 的文件**无法**进程内还原（rename 不是
copy）——按冻结语义上报为环境级故障（磁盘满/权限突变），先清理未提交的
临时文件再报错；若回滚也失败，两个错误都报。这不是「尽量回滚」的模糊话：
**进程内能保证的边界被明说**。

### 48.4 验收（6 项）

| 测试 | 证明 |
|---|---|
| TestStageBatchWritesAllTemps | 阶段一只写临时文件，目标不存在 |
| TestStageBatchRollsBackOnFailure | 任一失败 → 全部临时清理 + 原始原因保留 + 无目标文件 |
| TestCommitBatchRenamesAll | 阶段二全部落盘、临时消失 |
| TestCommitBatchOverwritesExisting | 成功批次才允许覆盖 |
| **TestExistingFileUntouchedOnFailure** | 失败后已有文件**内容与 mtime 原样**（G4 核心语义） |

### 59.2 R2-1 lastApplied 算法（本轮最重要的发现）

- 文本同光标不同：V==A 不 SetText ⇒ 光标/选区/IME 全保留（唯一手段）

### 83.4 两个自查发现（写下来防止重犯）

**① 第一条「长度前缀」测试当初是假的。**
最初用 `(SourceRel=ab, OutputRel=c)` vs `(a, bc)`，实测变异**不红**——
因为字段之间本来就有固定**标签**分隔，不需要长度也分得开。
真正的歧义向量是「值里嵌入了下一个标签文本」。已改为
`a+outputRel+b / c` vs `a / b+outputRel+c`，M1 才咬住。

**② 「把长度改成 0」不是有效变异。**
`uint32(0)` 仍然写出 4 个零字节，零字节本身充当分隔符，用例照样绿。
一开始据此误判「长度前缀没用」，用记录型 `hash.Hash` 打印真实字节流后才看清：

```text
A="\x00\x00\x00\x00sourceRel\x00\x00\x00\x00aoutputRelb\x00\x00\x00\x00outputRel\x00\x00\x00\x00c"
B="\x00\x00\x00\x00sourceRel\x00\x00\x00\x00a\x00\x00\x00\x00outputRel\x00\x00\x00\x00boutputRelc"
```

教训：**变异必须真的移除机制**，只把参数改成退化值可能仍在保留机制。

### 85.4 一次被变异测试抓住的错误论证（本轮最重要）

卡 §2.1 初版断言：「K3 若包含本轮产物，**命中率恒为 0**」。M3 变异（排除集只留 Manifest，
丢掉 batchTargets）**没有让任何用例变红**——说明这个论证是错的。

复查代码后确认：每次运行都在**写盘之前**把所有键算完，同批产物的写入发生在算键之后，
因此「本批 target」在正常流程下根本不会进入本次指纹。真实影响只在
**产物存在但未登记**（提交后/存 Manifest 前中断，或 Manifest 被清空）时出现：

- 本次键 ≠ 缓存键 → 未命中，且原因被误报成 `package-sources-changed`；
- 缓存记录被自己的产物挤掉。

处置：保留排除集（它防的是这个场景），**改写论证**，并新增
`TestCacheHitManifestLossKeepsKeyStable` 专门证伪该变异——补测后 M3 变红（8/8）。

同时把卡 §7 的 C14 说明改正（它原本声称覆盖 T1，实际不覆盖），新增 C14b 行。
