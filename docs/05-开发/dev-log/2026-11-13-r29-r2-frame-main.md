# R29-C R2：Gio 帧提交握手与进程级 Main 所有权（HY4，2026-11-13）

- 分支 `codex/r29-r2-hy4-window-host`，父 `230fe7d`。协调者帧握手红
  `c-frame-probe_test.go` 复现（台账 `r2-replay-frame-red` rc=1）：独立 pump
  在前一帧 Frame 回调之前进入下一次 Event。
- **依赖源码核对**（gioui.org v0.10.3，本机 module cache 只读）：
  `app/os.go` 的 `eventLoop.deliverEvent` 在投递 FrameEvent 后把
  `frames=e.frames`，等 client 调 `FrameEvent.Frame`（`eventLoop.Frame`
  发送到 frames 并阻塞在 `<-frameAck`），`ProcessFrame` 完成后 ack；
  随后用 `theFlushEvent` 确认前一事件已处理（`eventLoop.Event` 消费
  flushEvent 才返回下一个非 flush 事件）。`app/window.go:992` 的
  flushEvent 注释、`validateAndProcess` 的 sigChan 信号共同构成该顺序。
- **修复**：`WindowHost.loopWindow` 改为严格请求驱动——pump 只在 loop
  通过 `requests` 明确放行时读取一次 `Event()`；loop 处理完该事件
  （Layout + `e.Frame` 回调返回 + 关闭请求结算）后才发下一次请求。
  每窗独立 requests/events/pump；Close 仍只排队（非阻塞），首个事件前
  不交付，destroySeen/destroyed 双门闩销毁优先，关 A 不影响 B。
  **真实后端时序风险**：受控探针只证明生产宿主的事件顺序，没有在真实
  原生窗口执行帧交换/ack，不得表述为「原生已挂起/已验证」。
- **Main 混用审计**：删除 R1 只计数的 mainFunc 包装，改为包级
  `claimGioMain(who)` 状态机（owner/calls/blockedCalls/once）与
  `GioMainState()` 只读快照。旧入口 `App.Run`、`RunSingleWindowProcess`
  与 `WindowHost.Run` 都在调用 Main 前认领：
  - 旧入口先行 → Host.Run 返回 `ErrGioMainAlreadyOwned`；
  - Host 先行 → 旧 `Run`/`RunWith`/`App.Run` 返回同一错误（不启动窗口
    loop），`RunSingleWindowProcess` 经 Observer 交出错误并 exit(1)；
  - 并发入口由 mutex + once 串行，只有一个成功、Main 只调用一次；
  - 无 Host 的已批准单窗正常路径逐字兼容。

  反例与双窗 marker 回放保持绿。
