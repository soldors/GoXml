### 27.2 B3：产物落地与"可复现性"事故

产物：`pkg/runtime/theme/embedded/`

| 文件 | 字节 | SHA-256 |
|---|---|---|
| `GoxmlSansSC-Regular.otf` | 1,625,796 | `652910bee7fb0facfd9333b173c5ea7819eeadea8950592cf3f748bcb158e507` |
| `charset.txt`（7,540 行） | 52,780 | `d059792a99c1973fae338abaf24f54c383f91e7146888a75af61fa78487ae06f` |
| `LICENSE`（OFL 1.1 全文） | 4,301 | `6a73f9541c2de74158c0e7cf6b0a58ef774f5a780bf191f2d7ec9cc53efe2bf2` |
| `METADATA.json` | 1,754 | — |

**踩到的坑：改名步骤让产物不可复现。** 第一次落地的哈希是 `92d14965…`，
第二次重跑变成 `652910be…`，字节数却完全相同（1,625,796）——典型的"内容变了但长度没变"。
根因：`fontTools.ttLib.TTFont(src)` 默认 `recalcTimestamp=True`，保存时把
`head.modified` 改写成当前时间。

修法：`TTFont(src, recalcTimestamp=False)`，并在 `pyftsubset` 参数里显式加
`--no-recalc-timestamp`（4.67.0 的默认值本来就是 no-recalc，显式写出来是防默认值变化）。
**验证：连跑两次脚本，SHA-256 相同**。这是"产物哈希可断言"的前提——不可复现的哈希
不是证据，只是一次快照。

`scripts/font/subset.py` 的自我保护：输入文件 SHA-256 不符直接拒绝执行；
字符集规模偏离 (7540/6763) 拒绝执行；`--verify-only` 复算三个产物与字体名。
这几个"拒绝"是刻意的：宁可构建失败，也不要静默换字体。

### 27.3 B4：顺序由控制流保证，不是靠开关

- `ProviderOptions.Embedded EmbeddedFontLoader` 是**注入点**。没有它就无法证明
  "系统命中时不解析嵌入"——直接调用 `embedded` 包没法计数。
- `ResolveWithReport` 里 `probe()` 成功即 return，只有 `rep.Err != nil` 才走
  `loadEmbedded()`。顺序写在控制流里，不存在"忘了关开关"。
- 兜底成功后必须把 `rep.Err` **清空**。不清空的话调用方会把"已兜底成功"读成"失败"——
  这是很容易漏的一步，用例里单独断言了。

### 27.4 B5：demo 不能当靶子（本轮的第二个发现）

先按卡面说的用 `examples/demo` 前后对比，结果是：

```
未嵌入=15,158,272 B, 嵌入=15,157,760 B, 增量=-512 B
```

让 `theme → probe → defaultEmbeddedLoader → embedded.Load → fontData` 被真实链接。

| 目标 | 未嵌入 | 嵌入 | 增量 |
|---|---|---|---|
| `examples/demo`（参考，不断言） | 15,158,272 | 15,157,760 | −512 |

## 29. TASK-FONT-001-C：按字形覆盖的 fallback 链（实现 + 验收）

### 29.1 先取证再冻结边界

开工前用 `pkg/runtime/theme/testdata/fallbackprobe`（`testdata/` 不参与 `./...`）
跑了 6 个场景，三个结论直接决定了 C 的边界：

1. **Gio v0.10.3 已经内建逐字形 fallback，C 不重建它。**
   `fontscan.FontMap.ResolveFace` 有 5 级（精确族名 → 系统 fallback → 手动
   AddFace → script 覆盖 → **返回任意 face**）。第 5 级是问题根源：
   没有任何字体含该字形时它**不返回 nil**，而是返回一个任意 face 渲染成
   notdef，且全过程静默。C 的职责变成「可观测 + 准入 + 按需补链」。
2. **`Glyph.ID` 可反解**（`facebits=16 sizebits=16 gidbits=32`），
   `gid == 0 ⟺` 无字形。受控场景下与 `NominalGlyph` **10/10 一致**。
3. **collection 顺序 = 字形级优先级**，且**缺字形才跨到下一个**。
   指纹实测：`世` 嵌入=691 / 系统=1037；`[嵌入,系统]` 取 691、`[系统,嵌入]` 取 1037；
   `〇`（嵌入无、系统有）两种顺序都取 28579。

**最关键的一条**：遍历 charset.txt 全部 7,540 个码位比较嵌入与 msyh——

```text
两者都有 7540 | 仅嵌入有 0 | 仅系统有 0 | 两者都无 0
```

本机嵌入是系统覆盖的**真子集、零增量**。因此补充链设为**按需**触发：
覆盖完整时不加载嵌入（B4「系统命中不解析嵌入」的约束保持有效）；
只有覆盖判定发现缺口时才追加。否则就是纯付 1.6ms 解析换不到任何字形。

### 29.2 实现

- `pkg/runtime/theme/fallback.go`（新）：`splitGlyphID`、`GlyphResolution`、
  `Resolver`（`ResolveRune` / `MissingGlyphs`）、`Coverage` / `CoverageSufficient`、
  `RequiredRunes`（20 个码位：GB2312 一级字 16 + 全角标点 4）、`CoverageResult`。
- `font.go`（改）：新状态 `StatusCoverageInsufficient`、`Provider.supplement`、
  `ProbeReport.Coverage`。
- 一次只 shape 一个 rune：`text.Glyph` 只带 cluster 的 rune **计数**，不带 rune 本身。

### 29.3 两个值得记住的发现

**（1）变异测试抓出一个"没人断言"的字段。**
首轮把解码器的 faceIdx 位移改错，**测试仍全绿**——`FaceIdx` 当时没有任何断言，
而 gid 解码独立于该位移。修法不是放宽断言，而是补
"FaceIdx 必须指向 collection 的实际位置"，重跑同一变异后如期变红。
教训：新增诊断字段若没有断言覆盖，它就是装饰品，错了也无人察觉。

**（2）覆盖判定首版慢了 27 倍，瓶颈是接口解包不是字形查询。**
`Coverage` 把 `faces[i].Face.Face()` 写在码位循环里 → **589 µs/op**；
而 `NominalGlyph` 本身是纳秒级。把解包提到循环外 → **22 µs/op**。
判定跑在探测热路径上（每个候选一次），这个数量级差异会直接叠加到
本已 ~96 ms 的系统探测上。已在代码注释写明"勿回退"。

## 30. 架构评审回应 + TASK-FONT-001-D 设计冻结

### 30.1 评审结论的处理

评审同意 C 按子任务验收关闭，但 `TASK-FONT-001` 整体不关闭。两条被点名的风险
已写进 C 卡 §7 与父卡 §3.3：

1. **`Glyph.ID` 位布局是 Gio 实现细节**。146 个码位当前一致**不能**证明未来
   版本会保持布局 → 明确为「升级 Gio 时强制回归门禁」，且升级前主动读
   `text/shaper.go` 的 `newGlyphID`，门禁失败不许靠放宽断言变绿。
2. **本机零增量不是补充链无用的证据**。修正了 C 卡 §7-6 的原措辞
   （"无法证明收益" → "只说明本机 Windows 已覆盖，不能推广"）。
   补充链的**收益**论证未完成，只完成机制；Linux 精简环境验证列为必修项。

### 30.2 D1 基线实测（新探针 `testdata/coldstartprobe`）

| 阶段 | 冷（首次进程） | 进程内重复 |
|---|---|---|
| `ResolveWithReport`（探测+覆盖） | **97.4 / 109.1 ms** | 81–101 ms（每轮重扫，无缓存） |
| `text.NewShaper`（系统字体索引） | **38.5 ms** | ~0.5 ms（磁盘缓存） |
| 首次 shaping（10 字符） | **53.7 ms** | 36–50 ms（per-shaper，热轮不降） |
| 小计 | **~190 ms** | ~128 ms |
| 嵌入 Load + ParseCollection | 1.49–1.68 ms | — |
| `NewShaper(NoSystemFonts())` | ~0 s | ~0 s |

三条影响设计的读数：

1. 探测 97–109 ms 远超 20 ms，且**没有 Provider 层缓存**可依赖。
2. **首次 shaping 是 per-shaper 的** → D3「加载完换真字体」会重新付 41–53 ms，
   不能只看"后台加载完成了"。
3. **零值 `&text.Shaper{}` 首次使用会同步建系统字体索引（38.5 ms）**
   → 「首帧先用零值 shaper 顶着」等于没懒加载，首帧临时 shaper **必须
   显式 `NoSystemFonts()`**。

未测到真实首帧（需窗口环境）——上表最末一步是 shaping，已在 D 卡 §2 标注，
**不得用 shaping 时长冒充首帧时长**。

### 30.3 D 的设计冻结（依据 Gio v0.10.3 源码，非推断）

- `app/window.go:284`：`Window.Invalidate()` 注释原文
  **"Invalidate is safe for concurrent use."**，且明确
  "intended for externally triggered updates, such as a response from a
  network request" —— 正是异步加载完成的场景。
- `widget/material/theme.go:39`：`Theme.Shaper` 是 `*text.Shaper`；
  36-37 行要求每个顶层窗口有独立 Theme/Shaper。
- `text/shaper.go:210-216`：shaper 内部是 map 缓存，**跨 goroutine 布局会 panic**。

三个设计问题的冻结答复：

| 问题 | 答复 |
|---|---|
| 加载完成后如何更新字体？ | **帧内替换**：后台只算结果 + `Invalidate()`，
  在 FrameEvent 内（同一 goroutine）换 `th.Shaper`；**不在共享对象原地改集合** |
| 加载期间用什么字体？ | `NoSystemFonts()` + 嵌入子集（~1.5 ms，中文可见）；
  零值 shaper 方案因 38.5 ms 冷启被否决；**跳动必须有测试覆盖** |
| 失败后如何处理？ | 两条链路全失败 → `ErrFontNotFound` + 诊断可见 + 终态明确；
  允许有限重试，不做后台无限轮询 |

两个预算（20 ms 探测 / 首帧）已在 D 卡 §1 明确分开，且写明二者互不蕴含。

### 31.2 本轮只做一件事：冻结 D 卡 §3 的两个待选项

按评审建议冻结，不再保留备选：

| 待选项 | 冻结取值 |
|---|---|
| Loading 期间重复请求 | **立即返回临时字体**——不等待、不重复触发加载 |
| Failed 后重试 | **不自动重试**，只由显式请求触发（不做后台轮询、不每帧重试、不设自动退避） |

理由写进卡内：两者是同一条原则的两面——**调用方永远不该为一个它没主动要求的
加载等待或付代价**。"Loading 期间等待"会让"不阻塞首帧"的成果在第二个调用点
被抵消；"失败自动重试"则把已明确报告的失败重新变成周期性后台工作，且与 D5
「失败必须在诊断里保持可见」冲突。

同步补了两条验收（否则冻结没有落点）：

- **5a**：注入"永不完成"的加载器，断言请求**不阻塞**、返回临时字体、加载器只被调用 1 次；
- **5b**：注入失败加载器，断言失败后**不发起**第二次加载，只有显式重试才触发（1 → 2）。
