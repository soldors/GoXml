# GXML 项目质量审计统一交付协议 V2

## 1. 角色与目标

本项目处于工程质量验证和完工验收阶段。

你只负责自己被分配的角色，不得假设其他 Agent 的对话历史、推理过程或临时文件对你可见。

所有结论必须以当前仓库、项目文档、真实执行结果和可复核证据为依据。

## 2. 项目事实来源

按以下顺序确定判断依据：

1. 用户明确给出的本轮要求及强制验收条件。
2. 仓库中已冻结的接口契约、架构决策 ADR 和验收标准。
3. 当前有效的任务卡、WBS、项目状态和交接文档。
4. 当前候选提交的源码、测试和配置。
5. 可复核的外部事实。

发现文档互相矛盾时，必须记录冲突、引用证据并说明影响，不得自行选择一个版本后假装不存在冲突。

## 3. Git 基线规则

开始工作前，记录：

- 仓库地址；
- 当前分支；
- 候选提交完整 SHA；
- 工作区状态；
- 基线相对目标分支的差异；
- 实际审查的文件范围；
- 运行验证时使用的 Go 版本、操作系统和关键环境变量（可获取时）。

如果远程仓库有更新，先确认最新代码及目标提交，不得默默沿用旧的本地副本。

候选提交 SHA 是审计标识，不自动代表工作区干净。若存在未提交改动，必须单独记录其差异；不得把未提交代码描述成已经包含在该 SHA 中。

## 4. ZIP 交付包规范

优先生成一个真实可用的 ZIP 文件，目录结构如下：

GXML-Quality-<ROLE>-<SHORT_SHA>.zip

ZIP 内至少包含：

- REPORT.md：阶段结论和工作摘要；
- BASELINE.md：版本、环境和审计范围；
- COMMANDS.md：实际执行的命令、退出码和结果；
- FINDINGS.md：发现的问题及其证据；
- HANDOFF.md：给下一个 Agent 的交接摘要；
- evidence/：必要的测试日志、差异文件和补充证据。

根据角色增加专属内容，例如测试矩阵、覆盖报告、审查清单或修复记录。

没有对应内容时，应明确写“无”或“不适用”，不能伪造文件、命令输出或验证结果。

如果当前环境无法创建 ZIP，必须明确说明，并输出可保存为文件的完整内容。不得声称已经生成不存在的文件。

## 5. 证据规则

每项重要结论必须尽可能包含：

- 唯一问题编号；
- 严重程度；
- 文件路径、符号名或行号；
- 相关源码或文档依据；
- 复现步骤或验证命令；
- 实际观察到的结果；
- 预期结果；
- 当前状态；
- 影响范围及建议处理方式。

明确区分：

- 已证实；
- 待确认；
- 未验证；
- 已修复但尚未回归验证；
- 已验证修复。

禁止将计划执行的命令写成已执行；禁止把推测写成事实；禁止仅凭“未发现问题”推导出“没有缺陷”。

## 6. 问题严重程度

- P0：严重阻断、重大数据/安全风险或核心功能不可用。
- P1：重要功能错误、核心契约违背或重大回归。
- P2：一般功能、兼容性、可靠性或工程质量问题。
- P3：低风险问题、维护性改进或非阻断建议。

如项目已有更严格的严重程度定义，以项目现行定义为准，并注明映射关系。

## 7. ZIP 完成前自检

在交付前核对：

1. ZIP 文件确实存在且能够打开。
2. 必需文件存在，内容不是空白模板。
3. 候选 SHA、报告、日志和差异文件互相一致。
4. 日志保留实际退出码和关键输出。
5. 重要结论有可复核证据。
6. 未解决问题、未执行命令和未验证区域已明确列出。
7. HANDOFF.md 不超过 20 行，并指出最重要的风险。
8. ZIP 文件名、角色名和候选 SHA 正确。

## 8. 工作边界

不得假定其他 Agent 已经完成了自己的工作。

未经授权不得擅自改变冻结接口、重写架构或进行大规模重构。

发现问题时，遵守当前角色的修改权限。所有修改必须记录文件范围、原因和验证结果。

最终输出必须给出 ZIP 的真实路径或可用附件。如果文件无法生成，必须如实说明。
