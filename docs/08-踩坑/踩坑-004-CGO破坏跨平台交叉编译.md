# PIT-004：引入含 CGO 的第三方库破坏零 CGO 与交叉编译

- 分类：依赖管理 / 构建 / 平台
- 关联：`docs/03-架构/adr/ADR-0007-Zero-CGO降级为Windows侧约束.md`、`docs/03-架构/平台与平台依赖矩阵.md`、`AGENT.md`

> ⚠️ **本条目已修订。** 早期版本建议「严格遵守 ADR-0005，全平台 `CGO_ENABLED=0`」。该建议**已被 ADR-0007 推翻**——实测证明 Gio 在 Linux/macOS 上本身就需要 CGO，全平台 Zero-CGO 物理不可实现。下面是最新结论。

## 现象

引入 `getlantern/systray` 作为托盘实现后，交叉编译直接失败：缺少 C 交叉编译链。

## 根因

该库通过 CGO 调用各平台原生 API。`CGO_ENABLED=0` 下，这类包的 `.go` 文件全部被构建约束排除，编译报错形如：

```text
imports ...: build constraints exclude all Go files
```

更关键的是：**它把整个项目的构建条件从「纯 Go」降级为「需要 C 工具链」**，而这会连锁影响所有平台。

## 关键事实修正（ADR-0007 实测）

早期以为「全平台都能 Zero-CGO」，实测后不成立：

| 平台 | `CGO_ENABLED=0` | 原因 |
|---|---|---|
| **Windows** | ✅ 可行 | Gio 的 Windows 后端是纯 Go（`x/sys/windows` + 手写 D3D11 绑定） |
| **Linux** | ❌ 不可行 | Gio 的 `internal/vk`、`internal/gl/gl_unix.go`、`internal/egl/egl_unix.go`、`app/os_x11.go`、`app/os_wayland.go` 均 `import "C"` |
| **macOS** | ❌ 不可行 | `app/os_macos.go`、`metal_macos.go` 依赖 CGO |

Linux 上穷举 5 种构建标签组合均失败；`CGO_ENABLED=1` 可构建（11 MB 产物），但 `readelf -d` 显示需要 10 个系统动态库（`libEGL.so.1`、`libwayland-*`、`libxkbcommon*`、`libX11*`、`libXcursor.so.1`、`libXfixes.so.3`）。

因此当前策略不是「全平台零 CGO」，而是「**Windows 保持零 CGO，Linux/macOS 接受 CGO**」，并放弃一键三端交叉编译。

## 解决

### 对第三方依赖的准入检查

引入任何依赖前，确认它在目标平台是否需要 CGO：

```text
# 检查某个依赖是否含 import "C"
go list -f '{{.ImportPath}} {{.CgoFiles}}' <package>
```

`CgoFiles` 非空即说明该包需要 CGO。

### 平台能力用纯 Go 自行实现

OS 能力（托盘、剪贴板、文件弹窗、菜单）优先用：

- Windows：`golang.org/x/sys/windows` 直接调用 Win32 API
- Linux：D-Bus（纯 Go 实现）
- 必要时用 `purego` 做动态调用

代价是需要自己写平台适配层，收益是不破坏构建条件。

### CI 守护

CI 必须按平台分别设置：

| 平台 | 设置 |
|---|---|
| Windows | `CGO_ENABLED=0` —— 若某次改动意外引入 CGO，此门禁会失败 |
| Linux / macOS | `CGO_ENABLED=1` |

Windows 的 `CGO_ENABLED=0` 门禁是最有价值的一道：它把「意外引入 CGO」变成**构建失败**而不是**发布后才发现产物形态变化**。

## 预防

- 依赖评审时把「是否含 CGO」作为硬性检查项，而不只看功能与 License。
- 不要为了一个托盘图标引入整个 C 绑定库。
- 注意 `-race` 也需要 CGO，因此 Windows 上无法运行 `go test -race`（无 gcc），这条限制与本条目同源。

## 证据状态

| 项目 | 状态 |
|---|---|
| Linux/macOS 必须 CGO | ✅ ADR-0007 §3 有穷举实测 |
| Windows 纯 Go 可行 | ✅ ADR-0007 §3.4 有实测 |
| 产物依赖列表 | ✅ ADR-0007 §3.3 有 `readelf -d` 输出 |
| `getlantern/systray` 的具体报错原文 | ⚠️ **待核实**：仓库内未保留当时的完整错误输出 |

## 教训（与平台无关的部分）

这条踩坑真正可复用的结论不是「别用 CGO」，而是：

> **一个依赖会改变整个项目的构建条件。** 评审依赖时，构建条件的代价往往比功能缺失更难挽回——它影响所有平台、所有后续依赖，且只在特定平台或特定构建标签下才暴露。
