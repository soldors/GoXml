# PIT-015：多克隆 / 多工作树时，"已提交"的改动会在整合后消失

- 分类：工程纪律 / Git 拓扑
- 关联：`docs/05-开发/dev-log/2026-10-23.md` §1.2、§19.4

## 现象

在独立克隆里做了一笔纯日志提交（`827ab41`，登记用），工作树干净、看起来"完成了"。
但：

```text
① 该提交从未推送（独立克隆不继承 hook，没有自动推送）
② 主仓库并不知道这个对象
      git cat-file -t 827ab41   → fatal: Not a valid object name 827ab41
③ API 查该 SHA
      https://api.github.com/repos/<owner>/<repo>/commits/827ab41  → 422 No commit found
④ 它还不是整合目标的祖先
      git merge-base --is-ancestor 827ab41 b33ce6d   → 假（不在历史里）
```

于是当 master 快进到 `b33ce6d` 之后，这笔提交**既不在本地 master 历史里，也不在远端**，
只剩那个独立克隆里的一条孤立分支。更糟的是：此时再想"把它推上去"已经**不可能快进**了，
只能 cherry-pick 重开一笔（新 SHA）。

## 根因

三件事叠加：

1. **独立克隆不继承 commit hook** → 提交不会自动推送；
2. **同源的多棵树并不共享提交对象**：一棵树里的提交，在 fetch 之前另一棵树完全看不见；
3. 祖先行：一笔提交能否"平行保留"，取决于它是否在**整合后保留的那条祖先链**上。

"工作树干净"在这里是**最具误导性的信号**——它只说明那棵树没有未提交改动，
既不说明已推送，也不说明已进目标分支的历史。

## 解决

整合前先做三道核对：

```bash
git merge-base --is-ancestor <候选SHA> <目标HEAD>   # 是不是已经包含
git cat-file -t <候选SHA>                            # 目标仓库认不认这个对象
curl -s -o /dev/null -w "%{http_code}\n" \
  https://api.github.com/repos/<owner>/<repo>/commits/<SHA>   # 远端有没有（200/422）
```

处置顺序二选一，**不要混**：

- **先推后合**：先把该提交推到远端 master，再让本地跟上（后面再合就需要真正的 merge，不再是 FF）；
- **先合后再 cherry-pick**：先把主干 FF 到目标，然后从原克隆 `git fetch <path> <branch>`
  拿到对象，`git cherry-pick <SHA>` 在主干上重开一笔（**新 SHA**），再推送。

## 预防

- 每完成一批提交，就把"未推送清单"写进当天的 dev-log（分支名 + 本地 HEAD + 说明），
  网络恢复后照单处理。
- 不要把"某个克隆里提交过了"当成"项目已经有了"。
- 结论一律以 `git ls-remote`（或降级 API）+ `merge-base --is-ancestor` 为准，不用 `git status` 顶替。
