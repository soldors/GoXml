# PIT-003：Windows 下 `Process.Kill()` 无法清理子进程树

- 分类：开发体验 / 进程管理 / Windows 平台
- 关联：`docs/03-架构/adr/ADR-0004-双进程Live-Reload与独立预览器方案.md` §5、§6；`AGENT.md`；`docs/10-发布/回滚手册.md`

## 现象

`goxml watch` 热重启时，`go build` 报错：输出文件被占用，无法覆盖。

根因不是编译失败，而是**上一轮的预览进程还活着**，仍持有 `.exe` 的文件句柄。

## 根因

Go 的 `os.Process.Kill()` 只终止**直接子进程**，且不走优雅退出流程。

在 Windows 上这留下两个问题：

1. **孙子进程逃逸**：若子进程自己再派生了进程，`Kill()` 不会触及它们。预览进程退出后，其派生的进程仍持有句柄。
2. **句柄释放延迟**：即使直接子进程被终止，Windows 释放其文件句柄也不是瞬时的。紧接着执行 `go build` 会撞上「文件正在使用」。

因此「先 `Kill()`、立刻 `go build`」这个顺序在 Windows 上不可靠。

## 解决

ADR-0004 定义的双阶段清理：

```text
1. 向子进程发送 shutdown 指令，等待优雅退出
2. 超时后按平台规则清理整个进程树
3. 确认句柄释放后，才启动 go build
```

Windows 的进程树清理使用：

```text
taskkill /F /T /PID <pid>
```

`/T` 终止整个进程树（含孙子进程），`/F` 强制。这是 `os.Process.Kill()` 缺少的能力。

## 预防

- 关闭流程**永远先尝试优雅退出**，只在超时后才强制清理。强制终止会跳过状态序列化，导致热重启后 ViewModel 状态丢失。
- 清理后必须**确认句柄释放**再编译，不能假定 `taskkill` 返回即已完成。
- 监控项（`运维手册.md`）：进程树持续增长，或退出后仍有残留进程，视为异常。

## 相关影响

同一根因也解释了另一个现象：`回滚手册.md` 要求 Windows 下「按进程树清理策略终止整个子树，确认 exe 句柄释放后再替换文件」。回滚失败的最常见原因不是新版本有问题，而是旧进程没清干净。
