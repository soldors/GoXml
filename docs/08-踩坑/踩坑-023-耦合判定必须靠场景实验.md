# PIT-023：「A 与 B 是否耦合」必须靠场景实验，不能靠读 diff 目测

## 现象

一个分支同时改了 `pkg/runtime/theme/font.go`（报告出口深拷贝）与 `pkg/runtime/app/app.go`（+40 行），
需要判断这两处改动能否拆成两个提交。仅靠读 diff「看起来不相关」是不够的——
目测无法排除**隐含依赖**（例如 theme 侧新增的符号恰好由 app 侧提供、或测试文件跨包引用）。

## 根因

依赖分两类，只有一类能靠读 diff 发现：

1. **显式依赖**：直接引用同名符号（`copyProbeReport`、`ResolveWithReport`…）—— 可 grep。
2. **隐含依赖**：包级 import 关系、测试文件跨包引用、构建标签 —— 读单文件 diff 看不出来。

只做第 1 类检查，会漏掉第 2 类，从而得出「可拆」的错误结论。

## 处理与预防

判定「两处改动能否拆开」用**场景实验**，而不是目测：

1. **只放 A**：把 A 的文件写入干净克隆（与目标分支同 HEAD），跑 `go build ./...`。成功 ⇒ A 自洽。
2. **A + A 的测试**：再放入 A 的测试文件，跑 `go build ./...` 与对应包 `go test -count=1`。全绿 ⇒ 可独立成提交。
3. **反向 import 检查**：确认两个包不互相 import（若互相 import 会成环，必然不能拆）。
   例：`git grep -n goxml/pkg/runtime/app <ref> -- pkg/runtime/theme` ⇒ rc≠0 表示 theme 不 import app。
4. **全放对照**：再放入 B，确认仍 build 通过，证明两侧互不干扰。
5. **收尾**：字节级还原 + SHA 校验 + `git status` 为空。

2026-10-31 实测（`codex/night-font-integration` @ `c1da35e`）：

| 检查 | 结果 |
|---|---|
| `app.go` diff 命中字体符号（`ProbeReport`/`copyProbeReport`/`ResolveWithReport`/`LastReport`/`Font`/`Family`/`LoadElapsed`） | **0 个** |
| `pkg/runtime/theme` 是否 import `pkg/runtime/app` | **否**（grep rc=1） |
| 只放 `font.go` → `go build ./...` | rc=0 |
| `font.go` + `provider_report_test.go` → build | rc=0 |
| 同上 → `go test ./pkg/runtime/theme -count=1` | rc=0（`ok … 12.890s`） |
| 再放入 `app.go` + `window_lifecycle_test.go` → build | rc=0 |

⇒ 结论：两处改动互不耦合，可拆成两个提交。

> 反过来也成立：**「某符号不存在」类断言不能只写 `not in`**。
> 本例 `copyProbeReport` 在**两个分支都有**（定义在 `pkg/runtime/theme/lazy.go:510`），
> master 的 `font.go` 也已在 `:331` 用过一次；真实差别是**出口隔离数**（master 2 处 / 分支 6 处，且 master 的
> `return id, rep, nil`、`return p.last` 未隔离）。写成 `not in` 会直接错判；
> 应写成「计数 == N **且**含/不含具体语句」。
